## 2. 因 Q2 而收窄的范围（必须如实写进文档与响应）

- 规范化**只做平台无关的保守处理**：scheme/host 小写、去默认端口、去 fragment、去尾部多余 `/`、查询参数按 key 排序、去掉**通用**追踪参数（`utm_*`、`fbclid`、`gclid` 这类跨平台通用的，名单写在常量里并注明来源是通用约定而非小红书调研）。
- **不识别短链**：`link_kind` 在本包只会是 `LONG` 或 `OTHER`，**不产出 `SHORT`**（取值域保留，因为 DDL 已定，但没有产出路径，测试断言这一点）。
- **不做「短链 ⇄ 长链」等价**：因此验收项「短链与长链不重复」**本包不承诺**。同一条笔记的短链与长链会被当成两条不同链接。这是 Q2 关闭的直接后果，要写进说明的「已知缺口」。
- **不从 URL 抽 `note_id`**：笔记 ID 的位置因平台而异，没有样例就不猜。
- 响应里**不返回「长链」字段**（契约 `PublicationLink` 只有 `rawUrl` / `canonicalUrl`，本包不扩）。

## 3. 范围

### 3.1 要做
1. 规范化纯函数（标准库，无 IO）。**幂等**：`normalize(normalize(x)) == normalize(x)`。
2. 迁移：`publication_links` 加 `project_id`（NOT NULL，FK `projects` RESTRICT）+ 唯一索引 `uq_publication_links_project_canonical(project_id, canonical_url)`；存量表为空，直接 NOT NULL。降级只删自有对象。
3. 服务层：
   - 登记链接：规范化 → 项目内命中同 `canonical_url` ⇒ 409 `DUPLICATE_PUBLICATION`（`details.reason` 区分）；**跨项目命中**且当前用户无确认权 ⇒ 同样 409，`details` 带 `crossProject=true`，**不泄露**对方项目的 id/名称（防枚举，照 WP36 的 404 同形原则）。
   - 管理者确认：见 3.3。
   - 回填 `publications.url_canonical`（该发布的首条链接规范化结果）。
   - 内容状态：`verify` 只接收调用方给的 `result ∈ {VERIFIED, UNVERIFIED}`，落库到 `publications.content_state`。取值域没有「已删除」，**结构上推不出删除**；不联网，因此「抓取失败」这个概念本包不存在，由 WP40 适配器未来产出。
4. 端点 3 个（路径以 `contracts/draft/m4-openapi.yaml` 为准）：`POST /publications/{publicationId}/links`、`GET /publication-links`、`POST /publications/{publicationId}/verifications`。
5. 「项目内按 distinct publication 计数」：提供一个只读的查询函数（repository 层），按 `publication_id` 去重，不做端点（契约没有）。

### 3.2 不做
联网展开、小红书专属规则、`note_id` 抽取、抓取与可达性判定、指标（WP38）、批量导入链接。

### 3.3 管理者确认（Q3 = a）怎么落，这里有一个需要你注意的缺口
契约草案**没有**「待确认」状态和确认端点。最小做法（本包采用，请知悉）：

- 新增 `OrgAction.CONFIRM_CROSS_PROJECT_NOTE`，仅 `ROLE_ADMIN` 为真。
- 登记链接的请求体**不**新增字段；**管理者本人调用**登记端点时，跨项目命中不再 409，而是放行并在响应里带 `crossProjectConfirmed=true`。即「确认」= 管理者亲自登记，不引入待办队列。
- 运营遇到跨项目命中得到 409，需要联系管理者代为登记。

这是**对契约的扩展**（响应多一个布尔字段），也是一个产品取舍：管理者无法“事后批准运营的登记”。如果你要的是「运营提交 → 管理者审批」的两步流，那需要新增状态和端点，应另开拍板。实现 agent 不得自行扩大，按此最小做法落地，并在说明里登记为 OP。
