# ADR-13 批次数量配置化

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-19 |
| 决策人 | 老大（业务负责人） |
| 影响范围 | `batches` 表 DDL、runtime_settings、应用层校验、配置变更审计、验收口径（AC-10~12） |

## 背景

评审硬伤 🔴6：原设计把试产/扩产/批产的数量上下限（`TRIAL=10` / `SCALE≤30` / `BULK≤50`）以 CHECK 约束写进了 `batches` 表的 DDL。

这带来一个明确的运维问题：**业务数字变更会触发数据库迁移**。运营调整一次试产条数（比如从 10 条改为 12 条），需要走"改 DDL → 写 Alembic 迁移 → 评审 → 停机窗口执行"的完整链路，而这件事本质是业务参数调整，不是数据结构变化。

同时带来第二个问题：DDL 约束是"隐式规则"——运营看不到当前生效的数字是什么、什么时候改的、谁改的。数量上限又直接关联验收项 AC-10~12（数量与方向），一旦数字变了，验收口径必须随之变化，必须有可追溯的来源。

约束的收益（数据库层强一致、非法值写不进去）需要保留，但不必由 CHECK 承担全部。

## 决策

**我们决定把批次数量上下限从 DDL CHECK 约束移到 runtime_settings + 应用层校验，DDL 只保留下界（正整数约束）。**

### 具体内容

| 层次 | 约束内容 |
|---|---|
| DDL（`batches`） | 删除 `TRIAL=10 / SCALE≤30 / BULK≤50` CHECK；**保留 `quantity > 0`** |
| runtime_settings | 键 `batch.limits`，默认值 `{ trial: 10, scale: 30, bulk: 50 }` |
| 应用层 | 创建/调整批次时读取生效配置校验上下限；越界拒绝并返回明确错误（含当前生效值与配置来源） |
| 审计 | 每次变更 `batch.limits` 写入审计记录（见下） |

### 配置变更审计要求

每次修改 `batch.limits` 必须留下可追溯记录，至少包含：

| 字段 | 说明 |
|---|---|
| 变更前值 / 变更后值 | 完整配置快照，而非仅差异字段 |
| 变更人 | 操作账号（关联企业身份，非共享账号） |
| 变更时间 | 服务端时间戳（依赖 NTP，见 ADR-11 C9） |
| 变更理由 | 必填文本，不接受空值 |
| 生效范围 | 全局 / 指定项目（若支持项目级覆盖，须在变更记录中标明） |
| requestId | 关联链路追踪 |

要求：

1. 审计记录**不可被后续修改或删除**，与费用账本、版本快照同级对待。
2. 配置读取走缓存时，缓存失效必须在变更后即时生效；不接受"重启后才生效"。
3. 变更需在站内可查（管理面或配置历史页），运营可自助确认当前生效值。
4. **验收按配置生效值执行**（研发计划 §16.2 AC-10~12），不按硬编码值执行。

### 迁移影响

| # | 影响面 | 具体内容 |
|---|---|---|
| 1 | Alembic 迁移 | 需要一个迁移删除三处 CHECK 约束，保留 `quantity > 0`。迁移是**宽松方向**（放开约束），不涉及数据回填，风险低 |
| 2 | 历史数据 | 已存在的批次行不会因放开约束变得非法；无需清洗 |
| 3 | 应用层 | 校验逻辑从"依赖数据库报错"改为"显式读取配置后校验"，错误信息需包含当前生效上下限，避免用户不明所以 |
| 4 | 并发 | 校验基于读取到的配置快照；配置变更与批次创建的并发窗口需在应用层处理，规则为"以创建时刻的生效配置为准"，不做跨请求加锁 |
| 5 | 默认值来源 | runtime_settings 初始值由迁移写入，保证新环境与旧环境行为一致（默认 10/30/50） |
| 6 | 前端 | 数量输入控件的上下限提示改为从接口读取，不得硬编码 |
| 7 | 契约 | OpenAPI 中数量字段的边界描述同步更新，避免契约与实现不一致（CI 契约 diff 会捕获） |
| 8 | 验收 | AC-10~12 的验收脚本改为读取生效配置构造边界用例（下界-1、下界、上界、上界+1） |
| 9 | 测试 | 新增用例覆盖：配置越界拒绝、配置变更即时生效、变更审计写入、默认值行为不变 |
| 10 | 同类项 | 研究文件软上限 `research.maxEffectiveFiles`（默认 2000/项目，M3）采用同一机制，本决策确立模式 |

## 理由

1. **业务数字变更不应触发数据库迁移**。数量上下限是运营参数，不是数据完整性约束。把它放进 DDL，等于让每次业务调整都付出迁移成本与停机风险。
2. **DDL 只保留下界即保留核心不变式**。`quantity > 0` 是真正的数据完整性要求（数量为 0 或负数的批次无意义）；"≤ 30"是业务策略，性质不同。分层承担各自的职责。
3. **可观测性**。放到 runtime_settings 后，当前生效值、变更历史、变更理由全部可查；CHECK 约束只会在插入失败时给出一条数据库错误，运营无法自助排查。
4. **验收口径与配置对齐**。AC-10~12 验的是"按当前业务规则正确处理边界"，规则变了验收就该跟着变；硬编码值反而会让验收与业务脱节。
5. **为后续同类需求确立模式**。研究文件软上限、平台文本/媒体限制（待实测后写入 runtime_settings）等都属同类，本决策一次性把模式定下来，避免重复讨论。

**否决的替代方案**

- **保持 DDL CHECK 不变**：评审 🔴6 已否定。迁移成本与可观测性问题未解决。
- **DDL 完全不管数量**：会失去"数量必须为正整数"这一真实不变式，允许脏数据写入。**否决原因**：下界是数据完整性，不应放弃。
- **应用层校验但无审计**：出现"数量上限被谁改了"的争议时无法追溯；且数量上限直接关联验收，无审计等于验收口径无依据。**否决原因**：不可审计即不可验收。
- **用配置文件（部署级）而非数据库配置**：仍需发版才能变更，本质与 DDL 迁移问题相同。**否决原因**：未解决"业务数字变更不应触发变更流程"的核心痛点。
- **引入独立配置中心组件**：本规模（20 在线）不值得新增一个组件与一套运维面。**否决原因**：runtime_settings 已足够，与 ADR-14 拒绝引入 Redis 的取舍逻辑一致。

## 代价与风险

**代价**

1. 失去数据库层的强一致保障：若存在绕过应用层直接写库的路径（如运维手工 SQL、导入脚本），非法数量可能落库。缓解手段是数据核检任务 + 导入路径复用同一校验函数。
2. 应用层校验代码需要正确覆盖所有入口（创建、调整、局部重做、批量操作），漏一个入口就是漏洞。
3. 配置读取引入缓存一致性问题，需保证变更即时生效。
4. 审计表随配置变更增长，需纳入容量规划（量级极小，可忽略）。

**风险与重新审视条件**

- 若出现"绕过应用层的写入导致非法数量长期存在"的真实事故 → 考虑在保留 runtime_settings 的同时，增加一条延迟校验（异步核检 + 告警），而非退回 DDL。
- 若配置项数量增长到难以管理（如超过几十项且相互约束）→ 需重新评估是否需要更结构化的配置模型。

## 验证方式

| 判据 | 验证方法 | 证据 |
|---|---|---|
| DDL 只保留下界 | 检查 `batches` 表定义：无 `TRIAL=10 / SCALE≤30 / BULK≤50` CHECK，有 `quantity > 0` | Alembic 迁移文件 + 表定义导出 |
| 配置生效 | 修改 `batch.limits` 后，不改代码、不发版、不迁移即可生效 | 配置变更前后同一请求行为对比记录 |
| 边界正确 | 按生效配置构造下界-1 / 下界 / 上界 / 上界+1 用例 | AC-10~12 验收记录 |
| 审计完整 | 逐条检查配置变更记录含变更前后值、变更人、时间、理由、requestId | 审计记录抽样 |
| 审计不可篡改 | 尝试修改/删除审计记录应被拒绝 | 负向测试记录 |
| 默认值一致 | 新环境迁移后默认值为 10/30/50，与旧行为一致 | 迁移后配置快照 |
| 无硬编码残留 | 全仓检索数量常量，前端与后端均不得出现硬编码上下限 | 代码检索记录 + CI 检查 |
| 契约一致 | OpenAPI 中数量字段边界描述与实现一致 | CI 契约 diff 通过 |
