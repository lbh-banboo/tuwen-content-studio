# ADR-17 采购先行

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-19 |
| 决策人 | 老大（业务负责人） |
| 影响范围 | 排期起算点（T0）、关键路径、机房与网络、Live 真机验证、企业配合清单 E1~E8、风险 R2/R3 |

## 背景

评审硬伤 🔴2：原排期与人日不自洽，且 M0 依赖企业配合。更具体地说，存在一个隐性吞噬关键路径的问题：

**硬件采购的等待时间被默认当作"可以并行、不占排期"的空档**，而实际上一旦关键动作依赖硬件到货，等待就会以"看起来在等、实际在耗"的方式吃掉排期。典型链条：

- 无服务器 → 只能在开发机上做最小链，无法验证"无公网依赖启动"、"重启不丢数据"等真实判据；
- 无 iPhone → Live 真机链路（首发硬要求）完全无法验证，只能挂"待实测"；
- 无 Mac → Live 封装与导入链路无法验证；
- 无网络设备/域名/证书 → 出网策略审批与连通矩阵无法落地。

这些都不是"可以先用文档推断"的事——M0 执行手册已明确禁止用"文档说可行"替代真机实测（Live 尤其）。

与此同时，D5 明确内网零基础，意味着几乎所有底座都要自建，服务器从"可选"变成"必需"。

## 决策

**我们决定硬件采购（服务器 / iPhone×2 / Mac / 网络设备）与 M0 验证并行推进，主排期从"企业输入全部到位"T0 起算。**

### 具体口径

1. **W1 即下单**，不等 M0 结论、不等架构评审完成。采购是 WP00，0 研发人日但**在关键路径**。
2. **主排期 T0 = "M0 企业输入全部到位"**，即出网策略、Brief 样本、测试手机三者缺一不可。T0 之前的工作（WP01~WP05 的启动动作）不占用主排期。
3. **服务器到货可先用开发机顶**，但**出网策略、Brief 样本、测试手机缺一不可**——这三项无法用开发机替代。
4. 企业配合事项晚到一周 = 排期顺延一周，且每周对老大曝光等待项（§15 清单状态更新）。
5. 采购与 M0 并行不是"两件事同时做"，而是**采购必须比 M0 更早开始**：M0 的 WP02（Live 真机验证）直接消费采购成果，采购晚一天，WP02 就晚一天。

### 企业配合事项清单要点（E1~E8）

| # | 事项 | 需要谁 | 截止 | 对排期的直接作用 |
|---|---|---|---|---|
| E1 | 服务器/手机/Mac 采购审批与下单 | 老大 + 采购 | W1 | **T0 前置项之一**；晚到即顺延 |
| E2 | 内部域名、DNS、内部 CA 证书 | 企业 IT | W2 | Keycloak 与反向代理前置；未到位 M1 网络验收无法通过 |
| E3 | 出网策略审批：模型供应商域名白名单 | 企业 IT/安全 | W2 | **T0 前置项之一**；未批准则模式 A 不成立（ADR-10） |
| E4 | 3 个品牌真实 Brief + 产品参考素材（含相近品类对抗样本） | 运营负责人 | W1 | **T0 前置项之一**；未到位评测集只能是骨架（G0-13 部分完成） |
| E5 | 指定运营负责人（AQ 通过线签字人）与试点运营 2 名 | 老大 | W1（试点 W13 到位即可） | 通过线签字人缺位则 G0-15 无法闭合 |
| E6 | 小红书相关账号权限盘点 | 老大 + 运营 | W2 | 决定 WP03 数据可得性清单结论 |
| E7 | 外部模型供应商账号、合同与额度 | 老大 + 采购 | W2 | 模型接入前置；无账号则 AQ 基线无法产出 |
| E8 | 内网用户账号源（Keycloak 独立建册或对接企业 IdP） | 企业 IT | W3 | 登录与权限前置 |

要点：

- **E1/E3/E4 是 T0 的三个硬前置**，三者任一未到位，主排期不起算。
- 每项都有明确截止周，超期即触发风险 R3（企业输入延迟，概率中、影响高），需每周对老大曝光。
- 配合清单必须在 W1 D1 启动会当天发出，不能等"整理完整"再发。

## 理由

1. **消除硬件等待对关键路径的隐性吞噬**。这是本决策的核心。把采购显式放进关键路径（WP00），等待就从"隐性缓冲"变成"显性占用"，排期不再假装它不存在。
2. **采购是外部依赖，不可被团队努力压缩**。团队加班无法让服务器早到货。既然不可压缩，就必须尽早启动，让等待与团队工作重叠。
3. **Live 真机验证无法用其他手段替代**。WP02 明确要求"纸质推断一律无效"，无 iPhone + 小红书账号 = 无法完成。因此 P5/P6 是硬前置，不是"有更好"。
4. **排期从 T0 起算使容量账自洽**。6 FTE × 16 周 = 480 人日容量，与 285~425 人日投入的差值被显式标注为联调等待、企业审批等待、试点观察的占用（§8.1），而不是含糊的"缓冲"。
5. **采购规格有容量估算支撑**。P2 的 2×2 TB NVMe 对应 PG 500 GB 起步 + 首年 200 GB 预留 + WAL 归档；P3 的 ≥24 TB 对应 MinIO 5 TB 可用起步 + 3.2 TB/90 天生成媒体 + 重试系数与备份副本（§6.1）。规格不是凭感觉配的。

**否决的替代方案**

- **等 M0 结论再采购**：M0 的 WP02/WP05 结论本身依赖硬件，形成循环依赖。**否决原因**：会把 M0 无限期后置。
- **采购只买服务器，手机/Mac 后补**：Live 是首发硬要求（§3.1 明确化 2），手机晚到 = Live 验证晚到 = G0-05 无法闭合。**否决原因**：把硬要求放到关键路径之外。
- **用 Android 设备替代 iPhone 验证**：目标平台为小红书 iOS 端 Live 能力，Android 结论不可迁移。**否决原因**：验证对象不对。
- **排期从 W1 起算（含企业等待）**：会让"企业等待"直接吃掉 16 周中的不确定比例，交付承诺失真。**否决原因**：掩盖真实起算条件。
- **先用云服务器替代自采**：数据必须留内网（ADR-10 E-5、ADR-11），且内网无出网通道承载数据面。**否决原因**：与出网边界冲突。
- **首版即采购 GPU**：模式 A 下不需要，且 GPU 采购周期与选型风险会显著拉长关键路径。**否决原因**：见 ADR-10。

## 代价与风险

**代价**

1. 采购在 M0 结论出来前发生，存在"结论导致需求变化"的少量浪费风险（例如服务器规格需微调）。缓解：规格按 §6.1 容量估算配置，留有余量；变更以追加采购而非退换处理。
2. 排期从 T0 起算意味着**交付日期对老大不可完全承诺**——T0 取决于企业配合。这是显式接受的代价，且需每周曝光等待项。
3. 硬件等待成为必须被管理的显性事项，增加项目协调成本（每周清单状态更新）。
4. 提前下单占用预算与机位，而 M0 尚未证明模式 A 可行。

**风险与重新审视条件**

| # | 风险 | 概率 | 影响 | 应对与监控信号 |
|---|---|---|---|---|
| R3 | 企业输入延迟（服务器/出网/Brief/手机） | 中 | 高 | 排期从输入到位起算；每周对老大曝光等待项；监控 §15 清单超期 |
| R2 | Live 真机链路不通 | 中 | 高 | W1 即验；辅助工具决策点 P0 末；不通则升级老大（禁止静默降级为静态图） |
| — | 采购到货周期超预期 | `[待核实: 采购实际到货周期 —— 采购单跟踪，W1 起]` | — | G0-22 要求"硬件采购已下单且交期已知；手机/Mac 已到或已定到货日" |

**重新审视条件**

- G0-04 判定模式 A 不成立（N6 不允许出网）→ 需采购 GPU，P8 从"暂缓"变为"立即启动"，本 ADR 需修订。
- 采购到货周期显著超出预期（如服务器 > 6 周）→ 需重新评估是否改用开发机 + 分批上线策略，并向老大升级。
- 若 M0 结论显示基础设施规模需求与 §14.1 规格偏差较大 → 以追加采购处理，不做退换。

## 验证方式

| 判据 | 验证方法 | 证据 |
|---|---|---|
| 采购已下单 | 检查采购单号与提交时间（应为 W1） | G0-22：采购单 |
| 交期已知 | 每项采购有明确到货日期或已到货确认 | G0-22 记录 |
| 手机/Mac 就绪 | iPhone×2 与 Mac 已到或已定到货日，且已安装目标小红书版本 | G0-09 设备矩阵（机型 × 系统版本 × 小红书版本） |
| T0 前置齐备 | E1/E3/E4 三项状态均为已到位，方可宣布主排期起算 | T0 起算确认记录 |
| 等待项被曝光 | 每周 §15 清单状态更新，含超期项与影响 | G0-24：E1—E8 状态更新记录 |
| 排期重估完成 | 以实测结论更新关键路径与缓冲占用 | G0-23：排期修订页 |
| 未静默降级 | Live 全部链路失败时，检查是否走升级流程而非默认降级为静态图 | WP02 判定记录 + 升级记录 |
