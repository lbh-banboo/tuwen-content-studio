# ADR-15 向量检索选型门槛

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-19 |
| 决策人 | 老大（业务负责人） |
| 影响范围 | 知识库向量索引、embedding profile 管理、PG 容量规划、索引重建流程、AQ-03 一致性 |

## 背景

评审意见 🟡9：原设计只写了"pgvector 适用于中等规模"，但"中等规模"没有数字，无法判定。

这不是文字问题，而是决策问题。没有阈值会导致两种失败：

1. **该分区的没分区**：chunk 数悄悄涨过 pgvector HNSW 的舒适区，检索延迟劣化、索引维护（重建、vacuum）耗时增长，而团队在问题爆发前没有预警信号。
2. **不该迁移的乱迁移**：一有性能疑虑就评估引入独立向量库，新增组件、新增运维面、新增一致性风险，而实际规模远未到必要程度。

同时存在一个容易被忽略的耦合：**embedding 模型换版会产生全新的向量空间**。旧索引在新模型下不可用，混用会导致检索结果错误且难以察觉（不是报错，而是"召回的东西不对"）。这必须在决策里写清，否则会变成一次静默的质量事故。

## 决策

**我们决定设定 pgvector 量化门槛：单个 embedding profile 的 chunk 数 ≤ 200 万时使用 pgvector HNSW；超出后按 profile 分区，或评估独立向量库。**

### 门槛与处置

| chunk 数（单 profile） | 处置 |
|---|---|
| ≤ 200 万 | pgvector HNSW，单表 + 索引，不分区 |
| > 200 万 | ① 按 embedding profile 分区（首选）；② 若单 profile 仍超限，评估独立向量库（需单独立项与 ADR） |

判定口径：

- **计数对象是"单个 embedding profile"**，不是全库总量。多 profile 并存时各自独立计数。
- 阈值以**实测校准**为准：WP21 完成后用真实数据量测，若实测显示阈值应调整，走 ADR 修订，而非私下改代码常量。
- 监控信号：chunk 数逼近 200 万即触发容量复核（对应风险 R8）。

### 索引空间估算

按研发计划 §6.1 的估算口径：

| 项 | 估算 |
|---|---|
| 向量维度 | 1024 维 float32 |
| 单条向量原始大小 | 1024 × 4 字节 ≈ 4 KB |
| HNSW 索引放大 | 约 1.2~1.5 倍（§6.1 采用 1.3 倍作为规划值） |
| 单条 chunk 向量 + 索引合计 | 约 5.2~6 KB |
| 200 万 chunk 上限场景 | 向量本体约 8 GB；含索引约 10~12 GB |
| 加上 chunk 文本（文本 ÷ 500 字/chunk） | §6.1 结论：上限场景约 30~40 GB |
| 整体 PG 容量 | 500 GB NVMe 起步，含数据库主体（版本/账本/审计/快照）首年预留 200 GB |

要点：**索引放大不是可忽略项**。1.2~1.5 倍意味着 200 万 chunk 场景下索引本身可能比向量本体更大，容量规划必须计入，不能只按向量条数 × 4 KB 估算。

### 模型换版必须新建索引空间，不混用

- 每个 embedding profile 绑定固定的 embedding 模型与版本。
- **换模型 / 换版本时，必须创建新的索引空间（新 profile），禁止在旧索引空间中混入新模型产生的向量。**
- 切换流程：
  1. 新 profile 建立独立索引空间；
  2. 全量重算（或按需回填）新 profile 的向量；
  3. 检索按 profile 路由，切换期间旧 profile 保持可用；
  4. 新 profile 检索质量经回归确认后，将流量切至新 profile；
  5. 旧 profile 保留至确认无需回滚，再回收。
- 混用的危害不是报错而是**静默劣化**：向量空间不同，距离比较失去意义，检索会返回语义无关的结果，表现为"AI 答非所问"而非"系统故障"。因此这条是硬约束，不是建议。

## 理由

1. **把"中等规模"落成数字，决策才可判定**。评审 🟡9 的核心诉求就是这条：没有数字，就无法回答"现在需不需要引入独立向量库"，也无法设置监控预警。
2. **200 万的来源是容量估算而非拍脑袋**。§6.1 指出上限场景 chunk 数逼近 200 万时需触发 ADR-15 分区评估；本 ADR 把该触发点固化为阈值。
3. **按 profile 计数而非全库计数**。向量检索在单 profile 内进行，跨 profile 不比较距离，因此规模压力天然按 profile 计。这也让"分区"成为最自然的超出处置手段。
4. **优先分区而非迁移组件**。分区复用已有 PostgreSQL 17，零新增组件；独立向量库会引入新的运维面、备份路径、一致性问题，与 ADR-11 的运维投入约束冲突。只有在单 profile 也超限时才值得考虑。
5. **模型换版独立索引空间是防止静默质量事故**。这条不依赖规模阈值，任何规模都必须遵守。

**否决的替代方案**

- **不设阈值，按需评估**：评审 🟡9 已否定。无阈值 = 无预警 = 问题爆发才发现。
- **直接采用独立向量库**：本规模（50 成员 / 20 在线）远未到必要程度；新增组件成本确定，收益不确定。**否决原因**：与 ADR-11 运维约束冲突，且不必要。
- **按全库总量计阈值**：会误判——多个小 profile 合计超 200 万但各自远未超限时，实际无需任何处置。**否决原因**：计数口径与检索实际执行方式不符。
- **换模型时原地覆盖旧向量**：省空间但导致新旧向量共存于同一索引空间，检索结果静默劣化。**否决原因**：不可接受的质量风险。
- **不建 HNSW，全表精确检索**：小规模可用，但超出后延迟线性增长，且无法复用已投入的容量规划。**否决原因**：本系统知识库规模明确会增长。

## 代价与风险

**代价**

1. 需维护 embedding profile 维度与切换流程，增加知识库模块复杂度。
2. 模型换版时需全量重算向量，是一次真实的计算与时间成本。
3. 按 profile 分区后，跨 profile 的检索需要应用层路由与结果合并逻辑（若业务需要）。
4. 阈值需在 WP21 实测校准，校准前按 200 万规划。

**风险与重新审视条件**

- **R8 向量/文本容量超预期**：概率低、影响中。应对为 ADR-15 阈值 + 按月容量复核；监控信号为 chunk 数逼近 200 万。
- **重新审视条件**：① 实测显示单 profile 在远低于 200 万时已出现不可接受的检索延迟或索引维护成本；② 单 profile 超过 200 万且分区后仍不满足；③ 业务出现跨 profile 检索需求导致分区方案复杂度过高。任一条件触发即启动独立向量库评估（需新 ADR）。
- 阈值本身若被 WP21 实测推翻，走 ADR 修订，不在代码中直接改常量。

## 验证方式

| 判据 | 验证方法 | 证据 |
|---|---|---|
| 阈值已校准 | WP21 用真实数据量测索引容量与检索延迟，校准 200 万阈值 | WP21 索引容量实测记录 |
| 计数口径正确 | 检查监控指标按 embedding profile 分别统计 chunk 数，而非全库合计 | 监控面板 / 指标定义 |
| 预警有效 | 构造逼近阈值的测试数据，确认触发容量复核告警 | 告警触发记录 |
| 空间估算准确 | 实测 200 万量级（或外推）下向量 + 索引实际占用，与 1.2~1.5 倍估算比对 | 容量实测报告 |
| 换版不混用 | 构造 profile 切换流程测试：新 profile 独立索引空间；检索路由正确；旧 profile 在新 profile 就绪前仍可用 | 切换流程测试记录 |
| 混用被阻止 | 负向测试：尝试向旧 profile 索引空间写入新模型向量应被拒绝 | 负向测试记录 |
| 质量回归 | 每次换 embedding 模型 / 版本执行 AQ-01~03 全量回归 | `docs/model-evaluations/` 归档 |
