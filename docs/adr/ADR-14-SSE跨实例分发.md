# ADR-14 SSE 跨实例分发

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-19 |
| 决策人 | 老大（业务负责人） |
| 影响范围 | API 双实例架构、domain_events 表、SSE 接口契约、前端断线恢复、异常矩阵第 16 项、权限过滤 |

## 背景

评审硬伤 🔴5：原设计缺少 SSE 双实例下的 fan-out 机制。

具体问题：API 采用双实例部署（ADR-01），SSE 长连接建立在**某一个**实例上。任务进度事件由 Worker 产生并写库，但 Worker 并不知道用户的 SSE 连接挂在哪个实例上。若不做跨实例分发，就会出现：

- 用户连接到实例 A，任务在实例 B 侧产生事件 → A 上的连接收不到 → 前端进度长期不更新，用户以为任务卡死。
- 更糟的是表现为"偶发"：同一用户刷新后连到另一个实例就正常了，问题难以复现与定位。

必须补齐的是一套机制，回答三个问题：事件在哪里是"真相"、跨实例如何及时送达、用户断线后如何补齐。

## 决策

**我们决定采用"domain_events 落库为真相 + PostgreSQL LISTEN/NOTIFY 跨实例实时分发 + Last-Event-ID 补漏"的三层机制。**

### 机制分层

| 层 | 作用 | 实现要点 |
|---|---|---|
| 真相层 | 事件的唯一持久化来源 | `domain_events` 表落库，含自增序列号（用于 Last-Event-ID） |
| 分发送达层 | 跨实例实时通知 | PG `LISTEN/NOTIFY`，channel 为 `domain_events_new`，**payload 只带 event id** |
| 补漏层 | 断线 / 漏收补齐 | 前端携带 `Last-Event-ID` 重连，服务端按序列号从库中补发缺失事件 |

### 关键实现约束

1. **NOTIFY payload 只带 event id，不带事件正文**。原因：NOTIFY payload 有长度上限，且正文可能含敏感内容；带 id 后由订阅实例按 id 读库并做权限过滤，保证"越权订阅被拒"发生在读库环节而非通知环节。
2. **订阅实例收到通知后必须按 id 读库并做权限过滤**，逐事件判定该连接所属用户是否有权接收。不允许把"通知到了"当作"可以推送"。
3. **权限过滤必须逐事件做**，不得只在建立连接时校验一次。理由：会话中权限可能变化（成员被移除、项目负责人交接）。异常矩阵已有"成员移除后重新鉴权"一项，SSE 必须与该口径一致。
4. **事件序列号单调递增**，作为 `Last-Event-ID` 的取值来源；库中补齐查询按 `sequence > last_event_id` 执行。
5. **补齐有上限**：若断线时间过长导致待补事件超过设定上限，服务端返回明确信号让前端改为"全量刷新"，而不是无界补发。

## 理由

### 为什么不用 Redis pub/sub

| 对比项 | PG LISTEN/NOTIFY | Redis pub/sub |
|---|---|---|
| 新增组件 | 无（复用已有 PostgreSQL 17） | 需新增 Redis 实例 + 运维面 + 备份 + 监控 + 补丁 |
| 运维成本 | 0 | 运维 0.5 人已在 M2 起回落，新增组件会重新吃紧（ADR-11） |
| 交付可靠性 | at-most-once（与 Redis pub/sub 同） | at-most-once |
| 丢失兜底 | 落库为真相 + Last-Event-ID 补漏 | 同样需落库兜底，Redis 不减少这部分工作 |
| 容量 | 内网 PG 500 GB NVMe 起步，事件量级远低于容量上限 | Redis 内存成本随事件量增长 |
| 本规模适配 | 20 在线 / 50 成员，NOTIFY 吞吐充裕 | 明显过配 |

结论：两种方案的**实时送达语义完全相同**（都是 at-most-once，都必须靠落库兜底才能真正必达）。Redis 带来的唯一增量是"独立通道"，但代价是新增一个组件与一套运维面，而系统已经在 M2 起把运维投入回落到 0.5 人。**20 在线规模下不值得为同等语义多养一个组件。**

**否决的替代方案**

- **Redis pub/sub / Redis Streams**：见上表。**否决原因**：语义无增益，组件成本确定，且与 ADR-11 的运维投入约束冲突。
- **应用内内存广播**：只在单实例内有效，正是 🔴5 要解决的问题。**否决原因**：未解决跨实例。
- **前端轮询替代 SSE**：改变已定契约（ADR-06 为 REST+OpenAPI+SSE），且轮询延迟与负载特性更差。**否决原因**：偏离既有决策，收益不明。
- **仅落库 + 前端轮询补齐（不做 NOTIFY）**：可实现必达但实时性差，用户感知为"进度条一跳一跳"。**否决原因**：SSE 的价值就是实时性，放弃实时等于放弃该决策的前提。
- **会话粘滞（同一用户固定路由到同一实例）**：减轻问题但不解决——Worker 产生的事件仍需通知到持有连接的那个实例；且粘滞会破坏负载均衡与故障转移。**否决原因**：治标不治本，且引入新的单点。

## 代价与风险

**代价**

1. 每个 API 实例需维持一个到 PG 的 `LISTEN` 长连接（专用连接，不进入业务连接池）。
2. 收到通知后需读库，等价于"通知风暴时会有集中读"。需在实现中按 id 去重与合并处理。
3. NOTIFY 为 at-most-once，因此**不能依赖通知本身保证必达**，必达由"落库 + Last-Event-ID 补漏"承担。这是必须被工程实现的，不是自动获得的。
4. 补齐逻辑需要索引支持（按序列号范围查询），随事件表增长需关注该索引的维护成本。

**风险与重新审视条件**

- **连接泄漏**：`LISTEN` 专用连接断开会静默失去实时能力（仍可靠补漏兜底）。需健康检查与重连。
- **通知丢失未被发现**：若补漏机制有缺陷，丢失会表现为主观"偶尔不更新"。因此"双实例必达验证"是硬验收项，不能只做单实例测试。
- **重新审视条件**：在线规模显著增长（如数百并发长连接）导致 NOTIFY 或补漏读成为瓶颈 → 重新评估独立消息通道或独立向量/缓存组件。当前规模下不预支该复杂度。
- 若后续因其他需求引入 Redis（如做限流或缓存），本决策可一并复核——但复核触发条件应是"Redis 已因别的理由存在"，而非"SSE 需要它"。

## 验证方式

### 双实例必达验证方法

| # | 步骤 | 期望结果 |
|---|---|---|
| V1 | 部署两个 API 实例（A、B），均挂同一反向代理 | 两个实例均建立 `LISTEN domain_events_new` |
| V2 | 用户 U 建立 SSE 连接，确认其落在实例 A（通过实例标识 / 日志确认） | 连接建立成功，可收到已有事件补齐 |
| V3 | 触发一条属于 U 的事件，且**确保产生事件的 Worker 与实例 B 相邻**（或直接在 B 侧写库产生事件） | 实例 A 上的 U 连接**收到该事件** |
| V4 | 交换角色：连接落 B，事件由 A 侧产生 | 实例 B 上的连接收到该事件 |
| V5 | 断开 U 的连接，产生 3 条事件，再以 `Last-Event-ID` 重连 | 补发恰好 3 条，无重复、无遗漏 |
| V6 | 越权订阅：用户 U2 订阅不属于其权限范围的事件流 | 被拒；且**逐事件**权限过滤生效（不因建立连接时点不同而放行） |
| V7 | 成员在会话中被移除后，继续尝试接收该项目的 SSE 事件 | 被拒绝（异常矩阵"成员移除后重新鉴权"口径） |

判据：V3 与 V4 必须**双向**通过。只测单向不能证明 fan-out 正确——这恰是原设计缺失的那一半。

### 断线恢复流程

```text
前端断线
  → 以 Last-Event-ID = 已收到的最大 sequence 重连
  → 服务端校验权限
  → 按 sequence > last_event_id 从 domain_events 查询待补事件
  → 逐事件权限过滤后补发
  → 若待补数量超过上限 → 返回"需全量刷新"信号，前端重拉快照
  → 补发完成后转入实时推送
```

边界要求：

- 重连时**先补漏再转实时**，避免"补漏过程中新事件已通过 NOTIFY 推来"造成乱序。实现上以序列号去重合并。
- 待补超限时的"全量刷新"路径必须有测试覆盖，不能只在正常路径上验证。

| 判据 | 验证方法 | 证据 |
|---|---|---|
| 双实例必达 | V1~V4 双向通过 | WP14 双实例必达验证记录 |
| 断线补齐正确 | V5：补发条数、顺序、无重复 | 异常矩阵 + 补齐日志 |
| 越权被拒 | V6：逐事件权限过滤生效 | 负向测试记录 |
| 权限变化即时生效 | V7 | 异常矩阵"成员移除后重新鉴权" |
| 通知丢失可兜底 | 人为阻断 NOTIFY（如断开 LISTEN 连接）后，靠重连补漏仍能拿到全部事件 | 故障注入记录（WP48） |
| 新增异常矩阵项 | 第 16 项"SSE 双实例下事件必达且越权订阅被拒"进入必测清单 | §12.2 异常矩阵 |
