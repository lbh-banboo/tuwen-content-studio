# ADR-16 知识激活缓解措施

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-19 |
| 决策人 | 老大（业务负责人） |
| 影响范围 | 知识库激活流程、knowledge_publications、站内通知、版本回滚、在跑任务输入固定机制、风险 R7 |

## 背景

评审硬伤 🔴4：知识资产"全员可确认生效"（需求 §15.3）没有第二人复核，存在误激活风险。

风险的具体形态是：某位运营在确认一条知识资产时判断失误（版本选错、范围选错、把未验证的内容当已验证），激活后该资产立即对全员生效，进入后续所有相关批次的生成输入。污染不是一次性的——它会被多个在跑与新建批次引用，直到有人察觉并回滚。

本问题已由 D2 拍板：**坚持全员自确认，靠版本回滚兜底，不加审批流**。因此本 ADR 不是重新讨论"要不要复核"，而是回答"在不加审批流的前提下，用什么缓解措施把风险压到可接受"。

需要注意的一个既有事实：系统本就有"在跑任务固定旧输入"机制（异常矩阵第 11 项），它天然构成一层隔离——激活新知识不会改变已在跑任务的输入。缓解措施设计应与该机制配合，而不是重复它。

## 决策

**我们决定知识资产维持全员可激活（业务决策，不做审批流），并配套四项缓解措施：激活前影响范围预览 + 二次确认、激活后站内通知管理者、详情页一键回滚上一生效版本；同时明确在跑任务固定旧输入的既有机制作为第一层隔离。**

### 缓解措施

| # | 措施 | 触发时机 | 具体行为 |
|---|---|---|---|
| M-1 | 影响范围预览 + 二次确认 | 激活**前** | 展示该次激活将影响的知识范围（范围/品类/品牌维度）、当前生效版本与目标版本差异摘要；必须勾选确认后激活按钮才可用 |
| M-2 | 二次确认强制留痕 | 激活**时** | `knowledge_publications` 的 ACTIVATE 事件强制要求 `impact_preview_ack=true`；未带该标记的激活请求被拒绝 |
| M-3 | 站内通知管理者 | 激活**后** | 激活事件触发管理者站内通知，含激活人、资产、范围、生效时间、一键查看详情入口 |
| M-4 | 一键回滚上一生效版本 | 激活**后**（详情页常驻） | 详情页提供一键回滚到上一生效版本的入口；回滚同样是一次激活事件，同样留痕 |

配套约束：

- 上一生效版本**必须保留**，不得被激活动作覆盖或清理（否则 M-4 无法执行）。
- M-1 的预览内容必须与实际影响范围一致；若预览与生效范围不一致，视为缺陷而非文案问题。
- M-3 的通知**不是审批**：管理者收到通知后不阻塞流程，激活已生效；通知的作用是把"事后发现"的时间窗口压到最短。
- 监控信号：激活通知发出后 24h 内该资产的修改率异常升高，视为疑似误激活（对应风险 R7）。

### 在跑任务固定旧输入的既有机制如何配合

| 层次 | 机制 | 作用 |
|---|---|---|
| 第一层（既有） | **在跑任务固定旧输入**：任务在启动时固定其知识输入快照，激活新知识不改变已在跑任务的输入 | 天然的隔离带。误激活不会追溯污染正在执行的任务，把影响面限制在"激活之后新建/重新取输入的任务" |
| 第二层（本 ADR M-1/M-2） | 激活前预览 + 二次确认 | 降低误激活**发生率**，把判断失误挡在生效之前 |
| 第三层（本 ADR M-3） | 激活后通知管理者 | 缩短**发现时间**，把污染窗口从"下次有人碰巧发现"压到"24h 内被注意到" |
| 第四层（本 ADR M-4） | 一键回滚上一生效版本 | 降低**修复成本**，把修复动作从"手工重建版本"降为"一键回滚" |

四层配合后的整体语义：**误激活仍可能发生，但影响面被限定、发现时间被压缩、修复成本被降低**。这是本决策换取"流程轻量"的完整代价与收益结构。

### 为什么不做第二人审批（老大已拍板）

- **D2 已拍板**：坚持全员自确认。本 ADR 不重新讨论该决策。
- 业务侧的实际理由：知识资产激活是高频、低单次风险的日常动作。若每次激活都要第二人复核，复核人会成为流程瓶颈，运营的实际反应是"能不改就不改"——知识库停止更新，损失的是系统最核心的资产价值。
- 全员可激活的前提是：团队规模小（运营约 50 人，实际高频使用者更少）、成员彼此知情、激活动作全程留痕可追溯。在这个前提下，**可观察性 + 快速回滚**比**事前审批**更划算。
- 审批流的收益是降低发生率，成本是永久性的流程摩擦；而本 ADR 的四项措施在降低发生率（M-1/M-2）之外，还覆盖了审批流覆盖不到的"发现"与"修复"环节。

### 风险接受说明

本决策**显式接受**以下风险，不做进一步缓解：

| # | 接受的风险 | 接受理由 |
|---|---|---|
| A1 | 误激活仍可能发生，无事前拦截 | 事前拦截的成本（流程瓶颈 + 知识库停更）高于其收益；改用 M-1/M-2 降低发生率 + M-3/M-4 兜底 |
| A2 | 管理者通知不阻塞流程，存在"通知了但没人看"的可能 | 通知是辅助信号而非控制点；真正的兜底是 M-4 回滚与在跑任务隔离 |
| A3 | 回滚后，误激活期间新建的任务可能已引用错误知识 | 影响面受第一层机制限制；已产生的任务需人工判断是否重做，不做自动回滚 |
| A4 | 恶意或严重失误的激活无法被系统阻止 | 属人员管理范畴；系统侧靠不可篡改的激活留痕提供追责依据 |

**不接受的边界**：不得以"全员可激活"为由取消 M-1~M-4 中的任何一项。若因排期压力要削减，必须先回到老大重新决策，不得由执行层自行删减。

## 理由

1. **D2 是业务决策，工程侧应做的是把风险压到可接受，而不是反复质疑决策**。
2. **在跑任务固定旧输入已经是强隔离**。它意味着误激活的影响面天然被限制在"未来任务"，而不是"全部任务"。这个既有机制大幅降低了误激活的严重度，是"可以不加审批流"的重要前提。
3. **可观察性 + 可回滚 > 事前审批**（本场景）。审批防的是发生率，回滚防的是后果；后者对高频低危动作更划算。
4. **留痕是不可让渡的底线**。即使不做审批，也必须能回答"谁在什么时候激活了什么、影响范围是什么、依据是什么"。M-2 的 `impact_preview_ack` 与激活事件留痕承担这一点。
5. **M-1 的预览有独立价值**：即使不发生误激活，让运营在激活前看到影响范围本身就能提升判断质量，成本极低。

**否决的替代方案**

- **加第二人审批流**：D2 已拍板否决；且会造成知识库停更。
- **仅靠回滚，不做预览与确认**：误激活发生率高，回滚频繁，运营对系统的信任度下降。**否决原因**：只治后果不治原因。
- **激活后立即全量重算在跑任务输入**：破坏"在跑任务固定旧输入"这一既有正确机制（异常矩阵第 11 项），引入任务输入漂移。**否决原因**：会用一个新缺陷换一个已有缓解的问题。
- **限制只有管理者可激活**：与"全员可激活"的业务决策直接冲突，且制造瓶颈。**否决原因**：违背 D2。
- **引入审批但只在特定范围（如跨品牌资产）触发**：会产生"哪些算跨品牌"的判定争议与例外管理成本。**否决原因**：复杂度不划算，且 D2 已明确不加审批流。

## 代价与风险

**代价**

1. 需实现影响范围预览的计算（依赖范围过滤与影响图能力，WP20 人日 +1）。
2. 每次激活多一步勾选确认，是运营侧的固定操作成本（设计目标是尽量轻，不引入填写负担）。
3. 管理者会收到激活通知，存在通知疲劳风险；需控制通知粒度与聚合方式。
4. 上一生效版本必须长期保留，增加存储与版本管理复杂度。

**风险与重新审视条件**

- **R7 知识误激活污染在跑批次**：概率中、影响中。应对为 ADR-16 缓解；在跑任务固定旧输入。监控信号为激活通知后 24h 内修改率异常。
- **重新审视条件**：① 出现一次实际造成对外内容事故的误激活 → 需重新评估是否引入审批（回老大决策）；② 激活频率极低（如月均个位数）→ 可重新评估措施强度是否过配；③ 运营团队规模显著扩大，成员间相互知情的前提不再成立 → 需重新评估。
- 任何重新审视都**不改变留痕要求**：激活留痕与 `impact_preview_ack` 在任何方案下都必须保留。

## 验证方式

| 判据 | 验证方法 | 证据 |
|---|---|---|
| M-1 预览存在且一致 | 激活前展示影响范围；核对预览范围与实际生效范围一致 | 影响预览页 + 范围一致性测试记录 |
| M-2 强制确认 | 负向测试：不带 `impact_preview_ack=true` 的 ACTIVATE 请求被拒绝 | 负向测试记录 + `knowledge_publications` 表约束 |
| M-3 通知送达 | 激活后管理者收到站内通知，含激活人/资产/范围/时间/详情入口 | 通知记录 |
| M-4 一键回滚 | 激活后详情页可一键回滚至上一生效版本；回滚后生效版本正确；回滚同样留痕 | 回滚功能测试 + 回滚事件记录 |
| 上一生效版本保留 | 检查激活动作不覆盖上一生效版本 | 版本历史查询记录 |
| 第一层隔离有效 | 构造在跑任务，激活新知识后确认该任务输入快照不变 | 异常矩阵第 11 项"在跑任务固定旧输入" |
| 监控信号有效 | 激活通知后 24h 内修改率异常可被检出 | 监控面板 / 告警规则 |
| 留痕完整 | 每条激活事件可查到激活人、时间、资产、范围、依据、ack 标记 | 审计记录抽样 |
