# 数据结构与接口契约

> 编制日：2026-10-11　依据：登记册 **OP-197**（正文切段口径）、**OP-199**（顺序对位派图）
> 定位：本仓**跨模块「不可互相 import、但必须同口径」的契约点**的**权威口径存证处**。
> 自检判据：`tools/quality/check_paragraph_split_parity.py`（**G8** 核对本文档）。

---

## 0. 为什么需要这份文档

本仓有一条既有铁律：**模块平级，模块间不可互相 import**
（出处与论证见 `services/backend/src/rednote/modules/media/repository.py`
的取数纪律说明）。这条铁律带来一个必然后果：

> **同一个口径若跨模块使用，就必然有多份实现 —— 无法收敛成"唯一实现"。**

而「一份事实、多处声称」恰是本仓的高发缺陷形态（ISS-95 / ISS-137 族）。
对这些点，本仓的处置**不是**"想办法合并成一处"，而是三步：

1. **口径公理化** —— 口径只在本文件定义一次，作为唯一权威文本；
2. **各实现只对口径负责** —— 各写一份代码、互不引用；
3. **一致性由判据机械钉住** —— 见 §1.5；判据的期望值来自本文档 §1.4。

> ⚠️ 本文档**只承载"权威口径"这一件事**：不复制实现、不复制判据逻辑。
> 复制出来的第二份文本会腐烂 —— 汇总列是唯一声称方时若无人对账，就会静默
> 漂移（ISS-85 族）。故本文档只写**判据要核对的那一份表**（§1.4），
> 逻辑一律由指针指向代码与判据，不在此处复述。

## 1. 正文切段口径（**权威定义** · OP-197）

### 1.1 一句话

> **段 = 被空行分隔的块；段内软换行不切段。**

### 1.2 规则（三句，即全部）

1. **按空行切**：分隔符为 `re.split(r"\n\s*\n")`（一个换行 + 任意空白 + 一个换行）。
2. **每段去首尾空白**（`.strip()`）。
3. **丢弃纯空白段**；段序号 = **过滤后**的连续下标，**从 0 起**。

> 规则的**唯一落点**是下面三处实现的 `_PARAGRAPH_SPLIT` 常量；
> 本文档不给出第二份可执行文本（那会变成"代码没兑现文档"的第二现场）。

### 1.3 三处实现（各自独立、互不 import）

| # | 位置 | 供谁消费 |
|---|---|---|
| 1 | `services/backend/src/rednote/modules/content/schemas.py::split_paragraphs` | 绑定覆盖校验（`paragraph_count`） |
| 2 | `services/backend/src/rednote/modules/knowledge/chunking.py::_split_paragraphs` | 检索切块 |
| 3 | `services/backend/src/rednote/modules/media/schemas.py::paragraph_refs_for_body` | 生成图的段落坐标（`paragraph_ref`） |

> ⚠️ `services/backend/src/rednote/modules/media/service.py::paragraph_refs_for_body`
> 是**转出**（`from …schemas import paragraph_refs_for_body as _paragraph_refs_for_body`），
> **不含第二份实现**。保留这个名字的理由：调用方按
> `media.service.paragraph_refs_for_body` 取它，改那些调用点属跨包改动，
> 不该由一次口径收口顺带做 —— 但**实现必须只有一份**。
> 见 **OP-197** 的处置记录（收口期实测：判据曾绑在未入库的 `service.py` 上
> ⇒ 共享树绿、干净检出红，ISS-95 族）。

### 1.4 场景期望表（★ **判据读本表，双向对账**）

> 本表是**权威口径的唯一样本集**：`check_paragraph_split_parity.py` 的
> `_EXPECTED` 必须与本表**逐行相等**（场景名 ↔ 期望段数）。任一侧单独改动
> 都会让判据 **G8 报红** —— 这一条正是 OP-197 要的"第二处文档副本"的
> **可对账**形态（对比 G6 只查脚本存在性、不查内容）。

| 场景 | 期望段数 | 说明 |
|---|---|---|
| `空行分段` | 2 | 最简形态：`A` + 空行 + `B` |
| `单换行是段内软换行` | 1 | `A\nB` —— **不切** |
| `连续多空行仍算一段` | 2 | `A\n\n\n\nB` |
| `段内换行加空行` | 2 | `A1\nA2\n\nB` |
| `缩进不切段` | 1 | `A\n  B` —— **不切** |
| `空正文切出零段` | 0 | 调用方必须 fail-closed（`PARAGRAPH_REF_UNKNOWN`） |
| `emoji加段内换行` | 1 | `A😀\nB😂` —— **小红书正文常态，不切** |
| `尾随空段被丢弃` | 1 | `A\n\n\n` |
| `前导空段被丢弃` | 2 | `\n\nA\n\nB` |
| `全空白切出零段` | 0 | `"  \n\n \n"` |
| `CRLF视作空行` | 2 | `A\r\n\r\nB`（`\s` 覆盖 `\r`） |

> ⚠️ 正文原文（含 emoji 与转义）只写在判据源码里（`_EXPECTED` 的字面量），
> 本表只承载 **场景名 + 期望段数** 这两个**可机械对账**的字段 ——
> 把转义文本也搬进 markdown 会把对账变成脆弱的文本解析（得不偿失）。
> 判据 G2 已单独验证"期望段数对不对"（对三处真代码），本表与 G2 合成
> "双判据"：G1 管三处相等，G2 管相等的那份对不对，**G8 管"对不对"这件事
> 有没有第二处独立声称**。

### 1.5 一致性如何被守住

| 判据 | 位置 | 抓什么 |
|---|---|---|
| **G1** | `tools/quality/check_paragraph_split_parity.py` | 三处真代码在同一批正文上**逐段全等** |
| **G2** | 同上 | 每处段数与**手写期望表**全等（防"三处一起错到同一个值"） |
| **G3** | 同上 | 段内软换行**不切段**（防退回 `splitlines()` 写法） |
| **G4** | 同上 | `media` 侧序号是**过滤后连续下标**且从 0 起 |
| **G5** | 同上 | 活性下界：三处实现**都真的被导入并调用过** |
| **G6** | 同上 | 三处 docstring 点名的判据脚本**真实存在** |
| **G7** | 同上 | 三处实现所在文件**已入库**（`git ls-files`）—— 干净检出可跑 |
| **G8** | 同上 | **本文档存在且已入库**；§1.4 的表与判据 `_EXPECTED` **双向对账** |

> ⚠️ **已知边界（刻意记下，不假装覆盖）**：G1~G8 能防"三处不一致"、
> 也能防"判据的期望表与本文档分叉"，但**防不住"三处实现连同本文档 §1.4
> 与 `_EXPECTED` 一起改错"** —— 那要求同时改动四处、且方向一致。
> 登记册 **OP-197** 已就此写明：剩下两条更彻底的出路（抽 `platform` 级
> 纯函数模块 / 把切段下沉为 `content` 的对外契约）**都要先动"模块平级能否
> 互 import"这条既有铁律**，不该由一个跨包收口顺手改。

## 2. 取数口径：「当前版本」的读法（跨模块只读 SQL）

> 同一族契约点：**跨模块取数只能走只读 SQL，列名即对方契约**。
> 口径不得两侧各写一份（各写一份的表现是"两侧对同一份数据有不同理解"）。

### 2.1 权威定义

> **「当前版本」= `content_items.current_version_id` 投影；
> 投影为 `NULL` 时回落 `ORDER BY version_no DESC LIMIT 1`。**

- **不允许**只按 `MAX(version_no)` 推断"当前版"：投影是**显式指针**，
  可以指向任意一版（回滚 / 标记），与"最后落库的那版"在有回滚或非单调
  推进时**分叉**（登记册"结构结论"节）。
- **不允许**只按投影：该列**可空**（`deferrable=True, initially="DEFERRED"`，
  为允许"先建身份、后建版本"）⇒ 只投影会把一个**合法的中间态**误报成缺正文。

### 2.2 实现落点

- `services/backend/src/rednote/modules/media/repository.py::content_body_for_paragraphs`
  —— 裸 SQL，列名 `body` / `version_no` / `content_item_id` / `current_version_id`
  即 `content_versions` / `content_items` 的契约。写错列名当场 `UndefinedColumn`，不静默。

> ⚠️ **本节当前没有独立判据**（与 §1 不同）。判断依据是"它被真跑覆盖"——
> 该路径由 `test_media_wp27.py` 的取数用例（含回滚分叉）真跑过。
> 本表如实记录"有判据 / 无判据"，**不把"有测试覆盖"写成"有判据"**（ISS-95 族）。

## 3. 段落引用（`paragraph_ref`）的口径

> 同族契约点：**一个标识的拼法只能有一处实现**（生成时与校验时不一致的
> 表现是"刚生成的图立刻被判未知"）。

### 3.1 权威定义

> **`paragraph_ref` = `"p{index}-{hash8}"`**，其中 `hash8` 是**段文本规范化后**
> 的前 8 位十六进制；`index` 是 §1 的**过滤后连续下标**。

- **归一化口径只有两件事**：去首尾空白、把内部连续空白折成单个空格。
  **不做大小写折叠**（中文无大小写，英文段落的大小写有意义）。
- **为什么带文本哈希**：只用序号（`p3`）的话，删掉第 3 段后原先绑在 `p3`
  上的图会**静默改指**到另一段；带哈希后同样的重排会让 ref 不再匹配任何
  当前段落 ⇒ 可判"需要重做"（`PARAGRAPH_REF_UNKNOWN`）。

### 3.2 实现落点

- 拼法：`services/backend/src/rednote/modules/media/types.py::paragraph_ref_for`
  —— **唯一实现**（生成与校验共用它）。
- 切段 + 拼 ref：`media/schemas.py::paragraph_refs_for_body`（§1.3 第 3 处）。

## 4. 顺序对位派图（**权威定义** · OP-199）

### 4.1 权威定义（老大 2026-10-08 拍板原文）

> **顺序对位** —— 第 i 张配第 i 段（i 从 0 起）；段落数不足 3 时，
> 多余张一律回落**最后一段**。

| 段落数 | 派出的 ref 下标 | 说明 |
|---|---|---|
| 1 | `[0, 0, 0]` | 三张都画唯一那段（同一段多角度） |
| 2 | `[0, 1, 1]` | 第 3 张回落最后一段 |
| ≥3 | `[0, 1, 2]` | 前 3 段各一张（第 4 段起不出图） |

- **返回值恒为长度 3**（`images_per_content()`），与"实际出几张"**同源**。
  不足 3 段时**不改成"少出几张"**：预占按固定 3 张算，若实际更少，
  差的那一笔**不会报错**，只表现为"账面永远差一笔"。
- **多张落同一段是合法的**，不是退化：身份键是
  `(content_item_id, sort_order)`（"这是这篇内容的第 N 张"），
  `paragraph_ref` 只是**当前版本的投影**、**不落唯一约束**。
- **段落为空 ⇒ fail-closed**（报 `PARAGRAPH_REF_UNKNOWN`，不编 ref、不跳过）：
  退化成"图照生成、只是没有段落坐标"是**静默降级**。

### 4.2 实现落点

- `services/backend/src/rednote/modules/media/schemas.py::assign_paragraph_refs`
  —— **唯一落点**（同模块于切段，避免判据绑未入库产物）。
  无 `image_count` 入参（老大拍板固定 3 张后该入参**没有合法来源**）。

> ⚠️ **本节当前没有独立判据**（同 §2）。由 `test_media_wp27.py` 相关用例
> 真跑覆盖。如实记录，不夸大。

## 5. 本文件自身的维护规则

1. **新增一条契约** ⇒ 必须同时给出：权威口径（一句话）+ 实现落点（路径）
   + **有无独立判据**（有则写判据路径；无则**显式写"无"**）。
   > 写"无判据"不是自曝其短，而是让"缺判据"成为可见的待办；
   > 把"有测试覆盖"写成"有判据"才是 ISS-95 族。
2. **§1.4 的表**是判据 G8 的读取对象 ⇒ 改表等于改判据期望 ⇒
   必须**同一批**改 `_EXPECTED`，否则 G8 报红（这是设计意图，不是负担）。
3. **本文档一经入库**，`check_paragraph_split_parity.py::G8` 会核对它已入库
   （`git ls-files`）—— 否则"文档在共享树、干净检出没有"，会让 G8 在别人
   的检出上红（铁律 18）。
