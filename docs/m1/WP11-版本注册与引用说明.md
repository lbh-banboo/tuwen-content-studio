## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

一句话：**让"某个东西的某一版"在全系统有一个统一身份证，从而让跨模块的溯源引用有据可依、
让"已定稿的版本"不可能被偷偷改掉。**

具体拆成三个互不重叠的问题：

| # | 问题 | 不解决的后果 |
|---|---|---|
| 1 | 跨模块引用无外键 | Brief 版本被"方案"引用、被"内容"引用、被"报告"引用。若每个引用方各自建一列 `brief_version_id`，那么 7 种版本类型 × N 个引用方就是 `7N` 个外键列，且"谁引用了谁"无法反查 |
| 2 | 历史版本可被原地改写 | 审核通过的正文被后台脚本改一个字段，所有已交付内容的事实依据静默失效。这类错误**不会报错**，只在事后对账时暴露 |
| 3 | 可变与不可变的边界不清 | 草稿能改（`lock_version` 递增、ETag 变）、版本不能改（ETag 恒定）。两者混在一起时，前端无法判断"该不该带 If-Match" |

### 1.2 核心用户是谁？

| 角色 | 什么时候用 | 关心什么 |
|---|---|---|
| **后端 A（本人）** | 写 WP18 Brief / WP20 知识 / WP21 方案 / WP29 内容 | 只要调 `register_version()` 就能拿到合法版本号，不必关心并发与唯一性 |
| **后端 B** | 写 WP13 任务 / WP16 模型网关 / WP38 指标 | `version_dependencies` 能直接回答"这个结果依赖哪些输入版本" |
| **前端** | 展示版本历史、做"回退到某一版" | 版本列表的分页游标不要错位；版本的 ETag 恒定可以直接做 `If-Match` |
| **测试** | 做溯源验收 | 能构造"跨项目引用"并确认被拒 |

**关键结论**：WP11 的主要用户是**开发同事而不是终端用户**。这直接决定了它应该是
"服务层能力 + 迁移"，而不是"一堆新页面端点"。

### 1.3 最小 MVP 应包含哪些功能？

只做三件事，缺一件则验收不可通过：

1. **`version_nodes` 注册表**（不可变）—— 提供 `(entity_type, entity_id, revision_no)` 唯一身份
2. **`version_dependencies` 依赖边** —— 提供"版本间引用"，并在此处落实"跨项目引用拒绝"
3. **不可变保护** —— 让"旧版本不可改"成为**数据库级**约束，而不是"代码里没写 UPDATE 语句"这种口头承诺

外加一件使能项（不是功能，是给上面三件事提供契约）：
4. **ETag 语义分层** —— 可变资源（草稿）用 `lock_version`，不可变资源（版本）用内容摘要

### 1.4 描述有哪些疏漏应当补充？理由是什么？

研发计划 04 只有一行 12 个字，以下是我主动补全的。**每一条都给出理由，不照单全收。**

| # | 疏漏 | 为什么必须补 |
|---|---|---|
| 1 | **没有说不可变保护落在哪一层** | "旧版本不可改"若只在 ORM 层实现，那么 `psql` 手工改、Alembic 数据回填、将来的批处理脚本都能破防。而这三种恰恰是**没有代码评审**的路径。必须在数据库层也拦一道 |
| 2 | **没有说 `entity_type` 的取值域从哪来** | 若允许任意字符串，`version_nodes` 会退化成"万能 JSON 仓库"——数据结构文档 02 明确禁止这一点。必须用受控枚举 |
| 3 | **没有说并发注册同一版本怎么办** | 两个请求同时"固化 Brief 版本"，会得到两个 `revision_no=1`。必须靠 `UQ(entity_type, entity_id, revision_no)` + 重试，而不是靠应用层先查后插 |
| 4 | **没有说跨项目引用拒绝是在**插入时**还是**读取时**校验** | 只在读取时拒绝，脏数据已经落库；只在插入时拒绝，就依赖调用方传对 `project_id`。**两者都要**，且插入时的判断必须由服务端从 `version_nodes` 里读，不能信调用方传参 |
| 5 | **没有说 DAG 环检测的深度上限** | 图遍历在有环时不会自然终止。必须有访问集合 + 深度上限，并明确"检测在事务内进行" |
| 6 | **没有说 `payload_hash` 的算法与规范化口径** | 同一个逻辑版本换一种 JSON 键序就算"不同内容"，会让幂等注册失效。必须规定规范化（`sort_keys` + 紧凑分隔符）后再哈希 |
| 7 | **没有说版本端点是否需要对前端开放** | 协议 03 的端点表里**没有任何 `/versions/*` 端点**。这是一个真实的规格缺口，不能默默补一个端点就完事 |
| 8 | **没有说"草稿"归谁所有** | 若 WP11 顺手建 `brief_drafts`，就越界到 WP18 了。必须明确：**WP11 只提供"草稿 → 版本"的升格逻辑，草稿表由各领域模块拥有** |
| 9 | **没有说删除语义** | 数据结构文档 02 §1："有业务引用的对象归档，禁止级联删除历史版本／审计"。`version_nodes` 不提供删除，物理删除由 `ondelete="RESTRICT"` 兜底 |

### 1.5 哪些功能现在不该做？

| 砍掉 | 理由 |
|---|---|
| `review_events` 表 | 属 WP18/WP30 审核范围。WP11 只建"审核对象"（版本节点），不建"审核动作" |
| `version_impacts` 表 | 属 WP34（回退与影响图）。现在建表会因为没有生产者而变成死表 |
| 各领域具体版本表（`brief_versions` / `content_versions` / …） | 属 WP18/WP20/WP21/WP29。WP11 建了它们，那些工作包就得反过来改 WP11 |
| 通用 `/versions/*` HTTP 端点 | 见 §1.4 第 7 条。协议未定义；且各领域模块自己的 `GET /contents/{id}/versions` 才是真实入口。现在加等于**替协议做决定**，且要背一份长期契约 |
| "延迟约束检查 `entity_type`/`entity_id` 与子表一致" | 数据结构 02 §5 原文要求它，但**它的前提是子表存在**。根本没有子表时这条检查无从写起。登记为待定项，由第一个领域版本表落地时补 |
| 版本内容的实际读写（`payload` 存取） | 数据结构 02 §5 明确"注册表不是替代各领域表的万能 JSON 仓库"。注册表只存 `payload_hash`，不存正文 |
| 归档端点 | 归档属于"改变可用性"的事件（`review_events` / `knowledge_publications`），不属 WP11 |

### 1.6 这个系统有哪些技术风险？

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| **不可变保护被绕过**（原生 SQL / Alembic 数据回填） | 🔴 高 | 静默的数据完整性失效，事后无法区分"被改过"与"本来如此" | ORM 事件 + PG 触发器**双保险**；触发器在迁移里建，与表同生命周期 |
| **触发器与 Alembic 冲突** | 🟠 中 | 迁移自动生成时不含触发器 → `downgrade` 漏掉 → 重建库后保护消失 | 触发器写在迁移文件里，`upgrade`/`downgrade` 成对；并在证据里回查 `pg_trigger` |
| **`version_dependencies` 成环导致遍历挂死** | 🟠 中 | 服务端请求永不返回，连接池被耗尽 | 访问集合 + 深度上限（`MAX_DEPENDENCY_DEPTH`）；深度超限报错而非静默截断 |
| **跨项目引用拒绝被"先查后插"的竞态绕过** | 🟠 中 | 两个事务同时插入，各自都读到"不跨项目" | 判断所需的 `project_id` 在**同一事务内**读；且依赖边的两端都带 `project_id` 冗余列用于一致性 CHECK |
| **`revision_no` 并发撞号** | 🟡 低 | 注册失败、用户看到 500 | `MAX_ATTEMPTS` 重试 + SAVEPOINT（复用 WP10 已验证的模式） |
| **注册表被当成万能存储滥用** | 🟡 低 | 表膨胀、Schema 失控 | `entity_type` 受控枚举 + 不提供 payload 读写接口（只有 `payload_hash`） |
| **`project_id` 可空导致可见范围判定歧义** | 🟡 低 | 平台级版本（如 `PROMPT_VERSION`）没有项目归属，可见性规则不清 | 明确规则：`project_id IS NULL` 的版本**仅管理者可见**；写入文档并测试 |

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**WP11 是给全系统的"版本"概念建户籍。** 它不生产版本、不展示版本、不审核版本 ——
它只回答三个问题：这个版本是谁（身份证）、它依赖谁（引用）、它能不能被改（不能）。

### 2.2 用户画像

**主用户是后端开发者。** 判据：WP18/WP20/WP21/WP29/WP13/WP34 六个工作包都要调它，
而终端用户永远不会直接请求 `version_nodes`。因此本包的成功标准是
**"下游模块接入成本低 + 接入后不可能写错"**，而不是"页面好看"。

具体落成两条设计约束：
- 下游只需要调一个函数：`register_version()`，其余（唯一性、并发、哈希规范）全部内部化
- "这条边会不会跨项目"由服务端自己判，**不要求下游传对 `project_id`**

### 2.3 核心功能清单（MVP）

| # | 功能 | 验收对应 |
|---|---|---|
| F1 | `VersionNode` 不可变注册表；`UQ(entity_type, entity_id, revision_no)` | 旧版本不可改（身份部分） |
| F2 | 不可变保护双层：ORM 事件 + PG 触发器 `BEFORE UPDATE OR DELETE` | **旧版本不可改** |
| F3 | `VersionDependency` 依赖边；`CHECK parent <> dependency` | 引用基础 |
| F4 | `link_dependency()` 三重校验：自引用 / 跨项目 / 成环 | **跨项目版本引用拒绝** |
| F5 | `register_version()` 幂等：同 `(entity_type, entity_id, revision_no)` 已存在时比对 `payload_hash` | 并发正确性 |
| F6 | `promote_draft()`：草稿 → 版本升格，返回新版本号与不可变 ETag | 草稿ETag |
| F7 | 版本历史键集分页 + 依赖边查询 | 下游可用性 |
| F8 | 版本可见范围：项目成员看本项目、管理者看全部、无归属版本仅管理者 | 越权防护 |

## 3. 阶段 3：多版本方案

### 方案 V1 —— 最快上线版

**做法**：只建 `version_nodes` 一张表，`entity_type` 用裸字符串；
依赖关系用 `version_nodes.depends_on uuid[]` 数组列；
不可变保护只在服务层"不写 UPDATE 端点"。

| 维度 | 评价 |
|---|---|
| 优点 | 半天做完；表少；数组列查"我依赖谁"很快（GIN 索引） |
| 缺点 | ① 依赖边无方向约束、无法加"跨项目"CHECK；② 数组列不能建外键，删节点后留下悬空 UUID；③ "不可变"是口头承诺，psql 一改就破；④ `entity_type` 裸字符串 → 注册表退化成万能表 |
| 适合场景 | 只有一种版本类型、且团队只有一个人的一次性脚本 |
| 风险 | **直接违反验收标准**：数组列无法在数据库层拒跨项目引用，只能靠应用层；一旦有第二个写入方就破防 |

**结论：否决。** 它省下的是半天，赔上的是本工作包存在的理由。

### 方案 V2 —— 只做注册表，不做保护（**不推荐**）

**做法**：建 `version_nodes` + `version_dependencies` 两张表，外键与 CHECK 齐全；
不可变保护只靠"ORM 不提供 update/delete 方法 + mapper 事件"。

| 维度 | 评价 |
|---|---|
| 优点 | 迁移干净（纯 DDL，无触发器）；ORM 层报错信息友好；移植性好（换库不用改迁移） |
| 缺点 | **原生 SQL 与 Alembic 数据回填不受保护** —— 而这两条路径恰恰没有代码评审 |
| 适合场景 | 数据库仅由本应用独占访问、且有 DBA 审计 |
| 风险 | 一次手工 `UPDATE version_nodes SET payload_hash=...` 就能让整个溯源体系失去可信度，且**事后无法察觉** |

**结论：不推荐。** "不可改"是数据完整性要求，数据完整性不该只由应用层的一厢情愿来保证。

### 方案 V3 —— 注册表 + 双层不可变 + 草稿升格（**推荐**）

**做法**：
- 迁移建两表 + **PG 触发器**（`BEFORE UPDATE OR DELETE` → `RAISE EXCEPTION`）
- ORM 侧同时加 `before_update` / `before_delete` 事件（给出可读错误，不让它走到数据库）
- `link_dependency()` 在**服务端自己读**两端 `project_id` 做跨项目判定；依赖边冗余存 `project_id`
  并用复合外键 `(parent_version_id, project_id)` / `(dependency_version_id, project_id)` 指向
  `version_nodes(id, project_id)` 的唯一键 —— 让"跨项目"成为**结构性不可能**，而不只是运行时检查
- `promote_draft()` 由调用方传入草稿的 `base_version_id`，WP11 不持有草稿表
- **不新增 HTTP 端点**

| 维度 | 评价 |
|---|---|
| 优点 | ① 验收两条都在数据库层兜底；② 跨项目引用**结构上不可能**（复合外键），不依赖任何运行时检查；③ 无 HTTP 端点 → 零契约负担、零前端变更；④ 下游接入只需调一个函数 |
| 缺点 | ① 迁移里带触发器，比纯 DDL 复杂；② 复合外键要求 `version_nodes` 有 `(id, project_id)` 唯一键（多加一个索引）；③ 无 HTTP 端点意味着**不能做端到端 HTTP 验证**，只能打服务层 |
| 适合场景 | 本项目的实际约束：多写入方、无 DBA、要求溯源可信 |
| 风险 | 触发器与 Alembic autogenerate 不兼容（autogenerate 不识别触发器，`downgrade` 需手写）。**已登记为铁律 G2 的延伸**：迁移含触发器时必须人工审校 `upgrade`/`downgrade` 成对 |

### 方案 V4 —— 完整版（注册表 + 通用端点 + 领域表）

**做法**：V3 之上再加 `GET /versions/{id}`、`/versions/{id}/history`、`/versions/{id}/dependencies`
三个通用端点，并顺手建 `briefs`/`brief_drafts`/`brief_versions` 作为首个消费者。

| 维度 | 评价 |
|---|---|
| 优点 | 有真实 HTTP 端点可做端到端验证；首个消费者一并落地，WP18 可以直接用 |
| 缺点 | ① 替协议 03 做了决定（协议未定义 `/versions/*`），要背一份长期契约；② `brief_*` 属 WP18 —— 越界，且 WP18 需要"解析与加厚"时可能推翻现在的表结构；③ 通用端点很可能**永远没人调用**（各领域都有自己的 `/contents/{id}/versions`），成为死代码 |
| 适合场景 | 已有真实需求驱动通用版本浏览器（例如做"全站版本检索"） |
| 风险 | 越界交付 → WP18 落地时要改 WP11 的表；通用端点无人用 → 契约维护成本长期挂账 |

### 选择与理由

**选 V3。** 三条理由，按权重排序：

1. **验收标准要求的两条都在数据库层兜底**，而不是靠"我们记得不写 UPDATE"。
   跨项目引用更进一步做成了**结构性不可能**（复合外键），比任何运行时检查都可靠。
2. **零契约变更**。协议 03 没定义 `/versions/*`，WP11 就不该造。
   各领域模块（WP20/WP29）自己的版本历史端点是真实入口，到那时才需要的是
   "复用同一套游标分页"，而不是一个通用端点。

### 4.2 两张表

| 表 | 列 | 关键约束 |
|---|---|---|
| `version_nodes` | 9 列：`id` / `entity_type` / `entity_id` / `project_id` / `revision_no` / `schema_version` / `payload_hash` / `created_at` / `created_by` | `UQ(entity_type, entity_id, revision_no)`；3 个 CHECK（取值域、修订号范围、schema 版本下界）；2 个索引 |
| `version_dependencies` | 5 列：`parent_version_id` / `dependency_version_id` / `purpose` / `selected_fragment_hash` / `created_at` | `PK(parent, dependency, purpose)`；`CHECK parent <> dependency`；1 个索引 |

三条刻意的取舍：

1. **`entity_id` 是逻辑实体，`id` 才是版本**。`UQ(entity_type, entity_id, revision_no)`
   的含义是"某类实体的某个对象，它的第 N 版"。
2. **两表都刻意没有 `updated_at` / `lock_version`**。文档 02 §1 规定
   "mutable 表有这两列、历史表不允许原地改写"，本表属后者 ——
   加了 `lock_version` 反而暗示"它会被改"。
3. **主键含 `purpose`**。同一下游版本可以因不同用途引用同一上游版本
   （既把某条知识当 `FACT` 又当 `STYLE`）。文档 02 §5 只写"复合 PK"没写明含哪几列，
   已登记 OP-89（`purpose` 取值域）与相关待定项。

### 4.3 三个触发器 / 两个函数

| 触发器 | 挂载 | 作用 |
|---|---|---|
| `trg_version_nodes_immutable` | `version_nodes` BEFORE UPDATE OR DELETE | 拒绝任何改写 |
| `trg_version_dependencies_immutable` | `version_dependencies` BEFORE UPDATE OR DELETE | 同上 |
| `trg_version_dependencies_scope` | `version_dependencies` BEFORE INSERT | 拒绝跨项目引用（SQLSTATE 23514） |

两表共用同一个不可变函数 `rednote_reject_mutation`（行为完全一致，
拆成多个只会让"DBA 改一处得改 N 个"）。

**DDL 与名字只有一个来源（`versions/ddl.py`）**：迁移与验证脚本都从它取。
若两边各自手写，就会出现"迁移建了 `trg_x`、验证脚本找 `trg_y`"这种
**看起来通过、实际没有保护**的情况。`RAISE EXCEPTION ... USING MESSAGE = ...`
一律用字符串拼接而**不用 `%`** —— psycopg 的 paramstyle 会把 `%` 当占位符，
未提供参数时直接报 `unsupported format character`（真踩过）。

### 4.4 迁移 `cedfe85c1bf9`：`downgrade` 必须分两趟

**踩到的坑**：`DROP FUNCTION IF EXISTS rednote_reject_mutation()` 报
`cannot drop function ... because other objects depend on it`。

根因：该函数被**两张表的触发器共用**，而第一版实现是"删一个触发器就删一次函数"
的配对处理 —— 删到第一张表时，第二张表的触发器还在引用它。

修法：**分两趟** —— 先删全部触发器，再删函数（用 set 去重）。**不用 `CASCADE`**：
CASCADE 会把"删对了没有"交给 PG 去猜，而 B 表专属的那个 scope 触发器
并不是我们这次想删的东西。

验证：downgrade → 新表 0 / 触发器 0 / 函数 0 / `smoke_meta` 仍 4 行；
re-upgrade → 新表 2 / 触发器 3。**双向可逆，且不误伤冒烟残留表**（G2 铁律）。

### 4.5 双层不可变保护的**实际**分工

| 层 | 管住什么 | 实现 |
|---|---|---|
| ORM 事件 | 应用正常写入路径；给出可读的领域错误 | `before_update` / `before_delete` |
| 数据库触发器 | **所有**写入（`psql` 手工、Alembic 回填、运维脚本、ORM DML） | `BEFORE UPDATE OR DELETE` |

阶段 5 审出的两个关键事实（均已修 / 已证，详见 §5）：

1. `before_update` **按"实例是否 dirty"触发**，而"给属性赋相同值"也算 dirty ——
   守卫内必须再判一次净变化，否则"读了不改"会被误伤成 500。
2. mapper 级 `before_update` **不覆盖 ORM-enabled DML**
   （`session.execute(update(...))`）—— 那条路径**只有触发器**能拦。
   这不是设计缺陷，而是"为什么触发器不能省"的最直接证据。

### 4.6 草稿 ETag → 不可变 ETag 的切换点

WP11 **不持有草稿表**（草稿归各领域模块，它们各有领域字段）。
本包负责的是升格这一刻的语义切换：

- 草稿阶段：`build_etag(draft_id, lock_version)`，每次保存递增；
- `promote_draft()` 之后：`build_immutable_etag(node_id, payload_hash)`，**此后永不变化**。

不可变 ETag 加 `h` 前缀（`"{id}:h{hash[:16]}"`）：载荷 hash 恰好全为数字的
概率约 0.27%，那时 `parse_etag` 会把内容摘要误判成版本号，让一个 400 变成 412。

`promote_draft()` 的返回值直接带 `etag` —— 调用方固化版本后把新 ETag 回给前端，
前端下一次读取就能看到"这个 ETag 不再变"。这个"不变"不是承诺，
是数据库层面的既成事实（触发器守着）。

### 5.1 两条 MAJOR 的共同特征：**声明了保护，但保护没生效**

**D1（ISS-27）—— 环检测**：设计文档 §2 的风险应对写的是两个措施
「**访问集合** + 深度上限」，实现只落了「深度上限」。而深度上限**防不住**
路径爆炸（`UNION ALL` 会把每条路径各展开一行，只把爆炸上限钉在 `扇出^深度`），
并且会**漏判**落在上限之外的环 —— 返回"不可达"从而放行一条成环的边，
下游拿到它真会挂死。

本机实测（PG 16，19 节点 / 36 边的"菱形链"，`max_depth=32`）：

| 场景 | `UNION ALL`（原） | `UNION`（修后） |
|---|---|---|
| 无环 depth=18 | 524,287 行 / 1,283 ms | **37 行 / 0.6 ms** |
| 含环 depth=9 | **查询不返回**（进程被拖死） | 62 行 / 5.4 ms |

环恰恰是环检测最需要处理的输入 —— 原实现在这个输入下**最先挂死**。

**D2（ISS-25）—— 不可变守卫**：`guard_immutable` 的 docstring 承诺
"读了不改不会误报"，而 SQLAlchemy 的实际行为是：`before_update`
对**所有 dirty 实例**触发，"赋相同值"也算 dirty（官方文档明写
*even those which have no net changes*），净变化判定发生在这之后。
于是 `row.x = row.x` 这种无害写法会被误伤成 500。

**共同的教训**：这两处都不是"漏写保护"，而是**保护写在了错误的位置**
（一个把"限制规模"当成"去重"，一个把"事件触发"当成"确认修改"）。
判定依据只能来自对底层机制的直接查证（SQLAlchemy 源码 / PG 实测），
不能来自"名字听起来对"。

### 5.2 两条 MAJOR 的回归测试都做了反证

**D1**：临时把 `UNION` 改回 `UNION ALL` 重跑 —— 测试失败，
报 `psycopg.errors.QueryCanceled: canceling statement due to statement timeout`，
被 3 秒超时**优雅截断**而非永久挂死（6.43 s 结束）。
即：该测试确实能抓住旧实现。

**D2**：`test_reading_a_node_without_changing_it_is_allowed`（净变化为零必须放行）
与 `test_immutable_node_update_via_orm_is_rejected`（真修改必须拦）**同时通过**，
说明修法是"精确放行"而不是"把守卫关掉"。

### 5.3 明确记录"不成立"的怀疑

第三遍审查时怀疑 `link_dependency` 的 `except IntegrityError` 分支里读
`parent.id` 会触发 WP10 踩过的 `PendingRollbackError`（flush 失败后读 ORM 属性）。
**实测否定**：这两个对象是在 `savepoint()` 之外加载且未被修改的，
SAVEPOINT 回滚不会 expire 它们（只有 savepoint 内 add 的 edge 对象会失效）。

**不加固**：不为不存在的风险增加代码噪声。这个结论本身写进了证据文件 ——
否则下一次审查会重复怀疑一遍。
