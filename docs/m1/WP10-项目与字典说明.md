## 3. 关键设计决定（含"为什么"）

### 3.1 编号用随机后缀 + 唯一约束重试，而不是"月份 + 递增序号"

递增序号需要一个"当月已用最大序号"的读取：并发创建下要么锁表、要么容忍跳号；跳号又与"编号连续好看"的诉求冲突。
随机后缀 + 唯一约束 + SAVEPOINT 重试在并发下天然正确，且不需要任何额外状态。

格式定为 `PRJ-YYYYMM-XXXXXX`：
- 带年月 —— 人看编号就能判断项目大概何时开项，排障与对账时比纯流水号有用；
- 6 位 base32 ≈ 30 bit ≈ 10.7 亿组合 —— 即使每月新增 1 万个项目，同月碰撞概率仍可忽略；
- **Crockford Base32（去掉 I/L/O/U）** —— 编号要在邮件、工单、文件名里传抄，常规 base32 的 `1/I/L` 与 `0/O` 手抄必错。

**编号必须文件系统安全**：需求 §3.x 规定交付包命名为 `项目编号_批次编号_导出时间/`，编号直接进目录名。因此前缀校验限定 **ASCII** 字母数字与连字符，且必须至少含一个字母数字（`-` / `---` 这类纯连字符前缀会被拒 —— 否则会生成以连字符开头的编号）。这两条是 code review 后补的，见 §5.5。

> 需求 §4.1 只规定"系统生成、全局唯一、不可变"，**没有规定格式** —— 属需求缺口，已登记为 OP-80。

### 3.2 两处并发保护都要有，缺一不可

`PATCH` 与交接的并发保护分两层：

1. **应用层** `require_if_match(request)` —— 缺失 428、通配符 `*` 428、格式错 400、不匹配 412（带 `currentEtag`）。
   它的价值是**在提交前给出明确错误**，让前端知道"该去重新读一次"。
2. **SQL 层** `UPDATE ... WHERE lock_version = ?` —— 只有这一层是**原子的**。
   只在应用层比对会留下"读到旧版本 → 校验通过 → 另一个请求先写入 → 本请求覆盖"的窗口。

`rowcount != 1` 即判为版本冲突。两层都在，任一单独存在都不足以覆盖。

**为什么显式拒绝 `If-Match: *`**：RFC 9110 允许 `*` 表示"资源存在即可"，但本系统用它专做版本防护。
接受 `*` 等于让客户端写一个字符就绕过全部并发检查 —— 这个机制会退化成"必须多写一个头部"的形式主义。
因此明确返回 428，让"忘传 ETag"的写法无法通过。

### 3.3 键集分页必须下推 SQL，字典列表例外

项目列表**不下推就是错的**：`OFFSET n` 基于"前 n 条没变"这个前提，而项目列表持续写入，偏移分页会漏项或重复。
实现用行值比较 `tuple_(due_date, id) > tuple_(:due, :id)`（可直接用复合索引）+ `limit+1` 判 `hasMore`
（不再发 `COUNT(*)` —— 在并发写入下 COUNT 与实际结果本就不一致）。

字典列表则**故意**用内存分页：字典是全组织共享主数据，行数在千级以内，一次取回的内存与查询成本可忽略；
项目列表不同 —— 需求 §2.3 明确"项目数量不设业务上限"。两处用不同策略是有依据的，不是不一致。
**代价已显式记录**：字典扫描上限 `DICT_SCAN_LIMIT = 2000`，超出会漏项（OP-84 / ISS-23）。

### 3.4 游标指纹必须包含"可见范围"

游标载荷里写的是 `SHA-256(排序字段 + 方向 + 筛选条件)`。**可见范围（scope）也是筛选条件之一**：

```
"scope": "all" if user.is_admin else str(user.id)
```

若指纹只绑排序与筛选、不绑可见范围，管理者把自己那一页的游标发给运营，运营就能拿到越界的一页。
`test_project_list_operator_scope_is_bound_into_cursor` 就是守这一点的。

用 SHA-256 而不是 HMAC 签名：协议要求 API 双实例（ADR-11 C8），进程内随机密钥会让 A 实例签发的游标在 B 实例验签失败；
关键判断是**游标载荷不承载权限**，伪造它最多改变"从哪条之后继续读"，改变不了"能读到什么"。
权限过滤必须在每个查询里重新执行 —— 把权限编码进游标以省一次查询，会在权限被撤销后让旧游标继续放行。

### 3.5 404 与 403 的区分延续 WP09

| 场景 | 返回 | 理由 |
|---|---|---|
| 项目不存在 | 404 | —— |
| 用户不是项目成员且非管理者 | 404 | 防项目存在性枚举（协议 §1.2） |
| 是成员但缺具体权限 | 403 | 用户已能看到该项目，隐瞒只会让人困惑 |

### 3.6 交接的三步顺序不可调换

```
1. 旧负责人让出 OWNER 位（降级为协作者，或置 removed_at）
2. 新负责人取得 OWNER 位
3. 更新 projects.owner_id + lock_version（带版本条件）
```

第 1 步必须在第 2 步之前：`uq_project_members_active_owner` 是"每项目至多一名活跃负责人"的数据库级约束，
若先插新负责人，此刻旧负责人仍活跃，会直接撞唯一索引。
**这正是"并发交接仍一名负责人"的实现机制** —— 两个并发请求中后到的那个在插 OWNER 位时必然失败。

第 3 步带版本条件；版本冲突时返回 False，上层抛 412 并回滚事务，
**成员变更一起撤销** —— 不会留下"负责人成员换了但 `projects.owner_id` 没换"的半成品。

第 2 步还必须**先查再决定"升格 or 新增"**：把项目交给一个已经在项目里的协作者是最常见的交接场景之一。
无条件 `INSERT` 会撞 `uq_project_members_active`（(project_id, user_id) WHERE removed_at IS NULL）。
这个缺陷在 code review 中被抓到，见 §5.1。

### 3.7 待办转交用单条 UPDATE

用一条 `UPDATE ... WHERE` 完成，而不是"查出来 → Python 里逐条判断 → 逐条更新"：
- 逐条更新在待办量大时产生 N 次往返；
- 更重要的是**逐条判断会引入"读与写之间的窗口"** —— 遍历过程中若有人新建了一条属于旧负责人的待办，它会被漏掉。
  单条 UPDATE 在同一语句内完成筛选与写入，没有这个窗口。

### 3.8 字典不提供删除

字典被项目引用后物理删除会产生悬挂外键。归档（`status = ARCHIVED`）已经表达"不再启用"，且保留历史引用。
归档前检查引用计数：**被引用时禁止归档**（409 `INVALID_TRANSITION` 带 `referencingProjectCount`），
而不是"归档时清空引用" —— 已引用该品牌的项目必须继续正常工作。

### 3.9 编号冲突重试必须包在 SAVEPOINT 里

随机后缀撞车概率极低但非零。直接 `catch IntegrityError` 而不回滚到保存点，PG 会把整个事务标记为 aborted，
后续语句全部失败 —— **重试反而变成新的报错**。

同时**必须精确判定冲突来源**（`_is_project_code_conflict`）：先取 `err.diag.constraint_name`，取不到才退化为文本匹配。
若一律重试，来自 `uq_project_members_active` 等其它约束的冲突会被吞掉，用户看到"重试 5 次后失败"，
真正的原因（例如负责人同时出现在协作者列表里）被掩盖。

## 5. Code Review 发现与修复

按 `superpower-workflow` 阶段 5 调用 code-review 技能，三遍法 + 五维度。
完整记录见 `evidence/m1/wp10-code-review.log`；问题条目见 `docs/issues/issue-log.jsonl` 的 ISS-18~ISS-23。

### 5.1 [MAJOR] 交接给项目内已有协作者 → 500（ISS-18）

**复现**：项目 owner=O、collaborator=C，`POST /assignments {"newOwnerId": C}`
**实际**：500 `PendingRollbackError`，原始异常 `UniqueViolation: uq_project_members_active`

两层根因，缺一不可：
1. `transfer_owner` 第 2 步无条件 `INSERT` OWNER 成员行 —— 协作者已有活跃行，必然相撞；
2. 异常分支去读 `project.lock_version` 组装错误详情 —— flush 失败后 SQLAlchemy 把 session 内所有实例 expire，
   该读取触发惰性加载 → 在已 aborted 的事务上抛 `PendingRollbackError`，把业务问题升级成 500。

**修复**：
- 第 2 步改为"先查活跃成员行：有则升格 `member_role = 'OWNER'`，没有才 INSERT"；
- API 层在 `try` 之前把 `project_id` / `expected_version` 取成局部变量，异常分支只用局部变量；
- `except` 的匹配从"任何 IntegrityError"收敛为两个成员约束（`is_owner_transfer_conflict`），
  其它 IntegrityError 原样抛出 —— 否则外键/CHECK 违规会被伪装成 412，看起来像"正常的并发冲突"。

**回归测试**：`test_assignment_to_existing_collaborator_promotes_membership`、
`test_assignment_to_collaborator_without_keeping_old_owner`（均先复现失败，修复后通过）。

### 5.2 [MAJOR] 写端点的 CSRF 校验从未生效（ISS-19）

**复现**：带 Cookie + Origin、**不带** `X-CSRF-Token` 的 `POST /projects` → 201（应为 403）。
全仓只有一个 `verify_csrf` 调用点：`identity/api.py` 的 logout 端点内部。

**根因**：WP08 实现了机制但把调用点写死在单个端点里，没有做成所有写端点必经的依赖。
WP10 按"HTTP 安全校验已就绪"的假设直接写业务逻辑，于是协议 §1.1 的要求在 13 个写端点上全部缺失。
**机制存在，但没有覆盖** —— 这比机制不存在更难发现，因为一遍 grep 能看到 `verify_csrf` 有实现。

**修复**：把校验挂进 `current_user` 依赖的第 5 步（`is_write_method(request.method)` 为真时校验）。
- 会话行本来就要为鉴权查出，**不产生额外查询**；
- GET/HEAD/OPTIONS 由 `is_write_method` 短路，读请求零开销；
- 所有需要登录的端点都必须经过该依赖，**结构上无法漏**。

**测试加固**：新增 4 条（缺令牌 / Origin 不符 / 令牌不符 / GET 不需要令牌）。
另新增 `_assert_permission_denied` —— 让"权限类 403"用例显式排除"403 来自 CSRF"这一歧义，
否则漏带 CSRF 头的权限用例会**假通过**。

### 5.3 [MAJOR] 列表响应 `page` 块被 `response_model` 静默剥掉（ISS-20）

**复现**：`GET /projects` → 200，`data`/`meta` 正常但无 `page`；`payload["page"]` 直接 KeyError。
而 `list_response()` 的实现里明确拼了 `page`。

**根因**：`response_model=DataEnvelope[list[X]]`，而 `DataEnvelope` 只有 `data` 与 `meta`。
FastAPI 的 `response_model` 是**输出过滤器**：声明模型里没有的键会在序列化阶段被静默丢弃。

症状是最难定位的一类：HTTP 200、数据正常、服务端无任何异常日志，前端表现为"只能看第一页"。

**修复**：新增 `PaginatedEnvelope[T]`（`data: list[T]` / `page: PageInfo` / `meta: Meta`），
三个列表端点改用它。教训写进了模型 docstring：**response_model 不只是文档，它是运行时行为。**

### 5.4 [MINOR] 只读端点的 422 缺口（ISS-21）

只读端点当时只声明 `ACCESS_ERROR_RESPONSES`（401/403/404），没有 422。
FastAPI 自动补 422 默认响应的条件是"**端点存在查询参数或请求体**"，与是否写数据无关 ——
因此只带 `limit`/`cursor`/`keyword` 的 GET 同样中招，ISS-15 的修法（只给写端点声明）覆盖不到。

**修复**：新增 `READ_RESPONSES = UNIVERSAL + ACCESS`，全部只读端点使用。
教训：定位一个坑的影响面要按"**触发条件**"推，而不是按"出现位置"推。

### 5.5 [MINOR] 两处静默降级（ISS-23）

1. **字典列表 2000 行扫描上限**：超出部分永远不出现在任何一页且无报错。
   → 登记 OP-84，触发条件与后果写进代码注释。
2. **编号前缀允许纯连字符**：`-` / `---` 能通过逐字符白名单，生成以连字符开头的编号。
   → 校验拆成两步（逐字符 ASCII 白名单 + 必须至少含一个字母数字），新增 7 条参数化测试。

### 6.1 阶段 7：代码简化

阶段 5（Code Review）与阶段 6（测试）之后的独立一轮，**口径不同**：
不看语义正确性，只看"有无可消除的重复 / 未使用物 / 可读性退化"。
扫描手法是自建 AST 脚本（未使用导入、函数长度、嵌套深度），
**不只看聚合数字** —— 聚合的"重复度 25%"没法直接改，得定位到具体块。

| 项 | 简化前 | 简化后 |
|---|---|---|
| 未使用导入 | 17 处（6 个文件） | **0** |
| 412 冲突 `details` 重复块 | 5 处逐字重复 | 1 个工厂函数 |
| `projects/api.py` 重复 import / 注释 | 各 2 处 | 各 1 处 |
| `create_assignment` | 109 行 | 103 行 |

| pytest | 308 passed | **308 passed / 0 failed** |
| 契约 `--check` | 退出码 0 | 退出码 0 |

新增 `platform/concurrency.version_conflict()` 的唯一理由：`details` 的键名
（`resourceId` / `currentEtag` / `reason`）是对前端的契约。让 5 个端点各自手写，
迟早有一处漏掉 `currentEtag` —— 而那正是前端"不发第二次 GET 就能重试"依赖的字段。
失败模式是**静默的**（412 照常返回），只有前端行为不对才暴露。

**刻意不动的**：`create_assignment`（103 行）与 `transfer_owner`（85 行）虽是本项目最长的函数，
但它们是**事务脚本**——顺序即语义（让位 → 取得 OWNER 位 → 条件更新 `owner_id`）。
拆成子函数会把"顺序不可调换"这条约束从代码里藏进调用关系，反而更难审查。
同理保留 `require_if_match` 自己的 412 分支：它多带 `providedEtag`，与工厂不同形。

删除未使用导入**必须**连带验证契约一致性：若某个符号其实被 `responses=` 或
`response_model=` 引用，删除会静默改变生成的 OpenAPI 文档。
