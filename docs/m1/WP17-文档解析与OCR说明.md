# WP17 文档解析、OCR 与来源定位说明

> 研发计划 04 §4.3：**WP17** 文本/Office/PDF 解析；OCR；来源定位与部分失败。
> 依赖 WP12（文件）、WP13（任务）。验收：**扫描件可定位，损坏及不支持格式不虚报成功**。
> 上游依据：数据结构 02 §4（`parse_runs` / `source_segments`）、协议 03 §4.2 第 7 行
> （`POST /files/{id}/parse-jobs`）、研发执行计划 V2.0 §5（解析栈锁版本 + 沙箱隔离）、
> §7 W7 出口条件。

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

**把"用户上传的一堆字节"变成"系统可以引用、可以定位回原文的文本片段"。**

这句话里有两个不能省的定语：

- **可以引用** —— 产出必须挂在某个版本上、有内容摘要，能被 WP18（Brief 拆解）
  与 WP21（切块 embedding）当作输入；
- **可以定位回原文** —— 每个片段必须能回答"它来自哪一页/哪一段/哪个单元格"。
  没有定位的文本对内容生产系统是**危险的**：它让"这条结论出自哪里"变成
  不可回答的问题，而项目的核心承诺（Brief 与来源可溯源）正是建立在
  这个回答之上的。

### 1.2 核心用户是谁？

| 用户 | 何时用 | 关心什么 |
|---|---|---|
| **WP18 Brief 结构化解构**（下游代码） | 用户上传 Brief 后 | 片段文本 + 定位（字段要标出来自哪一页） |
| **WP21 切块与 embedding**（下游代码） | 知识入库时 | 片段文本 + 稳定 id（切块要能回指片段） |
| **运营（前端）** | 上传后看"解析好了没" | 状态、进度、**哪些页没解出来** |
| **审核人** | 审核 Brief 字段时 | 点字段能跳到原文位置 |

**"哪些页没解出来"是一等公民**：部分失败必须可见，否则用户会以为
"解析完了"而实际上缺了一半内容 —— 后面所有环节都建立在残缺输入上。

### 1.3 最小 MVP 应包含哪些功能？

1. 两张表（`parse_runs` / `source_segments`）与迁移；
2. 一个端点 `POST /files/{fileId}/parse-jobs`（协议 §4.2 第 7 行）；
3. 解析器：纯文本（txt/md/csv）、Office（docx/xlsx）、PDF（含"无文本层"判定）；
4. OCR 通道（**引擎可注入**，本机无引擎时显式失败）；
5. **状态由计数推导**（见 §4.3），不是解析器自报；
6. 来源定位（受控 position 结构）；
7. 任务处理器接上 WP13 的注册表；`file.uploaded` 事件处理器接上 WP13 的投递器；
8. **把 WP12 的 `taskId: null` 闭合掉**（OP-95 的收口）。

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| # | 疏漏 | 补什么 | 理由 |
|---|---|---|---|
| 1 | 数据结构 §4 只说 `state`，**没说"部分失败"怎么表达** | `total_units` / `parsed_units` 两列 + **`state` 由二者推导** + `CHECK (parsed_units <= total_units)` | 验收原文是"部分失败**不虚报**成功"。若状态由解析器自报，"不虚报"就只能靠自觉；两列一约束之后，**虚报在数据库层被拦** |
| 2 | 没说"损坏"与"不支持"的区别 | 两个不同的 `error_code`：`UNSUPPORTED_FORMAT`（承诺清单外）与 `MALFORMED_DOCUMENT`（清单内但读不出结构） | 前者要用户转格式，后者要用户检查文件。合成一个，用户无法行动 |
| 3 | 没说 OCR 引擎不可用时怎么办 | **显式失败**（`OCR_ENGINE_UNAVAILABLE`），不静默降级为空文本 | 静默降级 = 扫描件"解析成功但内容为空"，正是"虚报成功"最严重的形态 |
| 4 | 没说 position 的结构 | 受控构造器 + `kind` 决定必填字段 + "至少一个定位字段" | 自由 jsonb 里 `{}` 也是合法 position，"可定位"就无从验证 |
| 5 | 没说"同一解析器版本结果可复用"的复用粒度 | **按 `(file_id, parser_version)`**，不跨文件复用 | 跨文件复用会泄露"系统里已有同字节文件"（数据结构 §4 明令禁止），收益只是省一次本机 CPU |
| 6 | 没说 `errors` 里能放什么 | 只放 `{unit, code, message(截断)}`，**不放正文** | 与 WP15 审计"不存正文"同一条判据；异常正文可能带文件内容片段 |
| 7 | 没说解析超时 | 逐 unit 时间预算（软超时）+ 显式登记"硬超时待内网补做" | C4：所有外部调用必须有显式超时。解析是 CPU 密集操作，是最容易挂死的一环 |
| 8 | 没说"0 个片段算不算成功" | **不算**。`parsed_units = 0` → `FAILED` | 一个"成功但什么都没解出来"的解析，对下游等于没有输入，报成功是欺骗 |

### 1.5 哪些功能现在不该做？

| 不做 | 为什么 |
|---|---|
| 解析结果导出为文件（`output_file_id` 的消费者） | 属 WP35（导出）。本包建列不用（同 WP13 的 `batch_id` / `content_id` 做法） |
| 表格结构重建（合并单元格还原） | 属 WP39（表格模板与导入）。本包只做"单元格文本 + 单元格定位" |
| 图片内的图表理解 / 版面分析 | 属 WP27（静态图适配）。本包只做 OCR 文本 + 行框 |
| 真实 PaddleOCR 接入 | 本机无引擎且**内网镜像未定**（OP-06/07 硬件未下单）。本包交付 Protocol + 不可用实现 + 测试用确定性实现 |
| 解析沙箱（子进程 / 容器隔离） | 需要容器编排，本机无 Docker 可用链（M0 遗留）。**显式登记为内网补做项**，不假装做了 |
| `parse_runs` 的清理 / 归档 | 数据结构 §1 的保留策略尚未定（登记册 §3）。不建死代码 |
| 前端"解析进度"页面 | 属前端工作包。本包只保证 `GET /files/{fileId}` 能给出状态（WP12 已交付该端点，本包扩展其响应） |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 应对 |
|---|---|---|---|
| R1 | **解析器挂死**（病态 PDF、压缩炸弹） | 🔴 高 | 逐 unit 时间预算 + 单片段文本上限 + 单文件 unit 上限；**硬超时（子进程 + kill）显式列为内网补做** |
| R2 | **OCR 结果错字导致下游事实错误** | 🟠 中 | `extraction_kind='OCR'` 显式标记 + `confidence` 落库；下游可据此降权。**不承诺 OCR 不出错** |
| R3 | **"部分失败"被下游当成"完整输入"** | 🔴 高 | `state='PARTIAL'` 是独立状态（不是 SUCCEEDED 的变体）+ `errors` 逐 unit 可查；WP18 必须显式处理 PARTIAL（登记为下游契约要求） |
| R4 | **解析结果与文件版本错配** | 🟠 中 | `parse_runs.file_id` 外键 + `blob_sha256` 由 file_id 反查；重解析产生**新 run**，旧 run 的片段不可变 |
| R5 | **依赖库版本漂移导致结果不可复现** | 🟠 中 | 依赖锁补丁号（C2）；`parser_version` 是**显式常量**，实现变更必须递增；**登记"如何保证必然递增"为待定项** |
| R6 | **解析沙箱缺失 = 恶意文件可达本机** | 🟠 中 | 本机是开发环境；内网必须补沙箱。已登记 OP |
| R7 | **`source_segments` 不可变导致测试残留清不掉** | 🟡 低 | 探针放事务内 + 最终 rollback（WP16 OP-134 的同一手法） |

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**把字节变成"带位置锚点、且"解出了多少"这件事无法被伪造的文本片段"。**

本包真正的难点不是"怎么解析 PDF"（那是库的事），而是
**"怎么让'部分失败'这个事实无法被隐藏"** —— 因为隐藏它的代价
（下游拿残缺输入当完整输入）远大于解析失败的代价。

### 2.2 用户画像

- **WP18 / WP21**：只读消费方。需要 `(segment_id, text, position, extraction_kind)`。
  **它们必须处理 `state='PARTIAL'`** —— 这是本包对下游的契约要求。
- **运营**：需要"解出了 18/20 页，第 7、12 页是扫描件且系统没有 OCR 引擎"这样的信息。
- **审核人**：需要从字段跳到原文位置。

## 3. 阶段 3：多版本方案

### 方案 V1 —— 只建表 + 能解 txt（**否决**）

- **做什么**：两张表 + 一个能解 txt 的解析器 + 状态由解析器自报。
- **优点**：半天能完，契约立刻动起来。
- **缺点**：`state` 自报 → **"不虚报成功"这条验收没有任何结构性保证**；
  PDF/OCR 完全没碰，"扫描件可定位"无法验证。
- **适合场景**：无。本包的两条验收项都落空。
- **风险**：**最危险的一种交付** —— 它看起来完成了（表建了、端点通了），
  但验收项一个都没真正达成。WP12 的 MinIO 分支教训（"未经验证的实现
  比明确未实现更危险"）在这里会重演。

### 方案 V2 —— 全做，但状态由解析器上报（**不推荐**）

- **做什么**：解析器齐、OCR 通道齐，但 `parse_runs.state` 由解析器
  返回一个字符串，`total_units` 只在"能算出来的时候"填。
- **优点**：实现直观，解析器可以自由决定"什么算成功"。
- **缺点**：**"不虚报"退回成纪律要求**。任何一个解析器分支忘了
  检查"解出来几个"，就会报 SUCCEEDED。而 `total_units IS NULL`
  时"解出 3 个"与"全部解出"在库里长得一样。
- **适合场景**：一次性脚本，没有下游依赖。
- **风险**：静默的数据残缺，发现时下游已经基于它产出过内容。

### 方案 V3 —— 状态由计数推导 + 计数受 CHECK 约束 + OCR 显式不可用（**推荐**）

- **做什么**：
  1. `total_units` **必须**在解析前确定（页数/段落数/行数/1），
     读不出结构 → `total_units IS NULL` → **只能 FAILED**；
  2. `state` 由 `(total_units, parsed_units)` **推导**（`derive_state()` 纯函数），
     解析器没有机会自报；
  3. 数据库层 `CHECK (parsed_units <= total_units)` +
     `SUCCEEDED → parsed_units = total_units` +
     `PARTIAL → 0 < parsed_units < total_units`；
  4. OCR 引擎抽象成 Protocol；**默认实现是"不可用"**，
     调用即抛 `OcrEngineUnavailable` → 该 unit 不计入 `parsed_units`；
  5. 测试注入确定性 FakeOcrEngine，让"扫描件可定位"这条验收
     **在本机真的被验证**（含 bbox 落库与回读）。
- **优点**：
  - 两条验收项都有**结构性保证**（不靠自觉、不靠测试覆盖运气）；
  - "虚报成功"在**数据库层**被拦 —— 即使有人绕过 service 直接写 SQL；
  - 扫描件路径本机可验证（引擎可注入），且**默认配置不可能虚报**。
- **缺点**：解析器要额外实现"数 unit"这一步；某些格式（如极简 txt）
  的 unit 数语义要定清楚。
- **适合场景**：本项目（有下游依赖、有验收项、有不可逆的数据沉淀）。
- **风险**：`total_units` 的语义若定错（例如 docx 把空段落也算），
  会出现"永远 PARTIAL"。应对：unit 定义写进 §4.2 并逐格式列明。

### 方案 V4 —— 完整版（**不选**）

在 V3 之上再加：解析沙箱（子进程 + rlimit）、断点续解（中途可恢复）、
多解析器投票、版面分析、表格结构重建、解析结果文件导出。

- **优点**：生产级健壮。
- **缺点**：沙箱需要容器编排（本机无可用链）；断点续解需要给
  `source_segments` 加序号与批次，属过度设计（单文件解析是分钟级操作）；
  其余属其它工作包。
- **适合场景**：日处理量上万、有专用 Worker 池之后。
- **风险**：现在做会在没有真实负载数据的情况下把接口定死。

### 选择与理由

**选 V3**。理由与本项目前十一轮一致：**验收项必须落在结构上，不落在纪律上**。
具体地：

- 第一半验收「扫描件可定位」→ 受控 position 构造器 + OCR 行框落库 +
  测试用确定性引擎真的走通一遍；
- 第二半验收「损坏及不支持格式不虚报成功」→ 两个不同的 `error_code`
  + `state` 由计数推导 + 三条 CHECK 在数据库层兜底。

V1/V2 的共同问题是把"不虚报"交给解析器的自觉；V4 的沙箱确实该做，
但它需要内网环境，**显式登记而不是假装做了**。

### 4.2 两张表（性质正好相反）

| 表 | 性质 | 关键设计 |
|---|---|---|
| `parse_runs`（15 列） | **过程记录**，可变 | 状态由计数**推导**；`total_units` 可空（= 数不出总量）；三条 CHECK 拦虚报 |
| `source_segments`（12 列） | **证据**，不可变 | 触发器 + ORM 守卫双层保护；`segment_no` 是**显式落库的顺序事实** |

**`parse_runs` 刻意不加触发器**：状态必须能推进（`QUEUED → RUNNING → SUCCEEDED`）。
把可变的东西保护成不可变，唯一结果是系统不能工作。

### 4.3 `parsed_units` **不是** `len(segments)`（本包最容易搞错的一处）

初版把 `parsed_units` 直接定义成 `len(segments)`。**那是错的**：

| 场景 | unit | 片段数 | 初版算出 |
|---|---|---|---|
| 一页 PDF 有正文 | 1 页 | 1 | 1 ✓ |
| 一页扫描件 OCR | 1 页 | **N（每行一段）** | **N ✗** |
| 一张图 OCR | 1 张 | **N** | **N ✗** |

一张图 OCR 出 4 行 → `parsed_units=4 > total_units=1` → 被判成
"计数自相矛盾" → **FAILED**，而这张图识别得很成功。

**它只在"1 个 unit 产出多个片段"的格式上暴露** —— txt / csv / docx
全是"一个 unit 一段"，本机那些测试**全绿**。PDF 扫描页与图片才触发，
而那正是本包的第一条验收项。

修法：`ParseOutcome.units_parsed` 是**显式字段**（`None` 时退回
`len(segments)`，且**有文件级错误时恒为 0**）。登记 **ISS-51**。

### 4.4 顺序必须是**显式落库的事实**（`segment_no`）

`created_at` 的默认值是 `func.now()` —— **事务**时间戳，同一事务里
插入的所有行值完全相同。于是 `ORDER BY created_at` 对同批行是全序退化，
PG 返回的顺序取决于物理存储顺序（进而取决于随机 UUID 主键）。
**本机实测**：三行 `["甲","乙","丙"]` 读回来是 `["乙","丙","甲"]`。

下游（WP18 拼 Brief 原文、WP21 切块）必须能按原文顺序拿到片段。
顺序错乱会让"第 3 段的结论"配到"第 1 段的原文"，而**没有任何报错**。

修法：`segment_no` 列（批内序号）+ `UQ(parse_run_id, segment_no)`
（保证全序，不存在并列）+ 顺序索引。登记 **ISS-52**。

### 4.5 裸 SQL 状态迁移后必须强制刷新

本仓库所有状态迁移都用 `UPDATE ... WHERE state IN (...)`（裸 SQL），
**不经过 ORM 属性赋值**。于是 session 的 identity map 里那个对象仍是旧值，
`session.get()` 直接返回陈旧副本 —— 本机实测：写成了 `SUCCEEDED/3/3`，
读回来是 `total_units=None`。

修法：`ParseRepository.get_run` 加 `populate_existing=True`。
不用 `session.expire_all()`（会把调用方正在编辑的其它对象一起失效）。
登记 **ISS-53**。

### 4.6 `file.uploaded` 处理器只**建任务**，不解析

协议 §4.1 的时序图第 8 步之后，Worker 才做"扫描后隔离解析"。
直接在事件处理器里解析意味着**投递通道的调用栈里**要跑完整个解析 ——
一份 200 页 PDF 会占住通道，而通道的超时与重试语义是为"投递"设计的。

更关键的是**状态可见性**：建了任务之后，"这个文件的解析在排队"是一个
可查询的事实（`jobs.state='QUEUED'`）；直接解析的话，排队期间系统里
没有任何记录，用户看到的是"传上去了，什么都没发生"。

### 4.7 任务 → 解析运行：**反向查 `parse_runs.job_id`**，不用 `result_ref` 携带

初版想的是"入队时把 run id 写进 `jobs.result_ref`，处理器读它"。**两条都错**：

1. **竞态**：`enqueue_job` 与"写 `result_ref`"是两次写。Worker 若在两者
   之间领取任务，会看到一个 `result_ref` 为空的任务 ——
   "解析任务没有指定 run"这个失败会在**正常流程**里偶发。
2. **语义错位**：`jobs.result_ref` 的口径是"**结果**引用"，而 run 是任务的
   **输入**。用输入占住结果的字段，任务终态时就再也放不下真正的产出。

改用反向查：`parse_runs.job_id` 指向产出它的任务。run 与 job 在**同一事务**
里创建 → 处理器看得到 job 时 run 必然已存在（**无竞态**），
且关联只存在一处（**一个真相**）。

### 4.8 OCR 引擎不可用 → **显式失败**，绝不降级为空文本

图片唯一的内容来源就是 OCR。若引擎不可用却报成功，
`parsed_units = 1 = total_units` → `SUCCEEDED`，而这个"成功"的图片解析
**没有任何片段**。下游会拿它当完整输入。

因此 `UnavailableOcrEngine.recognize` **抛错**，且 `build_ocr_engine`
对**未知名称**也返回不可用实现（**不退回 Fake**）——
否则一个拼错的引擎名会让生产环境用假结果。

### 4.9 迁移 `55e35f7a4cb9`：G2 铁律**第八次**触发

autogenerate 又一次提议删 `smoke_meta` / `wp05_vec_probe`，并在 `downgrade`
里重建（`embedding` 被渲染成 `sa.NullType()`）。已全部人工删除；
文件头另补 `postgresql` 导入（ISS-32 的教训）。

### `UNIT_TIME_BUDGET_SECONDS` + `ERROR_UNIT_TIMEOUT` 曾**同时骗过四道防线**

`types.py` 里定义了常量、注册进了 `PARSE_ERROR_CODES`、`§1.6` 的风险表里
写了"逐 unit 时间预算"，但**没有任何解析器用过它们**。

| 防线 | 为什么没拦住 |
|---|---|
| 静态检查 | 常量被定义且在 `__all__` 里，不报未使用 |

| 覆盖率 | 定义行被执行了（模块被导入） |
| 文档 | 读起来像已经做了 |

**只落在 PDF**：txt/csv 是纯字符串操作；docx/xlsx 的慢发生在**打开文件**
这一步（属"文件级"，已由大小与行数上限约束）。
**不为了用上一个常量而到处塞计时** —— 那会把"实现了一个保护"
变成"实现了一个装饰"。

### 删除 `service.segments_payload()`（零调用）

它为什么曾经存在："下游 WP18/WP21 要读片段"，于是顺手给了个 camelCase 转换。
**问题**：camelCase 是 HTTP 层的关注点（协议 §1），而本函数明说了
