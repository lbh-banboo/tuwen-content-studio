# WP14 SSE 与断线续传说明

> 工作包：WP14（M1 第八个包，W6）
> 验收：**「断网重连后状态正确，越权订阅拒绝」**（研发计划 04 §4.2）

> 依赖：WP13（任务状态是事件的主要来源）、WP07（契约骨架）

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

**一句话**：让"任务在后台跑"这件事在**用户眼前可见**，并且在**连接断掉、事件漏收、实例切换**之后，用户看到的仍然是对的。

ADR-14 的原话把它拆得很清楚。评审硬伤 🔴5 是：

> API 采用双实例部署（ADR-01），SSE 长连接建立在**某一个**实例上。
> 任务进度事件由 Worker 产生并写库，但 Worker 并不知道用户的 SSE 连接挂在哪个实例上。

所以本需求**真正的难点不是"实现 SSE"** —— SSE 本身就是一个 `text/event-stream` 长连接，
半小时能写出能跑的版本。难点是这四件事：

| 难点 | 为什么难 |
|---|---|
| **跨实例 fan-out** | 事件在实例 B 产生，连接挂在实例 A。A 不知道 B 发生了什么 |
| **必达** | PG 的 `NOTIFY` 是 **at-most-once**（ADR-14 明写），通知本身不能承担必达 |
| **逐事件鉴权** | 权限**在会话期间可能变化**（成员被移除、负责人交接）。建连时校验一次不够 |
| **补漏有界** | 断线很久之后，待补事件可能成千上万。无界补发会打爆连接与前端 |

**这四条决定了一个关键判断**：`domain_events` 表**是真相**，SSE 只是"通知"。ADR-14 的三层机制
（落库为真相 / NOTIFY 实时分发 / Last-Event-ID 补漏）正是把"必达"从不可靠的通道
挪到了可靠的存储上。

**推论（很重要，决定了测试重点）**：既然"必达"由落库承担，
那么**"NOTIFY 完全失效"时系统仍必须正确** —— 只是实时性变差。
这条必须是测试用例，而不是"注释里写一句"。

### 1.2 核心用户是谁？

| 角色 | 什么时候用 | 关心什么 |
|---|---|---|
| **运营/内容同学**（主用户） | 提交批次后盯着进度条 | "跑到哪了、还要多久、出没出问题" |
| 前端代码 | 一直挂着这条连接 | 断线自动重连、不重复渲染、不丢事件 |
| 项目负责人 | 同时开几个项目的页签 | 每个页签一条连接（协议要求"尽量复用"） |
| 管理者 | 不常用 | 越权边界必须可靠 |

**主用户的行为特征决定了两件事**：

1. **他会切到别的页面再切回来**（浏览器可能挂起连接）→ 重连补漏是**常态**，不是异常路径；
2. **他会一直盯着看** → 进度必须**真实**（"心跳在跳但进度不动"比"连接断开"更糟，
   因为用户以为它在跑）。

### 1.3 最小 MVP 应包含哪些功能？

按 ADR-14 的三层机制 + 协议 §11 的契约：

| # | 功能 | 依据 |
|---|---|---|
| F1 | `domain_events` 表（自增 `sequence`）+ 事件写入服务 | ADR-14 真相层 |
| F2 | `GET /api/v1/events?projectId=...` SSE 端点 | 协议 §11 |
| F3 | Last-Event-ID 补漏（`sequence > last`） | ADR-14 补漏层 |
| F4 | **逐事件**权限过滤 | ADR-14 关键约束 2、3 |
| F5 | 待补超限 → **410 `EVENT_HISTORY_EXPIRED`** | 协议 §11 + §1.2 |
| F6 | PG `LISTEN/NOTIFY` 跨实例分发（payload 只带 id） | ADR-14 分发送达层 |
| F7 | 15 秒心跳 | 协议 §11 |
| F8 | 断线重连（先补漏、再转实时、按 sequence 去重） | ADR-14 边界要求 |

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **`domain_events` 的列清单不完整** | 数据结构 §11 列了 8 列，但协议 §11 的事件体还需要 `schemaVersion` / `projectId` / `jobId` / `occurredAt` / `payload`。`jobId` 没有对应列 —— 它只能落在 `payload` 里还是需要独立列？见 OP-110 |
| 2 | **`sequence` 是全局还是按项目** | 协议 §11 明写"**不假设全局 ID 连续等于本项目连续**"—— 直接回答了：全局序列号，前端不能拿它做项目内的连续性判断 |
| 3 | **补漏上限的取值** | ADR-14 只说"有上限"，没给数字。见 OP-111 |
| 4 | **NOTIFY 的发送方是谁** | ADR-14 说"channel 为 `domain_events_new`"，但没说谁来发。若靠应用层在写事件后调 `NOTIFY`，进程崩在两者之间就丢了通知（**但落库仍在，靠补漏兜底**）。见 §2.6 |
| 5 | **LISTEN 连接的健康检查** | ADR-14 明列"连接泄漏：LISTEN 专用连接断开会静默失去实时能力" |
| 6 | **本机没有第二个实例** | V3/V4 要求双向验证 fan-out。本机只有一个进程 → 必须把"实例"做成可模拟的（见 §3） |
| 7 | **事件与权限的关系** | `domain_events.project_id` 可空（平台级事件）。平台级事件谁能看？见 OP-112 |
| 8 | **`sync.required` 事件类型** | 协议 §11 的事件类型列表里有它，但没说谁发、什么条件下发。它正是"补漏超限"的对应信号 —— 服务端发 410，前端改为全量刷新 |

### 1.5 哪些功能现在不该做？

| 砍掉 | 为什么 |
|---|---|
| **前端（EventSource 客户端）** | `apps/` 尚未建立。本包交付服务端契约与语义，前端属后续 |
| **轮询降级（5~15 秒抖动）** | 协议 §11 要求"SSE 不可用时采用轮询"，但那是**前端**行为；后端只需保证 REST 快照端点可用（已有） |
| **`job.progress` 的细粒度进度来源** | `completedUnits` / `totalUnits` / `phase` 由**产生事件的业务包**决定（WP16/WP17）。本包只负责搬运与鉴权 |
| **事件保留期清理** | 属运维/保留策略（数据结构 §15）。本包提供按 sequence 查询，清理留给部署层 |
| **`notification_receipts`（已读/忽略）** | 属 WP15（站内待办） |
| **WebSocket** | 协议定的是 SSE（单向、只需服务端推） |
| **多实例的粘滞会话** | ADR-14 明确否决（"治标不治本，且引入新的单点"） |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **权限只在校验一次** | 🔴 高 | 成员被移除后仍持续收到项目事件（异常矩阵第 16 项、V7 直接失败） | 逐事件过滤（`can_view_event`），并有专门测试 |
| R2 | **把 Last-Event-ID 当授权凭证** | 🔴 高 | 协议 §1.1 明写"**不作为授权凭证**"。若用它过滤，改一个数字就能读到别的项目的事件 | 它只用于**定位**，鉴权一律走事件自身的 `project_id` + 当前成员关系 |
| R3 | **补漏与实时乱序** | 🟠 中 | 补漏过程中 NOTIFY 推来新事件 → 顺序颠倒、重复渲染 | 先补漏、再转实时；按 `sequence` 去重合并（ADR-14 边界要求） |
| R4 | **无界补发** | 🟠 中 | 断线一天后一次补十万条 → 打爆连接与前端 | 上限 + 410 明确信号（不静默截断 —— 静默截断会让前端以为数据完整） |
| R5 | **NOTIFY 丢失被当成"没有事件"** | 🟠 中 | 实时性静默失效，且**看不出来** | 落库为真相 + 补漏兜底；**专门测"NOTIFY 全失效仍正确"** |
| R6 | **LISTEN 连接泄漏** | 🟡 中 | 静默失去实时能力 | 独立连接（不进业务池）+ 健康检查 + 重连 |
| R7 | **事件体泄露敏感内容** | 🔴 高 | 协议 §11 明写"事件数据不带 Prompt、Brief 全文、外部密钥或其他项目对象" | payload 由产生方负责，但本包**在写入时做一层校验**（见 §2.6） |
| R8 | **代理缓冲导致"连上了但没数据"** | 🟡 中 | 用户看到空白，以为没有进度 | `Cache-Control: no-cache` + `X-Accel-Buffering: no`（协议要求"反向代理关闭事件流缓冲"） |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**：1 张表 —— `domain_events`（数据结构 §11）。**本包只建这一张**。

**接口**：1 个端点 —— `GET /api/v1/events?projectId=...`（协议 §11）。

**后端分层**：

```text
modules/events/
  models.py        # domain_events
  repository.py    # 按 sequence 查询、写入
  service.py       # 事件写入（含敏感内容校验）、逐事件鉴权、补漏
  notifier.py      # ★ LISTEN/NOTIFY 订阅器（独立连接）+ 进程内订阅表
  api.py           # SSE 端点
```

**前端**：不做（apps/ 未建立）。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**把"必达"从不可靠的推送通道挪到可靠的存储上**（`domain_events` 落库为真相），
推送只负责"尽快"，补漏负责"一定"，鉴权负责"只能看该看的"。

### 2.2 用户画像

**运营同学盯着进度条**。这个画面对"正确性"的要求比一般页面高：

- 进度条**停住不动**时，用户无法区分"任务卡了"与"连接断了"→ 心跳必须真的在跳，
  且前端能据此判断连接存活；
- 用户会**切走再回来** → 重连补漏是常态；
- 用户**不会**去点"刷新"来修问题 → 所以宁可返回 410 让前端自动全量刷新，
  也不要静默少给几条。

### 2.3 核心功能清单（MVP）

见 §1.3（F1~F8）。

### 2.4 待补充项及理由

| 编号（待登记） | 内容 | 归属 |
|---|---|---|
| OP-110 | `domain_events` 是否补 `job_id` 列（协议 §11 的事件体需要它，§11 表定义没有） | 文档作者 |
| OP-111 | 补漏上限的具体取值（ADR-14 只说"有上限"） | 开发 + 运营 |
| OP-112 | 平台级事件（`project_id IS NULL`）的可见范围 | 产品 |
| OP-113 | `NOTIFY` 的发送方：应用层显式发 vs 数据库触发器自动发 | 开发 |
| OP-114 | `sync.required` 事件的产生方与触发条件 | 开发 + 协议作者 |
| OP-115 | 事件保留期与清理策略（数据结构 §15 属运维） | 运维 |

### 2.5 砍掉清单

见 §1.5（7 项）。

### 2.6 技术风险评估（含应对）

见 §1.6。补充四条**必须在编码前定死**的实现约束：

1. **NOTIFY 的发送方**：本包采用**应用层显式发送**（`pg_notify`），与事件写入同事务提交后触发。
   不用数据库触发器 —— 触发器里发 `NOTIFY` 会与"事件体校验要给出可读错误"冲突
   （触发器只能抛 SQLSTATE，无法回带字段信息）。代价是"提交成功但发通知前崩溃"
   → 通知丢失，**但事件已落库，靠补漏兜底** —— 这恰好是三层机制的设计意图。
2. **`Last-Event-ID` 只用于定位**，鉴权一律重新查库。
3. **补漏与实时必须按 `sequence` 去重**：用一个"已推送的最大 sequence"水位线，
   低于等于水位线的一律丢弃。
4. **`payload` 写入时做敏感内容校验**：检查键名是否命中敏感标记
   （复用 `platform/errors.py` 的 `sanitize_details` 思路），命中即拒绝写入。
   这比"事后过滤"更可靠：事件一旦写进库里、又被推给错误的人，就无法撤回。

### 2.6.1 关于本机如何验证 V3/V4（跨实例）

ADR-14 判据说 V3 与 V4 **必须双向通过**，"只测单向不能证明 fan-out 正确"。
本机只有一个进程 —— 因此把"实例"抽象成**订阅器对象**：
两个 `EventNotifier` 各自持一条独立的 LISTEN 连接，**分别**写入事件，
断言两个订阅器都能收到。这在语义上等价于双实例（关键性质是"通知不依赖调用方自身"）。

真实双实例（两个进程 + 反向代理）留给内网（登记为待办）。

### 2.7 事件写入的一个关键约束：写事件不能拖垮业务

`domain_events` 是**追加表**且被 SSE 高频读取。两条约束：

1. **`sequence` 用 bigint 自增**（协议 §1 说"事件序号"对外为十进制字符串）——
   对外必须转字符串，否则前端在 2^53 之后丢精度；
2. **写入必须与业务同事务**（否则"业务提交了但事件没写"会让用户看不到进度）——
   与 WP12/WP13 的 Outbox 同一模式。

## 3. 阶段 3：多版本方案

方案的**分野是"实时分发怎么做"与"本包要不要带前端"**。

| 方案 | 定位 | 内容 |
|---|---|---|
| **V1 仅轮询兜底** | 1 天 | 只建表 + 提供查询端点，**不做 SSE**。前端轮询 |
| **V2 SSE 但单实例内存广播** | **不推荐** | SSE 端点 + 进程内订阅表 + 应用内广播。**正是 🔴5 要解决的问题** |
| **V3 SSE + LISTEN/NOTIFY + 补漏（推荐）** | 本包交付 | ADR-14 的三层机制完整落地；无前端 |
| **V4 完整版** | 生产级 | V3 + 前端 EventSource + 轮询降级 + 事件保留清理 + 度量 |

### 方案 V1 —— 仅轮询兜底（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 建 `domain_events`，提供一个"按 sequence 查事件"的 REST 端点；前端定时拉 |
| 优点 | 一天能交付；必达性反而**最强**（拉取天然不漏） |
| 缺点 | **偏离已定契约**：协议 §11 与 ADR-14 都定了 SSE，ADR 还明确否决"仅落库 + 前端轮询"（"SSE 的价值就是实时性，放弃实时等于放弃该决策的前提"）；验收项"断网重连后状态正确"也失去了测试对象 |
| 结论 | ❌ **否决**。它还丢掉了 ADR-14 四分之三的内容（分发与补漏层） |

### 方案 V2 —— SSE 但单实例内存广播（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | SSE 端点 + 进程内订阅表；产生事件的代码直接调用 `broadcast()` |
| 优点 | 最简单；单实例下完全正确 |
| 缺点 | ① **这就是 🔴5 本身** —— Worker 不知道连接挂在哪个实例；② 双实例下表现为"进度有时更新、有时不更新"，**取决于负载均衡把请求分到哪台**，是本项目最怕的那类缺陷（测试全绿、上线随机错） |
| 风险 | 交付一个"验收项在选定架构下必然失败"的包 |
| 结论 | ⚠️ **不推荐**。省掉的正是本包唯一的技术难点 |

### 方案 V3 —— SSE + LISTEN/NOTIFY + 补漏（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | `domain_events` 落库为真相；写入后用 `pg_notify` 广播**只带 event id**；每个实例持一条独立 LISTEN 连接，收到通知后**读库 + 逐事件鉴权**再推送；Last-Event-ID 补漏（有上限，超限返回 410）；15 秒心跳 |
| 优点 | ① **ADR-14 逐条落实**（三层机制 + 5 条关键约束）；② 本机能验证除"真实双实例"外的全部语义（V1~V7 的 V3/V4 用双订阅器等价模拟）；③ 无新增组件（复用 PG 17）；④ 边界清晰：不建前端、不建 WP15 的表 |
| 缺点 | ① NOTIFY 是 at-most-once，实时性**不保证**（但这正是设计接受的前提，必达由补漏承担）；② 每个实例多一条 PG 长连接（ADR-14 已列为代价）；③ 通知风暴时要按 id 去重合并（ADR-14 已列为风险） |
| 风险 | 若内网 PG 的 NOTIFY 行为与假设不符（如连接被中间件掐断），实时性退化 —— **而正确性不受影响**（补漏兜底）。这是本方案最重要的性质：**退化方向是安全的** |
| 适合场景 | 本项目的实际处境：双实例已定、本机无子网多实例、且必须能验证 fan-out |
| 结论 | ✅ **推荐** |

### 方案 V4 —— 完整版（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | V3 + 前端 EventSource 客户端 + 轮询降级 + 事件保留清理 + Prometheus 度量 |
| 优点 | 一次性到位，G1 的"接收进度"可在本包内端到端联调 |
| 缺点 | **越界严重**：`apps/` 前端尚未建立（WP06 起就是后续工作包的范围）；事件保留清理属数据结构 §15 的运维策略；度量属可观测性建设。在 WP14 做这些 = 用 WP14 的假设替后面几个包与运维做决定 |
| 风险 | 前端仓一旦建立，会发现本包写的客户端结构需要重做（技术栈未定） |
| 结论 | ❌ 不选。与 WP11/WP12/WP13 的 V4 判断一致：**边界按"有没有设计空间"划** ——
  SSE 协议与 fan-out 语义有设计空间（本包做），前端结构还没有（等 apps/ 建立） |

### 选择与理由

**选 V3。** 三条理由，按权重排序：

1. **ADR-14 是已经拍过的决策，本包是它的实现**。ADR 里连"为什么不用 Redis"都论证完了，
   还给了 V1~V7 的验证方式 —— 本包没有重新选型的空间，只有"落实得对不对"。
2. **必达性与实时性必须分开看**。ADR-14 明写 NOTIFY 是 at-most-once，
   "不能依赖通知本身保证必达"。V3 把这条从注释变成结构：**NOTIFY 全失效时系统仍正确**，
   只是慢。这条性质让"内网 PG 行为与假设不符"从"故障"降级为"性能问题"。
3. **本机能验证 V1~V7**（除真实双实例）。把"实例"抽象成订阅器对象后，
   V3/V4 的 fan-out 双向验证可以在一个进程里如实复现 —— 与 WP12 的存储适配器、
   WP13 的投递通道同一手法：**抽象出可替换的那一层，是为了让语义可验证，不是为了好看**。

**V3 的代价我接受**：真实双实例（两进程 + 反向代理 + 代理缓冲配置）要等内网。

> **请老大确认一件事**（其余我按 V3 直接开工）：
> **补漏上限的取值**（OP-111）。我倾向 **1000 条**：按"20 在线 / 50 成员"的规模，
> 1000 条约等于断线十几分钟的量；超过它就说明断得太久，让前端全量刷新反而更快、
> 更不容易出错（用户看到的是一次干净的快照，而不是几千条事件重放）。
> 若你希望更宽松（比如 5000），告诉我，改一个常量即可。

### 4.2 一张表

`domain_events`（11 列）。三个关键设计：

1. **`sequence` 用 `sa.Identity`，不是 `autoincrement=True`**（本机实测踩到，见 §5 D1）：
   `autoincrement` 只在"该列是主键"或"该列是唯一的整数列"时才生成序列，
   而本表主键是 UUID → DDL 会渲染成**裸 `BIGINT NOT NULL`**，插入即违约。
2. **`occurred_at` 与 `created_at` 分开**："事件什么时候发生的"（业务时间）
   与"什么时候写进来的"（落库时间）是两个不同的问题。
3. **`job_id` 独立一列**（数据结构 §11 没列，登记 OP-110）：
   协议 §11 的事件体需要它，而从 `payload` 里挖会让"能不能正确渲染"
   取决于各产生方记得把 jobId 放进 payload。

### 4.3 三层机制（ADR-14）如何落地

| 层 | 落点 | 关键 |
|---|---|---|
| 真相层 | `domain_events` 落库 | 序列自增；对外 `sequence` 一律**字符串**（协议 §1） |
| 分发送达层 | `notifier.py` | **独立 LISTEN 连接**（不进连接池）；payload **只带序号**；`notifies(timeout=...)` 不能无参（见 §5 D2/D3） |
| 补漏层 | `service.backfill_events` + 水位线 | **先补漏、再转实时**、按 `sequence > watermark` 去重；**超限返回 410，不静默截断** |

### 4.4 逐事件鉴权如何落地

ADR-14 关键约束 2、3："收到通知后必须按 id 读库并做权限过滤，逐事件判定"。
落地方式：

- **`can_view_event`** 每次调用都反映**当前**成员关系（`removed_at IS NULL`）；
- 建连时的 `_may_access_project` 与逐事件的 `can_view_event` **是同一个判据**
  （`_is_active_member`），避免两套漂移；
- 批量推送时先算一次 `member_project_ids`（快路径），但它是
  **每轮通知/心跳时重算**的，不是建连时算一次 —— 因此权限变化的
  生效延迟最多是"一次心跳（15 秒）"，而不是"整条连接的生命周期"。

### 4.5 一个关键结构判断：`native_dsn` + 独立连接

`EventNotifier` **收原生 DSN 而不是 SQLAlchemy Engine**（见 §5 D3）。
ADR-14 明写"LISTEN 专用连接（不进入业务连接池）"—— 我一开始把它当成
实现细节，实测才发现这正是**收不到通知的根因**（连接池在归还/重置时
对挂着 LISTEN 的连接做 `rollback`）。

### 4.6 迁移 `41b468c478a4`：G2 铁律**第五次**触发

autogenerate 又一次提议删 `smoke_meta` / `wp05_vec_probe`、`downgrade`
又试图重建它们（`embedding` 变成 `sa.NullType()`）、文件头又缺 `postgresql`
导入（用了 `postgresql.JSONB`，执行即 `NameError`）。三处都已修。

### 4.7 SSE 消息格式与代理缓冲

- 消息以**空行结束**（浏览器会等下一行），`id` / `event` / `data` 按协议示例顺序；
- 心跳用**注释行**（`: text`），因为规范定义它被忽略 —— 前端不需要为心跳写任何处理逻辑；
- 响应头带 `Cache-Control: no-cache` 与 `X-Accel-Buffering: no`
  （协议要求"反向代理关闭事件流缓冲"）。**代理缓冲这条只能真机验** ——
  它取决于 nginx 的 `proxy_buffering` 配置，本机没有那一层。

### 5.1 三条 MAJOR 的共同特征：**它们都藏在"看起来能跑"的表象下**

| 发现 | 表象 | 真相 |
|---|---|---|
| D1 | ORM 声明 `autoincrement=True` 看起来对 | DDL 是裸 `BIGINT NOT NULL`，没有序列 |
| D2 | `notifies()` 看起来是"读通知" | 默认行为是"**等**通知"（无 timeout 时永久阻塞） |
| D3 | `raw_connection()` 看起来是"拿一条连接" | 它在池里；池在归还/重置时对挂着 LISTEN 的连接做 `rollback` |

> **可复用的自检**：凡是"数据库帮我做的事"（自增、默认值、通知、
> 连接池、驱动默认值），都不能只看声明或跑一次 happy-path 就下结论 ——
> 要拿**渲染结果**（DDL）核对，或**探到它的边界行为**（阻塞/收不到）。

### 5.2 三条都值得说的细节

**D1**：这是本包唯一"不跑就会上线就崩"的缺陷，而它用一条
`print(CreateTable(...))` 就能发现 —— 代价比跑一次测试小得多。
凡是"数据库帮我生成值"的列，**渲染出的 DDL 才是真相**。

**D2**：第三方库的"读取类方法"默认行为差异极大（读现存 vs 等新的）。
凡是"循环读某个通道"的代码，必须先确认它没值时是**返回**还是**阻塞** ——
阻塞的话整个循环就是死锁，而且只在"恰好没通知"时暴露。

**D3**：连接池管理的资源必须满足"用完即还"的假设；任何"长驻、绑定状态、
跨请求"的用法（LISTEN、服务端游标、事务内长操作）都不能走池。
**约定里带"专用 / 不进池"字样的，按字面照做，不要绕。**

### 5.3 第三遍：明确记录"检查过但没问题"的点

- **NOTIFY payload 是否真的只带序号**：验证过（批次里只有 sequence，没有正文）；
- **`pg_notify` 是否随事务提交才投递**：验证过（写入在 session_scope 内，
  随后 poll 即收到 —— 证明投递发生在提交点）；
- **双实例 fan-out 双向**：验证过（V3/V4 两个方向各一条，ADR-14 要求双向）；
- **补漏是否"恰好 N 条"**：验证过（返回的 sequence 与写入一一对应）；
- **超限是否被静默截断**：验证过（`overflowed=True`）；
- **权限是否在补漏路径上逐事件**：验证过（非成员带任意大 Last-Event-ID 也拿不到；
  成员移除后收不到 —— V7）；
- **"算好的集合"与"现查"是否一致**：验证过（否则"批量推送"会变成绕过鉴权的后门）；
- **水位线是否单调**：验证过（只增不减）；
- **心跳是否小于常见代理超时**：验证过（`HEARTBEAT_SECONDS < 60`）。
