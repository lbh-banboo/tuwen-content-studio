## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

**一句话**：让系统**能调外部模型**，同时让"**调了没调、调成了没**"**永远有确定答案**。

验收标准的两半，其实是**同一件事的两面**：

| 半 | 本质 | 真正的难点 |
|---|---|---|
| **LOCAL_ONLY 无外部回退** | 出网是一个**授权**问题，不是路由问题 | 怎么让"不许出网"成为**结构性禁止**，而不是"记得别走那条路" |
| **未知调用状态不盲重试** | 外部调用**可能已经计费**，而结果未知 | 怎么让"状态不明"**不等于**"可以重来" |

第一半的难点在于：**"失败后降级到外部模型"看起来是个好设计**。
本地能力不可用时"顺手改走外部"能提高成功率、用户无感 ——
而这恰恰是 ADR-10 明令禁止的。原因不在技术：**LOCAL_ONLY 是数据合规承诺**，
一旦静默降级，承诺就变成了"看情况"。而且这种降级**不留痕迹** ——
用户看到的是一次成功的内容生成，没人知道数据出了网。
所以正确行为是：**让任务失败或进 UNKNOWN，把问题暴露出来**，而不是静默换路径。

第二半的难点在于：外部调用的失败与内部操作**性质完全不同**。
内部写入失败可以重试（幂等由数据库保证）；而外部调用**一旦发出就可能已计费**，
"重试"等于"再买一次"。更麻烦的是网络超时这类情况 ——
我们**不知道**请求有没有到达供应商。此时唯一安全的行为是：
**保存已有调用的状态，等核对**（数据结构 §13.4 原句："UNKNOWN 不因租约过期变成可自由重试"）。

### 1.2 核心用户是谁？

| 角色 | 什么时候用 | 关心什么 |
|---|---|---|
| **AI/业务 Worker**（直接调用方） | 执行任务时 | "这次能不能出网、调用能不能成功、失败了能不能重试" |
| **运营**（间接） | 内容生成失败时 | "为什么失败"、"要不要再来一次"、"会不会重复计费" |
| **管理者/合规** | 审计与事件复盘 | "这次调用出了什么网、送出了哪类字段、有没有正文" |
| **运维** | 排障 | "哪个供应商不健康"、"哪些调用卡在 UNKNOWN" |

**容易漏的一点**：本包的主用户是 **Worker（代码）**，不是人。
所以"策略"必须是**可调用的纯函数**，"禁止降级"必须是**调用路径上的硬判断**，
而不是一段写在文档里的约定。文档约束不了代码。

### 1.3 最小 MVP 应包含哪些功能？

| # | 功能 | 依据 | 为什么必须在 MVP 里 |
|---|---|---|---|
| F1 | `providers` + `model_profiles` 表（供应商与模型档案） | 数据结构 §11 | 网关不知道"调谁"就无法派发；`network_mode` 是策略判定的输入 |
| F2 | `capability_policies` 表（项目级出网策略，**缺省拒绝**） | 数据结构 §11「项目策略优先，缺省拒绝未授权出网」 | 验收第一半的落点 |
| F3 | **出网策略判定**（纯函数）：`LOCAL_ONLY` / 数据类别 / 供应商白名单 / 能力支持 | ADR-10 出网矩阵 E-1~E-6 | 策略必须可单测、可复用，不能散落在派发逻辑里 |
| F4 | `provider_calls` 表 + `UQ(provider_id, request_key)` | 数据结构 §11 | 验收第二半的落点：**未知状态不得直接另发计费请求** |
| F5 | **统一调用状态机**：`PREPARED → SUBMITTED → POLLING → SUCCEEDED/FAILED`，不确定 → `UNKNOWN` | 数据结构 §12 | "统一调用状态"就是它 |

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **出网留痕落在哪张表** | ADR-10 只说"网关记录摘要 + 版本 + 字段类别 + traceId"，数据结构 §11 没有对应表。必须定（见 §2.6） |
| 2 | **`capability_policies.external_policy` 的取值域** | §11 只列了列名。至少要能表达"允许外部/仅本地"，且**缺省必须是否决** |

| 4 | **`provider_calls.state` 的取值域与迁移规则** | §12 给了流程但没给完整取值域（`PREPARED`/`POLLING`/`UNKNOWN` 是否都落库？） |
| 5 | **`request_key` 怎么构造** | §11 只说 `UQ(provider_id, request_key)`。构造约定必须**单一来源**，否则幂等静默失效 |
| 6 | **`UNKNOWN` 与 WP13 任务状态的关系** | 调用 UNKNOWN 时，任务应该进 `WAITING_RECONCILIATION` 还是 `FAILED`？WP13 已有两个钩子，必须接对 |
| 7 | **真实供应商适配器归谁** | 本机无供应商、无白名单、无密钥 —— 本包只能交付接口与桩。真实适配器的归属与实现时机要显式登记 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **LOCAL_ONLY 静默降级到外部** | 🔴 高 | 数据违规出网，**且用户无感、无痕迹** | 策略判定在派发路径**之前**，且返回"否决"而非"换一条路"；出网留痕记录每一次决策；测试断言"被拒时适配器**一次都没被调用**" |
| R2 | **UNKNOWN 被当成可重试** | 🔴 高 | 重复计费（真金白银），且账面无法自证 | `UQ(provider_id, request_key)` + 派发前先查；**非终态一律不重发**；UNKNOWN 只能经 `reconcile` 出口 |
| R3 | **超时导致"调了两次"** | 🔴 高 | 同 R2，且更隐蔽（第一次其实成功了） | `request_key` 在**调用前**持久化（§13.4 原句）；超时归类为 UNKNOWN 而非 FAILED |
| R4 | **出网留痕泄露正文** | 🔴 高 | 网关日志成为最大泄露面 | 复用 WP15 的 `audit_events`：**模型层没有可存正文的列**（结构性保证），只有摘要 |
| R5 | **策略判定散落在业务代码** | 🟠 中 | 每个调用点各写一遍 → 迟早有一处忘记判 | 判定收敛为**一个纯函数**（`policy.evaluate_egress`），派发只是它的消费者 |
| R6 | **`request_key` 构造口径不一致** | 🟠 中 | 幂等静默失效（同一件事生出两条调用） | key 的构造**只有一个来源**（`service.build_request_key`），与 WP15 的 `build_dedupe_key` 同一判断 |
| R7 | **能力不支持时误报"成功"** | 🟠 中 | 下游拿到空结果继续跑 | 不支持返回 `CAPABILITY_UNSUPPORTED`（显式错误码），不返回空对象 |
| R8 | **结果校验把合法输出判成非法** | 🟠 中 | 正常生成被拦下（比漏放更烦人） | 校验只做"结构必需项"，不做业务语义判断；"模型说 A、实际 B"属 WP30 自检，不是网关 |
| R9 | **网关成为单点瓶颈** | 🟡 中 | 所有模型调用串行 | 网关是**库**（in-process 模块）而不是网络代理，不存在单点；真实出网由部署层白名单保证 |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（4 张新表，全部属数据结构 §11）：

| 表 | 新/建 | 说明 |
|---|---|---|
| `providers` | **新建** | 供应商与网络模式（LOCAL/EXTERNAL）；**不存密钥** |
| `model_profiles` | **新建** | 模型档案（模型名/修订/能力/参数 schema） |
| `capability_policies` | **新建** | 项目级出网策略；**缺省拒绝** |
| `provider_calls` | **新建** | 外部调用记录；`UQ(provider_id, request_key)` |
| `audit_events` | **消费**（WP15 已建） | 出网留痕落这里（见 §2.6） |

**接口**：**不新增 HTTP 端点**。协议 §12 明写"内部服务接口，不开放给前端直接调用"。
网关以**库**形式提供能力，由 WP17/WP18 的任务处理器调用。
契约维持 **24 paths / 29 operations / 59 schemas** 不变。

**后端分层**：

```text
modules/gateway/
  types.py         # CapabilityRequest / CapabilityResult / EgressDecision（值类型）
  policy.py        # 出网策略判定（纯函数，可毫秒级单测）
  adapters.py      # CapabilityAdapter Protocol + AdapterRegistry + StubAdapter
  models.py        # 4 张表
  repository.py    # 调用记录的幂等查/建 + 状态迁移（条件 UPDATE）
  service.py       # dispatch_call / poll_call / reconcile_call / validate_output
  handlers.py      # 与 WP13 的接缝：把调用状态映射为 HandlerOutcome
```

**前端**：不做（apps/ 未建立）。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**出网不是一个开关，是一条把"授权 → 派发 → 留痕 → 核对"串起来的链**：
链上每一步都必须有确定答案（能出/不能出、调没调、成没成），
而"不确定"必须是一个**显式状态**（`UNKNOWN`）而不是一个可以被重试吞掉的小故障。

### 2.2 用户画像

**主要用户是 Worker（代码）**，因此：

- **策略是可调用的纯函数**（`policy.evaluate_egress`），不是一段文档约定；
- **禁止降级是调用路径上的硬判断** —— 判定为否决时**直接返回错误**，
  不存在"换一条路"的分支（没有分支，就没有静默降级）；
- **凭据（`request_key`）在调用前落库**，"要不要重发"的回答来自数据库，不来自内存。

**次要用户是管理者/合规**：他们要能回答"这个项目有没有出过网、送出了哪类字段"。
因此留痕必须**不可篡改**（复用 WP15 的审计），且**结构上不含正文**。

### 2.6 技术风险评估（含应对）

见 §1.6。补充四条**必须在编码前定死**的实现约束：

1. **出网留痕复用 WP15 的 `audit_events`，不新建表**。
   ADR-10 要求"摘要 + 版本 + 字段类别 + traceId，不含正文"，而 WP15 的审计表
   **恰好已经有结构性保证**（`before_hash`/`after_hash` 是 `char(64)`，
   **模型层没有可存正文的列**）且**不可篡改**（双层保护）。
   再建一张 `gateway_egress` 表等于把"不含正文"这条保证重新证明一遍，
   而新表的保护强度只会**弱于**已验过的审计。落地映射：
   `action='gateway.egress'`、`object_type='provider_call'`、`request_id=traceId`、
   `after_hash=hash_payload(出网摘要)`、`reason='dataClass=…;policyVersion=…;promptVersion=…'`
   （字段类别是**元数据标签**，不是业务正文）。登记 **OP-125**。

2. **"缺省拒绝"落成"查不到策略 = `LOCAL_ONLY`"**，而不是"查不到 = 允许"。
   数据结构 §11 原句是「项目策略优先，**缺省拒绝未授权出网**」。
   这一条是验收第一半的地基：**任何"没配策略就当允许"的写法都是漏洞**，
   而且它的失败是静默的（不报错、直接出网）。登记 **OP-126 / OP-127**。

3. **`request_key` 的构造只有一个来源**（`service.build_request_key`），
   格式 `{capability}:{provider_id}:{job_attempt_id}:{attempt_no}`。
   理由与 WP15 的 `build_dedupe_key` 完全相同：两处拼法不同会让幂等**静默失效**
   （同一件事生出两条调用，两条都计费），而**不会有任何机制报错**。
   登记 **OP-129**。

4. **`UNKNOWN` 只有一个出口：`reconcile_call`**。
   调用状态机不提供"UNKNOWN → SUBMITTED"这条边（那等于"重新发一次"）。
   与 WP13 的 `reconcile_job` 一致：`WAITING_RECONCILIATION` **禁止 requeue**
   （WP13 §代码注释原句"`requeue` 在这里是被禁止的"）。
   本包的 `UNKNOWN` 与 WP13 的 `WAITING_RECONCILIATION` **一一对应**。

## 3. 阶段 3：多版本方案

方案的**分野是"出网策略怎么落地"与"UNKNOWN 怎么收口"**。

| 方案 | 定位 | 内容 |
|---|---|---|
| **V1 只建表 + 能调通** | 1 天 | 4 张表 + 一个 `dispatch`，**不做策略判定、不做幂等查、不留痕** |
| **V2 全做，但策略靠约定** | 不推荐 | 4 张表 + 状态机 + 幂等 + 留痕，但 `LOCAL_ONLY` 只在派发前"检查一下、记个 warn 日志" |
| **V3 策略硬判 + 幂等落库 + 留痕复用审计（推荐）** | 本包交付 | 4 张表 + **纯函数策略判定（否决即返回，无降级分支）** + `UQ(provider_id,request_key)` 派发前查 + UNKNOWN 仅经 reconcile 出口 + 结果校验 + 留痕写 `audit_events` |
| **V4 完整版** | 生产级 | V3 + 真实供应商适配器 + `/admin/providers` 端点 + 并发限流器 + 健康检查任务 + 费用联动 |

### 方案 V1 —— 只建表 + 能调通（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 4 张表 + 一个能返回结果的 `dispatch` |
| 优点 | 一天能交付，"调用链通了" |
| 缺点 | ① 验收第一半"LOCAL_ONLY 无回退"**完全没有落点**（没有策略判定）；② 验收第二半"未知状态不盲重试"**也没有落点**（没有 `request_key` 唯一约束、没有派发前查）；③ 不留痕，"出了什么网"无从回答 |
| 风险 | 交付一个"能调模型"但**两项验收都过不了**的包 |
| 结论 | ❌ **否决**。它省掉的恰好是两个验收项各自的命门 |

### 方案 V2 —— 全做，但策略靠约定（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 4 张表 + 状态机 + 幂等 + 留痕，但 `LOCAL_ONLY` 只在派发前"检查一下、记 warn 日志" |
| 优点 | 看起来全，且"不打断业务" |
| 缺点 | ① ADR-10 的违规判定口径是"**任何一条** LOCAL_ONLY 项目的出网记录 = 该次调用违规"，而"记个 warn 然后继续出网"**恰好产生那条违规记录**；② 它的失败是静默的：内容照常生成，没人知道数据出了网；③ "配置漏了""策略没生效"被 ADR-10 明确列为**不能免责**的理由 —— 而 warn 日志正是"配置漏了"的典型形态 |
| 风险 | 典型的"看起来像做了"：策略函数在、日志在、测试可能还过，但**合规承诺已经破了** |
| 结论 | ⚠️ **不推荐**。它把"合规禁止"降级成了"运维提醒" |

### 方案 V3 —— 策略硬判 + 幂等落库 + 留痕复用审计（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 4 张表 + **纯函数策略判定**（否决即 `EXTERNAL_POLICY_DENIED`，**不存在降级分支**）+ `UQ(provider_id, request_key)` + **派发前查**（非终态不重发）+ UNKNOWN 仅经 `reconcile` 出口 + 结果校验 + 留痕写 WP15 的 `audit_events` |
| 优点 | ① **两个验收都有结构性保证**：策略是纯函数（可单测、唯一判据）+ 幂等是唯一约束（并发下也成立）；② **禁止降级是"没有分支"而不是"记得别走"** —— 代码里根本没有第二条路；③ 留痕复用**已验证的**不可变审计（含"没有可存正文的列"这条结构性保证），不重新发明；④ 边界清晰：真实适配器/管理端点/限流器全部显式登记 |
| 缺点 | ① 真实供应商适配器要等内网（缓解：本包交付 Protocol + registry + 可配置桩，WP17/WP18 与真实适配器都只是"注册进去"）；② 项目级 `LOCAL_ONLY` 的归属需文档确认（OP-127）—— 本包按"策略即真相"落地 |
| 风险 | 低。没有新增设计风险，策略与幂等都是"把已经写清楚的东西接起来" |
| 适合场景 | 本包的实际处境：验收两半都需要结构性保证，且都能在本机验证（策略判定 + 幂等查是纯逻辑 + 真库约束） |
| 结论 | ✅ **推荐** |

### 方案 V4 —— 完整版（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | V3 + 真实适配器 + `/admin/providers` + 限流器 + 健康检查 + 费用联动 |
| 优点 | 一次性到位 |
| 缺点 | **越界**：真实适配器需要"用哪个供应商"（WP04 结论）与出网白名单（E3 审批）；`/admin/providers` 与 `/jobs/*` 端点**在计划里没有归属**（OP-123/124，本包替别人决定归属会重蹈 WP12 §3 V4 的覆辙）；限流器形态取决于部署（内网首日才定）；费用属 WP25 |
| 风险 | 建了一堆"看起来完整"但**要么做不动、要么不该做**的东西 |
| 结论 | ❌ 不选。**边界按"有没有设计空间"划**：策略判定与调用状态机没有（§11/§12/ADR-10 已定死），真实适配器与端点层有（等 WP04 / 等归属决定） |

### 选择与理由

**选 V3。** 三条理由，按权重排序：

1. **两个验收项都能在本机拿到结构性证据**。
   第一半 = 纯函数判定 + "被拒时适配器零调用"的断言；
   第二半 = `UQ(provider_id, request_key)` + "同 key 第二次派发不触发 `submit`"的断言。
   两者都不依赖外部供应商 —— 这很关键，因为本包是**唯一一个"核心逻辑可本机验证、
   但真实链路上不去"的包**，必须把可验证的部分做到满。
2. **"禁止降级"必须是结构性的**。ADR-10 把"配置漏了"列为免责理由之外，
   意味着实现上不能留任何"继续走下去"的分支。V2 的 warn 日志**正是**被判违规的形态。
3. **留痕复用审计而不是新建表**。WP15 已经把"不含正文"证明成了**结构性事实**
   （模型层没有那类列），并且已验过不可篡改。新建表只会得到一个更弱的复制品。

**V3 的代价我接受**：真实供应商适配器与端点层都不做。
但这不是"缺了一半"，而是**本机根本做不出真实出网**（无密钥、无白名单、无供应商）——
把接口定死、把桩做出来、把归属登记清楚，是此时**唯一诚实的交付**。

> **请老大确认三件事**（其余我按 V3 直接开工）：
>
> 1. **`capability_policies.external_policy` 的取值域** —— 我倾向
>    `ALLOW_EXTERNAL` / `LOCAL_ONLY` 两种，且**查不到策略 = `LOCAL_ONLY`**（缺省拒绝）。
>    若你希望缺省允许（即"没配就随便出网"），明确告诉我 —— 但那会与 ADR-10 冲突。
> 2. **`LOCAL_ONLY` 落在哪** —— 我倾向**只落在 `capability_policies`**（策略即真相），
>    不在 `projects` 上加列。理由：出网是"策略"问题不是"项目"问题，
>    而且策略可以按项目分版本（`policy_version`）；将来模式 B 上线时
>    只需改策略行，不用改项目表。若你要项目级开关，我加 `projects.is_local_only` 并让策略与它取"更严"的一方（登记 OP-127）。
> 3. **`UNKNOWN` 的任务映射** —— 我倾向映射到 WP13 的 `WAITING_RECONCILIATION`
>    （而不是 `FAILED`）。理由：`FAILED` 会触发重试路径，而 UNKNOWN 恰恰**不能**重试；
>    `WAITING_RECONCILIATION` 在 WP13 里是"禁止 requeue"的状态，语义严丝合缝。
>
> 默认按 V3 + 这三个口径执行，理由是上面三条。

### 4.3 `request_key` 不带 `attempt_id`（**本包最关键的一个判断**）

最自然的写法是 `f"{capability}:{provider_id}:{attempt_id}"` —— 但它是**错的**：

| 情形 | attempt 变化 | 若 key 带 attempt | 后果 |
|---|---|---|---|
| 正常的同一次执行 | 不变 | 查到既有调用 | 正确（不重发） |
| **租约过期 → 回收器接手** | **变** | **查不到** | **重复派发 → 重复计费** |
| **处理器崩在"已发出、未写结果"之间 → 任务重试** | **变** | **查不到** | **重复派发 → 重复计费** |

数据结构 §13.4 的原句是"**租约只防本地并发，不保证供应商已停工**；
`UNKNOWN` 不因租约过期变成可自由重试" —— 恰恰在说第二种情形。
所以 key 必须**跨 attempt 稳定**：它锚定的是"哪件活"，而不是"谁在干"。

落地：`request_key = f"{capability}:{provider_id}:{job_id}:r{round_no}"`，
`round_no` 默认 `0`。**要开新一轮调用，调用方必须显式传 `round_no>0`** ——
"重试"是一个需要有人负责的决定，不能是默认行为（登记 OP-133）。

### 4.4 判据顺序：**先判策略，再查幂等**（反过来是漏洞）

反过来（先查幂等、后判策略）会有一个恶劣后果：一个原本被拒绝的出网调用，
如果**曾经**存在同 key 的记录，就会被"幂等命中"直接返回 ——
等于用历史记录绕过当前策略。策略必须**每一次**都重新判。

### 4.5 被拒是**返回值**而不是异常（留痕必须活下来）

初版是 `写留痕 → raise`，而调用方在 `session_scope` 里 ——
**异常穿出 → 整个事务回滚 → 刚写的 DENIED 留痕一起被撤销**。

而 ADR-10 恰恰要求"任何一条 `LOCAL_ONLY` 项目的出网记录 = 该次调用违规"，
也就是说：**"曾经试图出网并被拒"本身就是需要留档的安全事件**。

落地：`DispatchResult` 增加 `denial` 字段，被拒时返回
`{call=None, dispatched=False, egress_id=..., denial=...}`，让事务**正常提交**；
调用方在提交之后调 `egress_error(denial)` 折成协议错误。
这与 WP12 的 `CompletionOutcome` 是同一个模式（见 §5 D2 / ISS-48）。

### 4.6 出网留痕**有自己的表**（复用审计表会撞约束）

初版复用 WP15 的 `audit_events`，实测直接撞 CHECK：

```
violates check constraint "ck_audit_events_hash_pair_consistent"
```

那条 CHECK 是 `(before_hash IS NULL) = (after_hash IS NULL)` ——
它为"**变更**记录"而设，而出网留痕是**事件**（没有 before）。
硬塞进去只能伪造一个 before（污染 `changed` 语义）或把一条事件拆成两条。

**结论：复用错误的抽象比多一张表更糟。** 改建 `gateway_egress`，
并**复用同一套不可变机制**（`guard_immutable` + 触发器生成器），
保持"凭据不可篡改"与审计一致。见 §5 D1 / ISS-47。

**本地调用不写留痕**：本地供应商不出网，记一条"出网记录"会让 ADR-10 的
违规判定口径退化成"本地调用也算违规"，模式 B 下系统将寸步难行。

### 4.7 两套状态值刻意分开

| 集合 | 谁的值 | 取值 |
|---|---|---|
| `CALL_STATES` | `provider_calls.state`（**落库**） | PREPARED / SUBMITTED / POLLING / SUCCEEDED / FAILED / UNKNOWN |
| `ADAPTER_RESULT_STATES` | 适配器返回（协议 §12.1 **原样**） | SUCCEEDED / ACCEPTED / FAILED / UNKNOWN |

它们**不是同一套**：协议 §12.1 里适配器返回 `ACCEPTED`，而落库状态是 `POLLING`。
合并成一套会迫使某一方改名 —— 改协议的名字是越界，改落库的名字会让
`provider_calls.state` 与数据结构 §12 对不上。因此保留两套 +
一个**显式**映射函数（`call_state_for_result`）。

`UNKNOWN` **不是终态**（它等核对），也不在"可以重新派发"的集合里 ——
`CALL_IN_FLIGHT_STATES` 就是验收第二半的判据。
