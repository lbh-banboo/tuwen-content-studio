> 工作包：WP12（M1 第五个业务包，W5）
> 验收：**AC-06**（并发上传仍无法超过 300,000,000 字节有效研究容量）、**AC-07**（不支持格式可归档、明确未解析）

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

**一句话**：让用户把研究资料交进系统，同时保证"一个项目的研究原文件累计不超过 300,000,000 字节"这条**配额约束在并发下也不被突破**。

拆开看是两件不同性质的事：

| 事 | 性质 | 真正的难点 |
|---|---|---|
| 把大文件收进来 | 传输工程 | 大文件不能走 JSON（协议 §1 明确禁止 Base64），必须分片 + 可断点续传 |
| 不超过配额 | **并发正确性** | 两个用户同时传，各自"先查余量再写"会双双通过 —— 这是本包唯一的**算法级**难点 |

第二件才是这个需求的本质。第一件是常规工程，有成熟做法；第二件的正确做法在数据结构 02 §13.1 已经给出（**条件 UPDATE 原子预占**），本包要把它落地并证明。

**为什么配额必须是"有效文件"而不是"上传过的文件"**：
需求 §6.2 原文——"每项目**有效**研究原文件累计不超过 300 MB"、"**不包含** Brief、生成媒体和系统提取出的内部索引"。
即：配额算的是 `project_file_links` 里 `purpose = RESEARCH` 且 `effective = true` 的关联，不是"上传动作发生过"。
一个被取消的上传、一个被解绑的文件，**占的额度必须还回去**。

### 1.2 核心用户是谁？

| 角色 | 什么时候用 | 关心什么 |
|---|---|---|
| **运营/内容同学**（主用户） | 项目开始前，把品牌资料、竞品截图、参考文档一次性拖进来 | 传得动、断了能续、别让我重传；传完知道"这个文件认没认出来" |
| **项目负责人** | 看项目资料齐不齐 | 剩余配额还剩多少（`remainingQuotaBytes`） |
| **管理者** | 排查"为什么传不上去" | 配额账面、上传会话状态 |
| 系统（解析 Worker，WP17） | 文件固化后 | 拿到一个可靠的 blob 与 UNSUPPORTED 标记 |

**注意一个容易漏的点**：主用户是**非技术用户**，且可能一次传几十个文件、单个文件几百 MB。
这意味着"失败后必须从头重传"是不可接受的（就是 300 MB 的配额，重传代价也极高）——
**断点续传不是优化项，是基本要求**。

### 1.3 最小 MVP 应包含哪些功能？

| # | 功能 | 依据 | 为什么必须在 MVP 里 |
|---|---|---|---|
| F1 | 创建 upload session（用途 + 声明大小）→ **同事务原子预占配额** | 协议 §4.2 / 数据结构 §13.1 | AC-06 的唯一实现点 |
| F2 | 分片上传（默认 8 MiB），重复分片一致则幂等返回 | 协议 §4.2 | 断点续传的基础 |
| F3 | 查询会话：已接收哪些分片、剩余预占 | 协议 §4.2 | 断点续传的"续" |
| F4 | 完成上传：核实大小与摘要 → 固化 blob/file → **预占转有效** | 协议 §4.1 | 配额的"转正"必须与文件固化同事务 |
| F5 | 取消上传：**幂等**释放预占 | 协议 §4.2 | 否则取消一次就永久漏额度 |
| F6 | 不支持格式 → 归档 + `UNSUPPORTED` 标记 | AC-07 / 需求 §6.2 | 验收项 |
| F7 | 文件元数据查询 `GET /files/{id}` | 协议 §4.2 | G1 端到端要看到文件状态 |
| F8 | 过期会话 TTL 回收预占 | 数据结构 §4「TTL 清理」 | 没有它，用户关掉浏览器就永久漏额度 |

### 1.4 描述有哪些疏漏应当补充？理由是什么？

按"老大给的描述不一定完美"的规矩，逐条列出我认为**文档没写清、但实现必须定**的点：

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **配额预占与"实际大小"不一致时怎么办** | 协议让客户端在创建会话时声明 `byteSize`，但真实字节数只有传完才知道。文档 02 §13.1 只说"完成后按实际大小核对"，**没说核对不一致时是拒绝还是按实际修正** → 见 §2.4 OP-93 |
| 2 | **`purpose` 与配额的对应关系** | 文档 02 §4 说"研究配额按 `project_file_links` 计算"，但 `purpose` 有 6 个取值（BRIEF/RESEARCH/REFERENCE/PROOF/GENERATED/EXPORT）。**只有 RESEARCH 进配额**，其余不进 —— 这条要点必须写死在代码里，否则 BRIEF 也会吃研究配额 |
| 3 | **物理去重与配额的关系** | 文档 02 §4 明确："配额去重按项目有效文件摘要处理，**不因跨项目共用 Blob 免掉该项目配额**"。即：blob 可以物理共用，但每个项目的配额都要算 → 实现时**不能**用 blob 存在与否短路 |
| 4 | **`sha256` 是服务端的还是客户端的** | 文档 02 §4 写"**SHA 为服务端结果**"，而协议 §4.2 的创建请求里 `sha256?` 是可选入参。两者结合的含义：客户端传的只是**提示**（用于提前判重），**权威值必须服务端重算** |
| 5 | **`Idempotency-Key` 落在哪张表** | 协议 §4.2 要求 completions 带它，但 `idempotency_records` 在数据结构 §11（**WP13 范畴**）→ 见 §2.4 OP-94 |
| 6 | **`taskId` / Outbox 的归属** | 协议 §4.1 要求"固化文件/转换配额/**Outbox**"同事务、§4.2 返回 **`taskId`**，但 `outbox_events` 与 `jobs` 都在 §11（WP13）→ 见 §3 与 OP-95 |
| 7 | **存储后端本机跑什么** | 内网 MinIO 尚未安装（M0 未验证，OP-75）。本机必须能跑通全流程 → 需要**存储适配器**抽象 |
| 8 | **文件名怎么处理** | 文档 02 §4 写"**不把文件名当路径**"。这意味着 `object_key` 由服务端生成；且下载时 `Content-Disposition` 里的文件名要防响应头注入 |
| 9 | **`DELETE /uploads/{id}` 重复调用** | 协议说"幂等释放预占"，文档 02 §13.1 说"**每次释放只允许一次**"。"幂等"与"只允许一次"要同时满足 → 返回值必须是 204 而不是 404/409 |

### 1.5 哪些功能现在不该做？

| 砍掉 | 为什么 |
|---|---|
| **对象存储直传（presigned URL）** | 协议 §4.1 的画法是"UI→API→FS"（服务端中转），不是浏览器直传。直传要额外做签名服务与 CORS，且内网 MinIO 还没落地。按协议做 |
| **断点续传的"跨设备续传"** | 只需同一会话内续传。跨设备恢复要引入"上传任务列表 + 用户绑定"的产品设计，无需求依据 |
| **秒传（同 blob 直接复用）** | 文档 02 §4 允许物理去重，但"不向无权限用户暴露某文件已存在"——秒传的响应差异本身就是存在性泄露。v1 一律真传，物理层去重在写入时静默做（同 sha256 复用 blob 行，但仍算本项目配额） |
| **多分片并发上传的编排** | 协议未定义并发度，服务端不需要知道。客户端自己决定 |
| **病毒扫描 / DLP** | `blobs.scan_status` 列保留，但本包只置 `PENDING`。真实扫描引擎要企业安全评审（OP-50 一类的安全项） |
| **`jobs` / `domain_events` / `idempotency_records`** | 属 WP13。见 OP-94 / OP-95 |
| **解析本身（parse_runs / source_segments）** | 属 WP17。本包只到"文件固化 + UNSUPPORTED 判定" |
| **配额预警 / 邮件通知** | 需求只要求"不超过"，没要求预警。`notification_receipts` 在 §11，也属 WP13 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **配额并发突破**（AC-06 直接失败） | 🔴 高 | 两个请求同时通过检查，账面超限，验收项挂了 | 单条**条件 UPDATE**（`WHERE effective+reserved+Δ <= limit`）原子预占，靠 `rowcount` 判定；不写"先 SELECT 再 UPDATE" |
| R2 | **预占泄漏**（取消/超时/失败没还额度） | 🔴 高 | 额度只减不增，用户无法上传且**账面看不出来** | 释放走状态机 + 条件 UPDATE（`WHERE state = 'UPLOADING'`），保"每次释放只允许一次"；TTL 回收兜底；对账函数按文件关联重建账面 |
| R3 | **大文件导致请求体限制误伤** | 🟠 中 | 分片 8 MiB × 某个倍数后撞上 2 MB 全局上限，上传 100% 失败 | 分片端点必须**豁免**普通请求体上限（协议 §1 说"普通请求体"），按 `partSizeBytes` 单独限流 |
| R4 | **路径穿越 / 响应头注入** | 🟠 中 | 恶意 `fileName` 写到任意路径，或换行符注入 `Content-Disposition` | `object_key` 服务端生成（不含用户输入）；`original_name` 只存不拼路径；下载头做白名单过滤 |
| R5 | **重复分片内容不一致** | 🟠 中 | 断点续传时客户端记错分片，拼出损坏文件却校验不出 | `upload_parts` 存每片 sha256；重传比对，不一致 → 409（文档 02 §4 明确要求） |
| R6 | **上传中进程重启，临时分片成孤儿** | 🟡 中 | 磁盘只涨不降 | 分片写"临时区"（`temporary_key` 前缀），TTL 清理同时清临时对象 |
| R7 | **本机无对象存储** | 🟡 中 | 无法端到端验证 | 存储适配器：本机 `local`（文件系统），内网 `minio`。同一接口、同一测试集 |
| R8 | **`bigint` 容量对外类型** | 🟢 低 | 前端把 300000000 当 number 处理，超 2^53 精度丢失 | 协议 §1 明确"所有数据库 bigint 对外固定为十进制**字符串**"。配额三个字段全部按字符串返回 |

**R1 与 R2 是本包的两条命门**：一个是"不能超"，一个是"不能漏"。两者的共同点是**账面错了不会报错**，只能靠专门测试发现 —— 所以 §6 的测试必须包含**并发**用例，而不是只测串行场景。

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（数据结构 02 §4，本包建 6 张表）：

| 表 | 角色 |
|---|---|
| `blobs` | 物理内容（sha256 + object_key + 字节数），**跨项目可共用** |
| `file_objects` | 逻辑文件（原名 + 可见性 + 上传人） |
| `project_file_links` | 项目 ↔ 文件 ↔ 用途，`effective` 决定是否计入配额 |
| `quota_accounts` | 每项目一行：`limit_bytes` / `effective_bytes` / `reserved_bytes` |
| `upload_sessions` | 一次上传的意图与状态机 |
| `upload_parts` | 已接收分片（PK `upload_id, part_no`） |

**另有 1 张表需要现在决定**：`outbox_events`（协议 §4.1 要求同事务写入）—— 见 §3 选型。

**接口**（协议 §4.2，6 个端点，全部照抄不多不少）：

| 方法 | 路径 | 关键点 |
|---|---|---|
| POST | `/projects/{id}/uploads` | 201；返回 `uploadId` / `partSizeBytes`(默认 8 MiB) / `expiresAt` / `remainingQuotaBytes` |
| GET | `/uploads/{id}` | 已接收 parts、实际大小、剩余预占 |
| PUT | `/uploads/{id}/parts/{partNo}` | `application/octet-stream`；200 分片摘要；**重复一致返回已有结果** |
| POST | `/uploads/{id}/completions` | 202；`fileId` + `taskId`；未知格式返回归档结果与 `UNSUPPORTED` |
| DELETE | `/uploads/{id}` | 204；取消并**幂等释放预占** |
| GET | `/files/{id}` | 元数据、扫描解析状态、权限 |

**后端分层**（沿用 WP10/WP11 的三层，新增两个横切件）：

```text
modules/files/
  models.py        # 6(+1) 张表
  storage.py       # ★ 存储适配器：Protocol + LocalBackend + MinioBackend
  repository.py    # 存储访问（含配额条件 UPDATE）
  service.py       # 业务规则：预占/释放/固化/UNSUPPORTED 判定
  permissions.py   # 可见性（复用 ProjectAccess）
  api.py           # 6 个端点 + 请求模型 + 响应模型
platform/
  request_limits.py  # ★ 请求体上限（OP-67 的落地位置）
```

**前端**：本包不做（apps/ 尚未建立）。但后端必须提供前端做分片所需的一切：`partSizeBytes`、已收分片清单、剩余配额。

见 §3。本包有**一个必须先拍板的边界问题**（Outbox / taskId 归谁），它直接决定选哪套 —— 所以在 §3 里把它作为方案的分野。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**把用户的研究文件安全收进系统，并在"两个请求同时上传"这种最坏时序下，仍然保证配额账面不超限、且任何一条失败路径都不会让额度泄漏。**

关键词是**账面**：配额不是"文件大小求和"这种可以事后重算的东西（重算要么慢要么不准），
它是一份必须靠**原子操作 + 状态机**维护的账。

### 2.2 用户画像

主用户是**非技术的运营同学**，行为特征是：

- **一次拖几十个文件**（不是一次一个）→ 配额检查必须扛得住并发，且错误信息要说清"还剩多少"
- **可能传几百 MB 的单个文件**（视频、打包资料）→ 必须分片 + 断点续传
- **会中途关掉浏览器** → TTL 回收不是可选项
- **不关心技术细节，只想知道"传上去了没有、认没认出来"** → `UNSUPPORTED` 必须是**明确可见的状态**，而不是静默忽略（AC-07 的核心）

### 2.3 核心功能清单（MVP）

| # | 功能 | 验收映射 |
|---|---|---|
| F1 | 创建会话 + **原子预占** | AC-06 |
| F2 | 分片上传 + 重复分片幂等 | — |
| F3 | 会话查询（断点续传） | — |
| F4 | 完成：核实大小与摘要 → 固化 → 预占转有效 | AC-06 |
| F5 | 取消：**幂等**释放预占 | AC-06（账面不泄漏） |
| F6 | 不支持格式归档 + `UNSUPPORTED` | **AC-07** |
| F7 | 文件元数据查询 | G1 |
| F8 | TTL 过期回收 | AC-06（兜底） |

### 2.4 待补充项及理由

| 编号（待登记） | 内容 | 归属 | 理由 |
|---|---|---|---|
| OP-93 | 声明大小与实际大小**不一致**时的口径（拒绝 or 按实际修正并回带差额） | 协议作者 | 文档 02 §13.1 只说"按实际大小核对"，未定不一致的处置。实现需在"严格"与"可用"之间选一个 |
| OP-94 | `Idempotency-Key` 的落表位置：是引入 `idempotency_records`（§11/WP13），还是由 `upload_sessions` 状态机承担 | 开发 + 协议作者 | 本包推荐后者（uploadId 本身即天然幂等键），差异登记 |
| OP-95 | `taskId` 的产生方：`jobs` 属 WP13，本包交付时该字段是否允许为 `null` | 开发 | 决定 G1 端到端能否在 WP12 单独跑通 |
| OP-96 | `partSizeBytes` 是否允许客户端上调（大文件减少请求数） | 协议作者 | 协议写"默认 8 MiB"，未写是否可协商 |

### 2.5 砍掉清单

见 §1.5（8 项）。其中**最需要老大知道的一条**：本包**不做对象存储直传**（协议自己的画法是服务端中转），
所以大文件会真实经过 API 进程。300 MB 配额 × 并发数决定了内存与磁盘水位 —— 这一点在 §2.6 R3 里按"流式写盘、不整片进内存"处置。

### 2.6 技术风险评估（含应对）

见 §1.6。补充三条**必须在编码前定死**的实现约束：

1. **分片必须流式落盘**，不允许 `await request.body()` 把 8 MiB 读进内存再写 —— 并发 10 个就是 80 MB 常驻。
2. **配额三个字段（limit/effective/reserved）对外一律字符串**（协议 §1 的 bigint 约定）。
3. **`object_key` 绝不包含用户输入**，形如 `projects/{project_id}/{upload_id}/{part_no}`。

## 3. 阶段 3：多版本方案

方案的**分野是这个边界问题**：协议 §4.1 要求完成上传时"固化文件/转换配额/**Outbox**"同事务写、§4.2 要返回 **`taskId`**，但 `outbox_events` 与 `jobs` 在数据结构 §11，属 **WP13**。

| 方案 | 定位 | 内容 |
|---|---|---|
| **V1 最快上线版** | 1~2 天 | 无分片（单请求上传）、无配额表（上传时现算 sum）、无 Outbox、无 TTL。**只够演示** |
| **V2 只做上传，不建 Outbox** | 不推荐 | 6 张表 + 全部分片/配额逻辑，但完成时不写 Outbox、`taskId` 恒为 `null` |
| **V3 上传 + 最小 Outbox（推荐）** | 本包交付 | V2 + 建 `outbox_events`（§11 已定义的表），完成上传时同事务写一条 `file.uploaded` 事件；仍不建 `jobs`，`taskId` 允许 `null` 并显式登记 OP-95 |
| **V4 完整版** | 生产级一次性到位 | V3 + 建 `jobs` / `domain_events` / `idempotency_records` + 调度器 + 通用幂等中间件 |

### 方案 V1 —— 最快上线版（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 单个 `POST /files` 带 multipart body；配额用 `SELECT sum(byte_size)` 现算 |
| 优点 | 一天能跑通，G1 演示够用 |
| 缺点 | ① 现算配额在并发下**必然突破**（AC-06 直接失败）；② 无断点续传，300 MB 失败要重传；③ 无预占概念，"上传中"的文件算不算额度无解 |

| 结论 | ❌ **否决**。它省掉的部分恰好是本包唯一的技术难点 |

### 方案 V2 —— 只做上传，不建 Outbox（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 6 张表 + 全部分片/配额/UNSUPPORTED/TTL；完成时只固化文件，**不写任何事件**；`taskId` 恒 `null` |
| 优点 | 表范围最小；WP13 做完后由 WP17 补挂扫描入口，不用改 WP12 的表 |
| 缺点 | ① 与协议 §4.1 的时序图**直接冲突**（协议第 8 步明写"固化文件/转换配额/**Outbox**"）；② "先登记文件、再想起来要扫描"这个窗口里，解析任务会**永久丢失**且无痕迹 —— 这正是 Outbox 模式要解决的问题；③ WP17 接入时必须回来改 WP12 的完成逻辑 |
| 风险 | 交付一个"协议里要求的东西没做"的包，且理由只是"表归别人"。这类越界节省通常会以"返工"收场 |
| 结论 | ⚠️ **不推荐**。省一张表的代价是协议不合规 + 后续返工 |

### 方案 V3 —— 上传 + 最小 Outbox（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | V2 的 6 张表 + **`outbox_events`（1 张，数据结构 §11 已给出完整列定义）**；完成上传时在同一事务写 `outbox_events(file.uploaded)`；**不建 `jobs` / `domain_events` / `idempotency_records`**；`taskId` 字段保留、值为 `null`，并登记 OP-95 说明"由 WP13 的消费者产生" |
| 优点 | ① **协议合规**（第 8 步的 Outbox 写入落在本包）；② 解析任务不会丢 —— 事件先落库，WP13 的 Worker 上线后自然开始消费，**WP17 不需要回来改 WP12**；③ 界限仍然清晰：只多了一张**协议点名要求**的表，且该表在数据结构里已有完整定义，无自创字段 |
| 缺点 | ① 本包要维护一张"别人的表"（缓解：表的列定义完全照抄 §11，且 `outbox_events` 本身是通用设施，不像 `jobs` 那样强绑定任务语义）；② 交付时事件只写不读，对账要等 WP13（缓解：提供 `list_unpublished_events()` 供 WP13 直接接） |
| 风险 | 若 WP13 最终设计的 Outbox 语义与 §11 定义不同，需要一次迁移。评估：**低** —— §11 的列（`aggregate_type/aggregate_id/event_type/schema_version/payload/attempts/next_attempt_at`）就是标准 Outbox 模式，没有可发挥的空间 |

| 结论 | ✅ **推荐**。它多做的唯一一件事，恰好是协议明确要求、且不做会留"静默丢任务"缺陷的那一件 |

### 方案 V4 —— 完整版（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | V3 + `jobs` + `domain_events` + `idempotency_records` + 租约调度器 + 通用幂等中间件 |
| 优点 | 一次性到位，G1 端到端可在本包内闭合（`taskId` 真值） |
| 缺点 | **严重越界**：`jobs` 的租约、`fence_token`、重试语义是 WP13 的核心设计，在这里"顺手建表"必然与 WP13 的设计打架（WP11 的教训：越界建的表要重做）。而且本包验收不要求任务能跑 |
| 风险 | 表建了但语义是错的，WP13 要迁移 + 回填；且 `domain_events` 牵出 SSE（WP14）的整套设计 |
| 结论 | ❌ 不选。**越界交付的代价在本项目已有先例**（WP11 §3 的 V4 讨论） |

### 选择与理由

**选 V3。** 三条理由，按权重排序：

1. **AC-06 的并发正确性只能靠"条件 UPDATE 原子预占"实现**，这是本包不可让渡的核心；三套方案里 V1 从这里就开始错，V2/V3 都做对了。
2. **Outbox 是协议点名要求的，不是我们想加的**。协议 §4.1 第 8 步写的是"固化文件/转换配额/Outbox"三件事同事务。不做它，等于交一个明知缺一步的包 —— 而且缺的这一步会导致解析任务静默丢失（没有事件 = 没有记录 = 事后无法发现）。
3. **`jobs` 坚决不建**。它与 Outbox 的区别在于：Outbox 是"写一条记录"（通用、无设计空间），`jobs` 是"一套调度语义"（有设计空间、属 WP13 的核心）。**边界不按"表在谁那"划，按"有没有设计空间"划。**

**V3 的代价我接受**：交付时 `taskId` 是 `null`，G1 端到端要等 WP13 完成后才能完整跑通。
但这**不是 WP12 的缺陷** —— G1 是 W5 末的检查点，而计划里 WP13 是"W5 启动、W6 完成"，两者本来就要合流。

> **请老大确认两件事**（其余我按 V3 直接开工）：
>
> 1. **是否同意建 `outbox_events`**（唯一越界项，理由见上）。若你希望严格不碰 §11 的表，我改 V2，代价是换掉协议 §4.1 第 8 步的做法并在文档里显式标注偏离。
> 2. **OP-93 的口径**：完成上传时实际字节数与声明不一致 —— 我倾向 **按实际修正并回带差额**（`reservedBytes` 调整、差额实时反映到 `remainingQuotaBytes`），而不是直接拒绝（拒绝会让用户"文件明明传完了却报错"，且声明值本身就是估计）。
>
> 默认按 V3 + "按实际修正"执行，理由是上面三条与"用户传完就该成功"这个常识。

### 4.3 配额的原子预占（AC-06 的全部含金量）

```sql
UPDATE quota_accounts
   SET reserved_bytes = reserved_bytes + :delta
 WHERE project_id = :pid
   AND effective_bytes + reserved_bytes + :delta <= limit_bytes
```

**判断条件写在 WHERE 里**，靠 `rowcount` 判定成功与否。
"先 SELECT 查余量、再 UPDATE 扣减"在并发下必然突破（两个请求各自读到
"还剩 100 MB"、各自判断放得下），而**串行测试永远发现不了** ——
所以 §6 的并发用例是本包最重要的一条测试。

不用 `SELECT ... FOR UPDATE`：它同样正确，但把"读"与"写"分成两条语句、
在读时就持锁。条件 UPDATE 一条语句拿到锁，持有时间更短。

### 4.4 存储适配器与四个状态出口

`StorageBackend` Protocol 只有 8 个方法（分片写入、拼装、读流、删除、
按前缀清理、移动、存在性、大小）。**MinIO 分支显式失败而不是静默降级** ——
静默降级会让内网切到 MinIO 时"看起来配好了"，实际写的是容器本地盘、重启即丢。

**对象 key 里没有任何用户输入**：`parts/<upload_id>/<part_no>`（uuid + 整数）、
`objects/<sha256 前 2 位>/<sha256>`。原文件名只存在 `file_objects.original_name`，
从不参与路径拼接 —— 这是路径穿越的**结构性**防护，不是"我过滤了危险字符"。

临时分片有**四个出口**，每个都要清（ISS-31 修的就是漏了第一个）：

| 出口 | 清理点 |
|---|---|
| 成功完成 | `complete_upload` 成功路径末尾 |
| 主动取消 | `cancel_upload` |
| TTL 过期 | `expire_stale_sessions` |
| 不可恢复失败 | `_fail_completion` |

> **这四个出口是列出来之后才对齐的**。最初的实现想起来了失败路径、
> 忘了成功路径 —— 逐个场景补漏的典型症状。列出口比补漏可靠。

autogenerate **又**提议删 `smoke_meta` / `wp05_vec_probe`，且 `downgrade` 里

因为 autogenerate 不识别 `vector` 类型 —— 重建出的表结构是错的）。

但**没有导入** `postgresql` —— 执行 `upgrade` 会直接 `NameError`（ISS-32）。

### 4.6 `CompletionOutcome`：为什么失败不能抛异常

不可恢复的失败要在**同一事务**里做两件事：会话置 `FAILED`、预占归还账面。
而这两件事要生效，前提是**事务正常提交**。若用异常传播，
外层 `session_scope` 会在退栈时回滚整个事务 —— 两步补偿一起被撤销，
预占一直挂在账上（要等 24 小时 TTL）。

因此 `complete_upload` 返回 `CompletionOutcome`，不可恢复的失败
（摘要不符 / 实际超余量 / 分片缺失）**返回结果而不抛异常**；
API 层据此直接构造错误响应（返回 `Response` 实例会跳过 `response_model` 校验）。

**可重试的输入错误仍抛 `ApiError`**（分片不连续、片数不符、没有分片、
状态不对）—— 那些情况会话还能救，用户补传后可以重试，
绝不能顺手置 `FAILED` 或释放预占。

### 10.3.1 一次事故的完整记录

本包交付过程中发生一次**工具层事故**：一次消息里并发发出三条
`log_issue.py --new`，导致（1）三条都分配 `ISS-28`、（2）
三进程交替写回把登记册末尾写坏成非法 UTF-8，此后任何读取都抛
`UnicodeDecodeError`，连 `--check` 都跑不起来。

处置：手工重编号、截断损坏尾部（备份在 `/tmp`）、`--render` 重建；
根因加固是**给工具加了 `fcntl.flock` 独占锁**，并实测验证 ——
加固后并发 3 条得到 `ISS-34/35/36`，无重复、文档可正常解码。

完整记录见 **ISS-33**。教训：任何"读-改-写"的文件维护工具在并发下都会坏，
且它的失败是**破坏性**的。不要指望使用侧自律，把互斥做进工具里。
