## 3. 关键设计决定（含"为什么"）

### 3.1 权限检查做成依赖，让端点"结构上无法绕过"

端点签名写 `access: ProjectAccessDep`，FastAPI 就会先执行权限检查、失败即中断。
**开发者不需要也无法在业务代码里手写权限判断** —— "忘了加检查"这个漏洞类型被结构性消除。

研发计划 01 §10.2 原文要求"所有接口、后台任务与 SSE 检查对象权限"。
靠约定（"记得加检查"）做不到 100%，靠依赖注入可以。

### 3.2 非成员返回 404，成员缺权限返回 403 —— 这个区分是刻意的

| 场景 | 返回 | 理由 |
|---|---|---|
| 项目不存在 | 404 | — |
| 非项目成员 | **404** | 协议 §1.2："对无权获知存在的对象也可返回404"。返回 403 会让攻击者通过枚举 UUID 判断"哪些项目存在" —— 这本身是信息泄露（能推出公司项目数量、编号规律） |
| 是成员但缺具体权限（如协作者结项） | **403** | 用户已能看到这个项目，隐瞒它没有意义，反而让用户困惑"项目怎么突然消失了" |

端到端 §[3] 与 §[5] 验证了"非成员"与"不存在"的响应**完全不可区分**。

### 3.3 管理者的权限不依赖成员记录

实现上，`load_project_access` 先判断 `is_admin` 再查成员关系。

**为什么**：若实现成"给管理者也插成员记录"，新增项目时容易漏插，
导致管理者看不到自己刚建的项目。显式判断让"管理者全权"这条规则在代码里可见。

端到端 §[4] 验证 `memberRole=None` 但 `isAdmin=True, canClose=True`。

### 3.4 每项目活跃负责人唯一 —— 用部分唯一索引而非普通唯一约束

```sql
CREATE UNIQUE INDEX uq_project_members_active_owner
  ON project_members (project_id)
  WHERE removed_at IS NULL AND member_role = 'OWNER';
```

**为什么必须带 WHERE**：普通唯一约束下，"移除旧负责人后新增新负责人"会失败 ——
旧行仍在表里。部分唯一索引只约束活跃行，正好表达"每项目活跃负责人唯一"。

这是"并发交接仍一名负责人"（WP10 验收项）的**最后防线**：
应用层事务逻辑可能写错，但唯一索引不会。已实测（§约束实测）。

### 3.5 成员移除用 `removed_at` 而非删除行

需求 §2.3 要求"历史审核、评论、交付记录保留原操作人"。
物理删除成员行会让历史归属失去依据。

同时 `removed_at IS NULL` 是"立即失效"的判据 ——
成员移除后下一次请求就失败，不需要等会话过期（与 WP08 的账号停用同原则）。

### 3.6 项目结项后禁止生产动作，但允许查看与报告

需求 §18.2 原文："结项后禁止新生产任务；允许查看、下载、补录／按需刷新数据、
处理事实纠错待办和生成新版报告。"

因此 `EDIT` / `REVIEW` / `DELIVER` 在 `PHASE_CLOSED` 下被拒，
`VIEW` / `REPORT` 仍允许。**管理者的全权优先于阶段限制** ——
否则结项后连管理员都动不了，重开流程会卡死。

### 3.7 权限判定是纯函数

`compute_project_permissions` 不查库、不抛异常，只做矩阵查表与阶段判断。
查库由仓储层完成。

**好处**：权限逻辑可被单元测试直接覆盖（51 条测试中 30 条是纯函数测试，
毫秒级跑完），不需要数据库。这也让"矩阵实现是否正确"与"权限是否被用上"
两个问题可以被分别验证。

## 4. 迁移说明（autogenerate 陷阱第二次出现）

迁移 `4531692fa005` 由 `--autogenerate` 生成后经人工审校。

**这次的表现与 WP08 完全一致**：

| 自动生成的问题 | 后果 | 修正 |
|---|---|---|
| 生成了 `op.drop_table('smoke_meta')` 与 `op.drop_table('wp05_vec_probe')` | M0 冒烟残留表被误删（**数据丢失**） | 删除这两条 |
| downgrade 用 `sa.NullType()` 表示 vector 列，且顺序倒置 | 回滚必然失败 | 重写为只做本迁移的逆操作 |

**这已是可复现的规律，不是偶发**：只要仓库里存在"手工建的验证表"，
每次 autogenerate 都会提议删除它们。因此**每次 autogenerate 后必须检查
并删除 drop_table / drop_index 语句** —— 这条已写入迁移文件的注释。

**本次表结构部分自动生成准确**：部分唯一索引的 WHERE 条件被正确保留
（`postgresql_where=sa.text("removed_at IS NULL AND member_role = 'OWNER'")`）。

### 双向验证

`upgrade head` → `downgrade 236d8fd94c52` → `upgrade head` 全部退出码 0，
残留表 `smoke_meta` 行数保持 4（未被误删）。

### 约束实测（脏数据必须被拒）

| 注入 | 结果 |
|---|---|
| 第二个活跃 OWNER | ✅ 被 `uq_project_members_active_owner` 拒绝 |
| 同一用户重复活跃成员 | ✅ 被 `uq_project_members_active` 拒绝 |
| 移除旧 OWNER 后插入新 OWNER | ✅ 成功（部分唯一索引的价值） |
| `phase='CLOSED'` 但 `closed_at IS NULL` | ✅ 被 CHECK 拒绝 |
| `target_delivery_count = 0` | ✅ 被 `target_delivery_positive` 拒绝 |
