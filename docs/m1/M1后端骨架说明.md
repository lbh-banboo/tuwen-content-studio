### 规范化做了什么，为什么

CI 契约 diff（协议 §13.2）要求"规范化"，否则 diff 里全是噪声。本脚本做三件事：

1. **`sort_keys=True`** —— 键顺序与 Python 字典插入顺序解耦。同一份代码在不同
   Python 小版本上可能产生不同顺序，不排序会让 diff 出现大量假变更。
2. **剥离 schema 内的 `title`** —— `title` 是 FastAPI 从 Python 类名派生的。
   重命名一个类（纯重构、对外行为不变）会让每个引用它的 `$ref` 与 title 都变，
   在 CI 里被误判成破坏性变更。**但 `info.title` 必须保留** —— 它是 OpenAPI
   规范要求的必需字段。
3. **折叠描述文本的行尾空白** —— 避免"改了个空格"产生 diff。

脚本还内置 `_assert_valid_openapi_skeleton` 自检：规范化是"删字段"操作，
删错必需字段会让契约不再合法，但脚本会静默成功、把坏契约写进版本库，
直到下游工具才报错。自检把失败提前到导出阶段。

### operationId 的口径

`operationId` 由 **HTTP 方法与路径**派生（如 `get_api_v1_health_db`），
不含 Python 函数名。FastAPI 默认实现会把函数名编进契约，导致重命名函数
在 CI 里表现为契约变更。

### CI 集成建议

```yaml
# 契约门禁（示例）
- run: python tools/contracts/export_openapi.py --check
```

退出码约定：`0` 一致 / `1` 有差异 / `2` 导出过程本身失败（app 装配不了等）。

## 7. 关键设计决定（含"为什么"）

### 7.1 liveness 与 readiness 分成两个端点

`/health` 只答"进程活着"，**绝不碰数据库**。理由：它会被反向代理/容器编排
当作存活探针。如果它依赖数据库，数据库短暂不可用会导致编排平台判定"应用已死"
并重启所有实例 —— 重启解决不了数据库问题，反而把故障从"数据库不可用"扩大成
"应用全挂"。这是 ADR-11 C8（双 API 实例 + 反向代理）下的硬要求。

### 7.2 handler 从 `request.app.state.settings` 读配置，而不是全局单例

app 工厂 `create_app(settings)` 允许注入配置。如果 handler 直接调
`get_settings()`（进程级单例），就会出现"app 用注入的配置装配、handler 却按
环境变量读配置"的两套真相 —— 表现为路由前缀、超时、环境标识全按环境变量走，
注入的 settings 只在路由装配阶段生效。这个错误很难发现：接口返回 200，只是值不对。

本机实测踩到过：`test_health_returns_ok_without_database_configured` 断言
`environment == "test"` 却拿到 `"dev"`，根因就是这个。

### 7.3 纯 ASGI 中间件，不用 `BaseHTTPMiddleware`

`requestId` 通过 ContextVar 传给下游（响应体的 `meta.requestId` 由 handler 读它拼出）。
`BaseHTTPMiddleware` 会在独立任务里运行下游 app，ContextVar 的写入时机与可见性
依赖 Starlette 版本实现细节。拿一个契约字段的正确性去赌框架内部实现不值得。
纯 ASGI 中间件与下游 app 在同一上下文顺序执行，可见性是确定的。

### 7.4 非法 X-Request-Id 不返回 400，而是生成新值

协议 §1.1 原文是"可由客户端提供 UUID；服务端验证或生成"。本实现：合法 UUID
原样透传（保持客户端追踪链路完整）；非法值生成新的，并记 DEBUG 日志。
理由：这是可观测性辅助字段，不是安全字段。为一个格式错误拒绝整个业务请求，
会让排障工具变成可用性风险。

### 7.5 超时分四层，任何一层都不能省

| 层 | 参数 | 生效位置 | 为什么不能省 |
|---|---|---|---|
| 连接 | `connect_timeout=3` | libpq（TCP+认证） | 网络黑洞时 TCP 握手可能挂很久 |
| 语句 | `statement_timeout=2000ms` | PostgreSQL 服务端 | 连上后一条慢查询同样能挂死请求；只在客户端超时无法中断服务端执行 |
| 拿连接 | `pool_timeout=5.0` | SQLAlchemy 连接池 | 池满时默认无限等待（None），是高负载下的隐性雪崩点 |
| 健康检查整体 | `health_total_timeout=3.0` | Python asyncio | 兜底：驱动在极端情况下不响应任何超时的场景 |

健康检查响应里回显这些值（`data.timeouts`），这样"配置真的注入了"可以从外部
验证，而不只是"代码里写了"。这些值不含凭据或网络位置，可以安全外泄。

### 7.6 游标是不透明 base64(JSON)，校验和只防手滑不防伪造

- **不用偏移量**：偏移量分页在并发写入下会漏项/重项。
- **游标绑定排序与筛选**：防止前端把"按点赞数排序"的游标拿去"按时间排序"的
  查询里复用（那样得到的下一页是无意义的错位）。绑定不匹配返回 400，不静默忽略 ——
  静默忽略会让前端以为在翻页、实际每次都拿第一页，形成难以察觉的数据重复。
- **游标不含权限**：每个查询都必须重新做权限过滤。若把权限"编码进游标"以省一次
  查询，会造成越权（权限在游标签发后被撤销时，旧游标仍放行）。
- **SHA-256 校验和只防截断/损坏，不做安全边界**：协议要求 API 双实例（ADR-11 C8），
  所以不能用进程内随机密钥签名（A 实例签发的游标在 B 实例会验签失败）。用全局密钥
  要引入配置项与轮换流程，成本高于收益。关键判断：游标载荷本身不承载权限，
  它只是"从哪条之后继续读"的位置。伪造它最多让攻击者从任意位置开始读，
  改变不了他能读到什么。

### 7.7 `details` 在返回前统一脱敏，而不是"约定调用方别传敏感内容"

约定靠自觉，脱敏靠代码。`details` 会经过多个模块的手（健康检查、未来的文件上传、
未来的模型网关），任何一处顺手把连接信息塞进去都会直接对外。做一次收口，
代价是偶尔多打码一个无害字段（可接受），收益是"凭据不可能经 details 外泄"。

脱敏做两层：**键名命中敏感标记**（password/token/secret/dsn/sql/stack 等）
整个值打码；**值级兜底**用正则识别 DSN 与 `password=xxx` 形式，即使键名无害
（如 `{"host": "postgresql://..."}`）也打码。

**已修复缺陷**：初版只在顶层做键名检查，`{"nested": {"token": "..."}}` 会原样外泄。
本机实测确认，已改为递归检查，并加回归用例
`test_details_redacts_nested_credentials`。

### 7.8 `INTERNAL_ERROR` 刻意不进 `ErrorCode` 枚举

协议 §1.2 的表只列"可预期错误"，没有 500 —— 因为未捕获异常是缺陷，不是业务状态。
若把 `INTERNAL_ERROR` 加进 `ErrorCode`，它会自动获得 HTTP 状态映射并进入契约里
`ErrorBody.code` 的 enum，于是一个"代码 bug"就变成契约里合法的业务错误码，
前端会以为可以按它写分支。

因此用 `Literal["INTERNAL_ERROR"]` 单值约束：它以单值 enum 出现在 500 的契约
声明里（前端能生成类型），但不在 `ErrorCode` 枚举中。

**已修复缺陷**：把 `ErrorBody.code` 从 `str` 改成 `ErrorCode` 枚举（为了让错误码
进入契约、前端可生成 TS 联合类型）后，500 兜底处理器因传入枚举外的
`INTERNAL_ERROR` 而自身抛 `ValidationError`，响应体变成空 —— 兜底处理器反而成了
新的崩溃点。已修复：新增 `InternalErrorBody` + `InternalErrorEnvelope`，500 走独立模型。

### 7.9 `migrations/script.py.mako` 用 `repr()` 而非字符串插值

初版模板写 `down_revision: str | None = "${down_revision}"`。字符串插值会把
Python 的 `None` 渲染成字符串 `"None"`，导致 `alembic revision` 报
`KeyError: 'None'`。改用 `${repr(down_revision)}` 后输出的是 Python 字面量。

| 1 | `curl` 请求 `127.0.0.1:8000` 返回 `502 Bad Gateway` / `upstream connect failed: Connection refused (os error 61)` | 本机 `HTTP_PROXY=http://127.0.0.1:55687` 拦截了本地回环请求 | 所有 `curl` 加 `--noproxy '*'`；改用未被占用的端口 8899/8898。原始输出见 `evidence/m1/backend-health.log` 第 0 节 |

### 障碍 #11 的教训（必须记住）

**动手改任何已有文件之前，先 `find` 盘点目录真实内容。**
本回合的覆盖之所以发生，是因为主 agent 假设"M1 骨架尚未开始"就直接落笔，
而实际上上一回合的子 agent 已完成并产出 117 个通过的测试。
测试文件完整定义了接口契约，因此恢复是可行的 —— 但这是运气，不是流程。

正确做法：写文件前先 `find <target_dir> -type f`，看到已有内容就**先读再改**，
绝不盲写。这与 C6/C2 同级的工程纪律。
