## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

**一句话**：让"谁、在什么时候、对什么、做了什么"**有凭据可查**，同时让"有人需要做什么"**以不重复的方式被看见**。

验收标准只有两半，但它们是**两个不同性质的问题**：

| 半 | 本质 | 真正的难点 |
|---|---|---|
| **日志可追踪且不泄露正文** | 审计 = 事实，正文 = 隐私 | 怎么让日志既有用（能追踪）又不泄密（不含正文） |
| **待办去重** | 提醒 ≠ 状态，重复提醒会让用户麻木 | 怎么让"同一对象同一类型只提醒一次"在**并发**下也成立 |

第一半是真正的设计难题：**审计最有价值的信息恰好是最敏感的信息**。
数据结构 §11 给出的答案是把正文换成**哈希**（`before_hash` / `after_hash`）——
它能回答"这份数据变没变、从哪个变到哪个"（比对哈希即可），
而**不包含正文本身**。这是"可追踪"与"不泄露"同时成立的关键。
若审计存的是正文，那么日志本身就是**最大的泄露面** ——
运维看一眼就知道每个项目的内容，而且**这个泄露不会留下任何痕迹**。

第二半的关键在于**"提醒"与"状态"是两种不同的东西**。
`domain_events`（WP14）是"发生了什么"（事实，会随时间累积、该重复就重复），
`work_items` 是"现在还有什么没做"（待办，同一对象同一类型只能有一条未结的）。
混淆两者的后果是：**每发生一次变化就生成一条待办** ——
用户的待办列表里全是同一对象的历史提醒，真正要做的事被淹没了。
而这条规则必须在**并发**下也成立：两个进程同时发现"该提醒"，只能有一条成功。

### 1.2 核心用户是谁？

| 角色 | 什么时候用 | 关心什么 |
|---|---|---|
| **管理者**（审计主用户） | 出问题时回溯 | "谁改的这个、从哪改到哪、为什么" |
| **运营/内容同学**（待办主用户） | 每天打开系统 | "今天我要做什么"，且**不想看到一堆重复的提醒** |
| 项目负责人 | 交接/审核时 | 待办有没有正确转交、有没有漏 |
| 运维/审计员 | 合规检查 | 审计不可被篡改 |

**注意一个容易漏的点**：审计的主用户**不是开发者**，是管理者与合规。
开发者会自然倾向"存正文好排障" —— 但那正是**不该做**的。
审计是给"需要凭据的人"用的，他们需要的是"发生了什么、变成什么样、为什么、是谁"，**而不是内容本身**。

### 1.3 最小 MVP 应包含哪些功能？

| # | 功能 | 依据 | 为什么必须在 MVP 里 |
|---|---|---|---|
| F1 | `audit_events` 表（含 `before_hash` / `after_hash`）+ 写入服务 | 数据结构 §11 | 验收第一半的落点 |
| F2 | 审计**不可篡改**（数据库触发器拦 UPDATE/DELETE） | 数据结构 §11「应用账户无 UPDATE/DELETE 权限」 | 审计若可被改，就没有凭据意义 |
| F3 | `GET /audit-events`（projectId/objectType/objectId 过滤 + 分页） | 协议 §10 | 审计的消费端点 |
| F4 | `GET /work-items`（**当前成员**待办 + 状态过滤 + 分页） | 协议 §10 | 待办的查询端点 |
| F5 | `POST /work-items/{id}/resolutions`（完成待办，**幂等**） | 协议 §10 | 待办的关闭端点 |
| F6 | **待办 dedupe**（`dedupe_key` 部分唯一索引 + 服务层正确用） | 数据结构 §3「同未结待办 dedupe_key 条件 UQ」 | 验收第二半 |
| F7 | `notification_receipts` 表 + 已读回执服务（**无端点**） | 数据结构 §11 | 「权限变化通知」的送达状态 |

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **审计的 `before_hash` / `after_hash` 是什么的哈希** | §11 只列了列名。是"整个对象的规范化哈希"还是"变了的那部分"？必须定（见 §2.6） |
| 2 | **`actor_kind` 的取值域** | §11 只列了列名。至少有 USER（人）/ SYSTEM（系统）/ SERVICE（服务账户） |
| 3 | **审计的 `object_type` / `object_id` 是否带项目归属** | §10 的过滤是 `projectId?`，而 `audit_events` 表没有 `project_id` 列 —— 怎么按项目过滤？见 §2.4 OP-116 |
| 4 | **`GET /work-items` 里"未认领待办"谁能看到** | 协议只说"当前成员待办"。未认领（`assignee_id IS NULL`）的归属项目待办，项目成员能不能看到（以便认领/转交）？ |
| 5 | **审计的不可篡改**怎么落地（GRANT vs 触发器） | §11 写"应用账户无 UPDATE/DELETE 权限"是 GRANT 级，但当前只有单账户。见 §2.6 |
| 6 | **`notification_receipts` 没有端点，已读怎么标记** | 协议 §10 没有 receipts 端点。见 §2.4 OP-117 |
| 7 | **`resolutions` 是否需要幂等键** | 协议没写。但完成待办是**状态机迁移**（OPEN→DONE），幂等由状态本身承担（见 §2.6，这也决定 OP-85 的答案） |

### 1.5 哪些功能现在不该做？

| 砍掉 | 为什么 |
|---|---|
| **`notification_receipts` 的已读标记端点** | 协议 §10 没有。它是内部设施（送达状态），已读端点待协议明确（OP-117） |
| **审计的 GRANT 级账户隔离** | 当前只有单数据库账户。触发器能做到"对**所有**账户都拦"（更强），GRANT 级隔离留内网多账户后做（OP-118） |
| **审计的按月分区** | 数据结构 §15 明说"初期不为所有大表预先分区，按增长实测决定" |
| **审计的敏感键名扫描** | 审计不存正文，天然不泄露。payload 只有哈希与元数据 |
| **`work_items` 的列表筛选器** | 协议只定义了 `projectId?` / `state` / `cursor` / `limit` |
| **`job_attempts` 的脱敏端点** | 协议 §10 的 `GET /jobs/{id}/attempts`（脱敏尝试历史）属 WP13/WP16 的任务历史，不是本包 |
| **审计的对象正文联查** | "想看正文就去查对应的对象版本"（`version_id` 给了它）——审计不该自己复现正文 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **审计存正文** | 🔴 高 | 日志本身成为最大泄露面，且**泄露无痕迹** | `before_hash` / `after_hash` 只存规范化摘要；写入时**显式拒绝带正文** |
| R2 | **待办 dedupe 在并发下失效** | 🔴 高 | 同一对象被提醒两次，待办列表重复 | `dedupe_key` 部分唯一索引（WHERE OPEN）+ `ON CONFLICT DO NOTHING` + 服务层返回"已存在" |
| R3 | **审计可被篡改** | 🔴 高 | 凭据失去意义（改了不留痕） | 数据库触发器拦 UPDATE/DELETE（本机可验证）+ 登记 GRANT 级隔离（OP-118） |
| R4 | **`GET /work-items` 泄露非成员项目** | 🔴 高 | 列出"未认领待办"时把别的项目的也带出来 | 未认领待办**也要**按项目过滤（当前用户是该项目成员） |
| R5 | **完成待办不幂等** | 🟠 中 | 重复点"完成" → 状态错乱或重复通知 | 条件 UPDATE（`WHERE state='OPEN'`）+ rowcount 判定；已 DONE 直接返回（不是报错） |
| R6 | **审计的对象归属泄露** | 🟠 中 | `GET /audit-events?projectId=` 让非成员枚举到对象 id | 项目过滤用 `project_id` 列（而非靠 `object_id` 反查），非成员返回空 |
| R7 | **审计写入拖垮业务事务** | 🟡 中 | 每笔业务操作都多写一条审计 → 慢 | 审计**同事务**写入（与业务数据一致），且只写必要字段（哈希 + 元数据） |
| R8 | **`notification_receipts` 与 `domain_events` 语义混淆** | 🟡 中 | 把"已读"当成"业务已完成" | 数据结构 §11 明写"通知已读不代表业务已完成" —— receipt 只跟踪**送达/阅读** |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**：

| 表 | 状态 | 说明 |
|---|---|---|
| `work_items` | **已建**（WP10） | 本包只消费，不重建 |
| `audit_events` | **新建** | 审计日志 |
| `notification_receipts` | **新建** | 送达/已读回执 |

**接口**（协议 §10，3 个端点，逐条照抄）：

| 方法 | 路径 | 关键点 |
|---|---|---|
| GET | `/work-items` | `projectId?` / `state` / `cursor` / `limit` |
| POST | `/work-items/{id}/resolutions` | body `reason`；**幂等** |
| GET | `/audit-events` | `projectId?` / `objectType?` / `objectId?` / `cursor` / `limit` |

**后端分层**：

```text

  models.py        # audit_events + notification_receipts
  repository.py    # 写入 + 分页查询
  service.py       # 审计哈希、待办 dedupe、resolutions、已读回执
  api.py           # 3 个端点
platform/
  （复用 immutability.py 的触发器生成）
```

**前端**：不做（apps/ 未建立）。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**审计存"摘要 + 凭据"而不是"正文"**，让"发生了什么、变成什么样、是谁、为什么"可追踪，但内容本身不进入日志；**待办是"未结状态"而不是"提醒历史"**，同一对象同一类型最多一条未结的。

### 2.2 用户画像

**两类，各有侧重**：

- **管理者/合规**：出问题时回溯。他要的是"能不能信这条日志"（不可篡改）与"能不能看懂"（有哈希/凭据，但没正文照样能定位）。
- **运营同学**：每天打开系统看待办。他要的是"列表里只有真正要做的事"，且**没有重复提醒**。

**两类用户共同的约束**：他们**不读代码**。所以审计不能只靠"运维自己记得别写正文"，待办不能只靠"业务包自己记得别重复建" —— 这两条都必须有**结构性**保证（哈希列 + 唯一索引），而不是靠自觉。

### 2.3 核心功能清单（MVP）

见 §1.3（F1~F7）。

### 2.4 待补充项及理由

| OP-119 | `actor_kind` 的取值域（USER / SYSTEM / SERVICE / ...） | 文档作者 |

### 2.6 技术风险评估（含应对）

见 §1.6。补充三条**必须在编码前定死**的实现约束：

1. **审计哈希的口径**：`before_hash` / `after_hash` 用**与 WP11 相同的规范化哈希**（`canonical_payload_hash`：sort_keys + 紧凑分隔符 + UTF-8）。理由：如果两处用不同算法，"这个哈希和那个哈希是不是同一份数据"就永远没有答案 —— 而且将来核对"审计哈希"与"版本哈希"时会多出一条不可能对齐的口径。复用同一个函数。
2. **审计不可篡改的落地**：本机用**触发器**拦 UPDATE/DELETE（复用 WP11 的 `platform/immutability.py` 的 `guard_immutable` + 触发器 DDL，**已验证可用**）。GRANT 级账户隔离留内网多账户后做（OP-118）。**不用 GRANT 做本机方案**：当前单账户，GRANT 连"谁会写"都分不出来，做了等于没做，还给了"已经隔离了"的假象。
3. **完成待办的状态机**：`OPEN → DONE` 是**条件 UPDATE**（`WHERE state='OPEN'`），rowcount 判定。已 DONE 返回"已完成"（**不是报错** —— 用户点两次"完成"是正常操作，报错只会让他以为没完成）。**这也直接回答了 OP-85**：`work_items` **不需要 `lock_version`** —— 因为完成待办用的是"状态机 + 条件 UPDATE"，不是"读-改-写"那种需要携带旧值的场景。详见 §9。

## 3. 阶段 3：多版本方案

方案的**分野是"审计不可篡改怎么落地"与"三块是否都做"**。

| 方案 | 定位 | 内容 |
|---|---|---|
| **V1 只建表 + 只读端点** | 1 天 | 两张表 + `GET /audit-events` + `GET /work-items`，**不做 resolutions、不做 dedupe、不做不可篡改** |
| **V2 全做，但审计可篡改** | 不推荐 | 全部三块 + resolutions + dedupe，但审计**只靠应用层不写 UPDATE**（没有数据库层拦） |
| **V3 三块 + dedupe + 不可篡改触发器（推荐）** | 本包交付 | 两张表 + 3 端点 + dedupe + 审计哈希 + **不可变触发器**（复用 WP11 已验证的机制） |
| **V4 完整版** | 生产级 | V3 + GRANT 账户隔离 + 按月分区 + 审计的正文联查端点 + receipts 已读端点 |

### 方案 V1 —— 只建表 + 只读端点（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 两张表 + 两个 GET，其余不做 |
| 优点 | 一天能交付 |
| 缺点 | ① 验收第二半"待办去重"**完全没有落点**（没有 dedupe）；② resolutions 不做，待办永远"打开"，等于没做待办；③ 审计可篡改，凭据无意义 |
| 风险 | 交付一个"看起来有审计有待办"但**两项验收都过不了**的包 |
| 结论 | ❌ **否决**。它省掉的恰好是两个验收项各自的命门 |

### 方案 V2 —— 全做，但审计可篡改（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 全部三块 + resolutions + dedupe + 审计哈希，但审计只"应用层不写 UPDATE" |
| 优点 | 看起来全 |
| 缺点 | ① §11 明确要求"应用账户无 UPDATE/DELETE 权限" —— 没有数据库层拦，这条就没落实；② 审计若可被改（手工 SQL、数据回填、运维脚本 —— 这些路径**没有代码评审**），凭据就失去意义，而"被改过"是**静默失败**；③ WP11 已经有现成的、已验证的不可变机制（`guard_immutable` + 触发器），不用它等于承认"审计这条凭据比版本那条凭据不重要" —— 而恰恰相反，审计**就是**凭据 |
| 风险 | 典型的"看起来像做了"：端点都在、测试都过、但验收标准的第一半"可追踪"在审计被篡改的那一刻就失去意义 |
| 结论 | ⚠️ **不推荐**。它把"审计是凭据"降级成了"审计是日志" |

### 方案 V3 —— 三块 + dedupe + 不可篡改触发器（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 两张表 + 3 端点 + resolutions 状态机 + dedupe（部分唯一索引 + ON CONFLICT）+ 审计哈希（复用 `canonical_payload_hash`）+ **不可变触发器**（复用 WP11 的 `guard_immutable` + `immutable_trigger_ddl`，本机已验证：试写 UPDATE/DELETE 被拦，sqlstate=23001） |
| 优点 | ① **验收两半都有结构性保证**：审计不可篡改（触发器）+ 待办去重（唯一索引）；② 复用已验证的机制（WP11 的触发器 + WP11 的哈希函数），没有新增设计风险；③ GRANT 级隔离登记为后续（OP-118），**本机可验证**而不是"等内网再说"；④ 边界清晰：`notification_receipts` 只建表 + 内部服务，不加端点（协议没有） |
| 缺点 | ① GRANT 级账户隔离要等内网多账户（缓解：触发器对所有账户都拦，**比** GRANT 更强 —— 它连 root 都拦）；② 审计的对象归属要补 `project_id` 列（§11 没列，登记 OP-116） |
| 风险 | 低。没有新增设计风险，全部是复用已验证机制 + 明确的边界判断 |
| 适合场景 | 本包的实际处境：两个验收项都需要结构性保证，且都有现成的、已验证的机制可复用 |
| 结论 | ✅ **推荐** |

### 方案 V4 —— 完整版（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | V3 + GRANT 账户隔离 + 按月分区 + 审计正文联查端点 + receipts 已读端点 |
| 优点 | 一次性到位 |
| 缺点 | **越界**：GRANT 需要内网多账户（现在做等于没做还给了假象）；分区 §15 明说"按增长实测决定"；正文联查端点会把审计变成"另一个对象查询端点"（与"审计不存正文"自相矛盾）；receipts 已读端点协议 §10 没有（在 WP15 替协议决定端点） |
| 风险 | 建了一堆"看起来完整"但**要么做不动、要么不该做**的东西 |
| 结论 | ❌ 不选。**边界按"有没有设计空间"划**：GRANT 隔离与 receipts 端点都有设计空间（等内网/等协议），触发器与 dedupe 没有（§11 已定义清楚） |

### 选择与理由

**选 V3。** 三条理由，按权重排序：

1. **两个验收项都需要结构性保证，而两个保证都已经有现成的、已验证的机制**。
   审计不可篡改 = WP11 的 `guard_immutable` + 触发器（试写被拦已验证）；
   待办去重 = `dedupe_key` 部分唯一索引（WP10 已建）+ `ON CONFLICT DO NOTHING`（WP12/WP13 已验证）。
   不需要新设计，只需要把它们**正确地接起来**。
2. **审计是凭据，不是日志**。凭据的意义就是"不可篡改"。
   V2 把它降级成"应用层记得不写 UPDATE" —— 那等于说"这条凭据取决于
   所有人都记得别碰它"，而**没有人能审计"谁改过审计"**。这条必须靠数据库层拦。
3. **`notification_receipts` 只建表，不加端点**。协议 §10 没有 receipts 端点，
   已读标记的语义（是"送达"还是"已读"）需要协议明确（OP-117）。
   在 WP15 替协议决定端点会重蹈 WP12 §3 V4 的覆辙（越界交付要重做）。

**V3 的代价我接受**：GRANT 级账户隔离要等内网多账户（OP-118），
但触发器对所有账户都拦，**比** GRANT 更强，所以这不是"缺了一半"，
而是"本机已经做到了更强的那一半"。

> **请老大确认两件事**（其余我按 V3 直接开工）：
>
> 1. **`GET /work-items` 里"未认领待办"的可见范围** —— 我倾向：
>    `assignee_id = 当前用户` **或** (`assignee_id IS NULL` 且当前用户是该项目成员)。
>    理由是需求 §2.3 明说有"未认领的项目待办"，项目成员要能看到它以便认领/转交。
>    若你希望"未认领只给管理者看"，告诉我。
> 2. **审计的 `actor_kind` 取值域** —— 我倾向 **USER / SYSTEM / SERVICE** 三种：
>    USER 是人（前端操作）、SYSTEM 是系统（定时任务、Worker）、SERVICE 是服务账户
>    （内部调用）。多了会失控，少了无法区分"人做的"与"系统做的"。
>
> 默认按 V3 + 这两个口径执行，理由是上面三条。

### 4.2 两张表：一张是凭据，一张是状态

| 表 | 列数 | 语义 | 关键约束 |
|---|---|---|---|
| `audit_events` | 13 | **凭据**（事实，不可篡改） | 触发器拦 UPDATE/DELETE；`before_hash`/`after_hash` 为 `String(64)`；**没有可存正文的列** |
| `notification_receipts` | 5 | **状态**（送达/已读） | **可变**（`read_at` 会被写）；复合主键 `(user_id, event_id)` |

两张表的约束**正好相反**（一个必须不可改、一个必须可改）—— 这正是数据结构 §11
把它们列成两张表的原因，也是本包不合并它们的原因。

`audit_events` 的三个设计点：

1. **`before_hash` / `after_hash` 复用 WP11 的 `canonical_payload_hash`**（§2.6 约束 1）。
   两处用不同算法会让"审计里的 before_hash 和版本里的 payload_hash 是不是同一份数据"
   **永远没有答案**。
2. **`project_id` 是补列**（数据结构 §11 没列）：§10 要求 `GET /audit-events?projectId=`，
   而靠 `object_id` 反查项目要对每种 `object_type` 做不同 join —— 而 `object_type`
   是开放的。补一列后过滤是**无条件**的 `project_id = :p`。登记 **OP-116**。
3. **`reason` 是唯一可能承载长文本的字段**（运营写的理由）：它**本来就该给人看**，
   但限长 512 并由 CHECK 兜底 —— 允许无限长度会让它变成"顺便把内容塞进来"的通道，
   而那正是"审计泄露正文"最常见的入口。

### 4.3 双层不可变保护：这次**两层都落了**

WP11 的机制原样复用，**两处都做了**：

| 层 | 落点 | 给出什么错误 |
|---|---|---|
| ORM 事件 | `models.py` 模块级 `guard_immutable(AuditEvent)` | 可读领域错误 `ImmutableRecordError` |
| 数据库触发器 | `ddl.py` 复用 `immutable_trigger_ddl` | SQLSTATE `23001`（管住 psql / 回填 / 运维脚本） |

> **本包实测踩到过**：一开始只写了 `ddl.py` 的触发器、漏了 `models.py` 的
> `guard_immutable`，于是 ORM 路径抛的是 `RestrictViolation` 而不是领域错误。
> 功能上"拦住了"，但**两层各有职责**（可读错误 vs 全路径兜底）。见 §5 D1 / ISS-42。

### 4.4 待办去重与完成：靠数据库，不靠自觉

| 点 | 落地 |
|---|---|
| **去重** | `dedupe_key` **部分唯一索引** `uq_work_items_open_dedupe`（`WHERE state='OPEN' AND dedupe_key IS NOT NULL`，WP10 已建）+ `ON CONFLICT DO NOTHING` + 回查 |
| **完成** | `OPEN → DONE` 的**条件 UPDATE**（`WHERE state='OPEN'`），靠 `rowcount` 判定 |
| **幂等** | 已 DONE 再次完成 → `resolved=false`（**不报错**） |
| **不自动通过业务对象** | 只置待办为 DONE，**不**改任何业务对象状态（协议 §10 原句） |
| **幂等命中不写审计** | 只有 `rowcount==1`（真的改了）才写审计 —— 否则重试会留下假凭据 |
| **可见范围单一来源** | 列表与完成**共用 `_may_see_item`**；非成员 → **404**（不是 403，防存在性枚举） |

`ON CONFLICT` 的目标是**部分唯一索引**，因此 `index_elements=["dedupe_key"]`
必须同时带 `index_where`（`state='OPEN' AND dedupe_key IS NOT NULL`）才能命中 ——
否则 `ON CONFLICT` 不会识别这个索引。

### 4.5 游标：非法即拒绝，不静默降级

`_encode_anchor` / `_decode_anchor`（`api.py`）把 `(created_at, id)` 编成 `|` 分隔的
不透明游标。**非法游标返回 422，不静默当第一页** —— 与 WP14 的 `Last-Event-ID`
（非法当新连接）**刻意相反**。判据是：**静默降级会不会造成错误数据**。
游标当第一页会让客户端从头无限翻页（永远拿第一页）；`Last-Event-ID` 当新连接
最坏只是多收几条它本来就可见的事件。见 `_decode_anchor` 的 docstring。

### 9.2 本工作包**关闭**的既有待定项

**OP-85 关闭**（`work_items` 是否需要 `lock_version`）。

§2.6 的结论原文：

> `work_items` **不需要 `lock_version`** —— 因为完成待办用的是"状态机 + 条件 UPDATE"
> （`WHERE state='OPEN'` + `rowcount` 判定），不是"读-改-写"那种需要携带旧值的场景。
> 并发由条件 UPDATE 的原子性保证，不需要乐观锁版本号。

这条也正是"为什么 `resolutions` 不需要幂等键"的同一理由：
**幂等由状态本身承担**（重复调用 `rowcount=0`，返回"已完成"而非报错）。
`work_items` 与 `jobs` 是两类不同的幂等来源，不能一概而论。

> 本包实现里确实**没有**给 `work_items` 加 `lock_version`，也没有 ETag —— 与结论一致。

但协议 §10 没有"取消待办"端点，本包也没有实现任何把它写入的路径
