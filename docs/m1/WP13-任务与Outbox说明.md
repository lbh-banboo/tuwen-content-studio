## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让"用户点了提交"与"任务真的被执行"这两件事，在**进程崩溃、队列停机、消息重复投递**这三种现实故障下仍然一致。

本质是**跨边界的一致性**：业务数据写在自己的数据库事务里，消息要通过另一个系统（RabbitMQ）传递。这两者**没有原子性** ——

- 先提交数据库、再发消息：发消息前进程崩了 → **任务丢了**，用户在界面上看到"已提交"，系统里没有任何东西会执行它；
- 先发消息、再提交数据库：消费方拿到消息时业务数据还没提交 → **任务执行了但查不到数据**。

**Outbox 模式**就是把"发消息"这个动作也变成一条数据库记录（同一个事务里写），再由一个独立的派发器把它搬出去。这样"要么都在、要么都不在"，而在"搬出去"这一步崩溃只会导致**重复投递**，不会丢 —— 于是问题从"不能丢"转化为"**重复也不能重复执行**"。

**这才是本包验收标准的两半**："消息失败仍恢复"（不丢）+ "重复投递不重复执行"（幂等）。两半都必须做到，只做一半都不算过。

### 1.2 核心用户是谁？

**不是人，是系统。** 本包是基础设施，消费者是其他工作包的代码：

| 消费者 | 怎么用 |
|---|---|
| WP12（已完成） | 已在完成上传时同事务写 `outbox_events(file.uploaded)` —— 本包给它配派发器 |
| WP17 文档解析 | `POST /files/{id}/parse-jobs` 建 job；消费 `file.uploaded` 事件 |
| WP16 模型网关 | 用 `jobs` 承载外部模型调用；`WAITING_PROVIDER` / `WAITING_RECONCILIATION` 状态由它驱动 |
| WP25 费用 | 用 `job_id` 关联账本条目 |
| WP32 扩产批产 | 用公平排队与部分失败恢复 |
| WP14 SSE | 用任务状态变化产生界面事件（`domain_events` 属 WP14） |

**"没有人类用户"这个判断很重要**：它决定了本包**不提供任何 HTTP 端点**（与 WP11 同）。
验收只能打服务层 —— 但本包的验收项（"重复投递不重复执行"）本来就只能在服务层验证，
用 HTTP 去验证一个没有 HTTP 消费者的东西，验证的是不存在的东西。

### 1.3 最小 MVP 应包含哪些功能？

严格按研发计划 04 §WP13 的 **4 个切片**：

| # | 切片（原文） | 要做到什么 |
|---|---|---|
| F1 | 事务写 job 与 outbox；验证**数据库提交后队列停机不会丢任务** | 提交与事件在同一事务；派发器停机时事件躺在表里，恢复后仍会被搬出去 |
| F2 | **派发器发布确认**；验证**标记前崩溃会重复投递但不会重复生成** | 先 publish、成功后才标 `published_at`；重复投递由消费侧幂等吸收 |
| F3 | **Worker 租约与 fence**；验证**旧 Worker 晚返回不能覆盖新执行状态** | `lease_owner` / `lease_until` / `fence_token`；写结果时必须匹配当前 token |
| F4 | **UNKNOWN 外部调用恢复**；验证网络超时后**先查询再决定重试** | job 层提供 `WAITING_RECONCILIATION` 状态与"不允许自由重试"的规则 |

**F4 的边界**：`provider_calls` 表属 WP16（数据结构 §11 把它与 `providers` / `model_profiles` 放在一起，且 WP16 的验收是"未知调用状态不盲重试"）。本包做到 **job 层的语义**：任务进入 `WAITING_RECONCILIATION` 后**不因租约过期而变成可自由重试**，恢复路径必须显式"先查询"。

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **本机没有 RabbitMQ** | 内网才有 3 节点 RabbitMQ（研发执行计划 §5）。派发器必须**抽象**，否则本机跑不通、也无法测试 |
| 2 | **谁调用 `claim`（本机没有 Worker 进程）** | 计划里 Worker 是独立进程分组。本机要有可手动触发的入口，否则 F3 只能靠"假装有 Worker"来测 |
| 3 | **`jobs.kind` / `queue` 的取值域未定义** | §11 只列了列名。没有受控取值域，"kind 拼写不同"会让同一类任务被分成两种，而**不会报错** |
| 4 | **租约时长与续租间隔未定义** | 太长 → 崩溃后任务卡住；太短 → 长任务被误抢。这是必须显式取值的参数 |
| 5 | **`fence_token` 的初值与递增方式未定义** | §13.4 只说"增加"。是实现细节但**语义关键**：它必须是单调的，否则"旧 Workers 晚返回"检测不出来 |
| 6 | **`job_dependencies` 是否在 MVP** | 4 个切片**都没提 DAG**。它在 §11 存在，但真正的消费者是 WP32（部分失败恢复）。建了不用 = 死表 |
| 7 | **幂等记录保留多久** | 协议 §1.3：一般响应缓存**至少 7 天**；**生产任务以数据库业务标识永久关联**。两种保留期必须区分，否则缓存过期会导致同一任务再次计费 |
| 8 | **派发器在多实例下会不会重复派发** | API 是双实例。两个派发器同时捞同一批事件 → 重复投递（可被幂等吸收，但要显式设计而不是"碰巧没事"） |
| 9 | **`usage_pending` 字段的用途** | §11 列里有它但没有解释。它指向 WP25 的费用对账（"费用未结"），本包只负责在合适时机置位 |

### 1.5 哪些功能现在不该做？

| 砍掉 | 为什么 |
|---|---|
| **RabbitMQ 真实接入** | 本机无 MQ。派发器抽象成 Protocol，内网实现留待接入；本机用"直接投递给注册的 handler"验证全部语义 |
| **`provider_calls` / `providers` / `model_profiles`** | 属 WP16。F4 只做 job 层语义，不建表 |
| **`domain_events` / SSE** | 属 WP14。WP13 只负责让任务状态变正确，界面事件由 WP14 消费状态产生 |
| **`audit_events`** | 属 WP15 |
| **`job_dependencies`（DAG）** | 4 个切片都没要求；真正的消费者是 WP32。**建了不用就是死表**（登记为待定项） |
| **独立调度器进程 / 定时轮询** | 本机提供一个可反复调用的派发函数（幂等），调度由部署层决定 —— 与 WP12 的 TTL 回收同一做法 |
| **`runtime_settings` 配置化** | 属 WP24。租约时长等先做常量 + 注释说明取值理由 |
| **费用估算 / 预算预占 / 账本** | 属 WP25 |
| **通用幂等中间件（挂到所有写端点）** | 本包只提供 `idempotency_records` 的读写服务。挂哪些端点由各包决定（WP12 的 OP-94 届时闭合） |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **fence 校验写错**（旧 Worker 的结果覆盖新状态） | 🔴 高 | 执行了两遍、后一遍的结果是旧的 —— **静默**，账面看不出（与 WP11 的"版本被改过"同类） | 写结果的 UPDATE 必须带 `AND fence_token = :token`，靠 `rowcount` 判定；专门测"旧 Worker 晚返回" |
| R2 | **租约过期 ≠ 供应商停工** | 🔴 高 | 以为可以重试，实际外部调用还在跑并**计费** | §13.4 原文明写："租约只防本地并发，不保证供应商已停工；UNKNOWN 不因租约过期变成可自由重试"。用 `WAITING_RECONCILIATION` 把这条写进状态机 |
| R3 | **重复投递导致重复执行** | 🔴 高 | 同一任务被两个 Worker 执行两遍 | 租约（同一时刻只有一个）+ fence（晚到的写回被拒）+ 幂等记录（跨投递去重），三层 |
| R4 | **派发器在多实例下重复派发** | 🟠 中 | 重复投递（可被吸收，但放大负载） | 用 `FOR UPDATE SKIP LOCKED` 批量领取 + 一次事务内标记，避免两个实例捞同一批 |
| R5 | **幂等记录无界增长** | 🟡 中 | 表越来越大 | 区分两种保留期（一般 7 天 / 任务关联永久），过期清理可手动触发（同 WP12 的 TTL） |
| R6 | **`jobs` 成为热点表** | 🟡 中 | 领取任务的查询变慢 | 索引 `(state, next_run_at)` 按领取条件建；`fence_token` 用 bigint 避免溢出 |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（数据结构 02 §11 的 4 张表）：

| 表 | 角色 |
|---|---|
| `jobs` | 任务的**业务状态权威**（原始文档明写）。租约字段也在它上面 |
| `job_attempts` | 每次执行的尝试（含 `fence_token`、`worker_id`）—— "迟到 attempt 不可覆盖新结果" |
| `idempotency_records` | 通用幂等（协议 §1.3）：同 key 同 hash 返回原结果、同 key 不同内容 409 |
| `outbox_events` | **WP12 已建**。本包加派发器（消费它），不重复建 |

**接口**：**无 HTTP 端点**。对外是 Python 服务函数：
`enqueue_job()` / `dispatch_outbox()` / `claim_job()` / `complete_job()` / `fail_job()` / `request_cancel()` / `reconcile_job()`。

**后端分层**：

```text
modules/jobs/
  models.py        # 3 张表（jobs / job_attempts / idempotency_records）
  repository.py    # 存储访问（含 SKIP LOCKED 领取、fence 条件写）
  service.py       # 业务规则（状态机、租约、幂等）
  dispatch.py      # ★ Outbox 派发器 + 投递通道抽象
  handlers.py      # ★ 任务处理器注册表（本机用 echo 假供应商）
platform/          # 复用 concurrency / errors / database
```

**前端**：无（apps/ 未建立）。任务进度由 WP14 的 SSE 推送。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**把"发消息"降级成"写一行数据"，从而让"提交业务数据"与"告诉别人去做事"变成一个原子动作；再用租约 + fence 保证"同一个任务不会被两只手同时做、也不会被一只晚到的手写坏"。**

### 2.2 用户画像

**系统**。特征：

- 调用方**不是**浏览器，而是其他模块的 Python 代码（因此不需要 URL 设计，需要**清晰的函数契约**）；
- 会被**多个进程**同时调用（API 双实例 + Worker 分组）；
- 崩溃是**常态而非异常**（进程重启、RabbitMQ 停机都是计划内会发生的事）。

### 2.3 核心功能清单（MVP）

| # | 功能 | 验收映射 |
|---|---|---|
| F1 | 事务写 job + outbox（`enqueue_job`） | 「消息失败仍恢复」 |
| F2 | 派发器（先发布、后标记；重复投递安全） | 「重复投递不重复执行」 |
| F3 | 租约与 fence（`claim_job` / `complete_job`） | 「旧 Worker 晚返回不覆盖新状态」 |
| F4 | UNKNOWN 恢复（`WAITING_RECONCILIATION`） | 「先查询再决定重试」 |
| F5 | 通用幂等（`idempotency_records` 读写 + 409） | 协议 §1.3；闭合 WP12 的 OP-94 |
| F6 | 任务处理器注册表 + 假供应商 handler | G1 的"假供应商任务" |

### 2.5 砍掉清单

见 §1.5（8 项）。

### 2.6 技术风险评估（含应对）

见 §1.6。补充三条**必须在编码前定死**的实现约束：

1. **fence 校验必须写在 UPDATE 的 WHERE 里**（`AND fence_token = :token`），不能用"先查再判再写" —— 那正是本包要防的竞争。
2. **派发器的"发布"必须幂等**：同一事件被投递两次时，处理器要能识别并跳过（靠幂等记录或业务侧的唯一约束）。
3. **`SKIP LOCKED` 用于领取**：多实例同时领取时不能互相阻塞，也不能领到同一批。

## 3. 阶段 3：多版本方案

方案的**分野是"本机没有 RabbitMQ 怎么办"，以及"要不要建 jobs"**。

| 方案 | 定位 | 内容 |
|---|---|---|
| **V1 只做 Outbox** | 1~2 天 | 建派发器消费 `outbox_events`，**不建 jobs**。任务只作为事件存在 |
| **V2 建表但无租约** | 不推荐 | 4 张表 + 派发器 + 幂等，但**不做租约与 fence**（"单 Worker 就够"） |
| **V3 4 张表 + 派发器 + 租约/fence + 幂等（推荐）** | 本包交付 | 完整覆盖 4 个切片；派发通道抽象；不加 HTTP 端点 |
| **V4 完整版** | 生产级一次性到位 | V3 + `job_dependencies` DAG + 调度器进程 + RabbitMQ + `provider_calls` + `domain_events` + 审计 |

### 方案 V1 —— 只做 Outbox（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 只实现派发器，把 `outbox_events` 里的 `file.uploaded` 搬出去交给注册的 handler |
| 优点 | 一天能跑通；WP12 的事件终于有人消费了 |
| 缺点 | **验收的两半都过不了**：①"提交后消息失败仍恢复"只验证了事件的持久性，没有任务可恢复；②"重复投递不重复执行"需要任务的状态与租约来表达，光有事件无处附着 |
| 风险 | 交付一个"看起来接上了"但**没有任何东西被执行**的包 |
| 结论 | ❌ **否决**。`jobs` 是验收的主体，不是可选项 |

### 方案 V2 —— 建表但无租约（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 4 张表 + 派发器 + 幂等；`jobs` 只有状态，没有 `lease_*` / `fence_token` |
| 优点 | 少一半复杂度；单 Worker 环境下确实够用 |
| 缺点 | ① 切片 F3 的验收**直接失败**（"旧 Worker 晚返回不能覆盖新状态"根本没有机制）；② 部署形态是 **Worker 分组**（研发执行计划 §5），多 Worker 是选定架构而非将来才有的；③ 租约字段在 §11 表定义里**本来就有**，不实现等于表结构假声明 |
| 风险 | 典型的技术债：上线后一旦扩到两个 Worker 就出现"结果被旧执行覆盖"，而那种缺陷**静默**（数值对不上才能发现） |
| 结论 | ⚠️ **不推荐**。省掉的正是本包唯一的并发正确性 |

### 方案 V3 —— 4 张表 + 派发器 + 租约/fence + 幂等（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | `jobs` / `job_attempts` / `idempotency_records` 三张新表（`outbox_events` 已由 WP12 建）；派发通道抽象成 Protocol（本机实现不依赖 MQ）；租约 + fence 按 §13.4 实现；`WAITING_RECONCILIATION` 承载 UNKNOWN 语义；**无 HTTP 端点** |
| 优点 | ① 4 个切片**逐一覆盖**，验收两半都有专门测试；② **本机能完整跑通并测试**（派发通道抽象后不依赖 RabbitMQ）；③ 边界清晰：`jobs` 上的 `lease_*` / `fence_token` 本就在 §11 定义里，不是自创；④ 幂等表同时闭合 WP12 的 OP-94 |
| 缺点 | ① 派发通道的本机实现与内网实现语义可能有差异（缓解：Protocol 只定义"投递 + 确认"两个动作，RabbitMQ 能直接表达）；② 没有调度器进程，需部署层自己定时调用（缓解：派发函数幂等且可反复调用，与 WP12 的 TTL 回收同一做法） |
| 风险 | 若内网 RabbitMQ 的投递语义（confirm / 重投）与 Protocol 假设不符，需要调整实现。评估：**低** —— 协议只要求"至少一次投递 + 可确认"，这是 MQ 的公共子集 |
| 适合场景 | 本包的实际处境：验收含并发正确性、本机无 MQ、下游（WP17/WP16）依赖任务基础设施 |
| 结论 | ✅ **推荐** |

### 方案 V4 —— 完整版（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | V3 + `job_dependencies` DAG + 调度器进程 + RabbitMQ 接入 + `provider_calls` + `domain_events` + `audit_events` |
| 优点 | 一次性到位 |
| 缺点 | **严重越界**：`provider_calls` / `providers` 是 WP16 的核心（出网策略、未知状态不盲重试）；`domain_events` 牵连 SSE（WP14）整套设计；`audit_events` 属 WP15；`job_dependencies` 的真正消费者是 WP32。在 WP13 建这些表 = 用 WP13 的假设替后面 4 个包做决定 |
| 风险 | 表建了但语义是错的，后续包要迁移 + 回填。**本项目已有先例**（WP11 §3 与 WP12 §3 都讨论并否决过越界交付） |
| 结论 | ❌ 不选。**边界不按"表在哪一章"划，按"有没有设计空间"划**：`lease_*` / `fence_token` 是 §11 已在 `jobs` 行里写死的列（无设计空间）→ 本包做；`provider_calls` 的"未知状态不得直接另发计费请求"是**一整套策略**（有设计空间）→ WP16 做 |

### 选择与理由

**选 V3。** 三条理由，按权重排序：

1. **验收的两半都只能靠"任务 + 租约"表达**。"重复投递不重复执行"需要任务身份与执行互斥；"消息失败仍恢复"需要任务在事件之外独立存在。只做事件（V1）或不做租约（V2）都缺一半。
2. **本机必须能完整验证 4 个切片**。派发通道抽象是这个目标的唯一途径 —— 与 WP12 的存储适配器同一手法，且同样的理由：**未经验证的实现比"明确未实现"更危险**。
3. **`jobs` 的租约字段不是自创**。数据结构 §11 的 `jobs` 行里明写了 `lease_owner?` / `lease_until?` / `fence_token bigint`；§13.4 专门定义了它们的语义。本包只是把它实现出来。

**V3 的代价我接受**：没有真实 MQ、没有调度器进程、没有 DAG。这三项都登记为待定项（OP-106 / OP-109），且内网接入时**不需要改本包的表结构与服务语义**（只加一个 Protocol 实现 + 一个定时调用）。

> **请老大确认一件事**（其余我按 V3 直接开工）：
> **派发通道的抽象方式** —— 我打算做成 `Dispatcher` Protocol（`publish(event) -> bool`），
> 本机实现是"直接调用注册的 handler"（同进程、同步），内网实现是 publish 到 RabbitMQ。
> 若你希望本机也用真实 MQ（比如本地起一个 RabbitMQ 容器），告诉我，我改成那样 ——
> 但那需要 Docker，而本机 Docker 链从未跑通过（OP-74/OP-75）。
>
> 默认按 Protocol 抽象执行，理由是上面第 2 条。

### 4.2 三张表

| 表 | 列 | 关键约束 |
|---|---|---|
| `jobs` | 21 | `UQ(idempotency_scope, idempotency_key)`；`CHECK (lease_owner IS NULL) = (lease_until IS NULL)`；`CHECK state IN (9 状态)` |
| `job_attempts` | 10 | `UQ(job_id, attempt_no)`；`CHECK state IN (4 状态)`；FK → `jobs` **CASCADE** |
| `idempotency_records` | 10 | `PK(scope, key)`；`CHECK state IN (IN_PROGRESS, COMPLETED)` |

共 **6 个索引**（2 个部分索引）、**7 个 CHECK**。逐条核对见 `evidence/m1/wp13-jobs.log`。

**两个部分索引的 WHERE 必须保住**：
`ix_jobs_lease_until ... WHERE lease_until IS NOT NULL`（否则回收扫描退化全表）；
`ix_idempotency_expires_at ... WHERE expires_at IS NOT NULL`（否则**永久保留的幂等记录
会被清理路径扫到并误删** —— 那意味着"同一任务在第 8 天再次计费"）。

**`job_attempts` 的外键是 CASCADE**（与 WP11 的 `version_nodes` 的 RESTRICT 相反）：
任务不是"历史事实"，它可以从属删除；而版本是历史事实，不允许被级联删掉。

### 4.3 四个切片的实现要点

**F1｜事务写 job + outbox**：`enqueue_job` 在**同一事务**里插 `jobs` 与
`outbox_events`。`insert_outbox_event` **刻意不加 commit** ——
由外层统一提交，这样"任务落库"与"事件落库"要么都在、要么都不在。

**F2｜派发器发布确认**：顺序是**先发布、成功后标记**。
倒过来（先标记）会在"标记后、发布前"的窗口里丢事件；
正过来则只会**重复投递**，而重复由幂等与状态机吸收。
退避是 `5s × 2^attempts`（上限 600s）——投递失败通常意味着下游不可用，
固定间隔会把重试次数打满、日志刷爆。

**F3｜租约与 fence**：三层保护。

| 层 | 挡什么 |
|---|---|
| 状态 + 租约 | 同一时刻只有一个 Worker 持有它（`FOR UPDATE SKIP LOCKED` 领取） |
| `fence_token` 条件写回 | 旧 Worker 的**晚到结果**不被采纳 |
| `idempotency_records` | 同一个业务请求重试时不会新建任务 |

**所有权转移必须让 fence 失效** —— 这条是本包审查中最有价值的一条
（见 §5.1 的 D1）：被抢占要递增，**被回收也要递增**。

**F4｜UNKNOWN 恢复**：外部调用状态未知 → 任务进 `WAITING_RECONCILIATION`。
它**不因租约过期变成可自由重试**（§13.4）；回收器把失联任务送进这个状态，
而 `reconcile_job` **禁止**把它重排回 `QUEUED` ——
要重试必须**以新的幂等键新建任务**，让"重试"成为一次显式的业务决定。

### 4.4 一个关键设计选择：执行路径不依赖 MQ

`enqueue_job` 会写 outbox 事件（协议要求"事务写 job 与 outbox"），
但 **Worker 的执行是通过轮询 `jobs` 表领取的，不是消费 MQ 消息**。

两条理由：

1. **本机没有 RabbitMQ**。若执行依赖 MQ，四个切片在本机一个都验证不了 ——
   而其中三条（不丢 / 不重复 / 不被旧 Worker 覆盖）恰恰只能在能跑起来的环境里验证。
2. **更稳健**：`jobs` 表本身就是"业务状态权威"（§11 原文）。
   让它成为执行的事实来源，MQ 就退化为"加速与解耦"的可选件。
   反过来若 MQ 是必需品，**MQ 停机就等于系统停产** ——
   而本包验收的第一句正是"队列停机不会丢任务"。

### 4.5 投递通道抽象

`DeliveryChannel` Protocol 只有一个方法 `publish(event) -> bool`。
本机实现 `InProcessChannel` 直接调用注册的处理器；
内网实现将 publish 到 RabbitMQ。

**两者的"确认时间点"不同**（broker 收到 vs 处理器跑完），
已在 `InProcessChannel` 的 docstring 里用表格列出。
共同点是"**至少一次投递**"—— 这正是 4 个切片依赖的唯一性质。

### 5.1 三条 MAJOR 的共同特征：**"我改了状态"不等于"我改了所有权"**

| 发现 | 建立在什么信号上 | 为什么这个信号不够 |
|---|---|---|
| D1 | "状态改了，所以旧 Worker 应该写不进来" | **凭据（fence）才是所有权的载体**。状态是结果，fence 是凭证 —— 不递增凭证，旧持有者仍然是"合法"的 |
| D2 | "记录是 IN_PROGRESS，所以这是重放" | 状态表达"现在处于哪一步"，**不表达"是不是我创建的"**。判定首次必须用 `created` 这个来源信号 |
| D3 | "任务要么在跑、要么在等外部" | 状态机有 9 个状态，白名单只写了 2 个 —— **状态机的表达分散在三处**（models 常量 / §12 文档 / 本函数），三处只对齐了两处 |

与 WP11/ISS-25、ISS-27 与 WP12/ISS-28~31 同源：**把判断建立在了不等于事实的信号上**。

> **可复用的自检**：凡是"我改了 X 所以 Y 就成立了"的判断，再问一句 ——
> **Y 真的跟着 X 走了吗？还是它有自己的载体？**

### 5.2 D1 值得单独说：fence 的语义边界

本包的切片 3 原文是"旧 Worker **晚返回**不能覆盖新执行状态"，
直觉上它只在"被别人抢走"时成立。但 D1 暴露了另一个入口：**被回收器接手**。

两者都是**所有权转移**，都必须让旧凭据失效。
把 fence 只在 `claim_job` 里递增、不在回收里递增，等于承认
"回收是一种不算转移的转移"—— 而代码里并没有这种语义。

### 5.3 第三遍：明确记录"检查过但没问题"的点

- **`FOR UPDATE SKIP LOCKED` 真的不重领吗**：验证过（2 线程 × 4 任务，

- **派发顺序**：验证过（模拟"发布成功但事务回滚"，事件仍是未发布、

- **退避生效**：验证过（失败后立刻再派发，`scanned == 0`）；
