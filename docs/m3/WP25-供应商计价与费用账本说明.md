## 0. 本包的一句话定位

**把"这次要花多少钱"从"事后才知道"变成"事前可预占、事中不超支、事后可对账"。**

WP16 已经让系统**能调外部模型**，并且把 `usage` / `cost` **透传**出来了 —— 但它**刻意不落账**（`gateway/models.py` 第 5 张表那一行的原话："费用体系是**一整套**策略（预估/预占/结算/退款/汇率），不是一个列"）。WP13 也已经把 `job_attempts.usage_pending` 在四种情形下置位 —— 但它明确写着"消费属 WP25"。

所以本包要做的不是"加一列 cost"，而是**接住两条已经修好的管道**，并把它们变成**有并发约束的账**。

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让**外部调用的钱**在**花出去之前**就被约束住，在**花出去之后**能被对上账 —— 因为外部模型调用**一旦发出就可能已计费**，而"重试"等于"再买一次"。

拆开是四个彼此独立、但必须同时成立的问题：

| # | 问题 | 若不做会怎样 |
|---|---|---|
| P1 | **钱要在花之前拦住，不能花完再报** | 一批 50 篇跑完才发现超预算 ⇒ 钱已经花了。**预算是"承诺"，不是"统计"** |
| P2 | **并发下预占不能超过承诺额** | 两个请求同时读到"还剩 100 元"，各自预占 80 ⇒ 合计 160。**账面两条都对，合计超 60%**，且**系统不报错** |
| P3 | **金额必须只有一种表示** | 全仓此刻**零 `Decimal`**（本包实测：`grep -rn "Decimal\|Numeric"` 在 `services/backend/src/rednote/` 下**零命中**）。金额精度在本仓是**空白** —— 一旦让 `float` 混进来，`0.1+0.2 != 0.3` 这类问题会散落在预占、结算、对账三处 |
| P4 | **"未结用量"必须能对上账** | WP13 在四种情形下置了 `usage_pending=true`（失联、处理器抛异常、暂停核对、UNKNOWN 结果）。**若无人消费它，这些标记就是一堆永远不消的旗子** —— 真金白银的差异就此无声消失 |

**为什么 P2 与 P3 必须同包做**：预占是**比较**（`committed + reserved + delta <= limit`）、结算是**加减**、对账是**求和再比较**。三处都要求"同一个数只有一种写法"。若金额表示不先定死，则"并发不超承诺"这条验收**测的是浮点比较的运气**，不是业务不变量。

**本包的产出边界**：它能回答"这个项目还剩多少钱、这次调用该预占多少、账上实际花了多少"。它**不发任何外部请求**（那是 WP16 的适配器）、**不创建任务**（WP13）、**不生成内容**（WP26+）。

### 1.3 最小 MVP 应包含哪些功能？

按"四块拼图"组织（对应 §1.1 的 P1/P2/P3/P4）：

| # | 功能 | 对应问题 | 验收映射 |
|---|---|---|---|
| F1 | **金额纯函数层**（`money.py`）：定点表示、量化、加减乘、比较、序列化 | P3 | AC-26 三类核对的地基 |
| F2 | `pricing_versions` **供应商计价版本**（不可变）+ 单价解析 | P1 | 预估的输入 |
| F3 | `cost_estimates` **费用预估**（数量 × 单价，读 WP24 的生效数量上限） | P1 | AC-26「估算」 |
| F4 | `project_budgets` **账面**（限额 / 已结算 / 已预占）+ `budget_reservations` **预占明细**（状态机） | **P2（本包命门）** | **W10「预算并发预占测试」** + 异常矩阵第 2 项 |
| F5 | `usage_ledger` **费用账本**（追加式不可变） | P4 | AC-26「账单」 |
| F6 | **对账**：消费 `job_attempts.usage_pending` + 网关 `usage`/`cost` → 结算或挂账 | P4 | AC-26「重试核对」；闭合 **OP-108** / **OP-132** |

**F1 必须先做、且做成纯函数**：它是本包唯一有数学性质的部分，做成纯函数才能穷举验证（与 WP24 §1.3 对 `allocation.py` 的同一判断）。

**F4 是本包唯一有并发语义的部分**，也就是验收标题本身。"预算并发不超承诺"这句话的难点不在"预占"，而在**"承诺"是一个跨请求、跨实例的不变量** —— 它必须由**单条原子语句**保证，不能由"先查后写"保证（WP12 已验证过一轮，见 §1.4 第 4 条）。

### 1.4 描述有哪些疏漏应当补充？理由是什么？

> 下面 6 条**来自本包勘察出的磁盘实况**（不是推演），4 条来自**上游已踩过的坑**。

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **全仓零金额类型 —— 精度口径是本包从零定义的** | 实测：`grep -rn "Decimal\|Numeric" services/backend/src/rednote/ --include="*.py"` **零命中**（`__pycache__` 除外）。全仓唯一提到金额的地方是 `gateway/types.py:238` 的 `cost_amount: str \| None` —— **它是 `str`，不是数字**。协议把金额当**十进制定点字符串**传输，本包必须与之对齐：**存储用 `Numeric(20,8)`、Python 侧一律 `Decimal`、进出 JSON 用规范化字符串**。选 8 位小数是为了能表达"每千 token 的单价"（token 级计价天然在 1e-6 量级），同时避免引入浮点 |
| 2 | **`ErrorCode.BUDGET_EXCEEDED` 已定死但零消费者** | 实测：`errors.py:66` 定义、`:87` → **422**、`:117` → "项目预算不足，无法提交该任务。"；而全仓消费点**只有** `test_errors.py:62` / `test_contract.py:57` / `contracts/openapi.json:2555` —— **零业务代码引用**。协议把错误码**逐条照抄不多不少**（`errors.py` docstring 原话），且契约里**零费用端点**（实测 55 paths 中无 cost/budget/ledger/pricing/usage 前缀）⇒ 这说明**协议预期有费用端点，只是没有包认领**。本包是它的落点 |
| 3 | **`usage_pending` 的四个置位点全在上游，本包只消费** | 实测四处：`jobs/repository.py:288`（失联 ABANDONED 回收，"失联一律置 true"）、`jobs/service.py:385`（另有）、`:476`（处理器抛异常）、`:505`（`pause_for_reconciliation`）；`gateway/handlers.py:90`（UNKNOWN 结果）。**本包一行都不改它们** —— 改上游等于跨包接缝改动。判据的权威定义在 `gateway/handlers.py:104`：**`_usage_pending` = "有过用量，且计费未确认"**（`bool(result.usage) and result.cost_status != COST_CONFIRMED`）。本包的对账判据**必须与它同源**，不能自己另写一个 |
| 4 | **预占在本仓已有两次成功先例，不要重新发明** | ① `files/repository.py:95` `reserve_quota` —— 条件 `effective + reserved + :delta <= limit` **写在本条 UPDATE 的 WHERE 里**（无读写窗口），`release_reservation` 带 `WHERE reserved_bytes >= :delta` 防"还多了"，`finalize_reservation` 一条语句做**双检查**（归还量够 + 转换后不超限）；② `upload_sessions` 的 docstring 原话"**预占与释放必须成对**"，靠**状态机 + 条件 UPDATE** 保证"每次释放只允许一次"（同一请求到两次，第二次 `rowcount` 为 0）。**本包的 `budget_reservations` 就是 `upload_sessions` 的同构体**，`project_budgets` 就是 `quota_accounts` 的同构体 |
| 5 | **`COST_LEDGER` 明确在"禁止出网"清单里** | `gateway/types.py:105` 的 `FORBIDDEN_EGRESS_DATA_CLASSES` 含 `"COST_LEDGER"`。这**不是提示而是硬约束**（ADR-10 E-5）：账本相关的**任何接口都不得出网**，包括"把账本摘要发给模型让它分析"这种看起来无害的用法 |
| 6 | **不可变机制与 ETag 机制都是现成的，不要另造** | `platform/immutability.py`（184 行）：`guard_immutable(*models)`（ORM 层）+ `immutable_trigger_ddl(table)`（DDL 层，复用共用函数 `rednote_reject_mutation()`），错误码 `IMMUTABLE_RECORD_SQLSTATE = "23001"`；`platform/concurrency.py`：`build_etag` / `build_immutable_etag(resource_id, payload_hash)` / `require_if_match`。`usage_ledger` 应与 `audit_events` / `version_nodes` / `gateway_egress` **同级**（追加式不可变），而不是新造一套 |

### 1.5 哪些功能现在不该做？

| 砍掉 | 为什么 |
|---|---|
| **真实供应商单价数据** | 本机无供应商合同、无报价单（OP-04/WP04 未结论）。"用哪个供应商、单价多少"是 WP04 的结论，现在填等于用猜测约束未来。本包只**建表与机制**，`pricing_versions` 的初始数据走运营录入 |
| **汇率换算的实际数据源** | 汇率需要外部汇率源 ⇒ **那是一条新的出网通道**，而 `COST_LEDGER` 在禁止出网清单里（§1.4 第 5 条）。本包只**支持多币种存储**（`pricing_versions.currency`），**不做自动换算**，跨币种汇总属 WP43 报表 |
| **退款的自动执行** | 退款需要与供应商对账确认，而"确认"是本包**唯一不能自动化**的一步（§1.6 R4）。`usage_ledger` 支持**冲正分录**（负数、必须引用被冲正的分录），但触发它的是**人工核对动作** |
| **费用端点的完整 UI** | 33 页原型里没有费用页。本包只提供后端数据源；接线属"前端接后端"那条线 |
| **`/admin/providers` 那类供应商管理端点** | 协议 §10 有它们但**无包认领**（WP16 已登记 OP-123）。本包同 WP16：只建 `pricing_versions` 表，不建管理端点 |
| **预算的审批流** | 企业侧需求未到（无 OP 登记）。"谁批预算"属 M4 管理面，不在 M3 |
| **按 token 的实时计量** | 用量来自供应商返回（`CapabilityResult.usage`），本包**不自己数 token** —— 自己数是第二真值来源，与供应商账单必然分叉 |
| **`batches` 表相关的成本归集** | 真正的消费者是 WP31/WP32（与 WP24 §1.5 同一判断：建了不用就是死表）。本包的预估粒度是**项目 × 批次类型**，不是"某个 batch 花了多少" |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **并发预占超过承诺额** | 🔴 高 | 预算是**对外承诺**，超了就是违约。且"先查后写"在 API 双实例（ADR-11 C8）下**必然**漏 —— 两个实例各自的本地判断都对 | 条件 `committed + reserved + delta <= limit` **写进单条 UPDATE 的 WHERE**（与 `files/repository.py:95` 同款）+ `CHECK` 兜底 + **`project_budgets` 无 `lock_version`**（乐观锁会引入多余的失败分支，见 `quota_accounts` docstring 原文）；判据：**N 线程并发预占，断言成功数 × 单笔 <= 限额且账面不变量恒成立** |
| R2 | **`float` 混入金额运算** | 🔴 高 | 精度静默丢失，且**偏差在对账时才显形**（此时已无法回溯是哪一次丢的） | ① 存储 `Numeric(20,8)`（PostgreSQL 任意精度定点，非浮点）；② Python 侧唯一入口 `money.py`，**不允许 `float` 出现在任何金额函数签名里**；③ 判据：**全仓 grep 金额相关模块零 `float()` 调用**（结构性检查，与 ADR-13「无硬编码残留」同一手法） |
| R3 | **预占释放不成对（重复释放 / 漏释放）** | 🔴 高 | 重复释放 ⇒ 账面虚高、钱"变多了"，**且不报错**；漏释放 ⇒ 钱被永久占用。**两者都是静默的** | `budget_reservations` 状态机 + 条件 UPDATE（`WHERE state IN (持有预占的状态)`，改成功才算还了 —— `upload_sessions` 已验证此形态）；`release` 语句带 `WHERE reserved_amount >= :delta` 防"还多了" |
| R4 | **对账把"未结"当"已结"（或反之）** | 🔴 高 | 前者 ⇒ 真实费用无声消失；后者 ⇒ 账面虚高、可用额度被误判 | 对账判据**与上游同源**（`gateway/handlers.py:104` 的 `_usage_pending`）；**`usage_ledger` 没有 `state` 列** —— "已结"由**分录类型**表达：`reconciliation.CONFIRMING_LEDGER_KINDS = frozenset({BILL})`，即**只有 `BILL` 算确认到账**，`USAGE`（网关按计价表估出的未确认金额）**仍算未结**；`UNKNOWN` 一律挂账等人核对，**不自动落终态**（`reconciliation.py` 模块 docstring 第 1 条） |
| R5 | **账本被篡改** | 🔴 高 | ADR-13 原话：审计"不可被后续修改或删除，**与费用账本、版本快照同级对待**"⇒ 账本可改就等于整个审计体系可改 | `usage_ledger` 追加式 + `immutable_trigger_ddl` 触发器（复用 `rednote_reject_mutation()`）+ 冲正用**新分录**而不是改旧行；判据：**UPDATE / DELETE 各断言被拦**（`23001`） |
| R6 | **账本相关数据出网** | 🔴 高 | `COST_LEDGER` 在 `FORBIDDEN_EGRESS_DATA_CLASSES` 里；一旦出网就是 ADR-10 违规，且**用户无感** | 本包**不注册任何出网数据类别**；判据：全仓 grep 确认本包模块未向 `gateway` 传 `COST_LEDGER`（结构性检查） |
| R7 | **金额量化口径不唯一**（同一个数有两种写法） | 🟠 中 | "100.00" 与 "100.00000000" 在**比较时可能不等**（字符串比较），或 `Decimal` 相等但序列化后不同 ⇒ 对账永远报差异 | 量化**只有一个函数** `money.quantize()`，DB 写入前必经它；序列化**只有一个函数** `money.to_wire()`；判据：**同一 `Decimal` 两次序列化逐字节相同** + 穷举量化幂等（`quantize(quantize(x)) == quantize(x)`） |
| R8 | **`pricing_versions` 被就地修改** | 🟠 中 | 改一个单价 ⇒ **历史所有预估与账单全部失真**，且改的人无感（他以为只影响未来） | 不可变表（触发器拦改删），单价的"变更"= **插新版本**；预估行**冻结引用**它当时用的 `pricing_version_id`，不回算 |
| R9 | **预估与实际分叉后无人发现** | 🟠 中 | 预估 100 元、实际 300 元，若不报警则项目一直按 100 元的节奏跑 | 结算时 `service.settle_reservation` 把预占转 `SETTLED` 并按实际金额入账（`entries` 为空时自动补一条 `BILL`，金额 = `actualAmount`）；**分叉本身由 `reconciliation.reconcile_project()` 报告**（`DriftReport`：账面数 ⟷ 按明细重算数），处置走待办 —— `ensure_work_item`（`modules/audit/service.py`，WP15） |
| R10 | **预算表与预占明细分叉** | 🟠 中 | `project_budgets` 是账面、`budget_reservations` 是明细；两张表一旦分叉，**两边都看着正常** | ① 预占 / 释放**同事务**改两表；② 提供 `recompute_committed(project_id)` 按明细重算（对账用，与 `files/repository.compute_effective_bytes` 同一手法）；③ 判据：**重算值 == 账面值** |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（5 张新表，数据结构 02 §11；可变性按用途分三类）：

| 表 | 角色 | 可变性 |
|---|---|---|
| `pricing_versions` | 供应商计价版本。单价一旦发布不可改 | **不可变**（触发器拦 UPDATE/DELETE） |
| `project_budgets` | 项目预算**账面**（限额 / 已结算 / 已预占）—— 一项目一份 | **可变**（单条原子条件 UPDATE，无 `lock_version`） |
| `budget_reservations` | 预占**明细**（每次预占一行 + 状态机） | **可变**（状态机条件 UPDATE） |
| `cost_estimates` | 费用预估（项目 × 批次类型的预计成本） | **可变**（结算时回填实际值；`lock_version`） |
| `usage_ledger` | 费用账本（追加式）。每笔外部用量 / 账单一条 | **不可变**（触发器拦 UPDATE/DELETE） |

**关键设计判断：为什么账面与明细分成两张表**（`project_budgets` / `budget_reservations`）

这不是"规范化洁癖" —— 两者的**更新模式完全不同**：

| | `project_budgets` | `budget_reservations` |
|---|---|---|
| 一行代表 | 一个项目的**当前账面** | **一次**预占意图 |
| 更新 | 高频单条条件 UPDATE（每次预占改一行） | 每次预占**插一行**，随状态迁移改自己那行 |
| 不变量 | `committed + reserved <= limit` | 每行状态自身合法 |
| 无 `lock_version` 的理由 | 更新全是单条原子条件 UPDATE，**没有读-改-写窗口**（`quota_accounts` docstring 原文） | 同上 |

这与 WP12 的 `quota_accounts`（账面）/ `upload_sessions`（明细）**完全同构** —— 那是本仓已经跑通并测过的形态，**重新发明一遍没有任何收益**。

**分层**：

```text
modules/billing/                       # 新模块（M3 第二个）
  money.py           # ★ 纯函数：定点表示、量化、加减乘、比较、序列化（零 float）
  pricing.py         # ★ 纯函数：单价解析（版本 × 计量单位 → 金额）
  models.py          # 5 张表
  ddl.py             # 触发器 DDL（与测试同源，不手抄）
  repository.py      # 存储原语（★ 条件 UPDATE 预占 / 释放 / 结算）
  service.py         # 预估 + 预占 + 结算（唯一写入口，同事务改两表）
  reconciliation.py  # ★ 对账：消费 usage_pending + 网关 usage/cost → 结算或挂账
  schema.py          # 请求/响应 DTO（金额一律字符串）
  api.py             # 端点（本项目补充端点 —— 协议零费用端点，见 §1.4 第 2 条）
```

|---|---|

### 2.1 需求本质（一两句话）

### 2.6 技术风险评估（含应对）

见 §1.6 的 R1~R10。其中 **R1（并发预占）与 R2（float 混入）是本包必须当场闭合的两条**，其余为设计约束。

**约束 R1 的机制（唯一正确形态）**：

```sql
UPDATE project_budgets
   SET reserved_amount = reserved_amount + :delta,
       updated_at = now()
 WHERE project_id = :project_id
   AND committed_amount + reserved_amount + :delta <= limit_amount
```

三个要点，缺一不可：

1. **条件在 WHERE 里**，不在 Python 的 `if` 里 —— 否则有读-改-写窗口；
2. **`rowcount == 1` 才是成功**，`0` 即预算不足（**不再查一次余量** —— 再查读到的是别人改过的账面，反而误导，`files/repository.py:100` 原文）；
3. **`CHECK (committed_amount + reserved_amount <= limit_amount)` 兜底** —— 应用层是主防线，但"数据回填、运维脚本、将来的批量对账都可能绕过它"（`quota_accounts` 注释原文）。

**约束 R2 的机制（唯一正确形态）**：

- 存储层：`Numeric(20,8)`（PostgreSQL 任意精度**定点**，不是浮点）；
- Python 层：**唯一入口 `money.py`**，对外只收发 `Decimal`；
- 传输层：**字符串**（`to_wire` / `parse_wire`）。

## 3. 阶段 3：多版本方案

### 方案 V1 —— 只记不预占（事后统计）（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 只建 `usage_ledger`，费用在调用完成后记账。预算"超支"只是统计结果 |
| 优点 | 最简单；零并发问题；一天可交付 |
| 缺点 | **验收直接失败**：W10 的验收是"预算并发预占测试"，本方案**没有预占**，无从测。且预算是**对外承诺**（§1.1 P1）—— 事后统计等于"先花再告诉你超了" |
| 适合 | 内部实验性用量监控 |
| 风险 | 无技术风险，但**没有做需求** |
| 结论 | ❌ 不选。**它把"承诺"降级成了"报表"** |

### 方案 V2 —— 单表：预算表里直接减（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 只建 `project_budgets`，预占 = `remaining -= delta`。取消 = `remaining += delta` |
| 优点 | 表少；无"账面/明细分叉"问题 |
| 缺点 | ① **无法回答"这笔钱被谁扣住了"** —— 只有余额，没有明细，对账时无凭据；② **重复释放检测不了**：`remaining += delta` 执行两次不会报错（没有状态可判）；③ `release` 无 `WHERE reserved >= delta` 那样的防线，账面可被扣成负数 |
| 适合 | 单人、无并发、无审计需求 |
| 风险 | **R3（预占不成对）在此方案下无法防御** —— 它正是本包要拦的故障形态 |
| 结论 | ❌ 不选。**它省掉的"明细表"恰好是防线所在** |

### 方案 V3 —— 账面 + 明细双表 + 条件 UPDATE + 追加式账本（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | `project_budgets`（账面：`limit` / `committed` / `reserved`）+ `budget_reservations`（明细：状态机）+ `usage_ledger`（追加式不可变）+ `pricing_versions`（不可变）+ `cost_estimates`（可变）。预占靠**单条条件 UPDATE**；释放靠**状态机条件 UPDATE**；对账消费 `usage_pending` |
| 优点 | ① **"预算并发不超承诺"由单条语句保证**，不依赖任何进程内状态 ⇒ 天然跨实例正确；② 明细表让"钱被谁扣住"可查；③ 追加式账本让 ADR-13 的"与账本同级"有代码落点；④ **与 WP12 已验证形态同构**，不需要重新论证并发正确性 |
| 缺点 | ① 两表需同事务维护（分叉风险，R10）；② 明细表随使用增长；③ 表多（5 张） |
| 适合 | 本项目：API 双实例（ADR-11 C8）、有并发、有审计要求、费用是硬约束 |
| 风险 | ①② 都有对应处置（同事务 + `recompute_committed` 对账判据） |
| 结论 | ✅ **选它** |

### 方案 V4 —— 完整版：加重试队列 + 分布式租约 + 汇率服务（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | 在 V3 基础上加：预占重试队列、跨实例预算租约（类似 `jobs.lease_*`）、自动汇率换算服务 |
| 优点 | "能力最全" |
| 缺点 | ① **预占不需要重试队列** —— 条件 UPDATE 失败就是"预算不足"，这是**业务结论**不是瞬时故障，重试毫无意义；② **预算不需要租约** —— 租约是为"持有一段时间的资源"设的（`jobs`），预占是**一条语句的原子结果**，加租约只会引入"租约过期后预占归属不明"的新问题；③ 汇率服务需要**新的出网通道**，而 `COST_LEDGER` 在禁止出网清单里（§1.4 第 5 条） |
| 适合 | 无。三条增强都与本包约束直接冲突 |
| 风险 | 引入三个**不存在的问题**的解法，且其中一个（汇率出网）**违规** |
| 结论 | ❌ 不选 |

### 3.5 方案选择与理由

选 **V3**。核心理由：**验收标题本身（"预算并发预占测试"）要求的是一个并发正确性证明，而 V3 是唯一一个把正确性放在单条 SQL 语句里、因而不依赖任何进程内状态或部署形态的方案**。

三条否决理由，逐条对应：

| 方案 | 一句话否决 |
|---|---|
| V1 | 没有预占 ⇒ **没做需求** |
| V2 | 没有明细 ⇒ **防线不存在**（R3 无法防御） |
| V4 | 三条增强分别与"预占是业务结论"、"租约不适用于原子操作"、"账本禁止出网"冲突 |

### 3.6 ★ 本包对上游待定项的回答

| OP | 待定项 | 本包回答 |
|---|---|---|
| **OP-108** | `job_attempts.usage_pending` 的**消费方** | **本包消费**。口径：扫 `usage_pending = true` 的 attempt，凡**尚无确认性分录**（`BILL`）的，进对账报告（`reconciliation.reconcile_pending()` → `ReconciliationReport.pending`）。判据**与 `gateway/handlers._usage_pending` 同源**（"有过用量，且计费未确认"），本包不另写一个判断。注：**不是**"尚无任意分录" —— 有 `USAGE` 分录仍算未结，理由见 `reconciliation.py` 的 `CONFIRMING_LEDGER_KINDS` docstring |

### 5.2 MAJOR-1：`append_ledger_entry` 并发同键 ⇒ HTTP 500

**发现路径：静态判据没有报红 —— 是读实现时发现 docstring 与代码不一致。**

`repository.find_ledger_entry_by_idempotency` 的 docstring 写「**直接 INSERT → 撞 23505 → 回查。而不是先查再插**」，而 `service.append_ledger_entry` 的实现正是"**先查再插**"且**不捕获 `IntegrityError`** ⇒ 两个请求同时查到"不存在"，都去 INSERT，其中一边撞 `uq_usage_ledger_idempotency`，`IntegrityError` 被 `session_scope` 原样抛出 ⇒ **HTTP 500**。这是 ISS-95 形态：**声称自己有防线**。

**实证 ①（8 线程同键并发追加）**：修复前返回成功 **3**（同一 id）/ 抛异常 **5**；修复后 **8/8** 收敛到同一条、**0** 抛异常、库里**恰好 1 行**。

**修法**：新增 `_is_unique_violation(exc)` 与 `_insert_ledger_entry_idempotent(...)` —— SAVEPOINT（`begin_nested`）+ 只对 `23505` 回查 + 判定走 `ddl.UNIQUE_VIOLATION_SQLSTATE` 常量（**不看 message 文本**）。三个设计点各有理由：

| 点 | 为什么 |
|---|---|
| 用 **SAVEPOINT** | `23505` 会让**整个事务**进入 aborted 状态（后续报 `25P02`），不划子边界则回查那条 SELECT 立刻失败 |
| 只对 **`23505`** 回查 | 其它 `IntegrityError`（FK / CHECK）是**真问题**，必须原样冒出去 |
| 判定走 **SQLSTATE 常量** | 文本随 PG 版本/语言变，`23505` 是 SQL 标准里的稳定标识 |

**保留"先查一次"是有意的**（`[C8]` 守卫）：它是**快路径**（省一次必然失败的 INSERT + 回滚），但**不能替代** `except` —— 并发正确性**只**来自 `23505` 捕获。

**实证 ②（反向验证）**：把调用点换回裸 `_insert_ledger_entries` ⇒ 并发用例报红（3/8 抛 `23505`）⇒ 恢复后 105 passed / 0 failed。**这一步不可省**（第 5 条纪律：『没跑』与『跑失败』同形）：原串行用例在缺陷实现下**照样绿**（只走快路径）。

### 6.3 ⚠️ `within_limit` 是恒真式，不能当判据

`committed_amount + reserved_amount + within_limit == limit_amount` 里的 `within_limit`
**由前面两项推出来**，因此它对**任何**实现都成立 —— 与 WP24 的"错误 ⑪"是**同一族**
（ISS-137 / 第 12 条纪律：穷举/不变量判据先问"这是两种独立事实的相遇，还是同一事实的两种写法"）。

**本包对它的处置**：把它**降级为辅助恒等式**，真正的判据改成**两条独立事实的相遇** ——
"并发成功数 × 单笔金额 ≤ 限额"（这条**能被错误实现打红**，因为成功数是实现真的做出来的，
限额是从别处读出来的）＋ 原生 SQL 层直接读三列验证 `WHERE` 真的拦住了超额那次。

> **判据纪律**：一条恒真式**可以留在测试里**（它守的是"三列之间的代数关系没被改坏"），
> 但它**不能单独承担**"预算不超额"这条验收 —— 那必须另有一条会在错误实现下变红的判据。
> 本包的 `[C10]`/`[C10b]` 就是这个区分。

## 9. 本包新增的铁律（值得沉淀）

承接《待定项与问题登记册》§4.4 的既有铁律，本包新增 **3 条**，全部来自**判据/工具自身或环境假设**的缺陷而非功能缺陷。

### 第 16 条 —— 用例的通过条件若可表述为"这个库里恰好没有某些数据"，它就在赌库的历史

> **把测试丢到"由迁移从零建出"的库上跑一遍** —— 迁移会 seed，而 seed 会被继承查询放大。
> 与"断言随外部库状态浮动"（ISS-121/ISS-148）同族，但根因不同：那两条赌"没有别人写入"，本条赌"本包的迁移没跑过"。

**现场（ISS-170 / CR-3）**：一条用例把"另一个项目不写项目级配置"当成"未配置上限"，而 WP24 迁移会 `bootstrap_defaults` 种下全局值并被继承 ⇒ 该用例的通过条件是"这个库没跑过 WP24+ 迁移"。**只有换库才暴露。**

### 第 17 条 —— 参照物与被测对象是两个会独立演化的东西：判据的参照值也必须从被验对象派生

> 凡断言里出现一个**由被验代码决定**的数字，问一句"这个数字是从哪儿来的" ——
> 答案若是"我写的时候它正好是 X"，就必须改为从被验对象派生。

**现场（ISS-171 / TOOLING-2）**：反向验证脚本把基线 `"36 PASS / 0 FAIL / 36 checks"` 写死，被验收集器从 36 涨到 40 ⇒ 两条断言**恒 FAIL**，而该脚本**再没重跑** ⇒ 证据自此陈旧。修法：新增 `_expected_checks_from_tool()` 从**被测脚本自己的源码**读 `EXPECTED_CHECKS`，CHECK 名去掉数字。**比 ISS-72/ISS-78 更隐蔽：红的形状看起来像被验对象出错。**

### 第 18 条 —— 收集器"报红"必须与"退出码"同形，否则判据的结论没有机械后果

> 一个把结论**只写进文本**的脚本，若恒返回 `0`，那么在"只断言 `rc==0`"的载体里，
> **"判据报红"与"判据全绿"机器可读层面完全同形**（ISS-143 变体）。

**现场（ISS-168 / TOOLING-1）**：CR 收集器打印 `31 PASS / 4 FAIL` 而 `echo $?` 是 `0`。同款形态当时也在 `collect_wp24_code_review.py`，只因"恰好 0 FAIL"而从未暴露 —— **那是运气，不是防线**。修法：补 `EXPECTED_CHECKS` + 条数核对 + `raise SystemExit(...)`；并新增门禁 `check_returns_exit_code`（用 **AST** 判，因为脚本刻意在引号里留了旧写法说明文字 —— 用正则写会被自己的引文骗过）。
