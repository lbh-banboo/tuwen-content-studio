## 0. 本包的一句话定位

**把"运营在预览页上逐段提意见 → 改正文 → 这条意见的锚点还在不在 → 这条内容能不能审过"这条闭环，做成可并发、可溯源、可机器判定的接口层。**

它不解决"生成内容"（WP26）与"生成图片"（WP27/28），也不解决"自动自检"（WP30）。它解决的是生成之后**人与人、人与 AI 之间对同一份稿子的协作**：意见落在哪里、改到哪一版、谁在什么时候审过、两个人在同一秒改同一段时谁不覆盖谁。

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

前端原型 `services/backend/static/content-feedback.html` 的页面标题是「逐条审核试产内容并处理意见」，正文写死了两条业务规则：

> 关键事实问题未解决不能通过。
> 可对选中文本添加意见或提交重生成。

在 WP29 之前，这两句话**没有一处落点**：

| 原型的动作 | WP26 交付后的能力 | 缺什么 |
|---|---|---|
| 在预览里点某一段、选中文字提意见 | 内容只读（`GET /contents/{id}`），没有任何"意见"实体 | 意见无处落库；`paragraph_ref` 坐标系无人消费 |
| "标记已通过" / "批量通过" | 无审核表、无接口 | 审核结论无处落库；"关键事实未解决不能通过"无法执行 |
| 用户改正文 | `content_items` / `content_versions` 只被生成任务写 | 人工编辑会与后台生成**并发写同一份正文**，没有任何协议级保护 |
| 「存在 1 条未解决的关键事实问题，当前内容不能通过」 | 无 BLOCKING 概念 | 阻断级反馈与审核结论之间没有判据 |

所以本包真正解决的是 **AC-28 的"协同 + 冲突"**：多人（以及 AI）对同一条内容并行工作时，**谁的意见、针对哪一版、现在还算不算数、谁能覆盖谁**。这不是"再加几个 CRUD 接口"，而是给内容生产补上**协作状态机**。

### 1.2 核心用户是谁？

| 用户 | 关心什么 | 本包给他什么 |
|---|---|---|
| 运营（提意见的人） | 我点的这一段是不是会被别人误解；我提的意见有没有被处理 | 段落 / 图片 / 整篇三选一锚点；`anchorState` 标记"这条意见指向的段落已随编辑失效" |
| 运营（改稿的人） | 我改的时候别人也改了怎么办；我改完意见还在不在 | `If-Match` + 412（不覆盖）；编辑追加版本，旧版原样保留；意见**不因编辑消失** |
| 审核者 | 哪些能过、哪些不能过、我上次审的是哪一版 | `content_reviews` 绑定 `subjectVersionId`；未解决 BLOCKING 时 409；改判靠 `supersedesId` 而非改历史 |
| AI（WP30/WP31 的编排） | 能不能以 AI 身份提意见、能不能批量处理 | 服务层接受 `authorKind=AI`；HTTP 端点固定记 USER（见 §1.4 第 7 条） |
| 下游（WP33 / WP34 / WP35） | 质量报告、影响图、打包能不能读到可追溯的结论 | 不可变事件表与审核表；反馈行带 `observedVersionId` / `resolvedVersionId` |

### 1.3 最小 MVP 应包含哪些功能？

**七个端点**（形状由本包定义，协议 03 原件不在本机 —— 与 WP24/WP25/WP26 同一处置）：

| # | 方法 + 路径 | 用途 | 成功码 |
|---|---|---|---|
| ① | `GET /contents/{contentId}/preview` | 预览聚合：当前版本 + 段落 + 图片位 + 标题候选 + 反馈计数 + ETag | 200 |
| ② | `POST /contents/{contentId}/edits` | 人工编辑，**追加一个新版本**（If-Match） | 201 |
| ③ | `GET /contents/{contentId}/feedback` | 反馈列表（游标分页，含 `anchorState`） | 200 |
| ④ | `POST /contents/{contentId}/feedback` | 新建反馈（锚点三选一，首行事件同事务） | 201 |
| ⑤ | `PATCH /feedback/{feedbackId}` | 推进反馈状态（If-Match 保护反馈行自己的锁） | 200 |
| ⑥ | `POST /contents/{contentId}/reviews` | 单条人工审核（通过 / 毙掉） | 201 |
| ⑦ | `POST /projects/{projectId}/content-reviews` | 批量审核（逐条独立，部分成功也 200） | 200 |

**三张表**（`modules/feedback/models.py`）：

| 表 | 角色 | 可变性 |
|---|---|---|
| `content_feedback_items` | 锚点 + 分类 + 严重度 + 状态 | 可变（`lock_version` 是 ETag 载体） |
| `content_feedback_events` | 状态迁移历史 | 不可变（只追加） |
| `content_reviews` | 审核决定 | 不可变（只追加，改判 `supersedesId`） |

**六条不可省的判据**（每一条都对应一个"看起来有防线、实际没有"的形态）：

1. **锚点三选一**：列占用由三条 CHECK + 一个延迟触发器兜住，服务层另给可读 4xx。
2. **`anchorState` 读时判定**：正文改过之后，旧段落反馈仍要出现在列表里，只打 `STALE` 标记。
3. **编辑是追加版本**：`content_versions` 不可变，编辑落成第 N+1 版。
4. **两条写路径各有一把锁**：内容锁（②）与反馈锁（⑤）不共享代码。
5. **状态与事件同一事务**：投影（`state`）与历史（`events`）要么一起落、要么一起回滚。
6. **批量审核逐条独立**：一条因 BLOCKING 失败不影响其余条目。

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| # | 疏漏 | 处置与理由 |
|---|---|---|
| 1 | **"预览页的自检摘要"没有数据来源** | 自检属 WP30（`modules/review`），本波未开工。`PreviewPayload.selfCheckSummary` **恒为 `None`**，不编造"通过 / 风险"数据。一份看起来通过的假摘要，比空字段危险得多 —— 原型里"批量通过"按钮正是以"已完成自检、无阻断问题"为前提 |
| 2 | **段落 ref 的切段口径容易长出第四份实现** | 接缝冻结 §5.1 明写三处实现（`content` / `knowledge` / `media`），平级不可互 import。本包**零切段**：`media_bridge` 只转发 `media/schemas.paragraph_refs_for_body` 与 `validate_paragraph_ref`；多写一份 `.splitlines()` 就是 OP-197 那个分叉的第二次现身 |
| 3 | **编辑之后旧意见怎么处理** | **不批量刷新**。读时判定 `anchorState`：一次编辑扫全表反馈是昂贵的写放大，且"漏触发"会留下永久过期的标记（静默错误）。代价只是列表读时切一次段 |
| 4 | **首行事件容易漏写** | 新建反馈**必须**在同一事务写 `from_state = NULL` 的首行事件。分开提交会造出"有反馈行但没有创建事件"的溯源断档（R6） |
| 5 | **反馈行自己的 ETag 没被想到** | ⑤ 的路径里没有 `contentId`，它改的是反馈行，不是内容行。ETag = `build_etag(feedbackId, feedback.lock_version)`。借用内容 ETag 会让"两个人分别改内容和改意见"互相 412 |
| 6 | **批量审核的状态码** | 200 而不是 201：请求可能部分成功、部分失败。统一 201 会让"20 条里 3 条失败"看起来像全成功 |
| 7 | **`authorKind` / `actorKind` 被当成了请求字段** | HTTP 端点是**登录用户**的操作入口，固定记 `USER` + 当前用户。让调用方自报"我是 AI"没有业务收益，却会让审计面（`actor_kind`）失真。AI 反馈由 WP30~32 的编排**直接调服务函数**写入 |
| 8 | **permissions 的 `REVIEW` 被忽略** | `permissions.py:85` 的原文是「生成、**反馈**、**人工审核**」，`content/api.py` 也写明它是 WP29~WP31 审核动作的落点。④⑤⑥⑦ 用 `REVIEW`，②（改内容）用 `EDIT`，③① 用 `VIEW` |
| 9 | **段落 ref 校验失败的 HTTP 码与 media 不同** | media 把自己的 `PARAGRAPH_REF_UNKNOWN` 映成 409（它的 ref 由系统派生，"重试无用"）；本包 ④ 的 `paragraphRef` 是**客户端提交的字段**，"刷新预览、重选一段"就能成功 ⇒ 422。两处码不同是两种修法不同，不是漂移 |
| 10 | **"终态不可再迁移"没有判据** | 本波只落了状态**取值域**（`OPEN` / `IN_PROGRESS` / `RESOLVED` / `REJECTED`），没有迁移矩阵：`advance_feedback` 接受任何合法状态之间的迁移，从 `RESOLVED` 回到 `OPEN` 也不会被拒。不在端点层临时补一份矩阵（那是第二个真值来源，且与 WP30/WP31 的处理规则可能冲突）。**登记为待定项**，由规则引擎落地时统一判 |

### 1.5 哪些功能现在不该做？

| 不做 | 理由 |
|---|---|
| 实时协同编辑（WebSocket / OT / CRDT） | AC-28 的要求是"冲突不覆盖"，乐观锁 + 412 已满足。实时协同需要长连接、光标广播、离线合并 —— 与"先让单机可演示"的 M3 目标不成比例，且会引入一个本仓还没有的连接层 |
| 意见的回复线程 / 点赞 / @提醒 | 原型的意见是"一条事实/语气/结构问题"，处理方式是改稿或拒绝。带线程的评论区是另一个产品形态，会把 `content_feedback_items` 变成社交表 |
| 反馈导出 / 统计报表 | WP33（质量报告）才是统计口径的落点。本包只提供可读的事实行，不在两张表上长出报表查询 |
| 自检摘要 / 规则命中 | 属 WP30。本包只留字段位（`selfCheckSummary: null`） |
| 富文本 / 结构化编辑器 | 正文是纯文本 + 段落切分（`paragraph_ref` 坐标系）。引入富文本会让"段落 ref"失去唯一坐标 |
| 批量编辑（一次改多条内容） | 批量只做审核（⑦）。批量编辑的冲突面是 N 条内容各自的锁，且没有原型入口 |
| 通知 / 待办自动生成 | 属 WP14/WP15。本包只在事件表留下事实，不决定"要不要通知谁" |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 表现（静默失败的样子） | 本包的处置 |
|---|---|---|---|
| R1 | 把 412 降级成 409 / 或直接覆盖 | 用户手打的修改被别人的版本静默覆盖，或前端不刷新、继续在旧正文上改 | 内容编辑的 412 由 `content.service.append_edited_version` 在**行锁内、任何写入之前**抛（`service.py:1697-1710`）；端点前置 `require_if_match` 只是早拒绝 |
| R2 | 第四份切段实现 | 预览里能点的段落，提交时被拒（或反过来）—— 两套实现各自测试都过 | `media_bridge` 只转发 media 纯函数；本包无任何切分代码 |
| R3 | 状态与事件分两次提交 | "状态前进了但没有事件"（断档）或"有事件但状态没变"（历史说谎） | 服务层只 `flush()`、从不 `commit()`；提交边界归 `session_scope` |
| R4 | 编辑绕过证据绑定校验 | "删掉两段"后旧绑定越界，库里仍显示"有 bindings" —— R4 静默降级成不判 | 编辑强制重跑 `validate_bindings`（`content.service:1779-1787`，无旁路参数）；失败在端点映成 422 |
| R5 | 锚点失效的反馈被过滤 | 反馈列表条数随编辑减少，运营以为"意见被处理了" | `anchorState` **只标记不过滤**；条数与锚点新鲜度无关 |
| R6 | 批量审核第一条失败就整批回滚 | 运营逐条重试、自己找哪条坏了 | 服务层每条一个 SAVEPOINT；PostgreSQL 语句报错会把整个事务标成 aborted，不带 savepoint 后续条目全部失败 |
| R7 | 预览跨快照拼装 | 展示的正文与 ETag 不属于同一版 ⇒ 提交时 412，用户看到"我明明看到的是 A" | `build_preview` 先取一次 `EditTarget`（身份侧 + 版本侧同一快照），其余数据以它的 `current_version_id` / `body` 展开 |
| R8 | 媒体 / 版本跨内容引用 | 一条反馈引用另一条内容的图，列表仍能渲染，但"这段意见对应哪张图"有两个答案 | DDL 延迟约束触发器（三条判据）+ 服务层可读 4xx（`media_item_content_id`） |

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**让"对同一份稿子的意见"成为一种有坐标（段落 / 图片 / 整篇）、有状态（OPEN → RESOLVED / REJECTED）、有历史（事件 + 不可变审核）的实体；并让人工改稿在并发下"不覆盖、可追溯"。**

### 2.2 用户画像

| 画像 | 场景 | 本包的证据 |
|---|---|---|
| 逐条审核的运营 A | 打开预览，逐段看；对"氨基酸表活占比 62%"那段提一条 FACT / BLOCKING 意见 | ④ 的 `anchorKind=PARAGRAPH` + `paragraphRef` + `severity=BLOCKING` |
| 改稿的运营 B | 按意见改正文，保存；不知道同事也在改 | ② 的 If-Match；编辑追加版本；A 的意见因锚点失效被标 `STALE` 而非消失 |
| 拍板的审核者 | 点"标记已通过"；系统告诉他还有 1 条阻断未解决 | ⑥ 的 409 `UNRESOLVED_BLOCKING_FEEDBACK` |
| 批量处理的运营 | 勾选多条内容"批量通过" | ⑦ 的逐条结果（哪几条因阻断失败） |
| AI 自检（WP30，未来） | 自动产出意见、自动推进状态 | 服务层 `authorKind=AI` + `actorKind=AI`；不经过 HTTP 端点 |

### 2.3 核心功能清单（MVP）

1. **预览聚合**：一次返回同一版正文的段落、图片对位、标题候选、已采纳标记、反馈计数、ETag。
2. **编辑追加版**：四字段部分更新（未传沿用上一版），`If-Match` 保护，落成新版本。
3. **反馈 CRUD（无删）**：新建（锚点三选一）、列表（游标 + 三筛选）、状态推进（四态机）。
4. **锚点新鲜度**：列表读时判 `FRESH` / `STALE`，不过滤。
5. **人工审核**：单条（绑定版本）+ 批量（逐条独立、版本取当前投影）。
6. **阻断闸门**：存在未解决 BLOCKING 反馈时禁止 `APPROVED`（判据下推 SQL）。
7. **溯源**：每次状态迁移一行事件；审核不可变、改判追加 + `supersedesId`。

### 2.4 待补充项及理由

| # | 项 | 理由 |
|---|---|---|
| 1 | **content 侧三件接缝**（`EditTarget` / `read_edit_target` / `append_edited_version` / `content_edit_etag`） | `modules/content/*.py` 根层禁改（接缝冻结 §1.1 第 21 行）。主 agent 已按 §5.12 落地，本包只调用、不改签名 |
| 2 | **media 切段纯函数** | §5.4：`modules/media/**` 本批"有主"，WP29 只读；`paragraph_refs_for_body` 是纯函数层，不含第二份实现 |
| 3 | **不新建 `ProjectAction`** | 既有 `REVIEW` 的原文定义就含"反馈、人工审核"；新建动作会在当前矩阵下逐行相同、只增加一个需要维护的枚举值 |
| 4 | **`paragraph_ref` 不加 FK** | 段落不是表。加一个 `paragraphs` 表会把"正文切段"从纯函数变成持久化实体，而切段口径会随正文编辑不断变化 |
| 5 | **反馈行不加 `content_version_id` 复合唯一约束** | 一条内容可以有多版，也可以对同一版提多条意见 —— 没有需要去重的业务键 |
| 6 | **`selfCheckSummary` 留空** | WP30 的落点，本包不编造 |
| 7 | **批量审核没有 If-Match** | 批量改的是**追加型**审核表（不可变），且每条绑定"当前版本"；给批量加 ETag 会要求客户端先持有一组版本号，而它本来就要逐条刷新 |
| 8 | **错误码映射表各写一份** | `content/api.py` / `media/api.py` 的 `_HTTP_BY_REASON` 是**它们各自的**对外契约。跨模块 import 私有名，会让"对方改一个 reason 的码"静默改变本包行为 |

### 2.6 技术风险评估（含应对）

见 §1.6 的 R1~R8。补充两条工程风险：

| 风险 | 应对 |
|---|---|
| **预览查询次数过多** | 预览一次装配，但内部仍是 5 次读（编辑目标 / 媒体位 / 标题候选 / 计数 / 切段）。当前量级（一条内容几十段、6 个图片位）可接受；若变成热点，先合并媒体位与候选查询，而不是在端点层加缓存（缓存会让"展示的正文"与"ETag"重新可分叉） |
| **`content_feedback_items` 无分区的持续写入** | 列表已用 keyset（`created_at DESC, id DESC`），不走 OFFSET；`content_item_id + state` / `project_id + state` 两个索引覆盖工作台读路径。数据量大到需要分区时，按 `project_id` 哈希分区是自然选择（不与现有索引冲突） |

## 3. 阶段 3：多版本方案

### 方案 V1 —— 内容行原地 UPDATE + 意见存 JSONB（**否决**）

做法：给 `content_items` 加 `feedback jsonb`，编辑直接 UPDATE 正文，意见是数组元素。

否决理由：

1. **版本历史消失**：`content_versions` 不可变的纪律被绕过，demo 的"改之前长什么样"无法回答；
2. **并发**：JSONB 数组的并发追加在 PostgreSQL 里只能整列覆盖，两个人各提一条意见会丢一条（典型的丢失更新）；
3. **无法索引**：按段落 / 状态 / 严重度筛选要全表扫 JSONB；
4. **审核结论与意见混在一个字段**，无法表达"审核绑定版本"。

### 方案 V2 —— 独立反馈表，但不留事件历史（**不推荐**）

做法：`content_feedback_items` 只存当前 `state`，推进状态时原地改；审核也原地改 `decision`。

不推荐理由：

- "这个意见是怎么被处理的"答不出来。原型上"待审核 / 已通过 / 已处置"是**过程状态**，没有历史就无法解释"为什么现在是 REJECTED"；
- 改判（通过 → 毙掉）会**抹掉**上一次决定，而审核是责任行为；
- 要补历史只能加审计日志 —— 那是第三张表，等于把 V3 的事件表换个名字，却失去了"事件与状态同事务"的约束。

### 方案 V3 —— 独立 `feedback` 模块 + 三张表 + 追加版本 + If-Match（**推荐，已实施**）

| 组成 | 落点 |
|---|---|
| 反馈项（可变，`lock_version`） | `content_feedback_items` |
| 状态迁移历史（不可变） | `content_feedback_events`（`seq_no` 项内递增） |
| 审核决定（不可变，可 `supersedes`） | `content_reviews` |
| 编辑 = 追加版本 | `content_bridge.apply_content_edit` → `content.service.append_edited_version` |
| 两把锁、两个判断点 | 内容锁在 content 服务层；反馈锁在 `feedback.service.advance_feedback` |
| 锚点坐标系 | `media/schemas.paragraph_refs_for_body`（零切段实现） |
| 四态机 | `OPEN` / `IN_PROGRESS` / `RESOLVED` / `REJECTED` |

推荐理由：

1. **不改 content / media 的源文件**：本包只调它们已冻结的公开接缝（接缝冻结 §5.12 / §5.1）；
2. **每个写动作都有唯一的权威判断点**：412 不会出现"端点判一次、服务层判一次、结论不同"；
3. **可溯源且不可篡改**：事件与审核由触发器兜底（`trg_*_immutable`）；
4. **代价已登记**：三张表、三个触发器、两处 ETag 载体 —— 换来的是"并发不覆盖 + 历史不丢 + 审核可改判"。

### 方案 V4 —— 完整版：实时协同（CRDT）+ 意见线程 + 通知（**不选**）

不选理由：

- 实时协同与"试产内容逐条审核"的产品形态不匹配：审核是**异步、逐条**的，不是多人同时打字；
- CRDT 需要长连接、离线合并、冲突可视化，超出 M3"可演示、可判据"的目标；
- 通知与线程属 WP14/WP15 与后续产品迭代，不在本包范围。

### 3.5 方案选择与理由

选 **V3**。判据是三条**可反向验证**的问题：

1. **两个人同时改同一段，会不会静默覆盖？** V3 不会（`If-Match` + 行锁内比对 + 条件 UPDATE，两层）；V1 会；V2 会（原地改状态）。
2. **改完之后，旧意见还能不能解释？** V3 能（事件历史 + `anchorState`）；V2 不能。
3. **审核结论绑的是"哪一版"？** V3 是 `subject_version_id`；V1 根本没有版本概念。
