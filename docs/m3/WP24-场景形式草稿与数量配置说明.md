## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让"这一批生成多少条、每一类各多少条"从**运营脑子里的约定**变成**可复现、可审计、可配置的整数**——因为这两个数字直接决定生成成本与内容策略。

拆开是三个彼此独立、但必须同时成立的问题：

| # | 问题 | 若不做会怎样 |
|---|---|---|
| P1 | **数量上下限不能写死在 DDL 里** | 运营把试产从 10 条改成 12 条 ⇒ 要写迁移、要评审、要停机窗口。**业务参数调整被当成数据结构变更**（ADR-13 的核心论点） |
| P2 | **比例必须是离散份额，不是浮点百分数** | `0.1 + 0.2 !== 0.3` ⇒「三个 30% 合计是不是 100%」要靠 epsilon 判。而"合计不等于 100%"会让整数分配**整体错位**，且**不报错** |
| P3 | **整数分配的总和必须严格等于总篇数** | 四舍五入的**和不等于**总数。而"10 篇变成 11 篇"在这个系统里是真问题 —— 篇数直接对应生成成本（历史收敛决议 C14 原文） |

**为什么 P2 与 P3 必须同包做**：比例是**输入**、整数分配是**输出**。两者分开做会出现"上游给浮点比例、下游做整数分配"的错配，而错配的症状是**某一类多一篇、另一类少一篇，合计照样等于总数** —— 账面完全正常。

**本包的产出边界**：它能算出"早八通勤 3 条、卸妆后二次清洁 2 条…"这份**分配结果**，但**不生成任何内容**。内容生成是 WP26 起的事。

### 1.2 核心用户是谁？

| 角色 | 规模 | 在本包做什么 |
|---|---|---|
| **运营（项目负责人）** | 约 50 人，峰值 20 在线 | 配置场景比例与形式比例、启用/停用场景、比对系统建议与本轮实际条数 |
| **管理者** | 2~5 人 | 查"数量上限被谁改了、什么时候改的、为什么改"（ADR-13 审计要求） |
| **下游工作包（系统）** | — | WP25 费用预估要读数量；WP31 试产关口要读上限；WP32 扩产批产要读上限并做越界校验 |

**"运营能在页面上自助确认当前生效值"是硬要求**（ADR-13 验证方式第 3 条）：不能只留一条数据库错误，也不能只在日志里。

### 1.3 最小 MVP 应包含哪些功能？

按"三块拼图"组织（对应 §1.1 的 P1/P2/P3）：

| # | 功能 | 对应问题 | 验收映射 |
|---|---|---|---|
| F1 | `runtime_settings` 表 + 默认值（`batch.limits` = 10/30/50、`research.maxEffectiveFiles` = 2000/项目）+ 读取服务 | P1 | ADR-13 验证方式「默认值一致」 |
| F2 | 配置变更 + **不可篡改审计** + **变更即时生效** | P1 | ADR-13 验证方式「配置生效」「审计完整」「审计不可篡改」 |
| F3 | 场景形式草稿：比例编辑、启用/停用、容量上限读取 | P2 | AC-10 / AC-11 |
| F4 | **整数分配纯函数**（最大余数法 + 三级次序） | P3 | AC-10~12「舍入、方向覆盖、边界」 |
| F5 | 草稿固化出 **PLAN 版本**（落 `version_nodes`，`entity_type='PLAN'`） | P1+P2+P3 的收口 | AC-08~09「固定版本」 |
| F6 | **项目级副本机制**：惰性补齐 + 全局变更同事务级联刷新 + 分叉显式暴露 | P1（老大已拍板"必须有副本"） | §3.6 的 J1~J4 四条判据 |

**F4 必须做成纯函数**：它是本包唯一有数学性质的部分（倍数性质、单调性、可复现），做成纯函数才能穷举验证。历史收敛决议 C19 已给出可用的判据形态（"两套最大余数法在 total 1..120 上逐项相同"）。

**F6 的机制必须是"结构兜底"，不是"约定"**：老大拍板的方案里存在天然张力 —— 副本一旦存在，全局改值就与副本分叉。这与本项目"判据纪律 #9（声称自己有防线比没有更危险）"直接相关：**要么机制保证同步，要么接口显式暴露分叉**，二者必居其一，不能靠"运营自己去看"。

### 1.4 描述有哪些疏漏应当补充？理由是什么？

> 这一节是本包最有价值的部分 —— 下面 8 条**全部来自历史原型已踩过的坑**（`历史版本文档/docs/00-收敛决议.md` 的 C14/C19/C20），不是推演出来的。

| # | 疏漏 | 为什么必须现在定 |
|---|---|---|
| 1 | **占比用千分位整数，不用浮点百分数** | C19 原文：占比是**一组离散的份额**，本就不该用浮点表示。改千分位后「和必须等于 1000」是一次整数比较，没有 epsilon 可谈；`30%` / `30.0%` / `29.999…%` 不再是三个不同值。粒度选千分位而非万分位：SOP 的粒度是 5%，千分位留两位余量；再细就是给「28.7%」这种没人能解释的数字开门 |
| 2 | **打破平局必须有显式三级次序** | C19 原文：8 类各 125‰、总数 4 时**八个余数全是 0.5**。原实现只有 `id.localeCompare` 兜底，而 id 是英文 slug —— **分给谁取决于英文首字母**，对人没有意义也不可预期。三级：**余数大的优先 → sortOrder 小的优先 → id 字典序**。第三级留着是因为人工新增的分类可能忘了给次序，那时仍要可复现 |
| 3 | **"可复现"不是洁癖** | C19 原文：同一份计划在前端预览与后端落库时必须算出同一个数字，而它们是**两次独立调用**。本仓对应形态：`GET`（预览）与 `POST`（固化）必须同源 |
| 4 | **容量上限与 `unallocated`：分不完不硬塞** | C14 原文：先按权重分，超容量的削到容量，削下来的再按权重分给还有余量的场景，反复直到分完或全部满容。**全部满容时剩余篇数计入 `unallocated`，不硬塞** —— 塞进去就是产出重复内容。宁可报「分不完」让人决定：补场景，还是降低总篇数 |
| 5 | **场景与形式是两个独立维度，不能合并成一张"矩阵比例"** | 原型 `trial-config.html` 原文：「场景与形式**分别**保证边际数量」。若做成联合分布（场景 × 形式 的格点比例），格点数 = 7×4 = 28，运营要配 28 个数字且**必须合计 1000‰** —— 而实际约束只是**两个边际分布**。合并会让"改一个场景比例"连带影响形式维度 |
| 6 | **停用场景后比例必须重新归一** | 原型展示："已停用 2 个 ·（不进入本批次）"，且「启用场景合计 100%」。若停用只把该行置 0 而不归一，合计变 990‰ —— 而**系统不会报错**，只会让整数分配少分一条 |
| 7 | **有先决条件的分类不得默认启用** | C20 原文：`竞品横测` 声明 `requires: "COMPETITOR_FACTS"`，而"系统里还没有登记竞品事实的地方"⇒ **可用先决条件恒为空集** ⇒ 默认八分类**不是拿来就能确认的**：7 类只有 850‰，人必须把那 150‰ 分掉。这是设计意图不是缺陷 —— **系统不替你补齐，因为「分给谁」是内容策略而不是算术** |
| 8 | **配置变更必须即时生效，不接受"重启后才生效"** | ADR-13 审计要求第 2 条原文。本仓有直接反例：WP12 ISS-28（进程内缓存跨实例失效，**API 双实例下随机失败而单机测试全绿**）⇒ 缓存只能放数据库侧或显式失效，**不能用模块级 dict / `lru_cache`** |

**另有三条属"上游文档与磁盘实况不一致"，以及一条本包实测出的原型自相矛盾，一并记录**：

| # | 不一致 | 处置 |
|---|---|---|
| 9 | **ADR-13 的「迁移影响 #1：需要一个迁移删除三处 CHECK 约束」在本仓不适用** | 全仓 47 张表里**没有 `batches`**（`grep __tablename__` 机械计数）。ADR-13 写在"表已存在"的假设下。实际是**从零建表** ⇒ 直接**不写那三个 CHECK**即可。这是"文档假设 ≠ 磁盘实况"的一例，登记为 OP |
| 10 | **ADR-13 的 `[待核实]`（平台文本/媒体限制）指向的是平台侧数值，与本包表结构无关** | OP-64 的结论写入 `runtime_settings`（同机制，键如 `platform.mediaLimits`），但**实测值未到**（M0 未开始）⇒ 本包**只建机制、不填值**，键名先占位 |
| 11 | **协议 §7（步骤 4 的端点表）本地不存在** | 全仓无《协议 03》副本。WP22/WP23 有"协议端点 + 本包补充端点"的先例（WP22 是 1+6、WP23 是 3+3）⇒ 本包按同一做法：**能对应的走协议路径风格，对应不上的作为本包补充端点并显式标注待协议确认** |
| 12 | **"场景维度" ≠ SOP §3.7 的"八分类"** | 历史 SOP §3.7 给的是**八分类**默认比例（买家秀 30% / 竞品横测 15% / …），而原型步骤 4 页面的两个维度是**场景**（来自步骤 3 已确认人群场景，7 个候选）+ **内容形式**（4 种）。两者**不是同一层**：八分类是历史 SOP 期的分类配额，原型页面的场景来自 `information_drafts.scenes`（每行带 `factRefs`）。**本包按原型的两个维度实现**（AC-10/11 原文是"场景比例与形式比例各自合计 100%"）。八分类若将来要落地，是**第三个维度**，属新增需求 |
| 13 | **原型的演示数值不可作为权威**（本包实测出的**机械证据**） | ① 比例和**不自洽**：场景"合计 100%"行下方，各行的比例是 30+25+20+15+6 = **96**；② **演示结果违反它自己声明的算法**：原型明写"按小数余数**由大到小**分配"，而「敏感肌换季维稳」余数 **0.60 > 0.50**，原型却判它"额度已被前序占满 ⇒ 0 条"。按 C19 定义，正确结果是 `[3,3,2,1,1]`（敏感肌 1 条、卸妆后 3 条），原型给的是 `[3,3,2,2,0]` —— **两者合计都等于 10，账面完全看不出差别**。这正是 R2/R3 的活体样本。**处置**：原型只作**交互与列结构**的依据，算法一律以 C14/C19 的定义为准，且证据脚本**自己算**、不与原型数值比对 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **浮点比例导致"和不等于 1000"** | 🔴 高 | 整数分配整体错位，而**合计仍等于总篇数** ⇒ 账面看不出，只有某一类多/少一篇 | 千分位整数 + `CHECK` 保证取值域 + 合成判据（`sum == 1000` 是整数比较） |
| R2 | **整数分配总和 ≠ 总篇数** | 🔴 高 | 生成成本与计划不符（10 条变 11 条就是真金白银） | 最大余数法 + 判据"任意输入下 `sum(result) == total`"（**穷举** total 1..120 × 项数 2..8） |
| R3 | **分配不可复现（平局靠字典序）** | 🟠 中 | 前端预览与后端落库给不同数字；运营看到"我明明配的是 3 条，保存后变 2 条" | 三级显式次序 + 判据"同一输入两次调用逐项相同" |
| R4 | **配置缓存跨实例失效** | 🔴 高 | API 双实例下 A 实例改了配置、B 实例仍读旧值 ⇒ 越界校验时对时错。**单机测试全绿** | 不加进程内缓存；若必须缓存，失效事件走 PG NOTIFY（ADR-14 同机制），且判据必须**跨实例**验证 |
| R5 | **审计被绕过或可篡改** | 🔴 高 | "上限被谁改了"无法追溯 ⇒ 按 ADR-13 的说法，**不可审计即不可验收** | 追加式表（不用 UPDATE/DELETE）+ 触发器拦改删（复用 WP11 已验证机制）+ 负向测试 |
| R6 | **越界校验漏入口** | 🟠 中 | ADR-13 代价 #2 原文：需覆盖创建、调整、局部重做、批量操作，**漏一个入口就是漏洞** | 校验函数**只有一个**（纯函数），所有入口调用它；判据：全仓 grep 上界常量，除校验函数外零命中（ADR-13 验证方式「无硬编码残留」） |
| R7 | **停用场景后比例未归一** | 🟠 中 | 合计 990‰ 而**不报错**，整数分配少分一条 | 归一是**保存草稿的副作用**（服务层做，不是前端做）+ 判据"停用后进行，合计 == 1000" |
| R8 | **`runtime_settings` 变成万能杂货表** | 🟡 中 | 无取值域、无类型约束 ⇒ 任意键任意值，读取方各自解释 | 每个键有**独立的 Pydantic 校验模型**（在服务层按 key 分派），未知键**拒绝**而不是放行 |
| R9 | **`created_at` 排序取"最新配置"** | 🟠 中 | 同事务时间戳相同 ⇒ 排序退化成随机（WP17 ISS-52 实证） | 用**显式递增的 `revision_no`** + 唯一约束保证全序，不靠时间戳 |
| R10 | **项目级副本与全局值悄悄分叉** | 🟠 中 | 老大拍板"项目级必须有副本"⇒ 副本若只复制、不同步，则全局改上限后项目仍按旧值跑，而**系统不报错**（助手在提问时明确指出过此风险，老大仍选择此路 ⇒ 必须由机制兜住，不能靠人记得） | ① 全局变更**同一事务内**刷新所有未覆盖副本（§3.6.2）；② 运营显式覆盖过的项目**不跟随**，但接口必须显式返回 `diverged=true` + 两个值（§3.6.4 J3）；③ 穷举判据 J2 断言"**所有**未覆盖项目的生效值都等于新全局值" |
| R11 | **副本首次产生依赖跨包改动** | 🟠 中 | 项目创建在 WP07（M1），本包在 M3 ⇒ 若回头改 WP07 的创建流程，就是跨包接缝改动（本项目明确的并行开发风险） | 副本走**读取路径惰性补**（§3.6.3），WP07 一行不改；代价是按 key 粒度补 + 必须并发安全（**按 key 的 `pg_advisory_xact_lock` + 普通 INSERT + 重读**，**不用 `ON CONFLICT DO NOTHING`** —— 见 §3.6.3 的实测论证） |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（2 张新表，均为**追加式/不可变**）：

| 表 | 角色 | 可变性 |
|---|---|---|
| `runtime_settings` | 配置的**历史**（每次变更插一行）。当前生效值 = 同一 `(key, scope_kind, project_id)` 下 `revision_no` 最大的一行。含 `origin`（`GLOBAL`/`INHERITED`/`MANUAL`）区分"全局真值 / 项目副本 / 项目覆盖" | **不可变**（触发器拦 UPDATE/DELETE） |
| `plan_drafts` | 步骤 4 的工作区（场景比例 + 形式比例 + 配对）。一项目一份 | **可变**（`lock_version`，ETag 载体） |

**为什么 `runtime_settings` 做成追加式而不是"就地 UPDATE + 独立审计表"**：

| 维度 | 追加式（本实现） | 就地 UPDATE + 审计表 |
|---|---|---|
| 审计要求的"变更前值/变更后值完整快照" | 前值 = 上一行，**天然可读**（不是哈希） | 需要审计表**自己带快照**，且快照与真值可能分叉 |

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**把"这一批怎么分"从一段商业约定，变成一组满足"合计恒等 + 可复现 + 可审计"三条硬性质的整数运算**——比例用千分位整数（无浮点），分配用最大余数法（和不漂移），平局用显式三级次序（可复现），上限放 `runtime_settings`（改动免迁移）。

### 2.2 用户画像

**运营是唯一的人，其余是系统。**

- 运营：一次配置 7 个场景 + 4 种形式的比例，看着"最大余数法换算过程"表理解系统为什么这么分；
- 运营**会算不对**：7 个比例手配到合计 1000‰ 很容易差 10‰，系统必须在**他还在拖数字时**就告诉他差多少，而不是提交时回 422；
- 管理者只看"上限被谁改了"；
- 系统（WP25/31/32）只读"当前生效值"，且**必须与运营看到的是同一个数字**。

### 2.3 核心功能清单（MVP）

| # | 功能 | 判据（能报红的那种） |
|---|---|---|
| F1 | 千分位比例归一与校验 | 停用场景后进行，`sum == 1000`；人工输入合计 ≠ 1000 时列出偏差 |
| F2 | 整数分配（最大余数法） | 穷举 total 1..120 × 项数 2..8 ⇒ `sum(result) == total` 恒成立 |
| F3 | 三级次序 | 8 类各 125‰、total=4 ⇒ 结果与"按 (余数, sortOrder, id) 排序"逐项一致 |
| F4 | 容量削峰 + `unallocated` | 全部满容时 `unallocated > 0` 且 `sum(result) + unallocated == total` |
| F5 | 子配额从剩余额度分 | 3 批各自分配 ⇒ 累计逐项 == 一次性分配（C19 的"列和恒等于总计划"） |
| F6 | 越界校验（唯一入口） | 下界-1 / 下界 / 上界 / 上界+1 四个边界各一条用例 |
| F7 | 配置变更 + 审计 | 变更后同一请求行为改变（不改代码、不发版、不迁移）；审计记录含前后值/人/时间/理由/requestId |
| F8 | 审计不可篡改 | 对真实行 `UPDATE` / `DELETE` ⇒ 被拦 + `sqlstate=23001` |
| F9 | 草稿固化出 PLAN 版本 | `version_nodes` 新增一行 `entity_type='PLAN'`，且 `payload_hash` 可复算 |

### 2.6 技术风险评估（含应对）

见 §1.6。补充三条**必须在编码前定死**的实现约束：

1. **比例只有一种表示**：`int` 千分位，全链路（DTO / 列 / 纯函数参数 / 前端）不得出现 `float` 百分比。若某处必须是百分数（如展示），转换只允许在**渲染边界**发生一次。
2. **分配函数不得读库**：`allocate_by_weight(items, total)` 的入参是纯数据。它一旦能读库，就再也无法穷举验证 —— 而穷举是本包唯一能证明"和不漂移"的手段。
3. **当前生效值的读取路径只有一条**：`get_effective_limits()`。任何地方直接 `SELECT * FROM runtime_settings ORDER BY created_at DESC LIMIT 1` 都是错的（R9）。
4. **写 `runtime_settings` 的路径只有两条**：`change_global_setting()` 与 `change_project_setting()`（§1.7）。**副本的插入是这两条路径与惰性物化的内部行为**，不得成为第三个公开入口 —— 否则"副本跟随全局"这条性质就有了绕过口（判据 J2 会因此形同虚设）。
5. **副本状态是"该行的属性"而不是"外部约定"**：判断"是否跟随"只允许读 `origin` 列，不得用"项目是否曾调用过覆盖接口"之类的外部推断（本项目高频坑"用 state 推断首次"的同族）。

## 3. 阶段 3：多版本方案

方案的**分野是两处**：① `runtime_settings` 做成"就地 UPDATE + 审计表"还是"追加式"；② 场景形式草稿**独立建表**还是复用 `information_drafts`。

### 方案 V1 —— 只做配置化，不做比例分配（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 只建 `runtime_settings` + 审计，满足 ADR-13 的字面要求；比例与整数分配留给 WP32 |
| 优点 | 一两天能交付，ADR-13 的验证方式逐条可过 |
| 缺点 | ① 覆盖度盘点给本包的包名是**「场景形式草稿 / 基点比例 / 整数分配」**，三者全属本包；② 比例是 WP32 的**输入**，把它留到 WP32 会让 WP32 同时承担"配置化 + 分配 + 批次创建"三件事，而**那正是排期里 W12 最挤的一天**；③ 更关键的：**整数分配是本包唯一有数学性质、可穷举验证的部分**。把它挪走 ⇒ 本包只剩 CRUD，而 CRUD 的测试永远发现不了"和漂移一篇"这类缺陷 |
| 风险 | 交付一个"看起来做完了 ADR-13"的包，而真正的成本正确性（篇数）无人验证 |
| 结论 | ❌ **否决**。ADR-13 是**本包的上游输入之一**，不是本包的全部 |

### 方案 V2 —— 就地 UPDATE + 独立审计表（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | `runtime_settings(key, value, updated_at)` 就地更新；另建 `runtime_setting_changes` 存审计（含前后值快照） |
| 优点 | 表结构符合直觉；"当前值"一查就有，不需要 `ORDER BY` |
| 缺点 | ① **审计要求"变更前值/变更后值完整快照"**。而快照存在审计表里 ⇒ 有两个真值来源（`runtime_settings.value` 与审计表的"后值"），分叉时**不报错**；② 不可篡改要**守两张表**，且"当前值"那张**仍可被改** ⇒ "先改当前值、再补一条看起来正常的审计"这条路是通的，而它**恰好是审计要防的事**；③ ADR-13 原文"审计记录不可被后续修改或删除，**与费用账本、版本快照同级对待**" —— 账本与快照在本仓都是**追加式**（`usage_ledger` / `brief_versions` / `production_baselines`），就地 UPDATE 与这个级别不同 |
| 风险 | 典型技术债：审计"看起来有"，但**它证明不了当前值的历史** |
| 结论 | ⚠️ **不推荐**。省下的是一次 `ORDER BY`，付出的是"审计可被绕过" |

### 方案 V3 —— `runtime_settings` 追加式 + `plan_drafts` 独立表 + 纯函数分配（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | ① `runtime_settings` **追加式**（`revision_no` 显式递增 + 唯一约束）；当前生效值 = 该 `(key, scope, project_id)` 下 `revision_no` 最大那行；表级不可变（触发器）。② `plan_drafts` 独立表（一项目一份，`lock_version`）。③ 纯函数模块 `allocation` / `permille` / `limits`。④ 草稿固化出 `version_nodes(entity_type='PLAN')` |
| 优点 | ① **审计与真值同源** —— "变更前值"就是上一行，不需要第二个真值来源，**分叉在结构上不可能**；② 不可篡改**一个触发器守全部**（与 `production_baselines` / `brief_versions` 同机制，已在 WP11/WP18/WP22 验证三次）；③ 分配是**纯函数** ⇒ 可穷举验证，"和不漂移"从"希望如此"变成"证明如此"；④ `scope_kind` 可空 = 平台级，与 WP16 `capability_policies` 的 `project_id` 可空**同一模式**（全仓一致），OP-60 的项目级覆盖因此**不需要改结构** |
| 缺点 | ① 读"当前值"不是 `LIMIT 1` 那么简单（要按 `revision_no` 取最大）—— 缓解：路径收进 `get_effective_limits()` 一个函数，且**判据禁止其它地方直接查**；② 表随变更增长 —— 量级极小（ADR-13 原文）；③ 纯函数与 ORM 分离，多一层 DTO —— 缓解：这正是可测性的来源 |
| 风险 | 若出现"绕过服务层直接写 `runtime_settings`"（运维手工 SQL），非法值可能落库。ADR-13 已识别该代价，处置是**数据核检 + 导入路径复用同一校验函数**；本包把校验做成**唯一纯函数**正是为了让那两条路径都能复用 |
| 适合场景 | 本包的实际处境：审计是 ADR-13 的核心要求（"不可审计即不可验收"）、分配的可复现性是 AC-10~12 的判据 |
| 结论 | ✅ **推荐** |

### 方案 V4 —— 完整版（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | V3 + `batches` 表 + 内容形式媒体数量校验 + 场景去重容量（C13 加权几何均值）+ 竞品事实账本 + 配置管理页面 + CLI 改配置工具 |
| 优点 | 一次性到位 |
| 缺点 | **严重越界**：① `batches` 的真正消费者是 WP31/WP32，建了就等它们来用 —— **建了不用就是死表**（与 WP13 砍 `job_dependencies` 同一判据）；② 场景去重容量需要"可用人群数/触发事件数/决策点数/独立证据数/视觉场景数"五个维度的实测输入，而这些数据的产生方（WP21 检索 / WP22 审核）**刚落地、尚无真实数据** ⇒ 现在算出来的是**用假数据算的真公式**；③ 竞品事实账本在 P03 未落地前**恒为空集**（C20 原文），建了只能用空集跑；④ **CLI 改配置工具与 ADR-13 的审计要求直接冲突** —— 给一条绕过审计的路径，等于把"不可篡改"作废 |
| 风险 | 表建了但语义错，后续包要迁移 + 回填。**本项目已有先例**（WP11 §3 / WP12 §3 / WP13 §3 都讨论并否决过越界交付） |
| 结论 | ❌ 不选。**边界不按"表在哪一章"划，按"有没有设计空间"划**：`runtime_settings` 的**列**（key/scope/value/revision）在 ADR-13 里已定死（无设计空间）→ 本包做；`batches` 的**批次状态机与关卡语义**是一整套策略（有设计空间）→ WP31/WP32 做 |

### 3.5 方案选择与理由

**选 V3。** 三条理由，按权重排序：

1. **审计必须是"结构上不可绕过"，不是"流程上不该绕过"。**
   追加式让"当前值"与"历史"是同一份数据 —— 反过来（V2）则有两个真值来源，而它们的**分叉不报错**。ADR-13 把配置审计定为"与费用账本、版本快照同级"，而本仓那两者的实现都是追加式。

2. **整数分配必须可穷举验证，所以它必须是纯函数。**
   "10 篇不能变成 11 篇"只有在能枚举所有输入时才是**被证明的**；做成读库的服务方法就只剩几条样例，"和漂移"会长期潜伏（历史原型里实测过：`[3, 3, 94]` 有 4 个分类对不上）。

3. **`scope_kind` 让"项目级副本"与"项目级覆盖"在同一张表里用同一套机制承载。**
   OP-60 老大已拍板：**支持且必须有项目级副本**（§3.6）。追加式表天然容纳这件事 —— **副本**就是一行 `origin='INHERITED'` 的 PROJECT 行，**覆盖**就是一行 `origin='MANUAL'` 的 PROJECT 行，两者同源同表，不需要第二张"项目配置表"。它们的唯一差异（是否跟随全局变更）由一个 `origin` 列表达 ⇒ "这条副本该不该跟随"从一段口头约定变成一条**可判据的属性**。

### 3.6 ★ 本包对 OP-60 的回答（ADR-13 要求"WP24 设计时定"）

**老大拍板结论：支持项目级配置覆盖，且每个项目必须有项目级副本。**

> 助手在提问时明确不推荐此选项（原文："全局改值时项目副本不会跟着变，而系统不会报错，只会让两个项目的上限悄悄分叉"）。
> 老大仍选择此项 ⇒ **这条分叉风险从"避免"转为"必须由机制兜住"**。下面的 §3.6.2~§3.6.4 就是兜住它的三件事：
> **同步（结构上保证）→ 分叉显式化（接口上保证）→ 四条能报红的判据（验证上保证）**。
> 不采用"靠运营记得去看"这种处置 —— 那正中本项目「判据纪律 #9：声称自己有防线比没有防线更危险」的靶心。

#### 3.6.1 三态模型：全局 / 副本 / 覆盖

"项目级副本"与"项目级覆盖"**不是两张表，而是同一张表的两种 `origin`**：

| `origin` | 语义 | 是否跟随全局变更 | 谁产生 |
|---|---|---|---|
| `GLOBAL` | 平台级真值（`scope_kind='GLOBAL'`，`project_id IS NULL`） | — | 管理者显式变更 |
| `INHERITED` | **项目级副本**：值为全局值的快照 | ✅ **是**（同事务级联刷新） | 系统（迁移回填 / 惰性物化） |
| `MANUAL` | **项目级覆盖**：运营显式改过 | ❌ 否（这是覆盖的意义） | 运营显式变更 |

**为什么用 `origin` 列而不是两张表**：副本与覆盖的唯一差异就是"是否跟随"，而"是否跟随"是**一行的属性**，不是**一类实体的属性**。同一项目从"跟随"变成"覆盖"时，只是插入一行 `origin='MANUAL'` 的新版本 —— 追加式表天然承载这次语义迁移，**不需要搬家**。这也让"当前生效值"的读取路径始终只有一条（`revision_no` 最大那行），不因 origin 而分叉。

#### 3.6.2 全局变更时的一致性机制（**结构上保证同步**）

**核心：副本刷新与全局变更在同一个数据库事务内完成。** 不存在"先改全局、稍后刷副本"的窗口。

```text
全局配置变更（唯一写入口 settings_service.change_global()）
└─ 单个事务
   ├─ ① INSERT runtime_settings(key, scope_kind='GLOBAL', project_id=NULL,
   │                              value=新值, revision_no=全局 max+1, origin='GLOBAL', ...审计列)
   ├─ ② 对所有项目 P、对本次变更的 key：
   │     若 P 的当前生效行 origin='INHERITED'（含"该项目该 key 尚无 PROJECT 行"）
   │        ⇒ INSERT (key, 'PROJECT', P, value=新值, revision_no=P 的 max+1, origin='INHERITED')
   │     若 P 的当前生效行 origin='MANUAL'
   │        ⇒ 跳过（覆盖必须稳定，否则"覆盖"没有意义）
   └─ ③ COMMIT（① 与 ② 同生共死）
```

三个关键性质：

1. **原子性**：读已提交隔离级别下，任何时刻读到的要么是"全局旧的 + 副本旧的"，要么是"全局新的 + 副本新的"，**不存在混合态**。这是 API 双实例场景（WP12 ISS-28 的坑）下的正确性来源 —— 不依赖任何进程内缓存，因此**双实例下行为一致**。
2. **覆盖稳定**：`MANUAL` 项目在全局变更后值不变 —— 这正是"覆盖"的定义，也是判据 J4。
3. **代价有界**：行数增长 = 变更次数 × 项目数。按 50 项目 × 每次变更新增 ~50 行，量级与 ADR-13 "量级极小，可忽略"一致。

> **不采用的做法**：把副本刷新放到异步任务 / 消息队列。那会引入"配置改了但副本还没刷完"的窗口，而这个窗口内**前端显示的生效值与后端校验用的值不一致** —— 与 R4（配置缓存跨实例失效）是同一类故障，只是换了个位置。

#### 3.6.3 副本的首次产生（**不动 WP07**，三条路径兜全）

项目创建在 **WP07（M1）**，本包在 M3 ⇒ 若回头改项目创建流程，那是**跨包接缝改动**（与并行开发纪律冲突，见 §1.6 R11）。因此副本的首次产生完全由本包侧完成：

| 路径 | 时机 | 覆盖的场景 |
|---|---|---|
| (a) **迁移回填** | 本包迁移执行时（迁移链由本包独占） | 存量项目（M1/M2 期间已建） |
| (b) **惰性物化** | `get_effective_limits(project_id)` 发现该项目该 key 无 PROJECT 行时 | 新项目首次被读取时（**兜底**，保证"必须有副本"在任何时序下都成立） |
| (c) **级联刷新** | 全局变更事务内（§3.6.2 步骤 ②，"尚无 PROJECT 行"视同 `INHERITED`） | 项目在两次全局变更之间创建且尚未被读取 |

**惰性物化的并发安全**（这是唯一的写副作用读路径，必须写对）：

```sql
-- ① 先取事务级排他锁（按 key，而不是 key+project）
SELECT pg_advisory_xact_lock(hashtext(:key)::bigint);
-- ② 拿锁后重读一次：另一事务可能刚插入并提交
SELECT ... FROM runtime_settings
 WHERE key=:key AND scope_kind='PROJECT' AND project_id=:pid
 ORDER BY revision_no DESC LIMIT 1;
-- ③ 仍无行 ⇒ 普通 INSERT（不是 ON CONFLICT DO NOTHING）
INSERT INTO runtime_settings (..., origin) VALUES (..., 'INHERITED');
-- ④ 重读一次拿 revision_no 最大的行（不信任本次 INSERT 的返回值）
```

**为什么插入后必须重读**：两个实例同时首次读取同一 `(key, project)` 时，只有一个插得进去，**另一个拿不到生效行** ⇒ 必须重读才能拿到实际生效行。这是本项目高频坑"用 state 推断首次"的同族问题：**不能靠"我插入了"推断"我就拿到了那行"**。

**为什么**不用** `ON CONFLICT DO NOTHING`（本节初稿的写法，已实测否决）**：

静默跳过在**同一个值**的竞争下是对的（幂等），但在**不同值**的竞争下会**丢写且不报错**：

    T1（全局改成 V2）与 T2（全局改成 V3）并发，项目 P 尚无副本行
    · T1 算得 P 的下一修订号 = 1，插入 (rev 1, V2)
    · T2 也算得 1，插入 (rev 1, V3)  ← 被部分唯一索引拒绝
    · T2 的 ON CONFLICT DO NOTHING **静默跳过**
    结果：全局 = V3，项目 P 的生效副本 = **V2**

这正是 J2 要拦的形态，而它是**静默**的 —— 两个数字都在、都不报错、合计也对得上。因此实际实现改为「**先取锁 → 普通 INSERT → 重读**」，让真正的冲突以异常暴露（那是缺陷，不是常态）。

> **锁的粒度为什么是 key 而不是 key+project**：全局变更要刷新**所有**项目的副本，逐项目加锁会引入"先锁 A 后锁 B、另一事务先锁 B 后锁 A"的死锁。按 key 一把锁最简单且无死锁。

#### 3.6.4 分叉的显式暴露（**接口上保证可见**）

机制保证同步（§3.6.2），但 `MANUAL` 覆盖**本来就应该分叉** —— 它是有意为之。要防的不是"分叉"，而是**"分叉了没人知道"**。因此读取接口必须携带来源与差量：

| 返回字段 | 含义 |
|---|---|
| `value` | 本项目**实际生效**值 |
| `source` | `'GLOBAL'` / `'INHERITED'` / `'MANUAL'`（**生效值从哪来**） |
| `global_value` | 当前全局值（**始终返回，不因被覆盖而为 null**） |
| `diverged` | `value != global_value`（bool） |

**这四条一起才构成防线**：只给 `value` 就是原选项里那个"悄悄分叉"；给了 `diverged` 才有可断言的对象；给了 `global_value` 才能让人**看见差在哪**（前端文案：`本项目已覆盖 · 当前 5 条 · 全局 10 条`）。

配套管理侧端点：`GET /settings/projects/diverged` —— 列出所有 `diverged=true` 的项目。管理者不必逐个点开 50 个项目找差异（这正是"分叉不报错"的实际杀伤路径）。

#### 3.6.5 `NULL` 的唯一约束问题（本包最易写错处）

`(key, scope_kind, project_id, revision_no)` 不能用裸 `UNIQUE` 约束：**PG 中 `NULL` 在唯一约束里不等于 `NULL`** ⇒ `project_id IS NULL` 的全局行可无限重复插入，而**约束不报错**。改用两条**部分唯一索引**（本项目已有部分索引"静默退化"的前车之鉴，故必须做活性验证，见 J1）：

```sql
CREATE UNIQUE INDEX uq_rs_global  ON runtime_settings (key, revision_no)
  WHERE scope_kind = 'GLOBAL';
CREATE UNIQUE INDEX uq_rs_project ON runtime_settings (key, project_id, revision_no)
  WHERE scope_kind = 'PROJECT';
```

不用 `COALESCE(project_id, sentinel)` 的做法：哨兵值会污染数据，且"哨兵"这个约定本身没有任何约束保证。

#### 3.6.6 判据（四条，全部可反向验证）

| # | 判据 | 反向验证（把正确实现改坏必须 FAIL） |
|---|---|---|
| **J1** | **副本存在性 + 索引活性**：(i) 任意项目读取后，其每个 key 都有 PROJECT 级当前行；(ii) 对 `scope_kind='GLOBAL'` 重复插同 `(key, revision_no)` ⇒ 被拒（`sqlstate=23505`）；对 PROJECT 级同理 | (ii) 把部分索引的 `WHERE` 写错（如 `WHERE scope_kind = 'PROJECTX'`）⇒ 索引**静默失效** ⇒ 必须 FAIL |
| **J2** | **同步性**：全局变更后，**所有** `origin='INHERITED'` 项目的生效值 `==` 新全局值（穷举所有项目，不是抽样） | 删掉 §3.6.2 步骤 ② ⇒ 必须 FAIL（这条正是助手担心的"悄悄分叉"） |
| **J3** | **分叉可见**：某项目 `MANUAL` 覆盖为不同值 ⇒ 接口返回 `source='MANUAL'` 且 `diverged=true` 且 `global_value` 为全局值（非 null）；`GET /settings/projects/diverged` 能列出它 | 让接口吞掉 `global_value`（返回 null）⇒ 必须 FAIL |
| **J4** | **覆盖稳定**：`MANUAL` 项目在若干次全局变更后值**保持不变** | 把级联刷新改成"无差别刷所有项目"⇒ 必须 FAIL |

> J2 与 J4 是一对**互相夹逼**的判据：只有"刷该刷的、不刷不该刷的"才能同时通过。
> 任何"全刷"或"全不刷"的实现都会至少踩中一条 —— 这是本包对老大那句"我不推荐"给出的工程回答。

#### 3.6.7 对既有设计的收束

| 维度 | 决定 |
|---|---|
| 列设计 | `scope_kind IN ('GLOBAL','PROJECT')` + `project_id`（GLOBAL 时必为 NULL）+ **`origin IN ('GLOBAL','INHERITED','MANUAL')`** |
| 唯一约束 | 两条**部分唯一索引**（§3.6.5），非裸 `UNIQUE` |
| 读取语义 | `get_effective_limits(project_id)`：取该项目 PROJECT 级当前行；无 ⇒ **惰性物化**（§3.6.3）后返回；返回结构含 `source`/`global_value`/`diverged` |
| 变更记录 | 审计行**自身**带 `scope_kind` + `project_id` + `origin` ⇒ ADR-13 要求的"生效范围"字段天然满足 |
| 默认行为 | 迁移写入 `GLOBAL` 行（10/30/50）+ 为存量项目回填 `INHERITED` 副本 ⇒ 所有项目生效值一致，与 ADR-13 "默认 10/30/50" 完全兼容 |
| 跨包改动 | **零** —— WP07 不改（§3.6.3），`batches` 不建（§1.5） |

### 5.4 ★ 判据自身的缺陷 —— 错误 ⑪：穷举不变量断言在**结构上恒真**

> 这是本包最值得记的一条，**它不是代码缺陷，是判据缺陷**。

**现场**：本包唯一能证明"分配和不漂移"的手段是**穷举**（`test_allocation_invariant_holds_exhaustively`，≥1000 组输入）。而收口时发现那条穷举的核心断言是：

```python
assert result.allocated_total + result.unallocated == total
```

**它恒真**。因为实现里 `unallocated = total - sum(allocated)`，而 `allocated_total = sum(allocated)` —— 代入后等式两边是**同一个表达式的两种写法**。这条断言对**任何**实现都成立，包括错误实现（比如"把某条多分 1 条、`unallocated` 相应减 1"，等式照样成立）。

**它与 ISS-75 同族但更隐蔽**：

| | ISS-75（WP19） | 错误 ⑪（WP24） |
|---|---|---|
| 恒真来源 | **数据库 CHECK** 保证（`has_evidence` 由 CHECK 保证为真） | **判据自己写出的代数恒等** |
| 发现方式 | 读 CHECK 定义 + 比较判据 | 需要**AST 检查"断言两侧是否引用了同一批变量再线性组合"** |

**处置**：改为对**每一项**断言其与"独立算出的期望值"逐项相等 —— 期望值由**另一条路径**算出（测试侧实现 `_expected_largest_remainder`，与生产实现**独立**），并做反向验证：

- 判据：`测试内无 allocated_total + unallocated == ? 自证断言`（AST 判定，0 命中）
- 判据：`测试侧存在独立实现 _expected_largest_remainder`（互证数据源）
- 判据：`unallocated >= 0 进断言（不是注释）`
- 反向验证③：把 `assert result.allocated_total + result.unallocated == 10` 加回测试 ⇒ 判据报红 `['L1105']` ✓

**沉淀的纪律（本包新增第 12 条）**：

> **凡"穷举/不变量"判据，必须先问：这个等式是"两种独立事实的相遇"，还是"同一个事实的两种写法"？**
> 后者恒真。恒真判据比恒假判据更危险 —— 恒假会有人去查，恒真则所有人都以为"穷举在看着"。

### 5.5 ★★ 错误 ⑫：判据**能报红**，但报红的**原因**是错的 —— "抛出点巧合"

**现场**：`get_global_setting_history` 的"白查"缺陷（MINOR-7），我第一版写的判据是"记录查库次数，断言 `<= 1`"。反向验证（把白查加回去）**确实报红了** —— 判据看起来有效。

**但它红的原因错了**：那条 422 的 `ensure_setting_key` 在**查库之前**就抛了异常，于是"查库次数"根本没涨到 2，报红是因为**别的断言先失败**。也就是说：**这个判据从来没有真正检测过它守卫的那个缺陷**。

**为什么这一类特别危险**：它骗过了**反向验证**这道最后防线。反向验证只回答"会不会红"，不回答"为什么红"。于是"偶然报红"与"判据有效"在观测上**同形**。

**处置**：把判据挪到缺陷**真正发生**的路径上（用合法 key 走完全流程再计数），并在反向验证里**同时断言红的形状**（失败断言的位置 + 消息），而不只是"退出码非 0"。

**沉淀的纪律（本包新增第 13 条）**：

> **反向验证必须校验"红的形状"。** 只断言"非 0 / FAIL"不够 —— 判据可能因为**别的**原因失败，
> 而那个原因与被守卫的缺陷**无关**。校验形状 = 断言失败的**断言文本/位置**是预期的那一条。

**该纪律已回灌到工具**（`ISS-140`）：`tools/m3/collect_wp24_code_review.py` 自身的反向验证方法
补了"红的形状"校验，因为**方法本身也需要判据**。

### 6.2 四条核心判据 J1~J4（本包验收的主干）

| 判据 | 断言什么 | 怎么做到能区分两种实现 |
|---|---|---|
| **J1** 惰性物化 | 首次读某项目的生效值时，副本行被建出且值等于全局值 | 断言"读之前 0 行 / 读之后 1 行 + 值相等"，并**对照**：第二次读**不再**新增行（幂等） |
| **J2** 全局变更级联 | **所有**未覆盖项目的生效值都等于新全局值 | **穷举全部项目** + 断言语句计数 `<= 3`（防 N+1 回归）；反向验证：循环内加回逐项目查询即报红 |
| **J3** 分叉可见 | 用户覆盖过的项目，接口必须返回 `diverged=true` + 两个值 | 造"全局 10 → 项目覆盖 20"的场景，断言响应含 `diverged` / `global_value` / `effective_value` 三者 |
| **J4** 覆盖稳定 | 覆盖后再改全局，该项目**不跟随** | 与 J2 **互为夹逼**：J2 断言"未覆盖的都跟随"，J4 断言"覆盖过的不跟随" —— 单看任一条都不足以证明机制正确 |

**为什么 J2 与 J4 必须成对**：只有 J2 ⇒ 一个"全员永远跟随"的错误实现能通过；只有 J4 ⇒ 一个"谁也不跟随"的错误实现能通过。**两条一起才锁住"跟随 / 不跟随"的分界线**。

### 6.3 分配算法：穷举与两条路径

| 项 | 做法 |
|---|---|
| 穷举规模 | 两条路径各 **≥1000 组**（无容量路径 / 有容量削峰路径） |
| 断言形式 | **逐项**与独立算出的期望值相等（**不是**总和自证 —— 见 §5.4） |
| 平局三级次序 | 余数大 → `sortOrder` 小 → `id` 字典序；构造 8 类各 125‰ 的"全平局"用例 |
| 停用项 | 停用后比例**重新归一**（合计 == 1000），且容量路径上**不参与分配**（MAJOR-5） |
| `unallocated` | 全部满容时**不硬塞**（计入 `unallocated`），且 `>= 0` |

### 7.2 处理的两处（都不是为行数）

**① `service._validate_dimension`：110 → 47 行**（拆出 `_validate_dimension_item`）
不是为行数：110 行里 90 行都在讲"**一个条目**长什么样"，而函数名说的是"**一个维度**"。两层的失败语义完全不同 ——

> 「判据纪律第 1~N 条」这一定义体系（见 `docs/判据纪律-编号口径.md` §2.3）。

### 第 12 条 —— 穷举/不变量判据必须问"这是两种独立事实的相遇，还是同一事实的两种写法"

> **凡"穷举验证"或"不变量断言"，先检查它的等式是不是代数恒等。**
> `sum(x) + (total - sum(x)) == total` **对任何实现都成立**，包括错误的实现。
> 它写在测试里、跑 1000 组、每次通过 —— 而它**什么都不判**。

**现场**：本包唯一能证明"分配和不漂移"的手段就是穷举，而那条穷举的核心断言是恒真式。
**发现方式**：AST 检查"断言两侧是否引用了同一批变量再线性组合"。
**处置**：改为与**独立路径算出的期望值**逐项相等（测试侧 `_expected_largest_remainder` 互证）。
**同族**：ISS-75（CHECK 保证恒真）——但本条的恒真是**判据自己写出来的**，比前者更隐蔽。

**反向验证必须做**：把恒真断言加回测试 ⇒ 静态判据立刻报红 `['L1105']`。

### 第 13 条 —— 反向验证必须校验"红的形状"

> **"注入错误实现 → 看判据是否报红"只证明了"会不会红"，没证明"为什么红"。**
> 判据可能因为**别的**原因失败，而那个原因与被守卫的缺陷**无关**。
> 于是"偶然报红"与"判据有效"在观测上**同形**。
> **必须同时断言失败断言的文本/位置是预期的那一条。**

**现场（错误 ⑫）**：`get_global_setting_history` 的"白查"判据，反向验证确实报红 ——
但红的原因是那条 422 的校验在**查库之前**就抛了异常，"查库次数"根本没涨到 2。
**这个判据从来没有真正检测过它守卫的缺陷**，而它骗过了反向验证这道**最后防线**。

**处置**：把判据挪到缺陷真正发生的路径上（用合法 key 走完全流程再计数）+ 反向验证断言红的形状。
**已回灌**：`tools/m3/collect_wp24_code_review.py` 自身的反向验证方法补了形状校验（ISS-140）
—— **方法本身也需要判据**。

### 第 14 条 —— "覆盖范围"由人写，就必须有判据对账它（第三次重申，仍是同一个病）

> 名单 / glob / 目录判断 / **包号上界** —— 只要"管到哪"是人写的，
> 就必须另有一条判据去对账它。**且对账必须双向**（既查"漏了"，也查"名单里有已失效的"）。

**现场（ISS-139）**：本仓同一族缺陷**第三次**复发（ISS-104 → ISS-111 → ISS-139）。
前两次的处置分别是"改递归"与"删早退"，本次是"glob 只扫 `tools/m1/`"。
**三次都是同一个病** ⇒ 它不是疏忽而是**结构问题**：防线本身没有防线。

**处置**：glob 改为 `REPO_ROOT.glob("tools/**/...")`（覆盖范围由磁盘决定）+ 拿掉隐含的包号上界。

### 第 15 条 —— 判据的**适用范围**必须写明，否则"没报红"会被误读成"缺陷不存在"

> 一条静态判据没报红，可能因为：①缺陷不存在；②**缺陷不在它的适用范围里**。
> 这两件事在输出上同形。**必须在证据里显式标出每条判据"管什么、不管什么"。**

**现场**：MAJOR-2（`unallocated` 可为负）的反向验证④（把 `total - sum(...)` 改成 `max(0, ...)`）
**不报红**，而这是**正确的** —— 该缺陷的判据在**测试侧**（互证 + `>= 0` 断言），
靠**跑测试**报红，不靠静态扫描。
如果不写清适用范围，读的人会把"静态判据没报红"误读成"这个缺陷不存在"。

**处置**：`wp24-code-review.log` 的每条判据都标了适用范围；
反向验证④ 那条**特意保留**在证据里，就是为了说清这件事。
