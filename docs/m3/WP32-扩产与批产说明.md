## 0. 本包的一句话定位

**把"提交一个 1~30 条的扩产批次 / 1~50 条的批产批次"变成一次可重放、可部分失败后恢复、可核对"到底按哪个上限、哪份方案、哪个基线提交的"的事务：同一个请求重发不会多出一个批次、多出一条内容、多出一个任务，也不会多花一笔钱；一半失败时，成功的不重做、失败的能补做、未知的不乱重试。**

最后半句是本包最难的部分：**"失败""未知""没做"在数据结构上必须无法混淆**（jobs 已有 `WAITING_RECONCILIATION` 这个"未知"态，批次层不得把它折成失败再重试，见 §2.3.5）。

### 1.1 这个需求真正解决什么问题？

不是"多建几条内容"——WP26 的 `content-generations` 今天就能一次建 N 条。**缺的是批次这个实体**，于是下面这些事在今天全部无法回答：

| 无法回答的问题 | 缺的是什么 |
|---|---|
| "这 30 条是同一次扩产提交的吗？提交时按哪个上限？" | 批次身份 + 创建时刻上限快照（ADR-13 迁移影响 #4） |
| "客户端超时重发，会不会多出第二个批次？" | 批次级幂等键（`content-generations` 的幂等是**每条内容**的，没有"这一批"的概念） |
| "50 条里 12 条失败了，补做哪些？成功的会不会被重做？" | 批次 ↔ 内容 ↔ 任务的稳定关系 + 轮次 |
| "扩产内容和试产内容有没有重叠？" | 一条内容至多属于一个批次的数据库级保证 |
| "这批是按哪份方案、哪个基线生成的？基线后来变了吗？" | 钉住的方案版本与基线 |
| "累计配额有没有收敛到总计划？"（`allocate_from_remaining` 的输入 `allocated_so_far`） | 历史批次的分配快照 |

|---|---|
| **`job_dependencies`（DAG）** | 批次内每条内容是**相互独立**的任务，没有先后依赖；"失败项重做"靠轮次，不靠 DAG。**建议关闭 OP-106 为"WP32 不需要"**（Q14，登记册归主线） |
| **DRAFT 状态 / 草稿批次** | 预览做无状态端点即可，见 G9 |
| **批次层预占一整批** | 见 G3 / Q3。默认方案是"预估 + 可用额度预检"，不持有预占 |
| **批次间公平调度算法** | 无量化要求（§1.0 未找到依据）。MVP 沿用 jobs 现有领取顺序（Q13） |
| **自动重试** | 重试只由人触发（`retries` 端点）。盲目自动重试计费类操作 = 重复扣费（`M4契约与幂等口径.md` §1 末句） |
| **批次数量 / 档位 / 方案的事后修改** | 批次提交后不可改；要改 = 取消 + 新批次。这让 `batch_items` 可以不可变，也让"创建时刻上限快照"始终有意义 |
| **按批次的实际成本归集** | WP43 |
| **相似度 / 集中度计算** | WP33 |
| **审核汇总的计算逻辑** | WP29/WP31 的数据；本包最多留一个可空读位（Q20） |
| **批次列写入的列级守卫触发器** | `batches` 有两个会变的"命令位"，列级守卫要自写触发器函数；代价大于收益，改由"只有 CAS UPDATE 一个写路径 + 测试"承担（已知取舍，§2.6） |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 级别 | 对策 |
|---|---|---|---|
| R1 | 批次级幂等只靠应用层"先查再插"，并发双提交各建一份 | 高 | `UNIQUE(project_id, idempotency_key)`；输家在 SAVEPOINT 内捕获 23505 后回查比对 `request_hash`（ISS-22 教训） |

| R3 | 批次 `quantity` 与成员行数不一致且不报错 | 高 | 延迟约束触发器（DDL 草案第五节），提交时检查 |
| R4 | 重试把"未知"当"失败"重做，重复计费 | 高 | 只重做 `FAILED`；`WAITING_RECONCILIATION` / `WAITING_PROVIDER` 一律不动（`jobs/models.py:62-66,95-98`） |

| R6 | 同项目并发创建两个批次，各自读到相同的 `allocated_so_far`，累计配额越界 | 中 | 事务级 advisory lock 串行化（仓内先例 `planning/repository.py:67`，Q17） |
| R7 | 读路径（GET）带写副作用 | 中 | GET 一律纯读；读限制时 `materialize=False`（WP30 R9 同款；登记册 OP-174 的教训：`GET information-draft` 会写库） |
| R8 | `jobs.batch_id` 补 FK 后，只 `create_all` 部分表的测试夹具报 `NoReferencedTableError` | 中（**推理，未实测**） | Q12 |
| R9 | 重试路径与 WP26 handler 对"同一内容第二个 job"的幂等交互**未实测** | 中 | Q15；测试计划 T-RETRY 系列要先做探针 |
| R10 | 跨模块 import 未被接缝冻结登记（content / planning / baseline / billing / versions / jobs） | 中 | §2.11 列清单，Q11 |

### 1.7 数据结构、接口、前端、后端怎么拆？

* **后端文件布局（计划，本阶段不创建）**：`models.py` / `types.py` / `ddl.py` / `repository.py` / `service.py` / `schemas.py` / `api.py` / `dependencies.py`，加四个**转发桥**：`content_bridge.py` / `planning_bridge.py` / `billing_bridge.py` / `baseline_bridge.py`（沿用 `review/*_bridge.py` 与 `content/billing_bridge.py` 的"只转发、不写业务"做法，接缝冻结 §5.14 末行）。

## 2. 阶段 2：方案设计

### 2.1 `batches` 表设计

**字段、约束、索引、触发器的逐条规格见 `docs/m3/WP32-ddl-草案.py`**，此处只讲取舍。

| 表 | 一句话 | 可变性 |
|---|---|---|
| `batches` | 一个批次：档位 / 序号 / 数量 / 钉住的方案与基线 / 分配快照 / 创建时刻上限快照 / 预估 / 幂等键 | `state` 与 `lock_version` 等"命令位"可变，其余写入后不改 |
| `batch_items` | 批次内第 n 条内容；`UNIQUE(content_item_id)` | 不可变 |
| `batch_item_runs` | 某条内容的第 n 轮执行 = 一个 job；`UNIQUE(batch_item_id, round_no)` / `UNIQUE(job_id)` | 不可变 |

**关键列取舍：**

| 列 | 取舍 |
|---|---|
| `quantity` | **只有 `> 0`**（ADR-13）。上界不在 DDL，在应用层。`limit_applied` / `limit_source` 把**创建时刻**的生效上界与来源快照下来，这是 ADR-13 迁移影响 #4"以创建时刻的生效配置为准"的落点，也是 AC-10~12 事后核对的依据。**刻意没有 `quantity <= limit_applied` 的 CHECK**：绕过应用层的人同样可以改 `limit_applied`，那条 CHECK 是装饰，且会和"DDL 只留下界"的 ADR 字面冲突（是否要加见 Q17 附注，默认不加） |
| `batch_kind` | `BULK / SCALE / TRIAL` 三值 CHECK。**TRIAL 是否入这张表**是 Q4：WP31 也需要批次实体，若本表不含 TRIAL，WP31 要么 ALTER、要么另建表。`planning/types.py:112` 的注释已经预告"batch 档位在库里没有列"，本包是首个给它列的 |
| `seq_no` | 项目内同档位序号。**展示码 `BATCH-S01` / `BATCH-B01` 是读时拼的，不存**（原型的编号规则 T/S/B + 两位序号是展示约定，不是数据约束）。分配 = `max+1`，撞唯一键则 SAVEPOINT 内重取 |
| `plan_version_id` | 钉住的 PLAN 版本节点（`version_nodes.id`）。**由请求显式携带**，服务端只校验、不推断"最新"（§2.7） |
| `baseline_id` | 提交时钉住的基线（`production_baselines.id`）。**不存 `revision`**：基线的"当前"是 `projects.active_baseline_id` 投影（§2.7） |
| `allocation` | 本批分配快照（场景 / 形式 / `unallocated`）。`allocated_so_far` 的求和读它。**与 PLAN 快照节点的 payload 是同一个函数产出的同一份内容**（`build_allocation_snapshot`），测试断言两者相等，避免两处声称 |
| `estimated_amount` / `estimated_currency` | 提交时预估总额。**可空且同有同无**：NULL = 未预估，**不是 0**。本包路径一定填，留可空是为了不替 WP31 的 TRIAL 路径决定（Q4） |
| `estimate_refs` | `[{taskKind, estimateId}]`。一次 `FULL` 范围要预估两个 `task_kind`（`content/billing_bridge.py` 说明），一列 FK 装不下；这是**无 FK 的审计指针**，代价已在 DDL 里登记 |
| `idempotency_key` / `request_hash` | 幂等载体，§2.3 |
| `state` | 仅 `SUBMITTED / CANCEL_REQUESTED`，§2.2 |
| `lock_version` | ETag 载体（`platform.base.lock_version_column`），§2.6。架构文档的 `batch.revision` 在本仓的对应物 |

**与 `jobs.batch_id` 的关系：**

1. `jobs.batch_id` 是 WP13 留下的**无 FK 预留位**（`jobs/models.py:195-200`）。本包写入时**两处都写**：job 行的 `batch_id` / `content_id`，以及 `batch_item_runs`。后者是进度折算的依据（有确定的 `round_no`），前者是 jobs 侧"按批次查"的依据；DDL 里的 `trg_batch_item_runs_ownership_consistency` 把两处钉成同一件事。
2. **FK 补全由主线收口动作完成**。目标语句与顺序要求（草案第六节）：
   ```
   -- 先建 batches / batch_items / batch_item_runs，然后：
   ALTER TABLE jobs ADD CONSTRAINT fk_jobs_batch_id_batches
       FOREIGN KEY (batch_id) REFERENCES batches (id) ON DELETE RESTRICT;
   CREATE INDEX ix_jobs_batch_id ON jobs (batch_id) WHERE batch_id IS NOT NULL;
   ```
   加 FK 前预检 `jobs.batch_id` 非空且无对应批次的行（磁盘上没有写入路径会设它，**这是推断**）；稳妥写法 `NOT VALID` + `VALIDATE`。downgrade 严格逆序。
3. **主线还要改**：`jobs/models.py` 的 `batch_id` 列加 `ForeignKey`，并更正 `:195-197` 那段点名"WP24 / WP29"的过期注释（接缝冻结 §8.4 ②）。**我没有改，也不会改。**
4. `jobs.content_id` 的 FK **不是**本包前置（批次关系已由 `batch_items` / `batch_item_runs` 完整表达）。

### 2.2 状态机

#### 2.2.1 一句话

**批次行只存"命令"（已提交 / 已请求取消），"执行进度"永远从 `jobs` 读时折算，不落库。**

理由：`jobs` 是执行状态的权威；批次行再存一份就是第二处声称，而且**没有钩子**能在 job 完成时回写（`jobs/*.py` 禁改，派发器 / 处理器也不是本包的）。持久化 roll-up 需要一个周期性 reconciler，那是一个新的运行时组件。**这是本设计最大的取舍，列为 Q6，由主线拍板。**

#### 2.2.2 落库状态（`batches.state`，CHECK 字面量）

```
          POST /batches                      POST /batches/{id}/cancellations
 (无) ───────────────────► SUBMITTED ─────────────────────────────────────► CANCEL_REQUESTED
                              │                                                   │
                              └──── 无其它转移（SUBMITTED 不会因任务完成而变）      └──── 终态（不可恢复）
```

| 转移 | 触发 | 条件 | 写法 |
|---|---|---|---|
| (无) -> `SUBMITTED` | 创建 | 校验全过 | INSERT（同事务写成员 / 内容 / 任务） |
| `SUBMITTED` -> `CANCEL_REQUESTED` | 取消 | `If-Match` 匹配 | 条件 UPDATE：`WHERE id=:id AND lock_version=:v AND state='SUBMITTED'`，`lock_version+1`，写 `cancel_requested_at/by` |
| `CANCEL_REQUESTED` -> `CANCEL_REQUESTED` | 重复取消 | — | 200 幂等返回，不改任何列 |
| 其它 | — | — | 409 `INVALID_TRANSITION` |

`CANCEL_REQUESTED` 不可恢复：要继续就新建批次。这让 `batch_items` 不可变和"累计配额"的口径都保持简单。

#### 2.2.3 派生进度（`progress.state`，**不落库、无 CHECK**，API 枚举）

输入：批次 `state` + 每条成员**最新一轮**（`round_no` 最大）的 job 状态。

| 条件（自上而下，第一条命中即返回） | `progress.state` |
|---|---|
| 成员数 = 0，或任一成员没有任何 run | `UNKNOWN`（**不得折成 0 或 FAILED**） |
| 批次 `CANCEL_REQUESTED`，且所有最新 job 已终态 | `CANCELLED` |
| 批次 `CANCEL_REQUESTED`，仍有非终态 | `CANCELLING` |
| 所有最新 job 为 `QUEUED` | `QUEUED` |
| 存在非终态 job（`QUEUED / RUNNING / WAITING_PROVIDER / WAITING_RECONCILIATION / CANCEL_REQUESTED`） | `RUNNING` |
| 全部终态且全部 `SUCCEEDED` | `SUCCEEDED` |
| 全部终态，无 `SUCCEEDED` 且无 `PARTIAL`（即全是 `FAILED / CANCELLED`） | `FAILED` |
| 其余全部终态组合 | `PARTIAL` |

附带计数 `progress.counts`：按 job 状态分列的整数，另有 `needsReconciliation`（`WAITING_RECONCILIATION` 的条数，**单列**——它不是失败也不是成功，不得被任何汇总吞掉）。**`counts` 各项之和必须等于成员数，否则整体降级为 `UNKNOWN`**（§2.8）。

`jobs` 的状态集合与终态集合来自 `jobs/models.py:58-101`，本包 `types.py` 只经桥引用，不抄。

> 派生域共 8 个值（`QUEUED / RUNNING / CANCELLING / SUCCEEDED / PARTIAL / FAILED / CANCELLED / UNKNOWN`），进 §2.9 取值域清单；因为不落库，无 DDL CHECK，**一致性靠 `types.py` 常量 ⇄ OpenAPI 枚举对账**（见测试 T-ENUM）。

### 2.3 批量与幂等设计

#### 2.3.1 为什么现有幂等不够

| 层 | 现状 | 缺口 |
|---|---|---|
| 任务层 | `jobs` 的 `UQ(idempotency_scope, idempotency_key)`，`enqueue_job` 同键同体返回既有、异体 409（`jobs/service.py:154-239`） | 只保证"不重复建**任务**" |
| 内容层 | `content_items.last_idempotency_key`，`start_generation` 命中即原样返回（`content/service.py:1260-1305`） | 只保证"不重复建**内容**" |
| 模型层 | `content-generate:{content_id}:v{n}:{kind}`（网关） | 只保证"不重复**买**" |
| **批次层** | **无** | 没有"这一批"的身份，客户端重发只能靠下面三层各自去重，批次、成员、版本节点、预估都会重复 |

#### 2.3.2 幂等键与判定（本包新增的一层）

| 项 | 设计 |
|---|---|
| **键** | HTTP 头 `Idempotency-Key`，落 `batches.idempotency_key`；作用域 = **项目**（`UNIQUE(project_id, idempotency_key)`） |
| **载体** | **数据库唯一约束**，不是应用层 if（`M4契约与幂等口径.md` §0） |
| **请求摘要** | `request_hash = canonical_payload_hash({batchKind, quantity, planVersionId, baselineId, modelProfileId, scope})`（`versions/service.py:132` 已有的规范化哈希；**不含时间戳 / 操作人**，理由同 `plan_payload` docstring） |
| 同键同体 | 返回既有批次（**200**，body 带 `replayed: true`）；**不**再写任何东西 |
| 同键异体 | **409 `IDEMPOTENCY_CONFLICT`**，`details = {reason: 'idempotency_key_reused', existingBatchId, ...}`（与 `content/api.py` `create_content_generations` 的"同键不同体"分支同形） |
| 并发双提交 | 输家撞 `uq_batches_project_idempotency_key`（SQLSTATE 23505）。**必须在 SAVEPOINT 内**捕获（ISS-22：PG 里任何失败语句都会让整个事务 aborted），回查赢家行，再按上两条分流 |
| 键缺失 | 本设计建议**必填**（缺失 → 422 `VALIDATION_FAILED`，`reason: 'idempotency_key_required'`）。与 `content-generations`（缺失则现生成一个，"没给键 = 不做幂等"）**刻意不同**：批次会花钱，"不幂等"不应是默认可选项。Q8 |
| 首次创建状态码 | **202**（异步生成，同 `content-generations`）；重放 **200**（`M4契约与幂等口径.md` §2 的"同键 ⇒ 返回同行（200）"）。Q8 |

#### 2.3.3 创建事务（顺序不可调换）

> 全程**一个事务**。N 受 `batch.limits` 约束（默认最大 50），一事务写得下，因此**不存在"批次建了一半"的可见状态**；唯一的部分状态是**执行层**的（job 级）。

| 步 | 动作 | 失败时 |
|---|---|---|
| 0 | `access.require(ProjectAction.EDIT)`；构造 `request_hash` | 403 |
| 1 | **重放前置**：按 `(project_id, idempotency_key)` 查批次 → 命中则按 §2.3.2 分流并**结束** | 409 / 200 |
| 2 | `pg_advisory_xact_lock(hashtext('batch:'||project_id))`（Q17）：串行化同项目创建，保护 `seq_no` 与 `allocated_so_far` | — |
| 3 | 档位只接受 `SCALE / BULK`（TRIAL 见 Q4）；数量走 `planning_bridge`：`get_effective_limits('batch.limits', project_id)` -> `validate_quantity`，越界 -> 422，`details` 带 `reason`（`quantity_below_min / quantity_above_max / batch_kind_unknown`）、`limit`、`source` | 422 |
| 4 | **前提校验（"不能先通过后补查"，架构 §7.5）**：`planVersionId` 属于本项目、是 PLAN、是该项目 PLAN 链头；`baselineId`（若传）= `active_baseline_id`；二者与 PLAN payload 里的 `baselineId` 一致 | 409（Q9） |
| 5 | **关口**（WP31 提供，Q5）：试产全部处置 / 无未解决阻断 / 方向有已批准样例；新增方向 -> `DIRECTION_UNVERIFIED` | 409 / 422 |
| 6 | **分配**：对场景、形式两个维度各调一次 `allocate_from_remaining`（`allocated_so_far` 由历史批次的 `allocation` 求和，口径见 Q18）；任一维度 `unallocated > 0` -> 422 `allocation_incomplete`（**不静默少产**，C14 的"unallocated > 0 是正确结果不是错误"在这里要升级为拒绝，因为批次承诺的是 `quantity` 条） | 422 |
| 7 | **预估**：每个 `task_kind` 各调一次预估，汇总；**预算可用额度预检**（只读，§2.4）；失败原样透传 billing 的 `ApiError` | 422 `BUDGET_EXCEEDED` 等 |
| 8 | INSERT `batches`（`seq_no=max+1`，**SAVEPOINT 包住**；23505 按约束名分流：幂等键 -> 回到第 1 步的分流；`seq` -> 重取，<=3 次） | — |
| 9 | **PLAN 快照节点**：`register_version(entity_type=PLAN, entity_id=batch.id, revision_no=1, payload=allocation 快照, project_id, created_by)`（Q7）；可选 `link_dependency` 登记依赖边 | 409/422 |
| 10 | 物化内容：`content.start_generation(count=quantity, idempotency_key=f"batch:{batch.id}")` -> N 条 `content_items` | — |
| 11 | INSERT `batch_items`（`ordinal=1..N`；`scene_key` 经 D1 新接缝写入（`start_generation` 带入 `GenerationRequest`）；`form_key` 在 OP-227（Q2）定之前写 NULL） | — |
| 12 | 逐条 `enqueue_job(kind=CONTENT_GENERATE, queue='content', batch_id, content_id, project_id, idempotency_key=f"{content_id}:batch:{batch.id}:r1")`；INSERT `batch_item_runs(round_no=1, job_id)` | — |
| 13 | 审计 `batch.create`（open-set 动作串，§2.9）；提交事务 | — |

提交时 `trg_batches_item_count_consistency` / `trg_batch_items_count_consistency` / 两个归属触发器一并检查——**一致性在数据库里再核一遍**。

#### 2.3.4 失败项重做（`retries`）的幂等

| 层 | 机制 |
|---|---|
| HTTP 层 | `Idempotency-Key` 头 -> `jobs.service.begin_idempotent_request(scope=f"batch-retry:{batch_id}", key, request_hash, permanent=True)`；`REPLAY` -> 回放 `response_json`；`CONFLICT` -> 409。**`permanent=True`**：生产任务类请求不得因 7 天过期而再计费（`jobs/models.py:324-343`、`jobs/service.py:656-709`）。这是本包唯一使用通用幂等表的地方（G8） |
| 并发层 | 对批次做 CAS：`UPDATE batches SET lock_version=lock_version+1 WHERE id=:id AND lock_version=:v AND state='SUBMITTED'`。重做与取消、重做与重做互斥 |
| 数据层 | `UNIQUE(batch_item_id, round_no)`：同一条内容同一轮只能有一个 job。第二个并发重做即使绕过上两层也会被挡 |
| 任务层 | job 键 `f"{content_id}:batch:{batch_id}:r{round_no}"`，轮次进键，重放命中既有任务 |

#### 2.3.5 重试语义（回应接缝冻结 §5.2 的"WP32 必须显式传重试相关参数"）

**原文**（`M3并行开发接缝冻结.md:493-497`）：`revision_no=None` 不幂等（OP-91）；同一修订号重复注册——摘要一致返回既有节点 `created=False`，摘要不同 409 `INVALID_TRANSITION`；"需要幂等就显式传 `revision_no` —— WP32（批产）必须显式传，它天生要重试"。

**遵守方式（Q7 通过的前提下）：**

* WP32 调 `register_version` 的**唯一**位置是创建事务第 9 步：`entity_type=PLAN`、`entity_id=batch.id`、**`revision_no=1`（显式）**。
* `revision_no` 的取值是**确定的**（批次提交后不可改，每个批次恰一个快照节点），不依赖 `max+1`，因此任何形式的重试（事务整体重放、崩溃后重提）要么命中同一 `(PLAN, batch_id, 1)` 返回 `created=False`，要么在第 1 步就被批次级幂等挡掉。
* **payload 必须是纯函数的确定产物**：不含时间戳、请求 ID、操作人（`plan_payload` docstring 同款理由）。否则同一批次重放会得到不同摘要，触发 409 `INVALID_TRANSITION`。测试 T-VER-02 专门钉这一点。
* **为什么不用 `entity_id=project_id`（接续 WP24 的 PLAN 链）**：WP24 的 `submit_draft` 对该链用**自动取号**（`planning/service.py:921-930`），WP32 若显式写 `revision_no=max+1`，会与方案重新提交竞争同一个修订号，且显式值依赖"此刻的 max"——不确定，也就不幂等。
* **代价**：同一个 `ENTITY_TYPE_PLAN` 下，`entity_id` 有两种含义（项目 / 批次）。WP34 遍历时要能区分。Q7 请主线裁决。

**除版本节点外的重试语义：**

| 场景 | 行为 |
|---|---|
| 创建请求超时、客户端重发 | 命中 `uq_batches_project_idempotency_key`，返回同一批次（200） |
| 创建事务中途失败 | 整体回滚：无批次、无成员、无内容、无 job、无版本节点、无 outbox（测试 T-ATOM） |
| 任务 `FAILED`（可重试） | 人工 `retries`；**只重做最新轮为 `FAILED` 的成员** |
| 任务 `WAITING_RECONCILIATION` / `WAITING_PROVIDER` | **不重做**。"外部调用状态未知"不得被当作失败（`jobs/models.py:62-66`："UNKNOWN 不因租约过期变成可自由重试"）；计入 `needsReconciliation` |
| 任务 `PARTIAL` | 是否重做见 Q15 |
| 任务 `CANCELLED` / 批次已取消 | 不重做；批次 `CANCEL_REQUESTED` 时 `retries` -> 409 `INVALID_TRANSITION`（`reason: 'batch_cancelled'`） |
| 无可重做成员 | 409 `INVALID_TRANSITION`（`reason: 'nothing_to_retry'`），不写 `idempotency_records` |
| 预算耗尽导致的批量失败 | 本包**不自动**重试；充值后人工 `retries`（§2.4） |
| 重做时的预占 | 逐条在 handler 执行时发生（现状），与首轮完全相同，**不会**因重做而叠加（失败任务的预占应已释放，核对项见 Q16） |

### 2.4 费用预占接入方式（billing 只读调用点）

**接缝冻结原文**（§5.7，`:538-542`）：`money.py`（`as_amount` / `as_quantity`）、`pricing.py` / `reconciliation.py`、预算账本条件 UPDATE（`reserve_budget` / `release_budget` / `settle_budget`）；"WP32（批产）出活前必须预占 —— 走 billing，不要自己算钱"。

**现状**：WP26 的 `execute_generation` 在**每条内容执行时**走 `estimate_generation_cost` -> `reserve_generation_budget` -> 派发 -> `settle_generation_budget`（`content/service.py:636-666,1027`）。也就是说，"出活前必须预占"在**逐条路径上已经满足**，WP32 不新增任何出活动作（它只入队）。

**本设计的默认解释（方案 B，待 Q3 确认）：**

| 动作 | 调用点（`billing`） | 性质 |
|---|---|---|
| 批次预估 | `billing.service.estimate_cost(repo, project_id, batch_kind, quantity, provider_id, model_profile_id, ...)`（`billing/service.py:1269`）；`quantity` 的口径**必须来自 `content.types.calls_for`**（唯一次数口径，`content/types.py:873`），对每个 `task_kind` 各调一次 | 写事务内调用（会物化项目配置副本、写 `cost_estimates`）；只读语义，**不预占** |
| 可用额度预检 | `billing.service.get_budget_view(repo, project_id)`（`:511`）：比较预估总额与 `available`；`BudgetView.configured=False` 时**报"未配置预算"，不报 `available=0`** | 只读、**建议性**（non-binding）：两个并发批次可能都通过预检，真正的闸在逐条 `reserve_budget` |
| 预占 | **不调用** `reserve_budget`；逐条预占留在 handler | — |
| 结算 / 释放 | **不调用**；逐条在 handler | — |
| 币种 | 沿用 `DEFAULT_CURRENCY`；币种不一致由 billing 的 `currency_mismatch` 透传 | — |

**预算中途耗尽**：已跑完的 job 成功，其余 job 因 `BUDGET_EXCEEDED` 失败 -> 批次折算为 `PARTIAL` -> 充值后 `retries`。这就是 WP13 说明所写的"部分失败恢复"。

**备选方案 A（批次级持有）**：创建时 `reserve_budget(ref=f"batch:{id}")` 持有整批预估，批次结案时结算 / 释放。**问题**：与 handler 的逐条预占叠加，同一笔钱占两次（G3）；要避免就得改 `content` handler 让它"认领"批次预占——`content/*.py` 根层禁改（§1.1 第 21 行）。**默认不选**，Q3 请主线拍板。

**WP25 的 `ref` 前缀惯例**：`content:` / `media:` 各占一个前缀（`content/billing_bridge.py` 说明）。若将来走方案 A，用 `batch:` 前缀。

### 2.6 并发与乐观锁

| 场景 | 机制 |
|---|---|
| 改批次（取消 / 重做） | `If-Match` = `build_etag(batch.id, batch.lock_version)`；端点先 `require_if_match`（缺失 428、格式非法 400、不匹配 412），服务层再用**条件 UPDATE** 做第二道（`WHERE id AND lock_version AND state`）；`rowcount == 0` -> **重读当前 `lock_version`** 后抛 `version_conflict`（与接缝冻结 §5.12 第 9 步同款，不得用旧值） |
| 创建（新资源） | 无 `If-Match`（没有可冲突的旧行）；靠幂等唯一约束 + advisory lock |
| 同项目并发创建 | 事务级 advisory lock（`planning/repository.py:67` 先例）；保护 `seq_no` 与 `allocated_so_far`。若不取锁，两个并发批次读到相同的累计量，累计配额会越界（R6） |
| `batches` 列写入面 | **只有两个写路径**：INSERT 与上述 CAS UPDATE（改 `state` / `lock_version` / `updated_at` / `cancel_requested_*`）。不做列级守卫触发器（§1.5），由测试 T-WRITE-SURFACE 枚举仓库层所有 UPDATE 语句断言列集合 |
| 配置变更与创建的窗口 | ADR-13 迁移影响 #4：**以创建时刻读到的生效配置为准，不跨请求加锁**。读到的值快照进 `limit_applied` / `limit_source` |
| 成员 / 轮次 | 不可变表，无锁需求；重复插入由唯一约束挡 |

## 3. 阶段 3：多版本方案

### 方案 V1 —— 不建批次实体，沿用 `content-generations` + `jobs.batch_id` 当标签（**否决**）

| 项 | 内容 |
|---|---|
| 做法 | 不建任何新表；用 `content-generations` 的 `Idempotency-Key` 当批次身份，`jobs.batch_id` 随便填个 UUID 当"批次号" |
| 优点 | 零迁移、零新表；与 WP35 阶段 1 Q1 的"不引入批次"一致 |
| 缺点 | ① `batch_id` 无 FK，指向不存在的东西——ISS-95 形态（声称有）；② 没有创建时刻上限快照，AC-10~12 事后无法核对；③ "扩产不含试产内容"、累计配额、钉住方案 / 基线全部无落点；④ 与接缝冻结 §8.4 ② 的指派（WP32 建 `batches`）直接冲突 |
| 结论 | ❌ |

### 方案 V2 —— 批次状态落库并由 reconciler 回写（**不选，作为 Q6 的备选**）

| 项 | 内容 |
|---|---|
| 做法 | `batches.state` 含 `QUEUED / RUNNING / SUCCEEDED / PARTIAL / FAILED / CANCELLED`，由周期任务扫 `jobs` 回写 |
| 优点 | 列表可直接按状态过滤 / 索引；下游读一个列即可；结案态可冻结 |
| 缺点 | ① 引入一个新的运行时组件（reconciler）及其部署形态问题（同 OP-109）；② 与 `jobs` 构成**两处声称**，两者分叉时没有报错；③ 失败项重做会让"终态"重新打开，终态的语义变得含糊；④ 无钩子即时回写，读到的状态总是滞后一个周期 |
| 结论 | ❌ 默认不选；若主线认为下游需要稳定的结案态，可在 V3 上叠加"显式结案动作"而非周期回写 |

### 方案 V3 —— 批次行只存命令 + 成员 / 轮次不可变表 + 读时折算（**推荐**）

| 项 | 内容 |
|---|---|
| 做法 | 本文 §2 的全部内容：三张表；`state` 仅 `SUBMITTED / CANCEL_REQUESTED`；进度读时折算；批次级幂等落 DB 唯一约束；创建同一事务；重试靠轮次；PLAN 快照显式 `revision_no=1`；费用走"预估 + 预检"，逐条预占留在 handler |
| 优点 | 无第二处声称；无新运行时组件；幂等有 DB 载体；原子性有触发器兜底；`batch_items` / `batch_item_runs` 不可变 ⇒ 无锁需求；对 `jobs` / `content` / `planning` 零改动（除主线的 FK 与索引） |
| 缺点 | ① 读时折算要 join 三张表（N<=配置上限，可接受）；② 无"结案态"可供下游一个列读取；③ 对 WP26 生成链路**不能**传递场景 / 形式（G1，与方案无关，所有方案都卡在这） |
| 适合场景 | 本项目当前阶段（W12，分支并行，jobs / content 禁改） |

### 方案 V4 —— 完整版：批次级预占 + 公平调度 + DAG + 自动重试（**不选**）

| 项 | 内容 |
|---|---|
| 做法 | 批次创建即 `reserve_budget` 整批；批次间轮转调度；`job_dependencies` 建模"批内依赖"；失败自动指数退避重试 |
| 优点 | 额度占用最早、最保守；调度最公平 |
| 缺点 | ① 批次级预占与 handler 逐条预占叠加（G3），要避免必须改 content 根层；② 公平调度没有量化需求，是为想象中的指标建机制；③ `job_dependencies`——批内任务无依赖，建了就是死表（WP13 的判据）；④ 自动重试对计费类操作等于重复扣费（`M4契约与幂等口径.md` §1 末句） |
| 结论 | ❌ |

### 3.5 方案选择与理由（一句话）

**选 V3**：它是唯一同时满足"不改禁改文件""幂等有数据库载体""不造第二处状态声称""不替未拍板的口径编造数据"的方案；V1 缺实体，V2 多运行时组件，V4 在没有需求支撑的地方堆机制。

### 4.2 与 DDL 草案 / 设计的偏差（逐条）

1. **表结构零偏差**：落库后以 `pg_constraint` / `pg_indexes` / `pg_trigger` 对账草案文本——42 个约束与索引名全部命中、无多余；4 个约束触发器按 `pg_constraint(contype='t')` 另见。草案头部“实测”字样仍由主线迁移落地后回填。
2. **成员侧计数触发器复用批次侧函数**：`consistency_items()` 里两项共享 `rednote_check_batch_item_count`，成员侧那一项的函数 DDL 是同一条 `CREATE OR REPLACE`、函数 DROP 是同一条 `DROP FUNCTION IF EXISTS`（第二次为空操作），保持五元组形状与其他模块一致，迁移里 `op.execute` 不需要特判。downgrade 仍须“先删全部触发器、再按 `consistency_function_names()`（3 个）删函数”。
3. **`details.reason` 全用 snake_case**；planning 抛出的 `QUANTITY_BELOW_MIN` 等大写原因码在本包 `.lower()` 后透传（与 §2.5 列的 `quantity_below_min / quantity_above_max / batch_kind_unknown` 一致）。
4. **新增了设计稿 §2.9 之外的 5 个 reason**（开集，不落库）：`plan_version_invalid`（PLAN 节点不属于本项目 / 不是 PLAN，422）、`baseline_not_ready`（无生效基线，409）、`budget_not_configured`（预算未配置，422 `BUDGET_EXCEEDED`）、`limits_not_configured`、`request_in_progress`。`currency_mismatch` / `seq_no_conflict` / `generation_request_invalid` 为防御性分支。
5. **PLAN 载荷的来源**：`version_nodes` 只存 `payload_hash`、不存载荷（说明 §2.11 S7 写的“按键读 payload”**无法成立**）。实现改为：分配输入读 `plan_drafts`（经 `planning.service.next_batch_allocation`），再用 `plan_payload(draft)` 重算摘要与钉住的 PLAN 节点比对，不一致即 409 `plan_changed`（“不能先通过后补查”）。
6. **预览里关口是“结论”不是“拒绝”**：未通过 `gate.passed=false`；未接线 `gate.passed=null`（缺失不填 false）。创建里则严格拒绝。
7. **`retries` 的 If-Match 只在首次执行路径校验**：重放（同 `Idempotency-Key`）不要求 ETag 仍新鲜——首次重做已推进 `lock_version`。
8. **`retries` 的生成参数**取自第一条成员对应 `content_items.generation_request`，不由请求再给一份。

### 4.3 关口检查依赖（`gate_checker`）约定

* 签名（`types.py`）：`GateChecker = Callable[[uuid.UUID], GateVerdict]`；`GateVerdict(passed: bool, decision_id: UUID | None, decided_at: datetime | None, reason: str | None)`。输入只有 `project_id`；会话由 `dependencies.get_gate_checker(db)` 的闭包绑定。
* 默认实现 `default_gate_checker`：**未接线 fail-closed**，抛 `ApiError(DEPENDENCY_UNAVAILABLE)`（HTTP 503）+ `details.reason = trial_gate_not_wired`。
* 未通过：409 `INVALID_TRANSITION` + `details.reason = gate_not_satisfied`，`details` 回显 `decisionId` / `decidedAt` / `gateReason`。
* 重放（命中既有批次）**不重判关口**。
