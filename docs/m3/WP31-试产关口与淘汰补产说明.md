## 2. 状态机

### 2.1 实体与两层状态

* **轮（`trial_rounds`）**：对应原型的"BATCH-T01 试产 / BATCH-T02 补充试产"。`kind ∈ {TRIAL, SUPPLEMENT}`。
* **名额（`trial_round_slots`）**：本轮的一条"场景（方向）× 可选形式"，绑定一条 `content_items`；替代关系 `replaces_slot_id`。
* **决定（`trial_gate_decisions`）**：人工"批准进入扩产"，冻结当时的条件、统计与逐名额依据。
* **名额的处置状态不存**，由 WP29 `content_reviews` 派生（§2.4）。**存的状态机只有轮的 `state`。**

### 2.2 轮的状态与迁移表（取值域见 §10）

状态：`PLANNED`（名额已切、未开工）→ `GENERATING`（出活中）→ `REVIEWING`（人工处置中）→ `GATE_PASSED`（已批准进入扩产，终态）；`CANCELLED`（终态）。

| from \ to | PLANNED | GENERATING | REVIEWING | GATE_PASSED | CANCELLED |
|---|---|---|---|---|---|
| PLANNED | — | **开工** | ✗ | ✗ | 取消 |
| GENERATING | ✗ | — | **出活完毕** | ✗ | 取消 |
| REVIEWING | ✗ | **淘汰补产回退** | — | **批准**（仅经 gate-decisions） | 取消 |
| GATE_PASSED | ✗ | ✗ | ✗ | — | ✗ |
| CANCELLED | ✗ | ✗ | ✗ | ✗ | — |

迁移前置条件（服务层判，失败一律 409 `INVALID_TRANSITION`，`details.reason` 见 §6.3）：

| 迁移 | 前置 |
|---|---|
| 创建（→ PLANNED） | 入口关口全满足（§4）；数量过 `validate_quantity`；PLAN 钉住且未漂移（§3.2）；分配后名额数 ≥ 1 |
| PLANNED → GENERATING | **重判入口关口**，且 `round.baseline_id == projects.active_baseline_id`（基线仍是钉住的那条） |
| GENERATING → REVIEWING | 每个在役名额已绑定内容，且内容 `state ∈ {GENERATED, FAILED}`（已落定；"部分成功"的媒体维度见 Q11） |
| REVIEWING → GENERATING | 在 REVIEWING 下新建了尚未出活的替代名额时由服务层在**同一事务**推进（不是独立入口） |
| REVIEWING → GATE_PASSED | 关口三个硬条件满足 + 人工选定方向（§2.5）；写 `trial_gate_decisions` 同事务 |
| 任意非终态 → CANCELLED | 必须带理由；已出的内容、已花的钱**不回收、不删除** |

### 2.3 非法迁移如何拒绝（三层）

1. **服务层**：`trial/types.py::ROUND_TRANSITIONS`（上表的常量形式）→ 不在表内 → 409 `INVALID_TRANSITION`，`details = {reason: ROUND_TRANSITION_ILLEGAL, from, to, allowed:[…]}`；终态出边 → `reason: ROUND_TERMINAL`。
2. **端点形状**：`POST …/transitions` 的 `toState` 只收 `GENERATING/REVIEWING/CANCELLED`；`GATE_PASSED` → 422（`TO_STATE_USE_GATE_DECISION`）；未知值 → 422。
3. **数据库**：`trg_trial_rounds_transition_guard`（BEFORE UPDATE）按矩阵拒绝（sqlstate `23514`），并拒绝改不可变列、拒绝 DELETE（`23001`）；`trg_trial_rounds_consistency`（延迟约束触发器）保证"到 GATE_PASSED 必有决定行"，`trg_trial_gate_decisions_consistency` 保证反向。**矩阵同时在 `types.py` 与触发器函数体里，须有一条判据对账**（DDL 草案 §一.5）。

> 注：WP29 §1.4 第 10 条登记了"反馈项终态不可再迁移没有判据，由规则引擎统一判"。WP31 **不碰**反馈状态机，只在自己的轮上建了矩阵。

### 2.4 名额处置状态（读时派生，不落列）

对每个在役名额取其内容的**当前版本**（§8），再取 `content_reviews` 在该内容上**未被取代**的那条有效结论：

| 派生状态 | 条件 |
|---|---|
| `UNBOUND` | `content_item_id IS NULL`（未出活，≠ 失败） |
| `AWAITING_REVIEW` | 已绑定，但无有效结论，**或**有效结论的 `subject_version_id` ≠ 当前版本（改稿后旧结论失效，同时带 `reviewStale=true`） |
| `APPROVED` | 有效结论 = APPROVED 且绑定当前版本 |
| `ELIMINATED` | 有效结论 = ELIMINATED 且绑定当前版本 |
| `REPLACED` | 存在别的名额 `replaces_slot_id = 本行`（"死名额"，不计入在役） |

"在役 live" = 非 `REPLACED` 且所属轮非 `CANCELLED`。原型指标口径（`project-overview.html` 136 行）：已淘汰＝"本轮不用，保留历史，可被替代内容关联"，与上表一致。

### 2.5 关口（派生判定 + 人工批准）

关口**不是状态**，是对事实的判定；`GATE_PASSED` 是"人工在满足条件时做了决定"的结果。条件码（`types.GATE_CONDITION_CODES`）：

| 条件码 | 含义（出处 R12/R13） | 硬/软 |
|---|---|---|
| `ROUND_ALL_DISPOSED` | 本轮所有在役名额均为 APPROVED 或 ELIMINATED（淘汰算已处置；未被替代的淘汰也算） | 硬 |
| `NO_OPEN_BLOCKING_FEEDBACK` | 在役且**非 ELIMINATED** 的内容无 `severity=BLOCKING` 且 `state∉{RESOLVED,REJECTED}` 的反馈（淘汰项不阻断，见原型 561 行） | 硬 |
| `DIRECTION_HAS_APPROVED_SAMPLE` | 人工选定的**每个**放行方向至少一个 APPROVED 在役样例（"每个准备扩产的方向"） | 硬（对选定方向） |
| `SELF_CHECK_COMPLETE` | 在役非淘汰内容当前版本均有自检轮次（STALE 视为未自检） | **待定**（Q6，默认只报告不阻断） |

* 人工批准 `POST …/gate-decisions` 带 `approvedSceneKeys`：选了没有 APPROVED 样例的方向 → 422 `DIRECTION_UNVERIFIED`（该错误码在 `platform/errors.py` 已存在且当前无人使用）。**未被选中的失败方向不阻止本轮通过**（原型 571 行"补充试产或从扩产方案移除该方向"），它们靠 SUPPLEMENT 轮补。
* 关口通过后：轮 → `GATE_PASSED`，决定行不可变。若之后基线/内容变化，读端用 `basis` 判 STALE（不改决定）。是否允许撤销决定见 Q12（本稿不做）。

### 2.6 淘汰补产

* "淘汰"本身由 WP29 `POST …/reviews`（ELIMINATED + 理由）完成，WP31 不写。
* "补产"= 在轮上建**替代名额**：`POST …/slots/{slotId}/replacements`。前置：该名额派生状态为 `ELIMINATED` 且尚无替代（否则 409 `SLOT_NOT_ELIMINATED` / `SLOT_ALREADY_REPLACED`）；方向不变（`scene_key` 同；DB 约束触发器钉住）；轮须在 GENERATING/REVIEWING（终态 409）；若在 REVIEWING 则同事务退回 GENERATING。
* 数量口径：**在役名额数始终 ≤ 本轮 `planned_quantity` ≤ TRIAL 上限**（替代一个、死一个，在役不增）。累计行数可超过 10，这是有意的（Q10）。补产总数上限见 Q10。
* 被替代名额的内容之后被改判为 APPROVED：**名额保持已死**，替代权威（登记为规则 + 测试）。
* 方向整体没有通过样例 → 开 `SUPPLEMENT` 轮（`source_round_id` 必须是 `GATE_PASSED` 的 TRIAL 轮；方向取自 `sceneKeys`，须在钉住的 PLAN 中且未停用）。对应原型"BATCH-T02 补充试产"与 `trial-config.html` 74 行"在补充试产轮次中覆盖该方向"。

### 3.2 ★ 设计阶段实测发现：PLAN 版本的分配正文没有落库

`submit_draft` → `register_version(payload=…)` 在 `version_nodes` 只存 `payload_hash`（`versions/models.py`："注册表不是万能 JSON 仓库"）。分配结果唯一来源是 `plan_drafts` 那一行**可变**草稿；而 `save_draft` 对 `SUBMITTED` 草稿没有状态拦截，`submit_draft` 又拒绝第二次提交 ⇒ 草稿提交后可漂移、且无法产出第二个 PLAN 修订。于是"读 PLAN 版本的分配结果"（R5）没有直接路径。

**本稿的处置**：创建轮时重算草稿 `plan_payload`，与 `plan_version_id` 节点的 `payload_hash`（`canonical_payload_hash`）比对——一致才放行，并把 payload **冻结进 `trial_rounds.plan_snapshot`**；不一致 → 409 `PLAN_DRAFT_DRIFTED`。此后补充轮/补产/累计额度只读快照，不再读草稿。副作用：草稿提交后一旦被改，**无法再开新轮**，且 WP24 没有"重开草稿"路径——这是对 WP24 的缺口，WP31 不得单方面补（planning 根层文件，Q5）。

### 3.3 名额的切分

* 方向维度：`allocate_by_weight(scene_items_from_snapshot, n)` → 每个场景 `allocated` 个名额，按 `(sortOrder, key)` 编 `slot_no`。`n` 默认 = 快照 `totalQuantity`，也可更小；n=快照总量时必须与快照里的 `allocated` **逐项相同**（测试 U-03）。
* 形式维度：快照里 `pairings` 只是"允许配对"的清单、**没有格级权重**，所以"场景×形式"的格级指派没有定义。本稿 `form_key` 暂留 NULL（= 未指派，≠ 空串），**是否指派、按何规则指派，Q4 / OP-227**（D1 已决策：`content_items` 将由主线接缝新增可空列 `scene_key`/`form_key`，`GenerationRequest` 可带入，故本列保留；`scene_key` 可由场景边际派生，`form_key` 在 OP-227 定之前仍为 NULL）；若答复"不做"，DDL 草案应删该列（否则就是 ISS-95 式"声明了没实现"）。
* 方向 = `scene_key`：原型所有"方向"都是场景名（Q3 之外的另一假设，列入 Q4）。

## 4. 八步关口：只读 `step_approvals`

## 7. 幂等与并发

沿用 `platform.concurrency`（`build_etag`/`require_if_match`/`version_conflict`）与 planning 的层次：**412 在前（乐观锁）、409 在后（业务状态）**。

| 场景 | 机制 |
|---|---|
| 轮 ETag | `build_etag(round.id, lock_version)`；每次状态迁移 +1（与 `plan_drafts` 同：状态变更也 +1，宁慢不错） |
| 迁移/批准/补产 | 先 `SELECT … FOR UPDATE` 取轮行 → 判前置 → 写 → 条件 UPDATE（`WHERE lock_version=:v`），`rowcount=0` 重读 `current_version` 抛 412（不得回带陈旧值，仿 WP26 `reload`） |
| 重试 | 旧 ETag → 412（更早拦截）；新 ETag → 状态已变 → 409。两者都是正确拒绝，须文档化并有用例（仿 `test_plan_draft_submit_retry_is_rejected_in_two_distinct_ways`） |
| 创建幂等 | `(project_id, idempotency_key)` 部分唯一 + `request_hash`；同键同体返回既有轮；同键异体 409；无键 = 不幂等 |
| 取号 | `round_no` 在 `pg_advisory_xact_lock(hashtext('trial-round:'||project_id))` 下取 `max+1`；`(project_id, round_no)` 唯一兜底 |
| 同时一轮 | `uq_trial_rounds_project_open` 兜底，服务层先判给可读 409 `ACTIVE_ROUND_EXISTS` |
| 绑定内容 | `uq(content_item_id)` 兜底：并发把同一内容绑两个名额只有一个成功 |
| 双击补产 | `uq(replaces_slot_id)` 兜底：只有一个替代名额 |
| 批准的 TOCTOU（R13 "不能先通过后补查"） | 持轮行锁；对在役内容 `FOR SHARE` 锁 `content_items`（挡住并发改稿推进 `current_version_id`）；`basis` 记录 `(slotId, contentItemId, subjectVersionId, reviewId)`。**残余风险**：`content_reviews`/反馈是追加式表，我们锁不到；并发改判会在决定之后出现，由读端 STALE 标记暴露而非阻止（Q13） |
| 事务内顺序 | 与 `submit_draft` 同：锁 → 判 → 写决定 → 改轮 → `flush`；审计 `audit.record_audit`（同事务，`before/after` 配对） |
| 测试库 | 并发用例需两个独立事务/连接，自己 `commit`（G6），不得写共享库 |

## 8. "当前版本"取数口径（契约 §2）

* **内容当前版本** = `content_items.current_version_id` 投影；仅当其为 NULL 才回落 `content_versions … ORDER BY version_no DESC LIMIT 1`。**禁止**把 `ORDER BY version_no DESC` 当主路径。SQL 形态：`COALESCE(ci.current_version_id, (SELECT cv.id … ORDER BY cv.version_no DESC LIMIT 1))`。必须有"回滚分叉"用例：投影指向 v1、存在 v2，v2 上的审核**不得**计入通过。
* **基线** = `projects.active_baseline_id`（投影），不取"最新创建的基线"（对照 `newest_baseline_of` 的 NOT EXISTS 教训）。
* **PLAN** 无投影：本稿**不取"最新 PLAN"**，由客户端显式传 `planVersionId` 并钉住；是否给 PLAN 增加投影见 Q5。
* **当前轮** = 未终态那一轮（部分唯一索引），不是 `ORDER BY round_no DESC`。
* **最新自检** = `(content_item_id, created_at DESC, id DESC)` 且 `subject_version_id` = 内容当前版本，否则视为未自检（WP30 同口径）。
* 本契约节自述"无独立判据"；本包加两条：① AST/文本判据：`planning/trial/` 内出现 `ORDER BY version_no DESC` 必须在 `COALESCE` 回落分支内；② 上述回滚分叉用例。

### 与稿的偏差

1. 创建轮时 `before` 审计负载传 `{}`（audit 要求 before/after 哈希成对）。
2. 新增 `details.reason`：`ROUND_NOT_GENERATING`（绑定内容仅 GENERATING 轮）、`QUANTITY_INVALID` / `KIND_INVALID` / `SOURCE_ROUND_REQUIRED` / `SCENE_KEYS_REQUIRED` / `PLAN_VERSION_INVALID` / `REASON_REQUIRED` / `TO_STATE_INVALID` 等 422 类细分码（错误码仍用协议封闭码）。
3. #7 补产**未实现 Idempotency-Key**：DDL 无存放列；双击防护靠 `uq(replaces_slot_id)` + If-Match（旧 ETag 412 / 新 ETag 409 `SLOT_ALREADY_REPLACED`）。
4. 补产也推进轮的 `lock_version`（名额集合变了，ETag 跟着变）；绑定内容（#6）不推进、不要求 If-Match，靠轮行锁串行。
5. REVIEWING→GENERATING 经 `transitions` 端点 409（`details.via=replacements`），仅由补产同事务推进。
6. 关口 `basis` 条目额外记 `sceneKey` / `status`；`SUPPLEMENT` 未传 `quantity` 时默认 = `len(sceneKeys)`（稿未规定）；TRIAL 未传时默认 = 快照 `totalQuantity`（超上限则 422，需显式传更小值）。
7. 绑定内容时 `content_items.scene_key`/`form_key` 为 NULL 视为未指派、放行；两者均非 NULL 且与名额不同则 422 `CONTENT_SCENE_MISMATCH`。
8. 校验顺序（批准）：If-Match(412) → 状态 → 方向属本轮(422) → 硬条件 ROUND_ALL_DISPOSED/NO_OPEN_BLOCKING(409) → `DIRECTION_UNVERIFIED`(422)。
9. 复用 `audit.record_audit`、`versions.canonical_payload_hash`（Q15 待主线确认）；其余他表一律裸 SQL 只读。
