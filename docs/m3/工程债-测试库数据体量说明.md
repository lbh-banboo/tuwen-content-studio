# 工程债清偿包 · 测试库数据体量 说明

> 工作包：**WP-DEBT-05**（非里程碑包，属技术债清理；紧随 WP-DEBT-01~04 之后）
> 验收：**「无主根表的行数不会无界累积」这件事由一条机械判据守着，且判据被反向验证过它会报红**
> 触发来源：本次诊断实测——共享测试库 `rednote_test` 的 `projects`/`users`/`brands` 已累积到 116,822/166,099/117,875 行，使判据 B（`check_test_residue.py`）在共享库上跑全量 pytest 超过 3600s 超时
> 关联：WP-DEBT-02（测试库可信度，本包补的是它 §8 已知边界里不成立的那一句）

---

## 0. 本包的一句话定位

**给"没人拥有的根表"补一条数据体量判据 + 一个手动重置入口；不改测试事务架构，不改 21 个测试文件的种子逻辑。**

因为在此之前，`projects`/`users`/`brands` 三张表同时满足"被几十张表依赖"与"没有任何单一模块对它负责"两个条件，而这个组合在现有机制里是一个盲区：

| 现有机制 | 为什么管不到这三张表 |
|---|---|
| `conftest.py` 的 `drop_own_tables` | 闭包算法只删"没有跨包入向 FK 的表"——这三张表被几十张表引用，永远落在"保留"集合，从未被任何模块重建 |
| `conftest.py` 的 `truncate_targets` | 闭包方向是"找引用者"，没有任何模块把这三张表列为**自己**的种子集去清 |
| 判据 B（`check_test_residue.py`） | 只测**结构**差分（表/索引/视图/序列/触发器/约束），docstring 里已写明"不判数据行数"是已知边界 |
| 21 个测试文件各自的种子函数 | 直接 `INSERT`，没有一个做 `DELETE` 清理（`grep` 全仓命中 0） |

结果：18 天里 2333+ 个测试反复跑，每次都往这三张表加新行、从不清理，线性堆到了 116k~166k 行，最终让依赖真库的判据超时。

## 1. 需求追问

### 1.1 这个需求真正解决什么问题？

**一句话**：让"共享测试库的行数增长"这件事从"没人管、直到撞墙才发现"变成"有判据提前报警、有工具一键止血"。

### 1.2 核心用户

| 角色 | 在本包做什么 |
|---|---|
| 本机开发者 | 共享库行数超阈值时被判据 D 当场告知，并给出重置命令 |
| CI 门 3 | 每次 push 后秒级核对一次（判据 D 只读三个 `count(*)`） |
| 后续工作包的开发者 | 新测试若继续往根表灌数据，判据会在膨胀到真正影响 pytest 耗时**之前**先报警，而不是等判据 B 超时才发现 |

### 1.3 为什么只测三张根表、不测闭包全表（最该交代的一条设计取舍）

根表行数天然上界住整条派生链——FK 约束下不可能存在无根的子行，派生表的增长是根表增长的函数。测闭包全表（本仓约 60~70 张表）需要逐表 `count(*)`，且各模块合法的"只清自己的表"节奏不同会引入噪声；而根表测三个数就能覆盖同一个信号。

**已知边界（刻意，不是遗漏）**：不引用这三张根表的独立表（配置/价目/提示词/队列类）若被测试灌脏，本判据看不见。留了一个诊断性开关 `--report-largest`（只提示最大的几张表，不参与判定）作为补偿，不升级为判定输入。

### 1.4 为什么不做全局事务回滚（排除方案，写明理由防止下次又提出来）

pytest + SQLAlchemy 的标准"每测试 SAVEPOINT + 结束 ROLLBACK"模式是这类问题的教科书解法，本包评估后**排除**它：

1. `platform/database.py` 的 `session_scope()` 是"请求级显式提交"——每次调用可能拿到新引擎、正常路径下立即 `commit()`。这个提交边界本身就是被测试覆盖的业务行为（阶段推进/配额预占/费用结算要求"要么全成要么全不成"），强行包一层外部事务会改变被测代码的提交语义。
2. `test_events_wp14.py` 显式测试**跨实例** `LISTEN`/`NOTIFY`（channel `domain_events_new`），需要真实独立连接和真实 commit 才能让 NOTIFY 送达另一条 LISTEN 连接；全局 rollback 包裹会让这类测试失真。

结论：**只做检测 + 手动止血，不碰测试事务架构。**

### 1.5 哪些功能现在不该做

| 不做 | 理由 |
|---|---|
| 自动周期清理 | 判据的职责是报红，不是修——自动清理会掩盖"谁在留残留"，且本身是新的"共享资源写权"问题（ISS-160 同族） |
| 去 21 个测试文件里逐一加清理 | "N 处都要改,必然会漏"——不符合本仓"一处差分覆盖全部测试"的一贯做法 |
| 把判据 B 改成测数据残留 | 判据 B 的定位是"结构"，混进数据行数会让一条判据管两件独立的事，报红时读的人无法第一时间判断是哪一类 |
| 测闭包全表而不是只测根表 | 见 §1.3 |

### 1.6 至少三个版本方案

| 方案 | 做法 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|---|
| V1 最小版 | 只把超时阈值再调高 | 一行改动 | 纯治标；本仓已调过 900s→2400s→3600s 两轮，每次都被继续膨胀追上 | 应急 |
| **V2 本包采用** | 判据 D（阈值机械派生）+ 手动重置工具 + 反向验证 + Code Review | 治标又不过度治理；不碰测试事务架构；判据只报红、手动止血，符合本仓纪律 | 需要开发者看到报警后手动执行一次重置 | ✅ 当前 |
| V3 架构级 | 全局事务回滚（每测试 SAVEPOINT） | 彻底杜绝残留 | 与 `session_scope` 的显式提交语义、`test_events_wp14.py` 的跨实例 LISTEN/NOTIFY 测试冲突，见 §1.4 | 不适合本仓当前架构 |
| V4 自动清理 | 判据报红时自动触发重置 | 零人工干预 | 违反本仓"判据只报红不自动修"的一贯纪律；且可能在别人正用共享库时被自动触发，重演 ISS-160 | 不采用 |

## 2. 方案设计

### 2.1 判据 D：`tools/quality/check_test_data_volume.py`

- 连真库，count `projects`/`users`/`brands`，每表先判存在性（`to_regclass`）再 `count(*)`
- 判定：`rows > limit` 才算超阈值（等于放行）；缺表/连不上归入独立的 `problem`（不折算成 0 行，fail-closed）
- DSN 口径：`REDNOTE_TEST_DATABASE_URL` 环境变量 > 默认常量 `rednote_test`——与 `check_test_residue.py`/`conftest.py` 的常量保持一致，但**刻意不互相 import**（避免判据之间产生依赖），靠 `test_test_data_volume.py::test_default_dsn_matches_conftest_and_residue_judge` 做漂移对账

### 2.2 阈值测量（§2.5 的数据来源，不是拍脑袋的数字）

在隔离的 git worktree（与并行的 WP29 编码工作完全分开，避免互相踩文件/数据库）里，私有干净库上实测两轮全量 `pytest -m "not slow"`：

```
库: rednote_wpdebt05_measure1 / rednote_wpdebt05_measure2（均迁移到 head a9d3f6c2b815）
第一轮：2333 passed in 171.84s，projects=1588 / users=2303 / brands=1601
第二轮：2333 passed in 177.55s，projects=1588 / users=2303 / brands=1601
```

两轮结果**完全一致**（0% 误差），取该值为 `MEASURED_ROWS_PER_RUN`，乘安全倍数 `SAFETY_FACTOR=4`、向上取整到千位，得到：

| 表 | 单次实测净增 | × 4 | 向上取整到千位 |
|---|---|---|---|
| `projects` | 1588 | 6352 | **7000** |
| `users` | 2303 | 9212 | **10000** |
| `brands` | 1601 | 6404 | **7000** |

为什么 ×4：允许约 4 次全量测试不触发判据；共享库当前实际膨胀到约单次运行的 70~100 倍才让判据 B 超时，判据 D 能在远早于那一步时就报警。

### 2.3 手动重置工具：`tools/dev/reset_shared_test_db.py`

安全门（顺序即防线）：

1. 只认 `REDNOTE_TEST_DATABASE_URL`——刻意不读 `REDNOTE_DATABASE_URL`
2. 保留库白名单拒绝（复用判据 A 的 `STATIC_RESERVED_DATABASES`）
3. 默认只读 dry-run（不带 `--yes` 只打印计划，不建写连接）
4. 真执行需要 `--yes --confirm <库名>`，且 `--confirm` 必须**原样**等于解析出的库名
5. 建写连接**之前**先调用 `check_shared_db_quiet.assert_quiet`（ISS-160 教训：任何真连库写操作都必须先确认没有并行会话）
6. `lock_timeout`/`statement_timeout` 兜底：中途来了别的 pytest 会变成可读失败，不是无限等锁

闭包算法复用迁出的 `rednote.platform.db_graph.truncate_targets`（原在 `services/backend/tests/conftest.py` 里，WP-DEBT-05 迁到 `platform/` 供测试层与 `tools/dev/` 共用，`conftest.py` 改为 import 后 re-export，21 个既有 `from conftest import truncate_targets, ...` 的测试文件零改动）。不用 `TRUNCATE ... CASCADE`——闭包已显式列出整条引用链，`CASCADE` 会在将来出现新引用时静默清空未被列出的表（同 `drop_own_tables` 的 ISS-106 论证）。

实测（可丢弃的私有库上验证端到端）：闭包含 **61 张表**，清空前 `1588/2303/1601` 行，清空后 `0/0/0`，判据 D 随即 `[PASS]`。

### 2.4 为什么用 TRUNCATE 闭包而不是按 project_id 定向 DELETE

查过 `pg_constraint`：引用 `projects`/`users`/`brands` 的外键几乎全是 `RESTRICT`（少数 `project_members`/`project_assignments`/`work_items`/`user_sessions` 是 `CASCADE`），行级定向 DELETE 不可行——必须走闭包 + 单条多表 `TRUNCATE`（PG 原生支持一次性处理整条 FK 链）。

## 8. 已知边界（不做假保证）

| 边界 | 说明 |
|---|---|
| 只测三根表，不测闭包全表 | 不引用根表的独立表泄漏不可见；`--report-largest` 只做诊断提示，不参与判定 |
| 阈值是静态常量 | 套件规模显著增长后需按 §2.2 同样流程重测，不允许无实测地调大 |
| 判据必须连真库 | 连不上是 FAIL，不是 skip——没有真库就没有可对账的对象 |
| 重置是手动触发 | 不做自动周期清理：自动清理是新的"共享资源写权"问题（ISS-160 同族），且违反本仓"判据只报红不自动修"的纪律 |
| 21 个测试文件的种子函数本身未改 | 本包是"检测 + 手动止血"，不是"杜绝产生残留"；后者需要更大的架构改动（已排除的全局事务回滚是其中一种，§1.4 已判定不可行） |
| quiet 预检与 TRUNCATE 之间有残余 TOCTOU 窗口 | `lock_timeout`/`statement_timeout` 把风险转成可读失败，不是彻底消除 |
