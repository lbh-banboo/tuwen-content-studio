> 工作包：**WP-DEBT-02**（非里程碑包，属技术债清理；紧随 WP-DEBT-01 之后）
> 验收：**「'测试库里的东西可信' 这件事由三条机械判据守着，且每条判据都被反向验证过它会报红」**
> 触发来源：`docs/研发进度复盘_2026-09-29.md` §4.2-B / §4.2-C / §4.2-D
> 关联：WP-DEBT-01（工程债清偿范式）；WP21（HNSW 索引，本包抓到其残留缺陷）；WP25（并行会话，本包零冲突）
> 冲突声明：**本包零迁移、零表、零端点、零业务代码逻辑改动** ⇒ 与进行中的 WP25（会话 `597b22f4`）**无任何资源冲突**

## 0. 本包的一句话定位

**把"测试库里的东西可信"从一句默认假设，变成三条能被违反、且违反即报红的机械判据。**

因为在此之前，测试库同时承载了三个**互相独立、都没有人看**的隐含假设：

| 假设 | 实际状态（2026-09-29 现场） |
|---|---|
| "默认测试 DSN 指向测试库" | ❌ 指向 `postgres` **系统维护库**，累积 **665,951 行**测试垃圾、54 张业务表 |
| "跑测试不会往库里留东西" | ❌ 每跑一次 WP21 测试留 **8 个 HNSW 索引**，跨 9 天累积，`hnsw_index_drop_ddl` **零调用点** |
| "迁移建的库 = 夹具建的库" | ❌ 测试库 `alembic_version` 停在 `ebc05dfca16b`(WP20)，迁移头已是 `022ba9804d66`(WP24)——中间两个大包加的表**全部不在**，而全量 pytest **全绿** |

三个假设同时失效的直接后果：**全量 pytest 从 9s 退化到 13~20 分钟（约 130 倍）**，
而"测试通过"这一信号的含金量无人测量。

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让「测试结果可信」这件事，**不再依赖于"碰巧没人踩坑"**。

拆开是三个彼此独立、但必须同时成立的问题（对应 §4.2 的三条）：

| # | 问题 | 若不做会怎样 |
|---|---|---|
| P1 | **默认 DSN 不许指向系统库** | 不设环境变量的开发者/CI 直接污染 `postgres` 系统库。实测代价：665,951 行垃圾、54 张业务表、pytest 慢 130 倍，且它还被当成"集成环境"做诊断——**而它其实是垃圾场** |
| P2 | **跑测试不许在库里留结构对象** | 残留跨天累积、无上限。更隐蔽的是：**结构残留比数据残留更难发现** —— `conftest.drop_own_tables` 清的是"自己建的表"，而运行期动态建的索引不属任何包的 `create_all`，**没人管** |
| P3 | **迁移建的结构必须等于模型建的结构** | 测试全绿**不能**说明迁移是对的——夹具用 `create_all`，**根本不走迁移**。本仓两个大包期间，迁移链断档而无人察觉 |

**为什么 P1/P2/P3 必须同包做**：三者是"测试库可信"的**三个必要条件，缺一不可**。
只修 P1（换库名）⇒ 残留照样累积；只修 P2（清残留）⇒ 库结构仍可能与迁移不符。
**任一条单独成立，都不足以让"测试通过"这个信号可信。**

**本包的产出边界**：它回答"测试库可信不可信、怎么测、怎么保证以后还可信"。
它**不改任何业务代码逻辑**、**不新增任何迁移**、**不动共享测试库的数据**。

### 1.4 描述有哪些疏漏应当补充？理由？

| # | 原描述 | 补充 | 理由 |
|---|---|---|---|
| 1 | §4.2-B 说"清库 + 加残留判据" | **判据 B 必须真跑一遍 pytest**，不能只查现状 | "残留"的定义就是"跑测试**多出来的**"。只查现状无法区分"迁移该有的 52 张表"与"残留的表" |
| 2 | §4.2-C 说"迁移头 vs 测试库版本" | 不做"版本号比较"，做**全量结构对账** | 版本号相等**不蕴含**结构相等（迁移可被改写）；且"恰好等于某版本"是 ISS-44 型的短期判据 |
| 3 | §4.2-D 说"各开发线独立库" | 判据 B **必须可被环境变量覆盖** | 否则判据自己会破坏它声称的隔离——判据成了并发冲突源 |
| 4 | 未提 | **判据 A 的保留名单必须有对账判据** | `{postgres, template0, template1}` 是人写的名单（铁律 14）。PG 小版本可能新增模板库 ⇒ 需连真库读 `pg_database.datistemplate` 对账 |
| 5 | 未提 | **排除集必须由磁盘派生，不是人写名单** | 判据 C 要排除"路径固有差异"（alembic 记账表、ANN 索引）。若写死名字，改名即静默失效（本包实测踩到，见 §4） |

### 1.5 哪些功能现在不该做？

| 不做 | 理由 |
|---|---|
| **清空/重建共享测试库的数据** | 那是**破坏性操作**，且与并行会话（WP25）抢资源。本包只做**结构层面**的判据与一处夹具修复 |
| **让夹具改走迁移**（`create_all` → `alembic upgrade`） | 那是架构改动，会让每个测试慢一个数量级。判据 C 已用"两库同时从零点建"给出等价保障 |
| **给残留判据加"自动清理"** | 判据的职责是**报红**，不是**修**。自动清理会掩盖"谁在留残留"，且清理动作本身可能破坏共享库 |
| **在 CI 上跑完整版反向验证** | 完整版要建库 + 跑 pytest（约 10 分钟）。CI 用 `--fast`（判据 A 纯静态），完整版在本机收口时跑一次 |
| **给所有测试加"残留断言"** | 那是 N 个地方各写一遍（必然会漏）。判据 B 用**一处差分**覆盖全部测试 |

### 1.6 这个系统有哪些技术风险？

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 判据 B 的 pytest 目标参数被写坏 → "没跑"伪装成"无残留" | **高**（已踩） | 判据恒绿 | 加"只有真跑过才满足"的前置条件（`collected == 0 → FAIL`）+ 成对变异证明它是必要防线 |

### 1.8 至少输出 3 个版本方案

| 方案 | 定位 | 做法 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|---|---|
| **V1 最小版** | 只堵最急的洞 | 只做判据 A（换默认 DSN + 静态判据） | 半天完成；纯静态、零风险 | P2/P3 完全没管，残留与迁移断档照旧 | 只是想"别再污染系统库" |
| **V2 本包采用** | 三条判据 + 反向验证 | A/B/C 三条 + 各自判据 + 反向验证矩阵 + CI 门 3 | 三个必要条件全覆盖；每条判据都被验证过"会报红"；零迁移零冲突 | 完整版反向验证约 10 分钟（仅本机一次） | ✅ **当前**：并行会话活跃、要当场可验收、要能防复发 |
| **V3 架构级** | 夹具改走迁移 | 测试库统一由 `alembic upgrade head` 建，废弃 `create_all` | 治本：测试即在验迁移 | 每个测试慢一个数量级；需改 conftest 全体；**与并行会话强冲突** | 单线开发、有充足 CI 时间预算 |
| **V4 完整版** | V2 + 自动清理 + 全量测试残留断言 | 判据 B 不仅报红，还自动 DROP 残留；每个包加残留断言 | 库永远干净 | 自动清理掩盖根因；断言散落 N 处必漏；清理动作可能破坏共享库 | 独占据库、追求"零人工干预" |

**为什么选 V2**：V1 治标不治本（P2/P3 仍在）；V3 与并行会话强冲突且收益需长期摊还；
V4 的"自动清理"违反本项目的判据纪律（判据职责是报红，不是修，修会掩盖根因）。
V2 在**零资源冲突**前提下把三个必要条件全覆盖，且每条都有反向验证兜底。

## 2. 阶段 2：方案设计

### 2.1 判据 A：默认 DSN 目标自检（ISS-145）

**方向：反向覆盖。** 遍历「代码里实际写着的 DSN 字面量」，要求「它的库名不是保留库」。

> ⚠️ 不能反过来遍历"一份保留名单再去找它出现在哪"——漏掉的 DSN（新写的、换个变量名的）
> 根本不参与比较，那是 **ISS-115 的形态：判据对"漏掉"恒真**。

| 要素 | 设计 |
|---|---|
| 第一段范围 | `services/backend/tests/**/*.py`（`rglob` 递归，**不写目录名单**） |
| 第二段范围 | 从 `.github/workflows/ci.yml` 机械提取 `python <路径>.py` 引用的 `tools/**` 脚本（与 `check_test_db_isolation` 同口径） |
| 保留库 | `{postgres, template0, template1}` —— **PG 自身固定的名字**，不是项目名单 |
| 对账判据 | 连真库读 `pg_database.datistemplate`，断言**每个模板库名都在静态名单里**（铁律 14） |
| 覆盖下界 | `MIN_TEST_FILES=20` / `MIN_JUDGED_LITERALS=20`（防"扫到但一个都没判"） |
| 三计数分离 | 回报「字面量总数 / 豁免数 / 真判数」——"豁免吃光范围"必须可见（ISS-143） |
| 豁免 | `ALLOW_FILES` 逐条给理由；`parametrize` 实参**按位置**豁免（不按文件名） |

实测输出：
```
[PASS] 无违规：25 个测试文件 + 11 个 CI 引用脚本的默认 DSN 都不指向保留库
      （40 个字面量 = 豁免 8 + 判定 26）。
```

### 2.2 判据 B：测试残留判据（ISS-147）

**做法：前后结构差分，不是"查名字名单"。**

```
1. 对目标库做结构快照（table/index/view/sequence/trigger/constraint 六类）
2. 跑一遍 pytest（默认 -m "not slow"，可用 REDNOTE_TEST_RESIDUE_PYTEST_ARGS 覆盖）
3. 再做一次快照，相减
4. 差集非空 → 报红，逐条列出"谁在什么时候多建了什么"
```

> **为什么用差分而不是"找名字像测试垃圾的表"**：那条路**必然**变成人写名单（铁律 14）。
> 差分**不需要知道垃圾长什么样** —— 一个从不被清理的新索引和一个从不被清理的新表，
> 在差分里是**同一种东西**。
>
> 实测证据：真实残留是 `ix_chunk_embeddings_hnsw_<profile_uuid>`，
> 名字里**没有任何**测试特征词——它看起来就像个正常业务索引，名字名单对它**必然无效**。

| 要素 | 设计 |
|---|---|
| 前置条件 ① | `collected == 0 → FAIL`（ISS-143：没跑 vs 跑失败同形） |
| 前置条件 ② | `returncode != 0 → FAIL`（测试红了时差分不可信） |
| `-m` 表达式 | `DEFAULT_PYTEST_ARGS` 是 **tuple**，`"-m", "not slow"` 是**一个** argv 元素 |
| 环境变量解析 | `shlex.split`（尊重引号）—— `str.split()` 会拆坏 `-m` |
| 判定 | 完全由差分决定；`_classify` 的名字启发式**只影响提示文案** |

实测输出（修复后）：
```
[PASS] 跑测试前后库结构一致 —— 无残留。
```

### 2.3 判据 C：迁移结构 ↔ 模型结构全量对账（ISS-146）

**做法：两条路径都从零点建起，然后逐对象比较。**

```
库 A: 全新空库 → alembic upgrade head        （迁移路径）
库 B: 全新空库 → Base.metadata.create_all     （模型路径）
       ↓
逐对象比较：表 / 列(类型+可空+默认) / 主键 / 唯一约束 / CHECK / 外键(含 deferrable) / 索引
```

> **为什么"两库同时从零点建"**：`test_schema_parity.py` 刻意不做全量 diff（它 docstring 里
> 写了理由：全量 diff 会被"合理的差异"淹没）。本判据换个打法 —— 让两个库的**唯一变量**
> 就是"谁来建表"，这样"合理的差异"**不再存在**，任何不一致都是真缺陷。

| 要素 | 设计 |
|---|---|
| 隔离 | `rednote_parity_audit_mig_<pid>` / `rednote_parity_audit_mod_<pid>`，跑完 `DROP DATABASE` |
| 排除集 §1 | **alembic 记账表**：三级派生（`env.py` 的 `configure(version_table=...)` → `alembic.ini` → alembic 包源码的 `opts.get("version_table", <缺省>)`）|
| 排除集 §2 | **ANN 索引**：按磁盘查出的 `pg_am.amname ∈ {hnsw, ivfflat}` 判定，**不写索引名** |
| 排除集自检 | ① 派生记账表名必须在迁移库**全部找到**；② 不许出现在模型侧；③ 模型侧不许有 ANN 索引 |
| 覆盖下界 | `MIN_TABLES = 45`（低于它说明 metadata 没收齐） |

实测输出：
```
迁移库：51 张表 / 模型库：51 张表
[表]一致(51) / [列]一致(541) / [约束]一致(399) / [索引]一致(186)
[PASS] 迁移与模型两条路径产出的结构逐项一致。
```

**21 处的定性**：逐条取证后 —— **全为假阳性，真硬编码 0 处**。四类：

**修法**（三处，均为"扩大识别面"，**不放宽结论**）：

| # | 改动 | 目的 |
|---|---|---|
| 1 | `_PATTERN_METHODS` 补 `replace`（附已知边界注释） | 协议替换的实参不是地址 |
| 2 | 新增 `_environ_name_of()` / `_or_chain_is_isolated()` | 能解析 `or` 链里的 `os.environ.get(<隔离变量>)` |
| 3 | 新增 `_data_position_literal_ids()`，豁免**按 `id()`（节点身份）而非行号** | parametrize 参数表 / `assert` 期望值 / `or` 链兜底 / `os.environ[<隔离变量>] = <DSN>` |

> 🔁 **范围随磁盘自增**：上述 `26` 是修复当时的数字。紧接着新建的 `test_test_db_isolation.py`
> **自己也被这条判据扫**（它在 `tests/**` 内），所以收口时的实测输出是
> `[PASS] 27 个测试文件 + 16 个 CI 引用脚本（49 个字面量 = 豁免 8 + 判定 29）`。
> 这不是"数字变了"，而是**判据的覆盖范围由磁盘决定**（铁律 14）——新文件天然入册，
> 无需改任何名单。**这正是它值得被信任的原因**：本包新增的测试文件若写坏 DSN，
> 会当场被自己报红（已由 `test_this_file_itself_is_clean` 固定下来）。

> ⚠️ **豁免必须成对证明**（这是本包新增的第 4 类判据纪律）：
> 豁免**天生只会把红变绿，不会把绿变红** ⇒ 每扩一次豁免，必须同时给出
> **阳性对照**（"该放过的真的放过了"）与**阴性对照**（"不该放过的真的没放过"）。

| 边界 | 说明 |

| 判据 A 只判**字面量** | 用变量拼出来的 DSN（`f"{host}/{dbname}"`）扫不到。本仓实测该形态为零；引入时需扩充 |
