## 1. 为什么需要冻结

M3 剩余 7 个包的模块目录**不是天然独立的**：

- WP30（AI 自检/硬软规则）与 WP33（重复检查/质量报告）都是"质量"语义，放一个模块里两边会 `mkdir` 同一目录；
- WP31（试产关口）与 WP32（扩产/批产）都是"数量 + 状态机"，都想写 `modules/planning/`；
- WP29（预览/编辑/反馈定位）要同时读 `content` 与 `media` 两侧坐标，而这两个模块**都有在途改动**；
- WP34（回退影响图/导出失效）要遍历 `version_dependencies`（WP11 的公共设施），还要让 `export_items` 失效（WP35 的表）。

更关键的是：**迁移是唯一仲裁资源**。`migrations/versions/` 是一条单链，`down_revision` 必须首尾相接。
7 个分支各生成一个迁移文件，会得到 **7 个都指向 `a9d3f6c2b815` 的分叉**，`alembic upgrade head`
当场报 `Multiple head revisions are present`，回滚序列不再唯一（M5 的 WP47 回滚演练会整体 `downgrade base`，分叉即不可执行）。

因此并行的前提不是"目录不重叠"，而是**把共享面显式切开**：让冲突在**写之前**就不可能发生，
而不是在 merge 时靠人工分辨（M4 §1 原话）。

## 4. 迁移的并行协议（最容易出事的地方）

### 4.1 铁律：**分支禁写 `migrations/versions/`**

| 允许 | 禁止 |
|---|---|
| `docs/m3/WP<NN>-ddl-草案.py`（**逐包 DDL 文本草案**） | `migrations/versions/*.py`（**禁建**） |
| `modules/<自己的模块>/ddl.py`（触发器 DDL 的唯一来源） | `migrations/env.py`（禁改） |
| 自己模块的 `models.py`（ORM 元数据） | `contracts/openapi.json`（主 agent 串行导出） |

**分支只能交 DDL 的文本草案；建迁移是主 agent 的独占动作。** 这是 M2 已验证的办法。

草案内容 = 一张建表清单，含（M2 §4 原款）：
- 表名、列名、类型、可空性、默认值
- 全部 `UniqueConstraint` / `CheckConstraint` / `Index`（**含部分索引的 `WHERE`**）
- 外键指向（**只指向已存在的表**；指向其他包新建的表 = 越界，报告主 agent）
- 触发器需求（若有）

### 4.2 串行落迁移的顺序（主 agent 执行）

本批的 `down_revision` 链按下列顺序接，**每接一个都要跑 §4.4 的往返判据**：

```
a9d3f6c2b815（WP28，当前 head）
  → WP35（续作：e5a8c3b1d704 已写，须先入库并核对 down_revision = c4d9f2a17e35 的链位，见 §8.4 仲裁项 ③）
  → WP29 → WP30 → WP31 → WP32 → WP33 → WP34
```

**排序理由**：WP35 的迁移文件**已经存在于工作树**（`down_revision = c4d9f2a17e35`），
而当前 head 已经是 `a9d3f6c2b815`（WP28 的 `down_revision = e5a8c3b1d704`）——
也就是说 **WP35 的迁移已经在链上、排在 WP28 之前**，只是**文件未入库**。
⇒ 它不是"要新接的一环"，而是"**要先补进版本库的既有一环**"。这件事必须在任何新迁移之前办完。

其余 WP29~WP34 按包号升序，与 V2.1 §9 的 W12/W13 排期一致（W12：WP29/30/31/32；W13：WP33/34/35）。

每次 `autogenerate` 后必过 **G2 三件事**（删探针表 drop / 重写 downgrade / 补 postgresql 导入）。

### 4.3 分支的测试怎么建表（关键机制，别自己发明）

分支**不生成迁移文件**，但测试又必须有表。**不要**去改 `env.py` 或往 `migrations/versions/` 里放文件
—— 那会让其他分支的 `alembic upgrade head` 撞上 `Multiple head revisions are present`。

**正确做法**：分支在自己的测试文件里，用一个 **module 级 fixture** 建**自己那几张表**（M2 §4.1 原款）：

```python
import os
import pytest
from rednote.platform.base import Base
from rednote.platform.configuration import Settings
from rednote.platform.database import get_engine, reset_engines


def _make_settings() -> Settings:
    """与 tests/test_versions_wp11.py 同款：DSN 从环境变量取，缺省本机。"""
    dsn = os.environ.get(
        "REDNOTE_TEST_DATABASE_URL",
        "postgresql+psycopg://rednote@localhost:5432/postgres",
    ).strip()
    return Settings(database_url=dsn, environment="test")


@pytest.fixture(scope="module", autouse=True)
def _ensure_own_tables() -> None:
    """只建本模块的表 + 自己的触发器。

    为什么用 create_all 而不是迁移：
      · 迁移是共享单链，7 个分支各生成一个会分叉（见 §4.1）；
      · create_all 只建 tables=[...] 里列出的表，不碰别人的；
      · FK 目标表（version_nodes / content_items / projects / users 等）
        已由迁移建好，create_all 只发 FK 约束、不会尝试创建被引用表。

    为什么要先 reset_engines()：conftest 的 _isolate_settings_cache 是
    autouse 的 function 级 fixture，module 级 fixture 拿到的 engine
    可能已被上一轮清掉 —— 重取一次最稳。
    """
    reset_engines()
    settings = _make_settings()
    engine = get_engine(settings)
    from rednote.modules.feedback import models as _m  # noqa: F401  触发注册

    Base.metadata.create_all(engine, tables=[
        # …只列本包的表…
    ])

    # 不可变表的触发器：与迁移里用的是**同一份来源**（modules/<包>/ddl.py），
    # 这样主 agent 落迁移时直接引用它，不会出现两份不一致的 DDL。
    #
    # ⚠️ 必须先 DROP 再 CREATE —— **CREATE TRIGGER 不是幂等的**。
    #    本机实测：直接 CREATE 会报
    #    `DuplicateObject: trigger "trg_..." for relation "..." already exists`
    #    （迁移已建过，create_all 建表是幂等的但触发器不是）。
    from sqlalchemy import text
    from rednote.modules.feedback import ddl as own_ddl
    with engine.begin() as conn:
        # 元组形状（已核实 modules/parsing/ddl.py、modules/versions/ddl.py）：
        #   (表名, 函数 DDL, 触发器 DDL, 触发器 DROP, 函数 DROP)
        # 用前四个；最后一个（函数 DROP）是 downgrade 用的，**别在这里执行**。
        for _t, _func_ddl, _trigger_ddl, _drop_trigger, _drop_func in own_ddl.all_trigger_ddl():
            conn.execute(text(_drop_trigger))   # 幂等关键
            conn.execute(text(_func_ddl))
            conn.execute(text(_trigger_ddl))
    yield
```

> **触发器 DDL 的形状**（已核实，别猜）：`all_trigger_ddl() -> list[tuple[str, str, str, str, str]]`，
> 五元组 = `(表名, 函数DDL, 触发器DDL, 触发器DROP, 函数DROP)` —— 见
> `modules/parsing/ddl.py` / `modules/versions/ddl.py` / `modules/exports/ddl.py`。
> 底层函数在 `platform/immutability.py`：
> `immutable_trigger_ddl(table)` / `immutable_trigger_name(table) -> f"trg_{table}_immutable"`。
>
> **直接复用 `platform.immutability`，不要自己写触发器 SQL** —— 所有不可变表共用同一个函数
> `rednote_reject_mutation()`，自己写一份会在 downgrade 时撞
> `cannot drop function ... because other objects depend on it`（WP11 踩过、WP16 差点再踩、**ISS-79** 已记）。
>
> **本机制的代价（必须知情）**：测试建的表结构 = **ORM 元数据**，**不等于**迁移建的结构。
> 这道缝由主 agent 在并入迁移后用 §4.4 的往返判据 + `parity` 判据补上（M4 §4.2 原话）。

### 4.4 并入后必过的往返判据

每个 M3 迁移并入后立即跑：

```
upgrade head → downgrade base → upgrade head
```

载体：`services/backend/tests/test_migration_roundtrip.py`（静态扫描）+
`tools/quality/check_migration_roundtrip.py`（真库往返）+
`test_migration_model_parity.py` / `tools/quality/check_migration_model_parity.py`（ORM ⇄ 迁移对账）。

**`downgrade` 硬约束**（**ISS-79** 教训）：
- **不得删除跨包共用函数**（`rednote_reject_mutation()` 类）；
- 函数删除范围必须**按归属取**（`owned_functions()`），**不得**用 `all_trigger_ddl()` 的并集。

> M5 的 WP47 回滚演练会整体 `downgrade base`，M3 每个新迁移都会被逆序执行
> —— 往返判据不是可选项。

### 4.5 迁移文本必须是**化石**（ISS-191）

迁移里**不得活引用**取值域（不得 `from rednote.modules.x.types import SOME_ENUM` 后循环它）。
一旦活引用，parity 判据会恒绿：类型改了迁移也跟着改，两边永远一致 —— 判据**永不报警**。

**⇒ 迁移里的取值域必须写成字面量**，由 parity 判据反向核对。
判据载体：`tools/quality/check_migration_value_domain_no_live_import.py`。

**本批的高危点**：WP30 的硬软规则码、WP31 的试产状态机状态名、WP32 的批次状态、
WP33 的报告类型 —— 四个包都会引入新取值域，四个包都在这条判据的射程内。

## 8. 冲突处置流程（**撞车了怎么办、谁来仲裁**）

> ⚠️ **本节的来历与取舍**：M2 与 M4 **都没有独立的"冲突处置"小节** ——
> M2 把它散在 §2（「停下来报告主 agent」）、§4（「迁移是唯一仲裁资源」）、§5（「不得修改签名，
> 需要变更时停下来报告主 agent」）三处；M4 散在 §4.1 与 §6。
> M3 有 **7 个并行包 + 3 个在途模块**，散着写会让分支在撞车当场找不到动作。
> **⇒ 本节是把 M2/M4 已有的三句话展开成流程，不引入任何新概念、不改变任何既有口径。**

### 8.1 仲裁人

| 角色 | 谁 | 权限 |
|---|---|---|
| **仲裁人** | **主 agent（收口方）** —— 与 M2 的「冻结人」同一人 | 唯一有权改 §1.1 的 26 处共享文件；唯一有权改本文件；唯一有权重新指派 §2.1 的模块归属 |
| **分支** | WP29~WP35 各自的会话 | 只写 §1.2 的三处；**发现越界必须停，不得自行协商** |

> **为什么分支之间不许直接协商**：共享工作树里两个会话的改动在 `git status` 上**完全同形**
> （同一个 `M`、同一个 mtime 区间）—— **ISS-207 / ISS-217 已定：不把"谁改的"当断言**。
> 两个分支私下约定"这块归我"，在磁盘上留不下任何可对账的痕迹 ⇒
> 第三个分支与收口方都无从知情。**一切边界变更必须经主 agent 落到本文件里**。

### 8.2 分支侧：撞车当场的四步

| 步 | 动作 | 不许做什么 |
|---|---|---|
| **1. 停** | 发现要改的文件不在 §1.2 的三处里 ⇒ **立刻停手**，不要"先改了再说" | 不要 `git stash` 别人的改动；不要 `git checkout --` 覆盖 |
| **2. 取证** | 跑 `python tools/quality/check_cross_session_shared_files.py --paths <那个文件>`，拿到它是 §1.1 第几处 + 权限；若不在 26 处内，记下路径与"为什么需要改它" | 不要凭印象汇报"好像是共享的" |
| **3. 报告** | 把**三件事**报给主 agent：① 要改的路径；② 要改成什么（最小改动）；③ **不改它的话有没有替代实现**（往往有，见 §8.3 的四种标准处置） | 不要只报"我被挡住了" |
| **4. 等** | 在主 agent 回话前，**绕开这一块继续做自己目录内的部分**；不要空等，也不要"先写死一个假的接口" | 不要用假设字段实现（WP28 挂起期的同款禁令，V2.1 §9.1 原话「**不允许用假设字段实现**」） |

### 8.3 主 agent 侧：四种标准处置（**按优先级从上到下试**）

| # | 处置 | 适用 | 代价 |
|---|---|---|---|
| **A. 加只读接缝** | 分支只是要**读**某个既有模块的东西 ⇒ 主 agent 在那个模块里加一个只读函数/属性，登记进 §5，各分支都能用 | 最常见（M2 的 `JobRepository.session` 就是这么加的） | 一次串行提交 |
| **B. 前置骨架提交** | 两个分支要往**同一个目录**写（WP31/WP34 的子包、WP30/WP33 若最终同模块）⇒ 主 agent 先提交空骨架，各写各的子包 | **M4 §6 铁律 5** 原款 | 一次串行提交 |
| **C. 重新指派模块** | 发现 §2.1 的指派在实现上站不住（比如 WP29 确实必须写 `content` 根层）⇒ 改 §2.1 + 改 §1.1 的权限行 + 改标题计数 | 改本文件 = 改边界，必须留痕 | 需要通知全部在跑的分支 |
| **D. 串行化** | 两个包的写面**本质不可切开**（典型：WP34 的"导出失效"要改 `export_items` 而 WP35 正在写它）⇒ **放弃并行，排成先后** | 最后手段 | 失去并行收益，但**比静默覆盖便宜得多** |

> **不在选项里的两种做法**（显式禁止）：
> - **"两个分支都改，merge 时再说"** —— 本项目在冻结前没有版本控制时的默认行为，
>   后写者**静默覆盖**先写者（M2 §1 原话）。
> - **"给判据加个豁免开关让它别报"** —— 假红会逼人削弱判据，而削弱后的判据比没有判据更坏
>   （**ISS-222** 的处置原则：加豁免必须**同时**加一条"豁免不得空转"的判据，如 G4）。
