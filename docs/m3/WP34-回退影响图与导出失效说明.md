## 0. 一页结论

1. **遍历**：以 `version_dependencies` 为边，边方向 `parent → dependency` = 「下游引用上游」；影响图 = 从起点版本沿**反向**（`dependency_version_id = X` 取 `parent_version_id`）做**分层 BFS**，带访问集合、深度上限 12、节点上限 2000，超限**不报错而返回 `complete=false`**；起点取 `current_version_id` **投影**，全包禁 `ORDER BY version_no DESC`。
2. **回退**回退的是**投影指针**（`content_items.current_version_id`），不是任何版本数据；影响分三层：下游版本（`REVIEW_REQUIRED` / `HISTORICAL` / `UNRESOLVED`）、导出行（`FROZEN_ON_DEPARTING` / `FROZEN_ON_DOWNSTREAM` / `FROZEN_ON_TARGET`）、以及不经边的图片资产（由资格指纹捕获）。
3. **导出失效**：新增**一张**不可变事件表 `export_validity_events`（建在 `versions/impact/`，由 WP34 自带 DDL），FK 指向 `export_items.id`；`export_items` 零改动、零新列；当前态 = 最大 `seq` 的 `transition`（无事件 = VALID）。判定一律走 WP35 已登记的只读接缝重算资格指纹，**本包零哈希实现、零「当前版本」第二份读法**。
4. **两个必须主线先拍板的发现**（详见 §2.2 / §15）：① **全仓 `link_dependency` 零调用方**，`version_dependencies` 里没有生产者写的边，影响图在生产数据上恒空（OQ-34-01）；② WP35 **没有**按接缝冻结 §8.4 ③ 的约定「预留失效语义」，只留了 `ix_export_items_version` 与 `eligibility_hash`（OQ-34-02）。

## 3. 「回退」到底回退什么，对下游的影响怎么分类

### 3.1 名词定义（本文档内的唯一口径）

| 词 | 定义 | 依据 |
|---|---|---|
| **版本** | `version_nodes` 一行；不可变 | `versions/models.py` |
| **投影 / 当前版本** | 逻辑实体上的**显式指针**，如 `content_items.current_version_id`；可指向任意一版（含旧版） | 契约 §2.1；`content/models.py` 第五节 |
| **回退（rollback）** | 把某逻辑实体的投影指针从版本 D（**离开版本 departing**）改指向另一已存在的版本 T（**目标版本 target**）。**不产生新版本、不改任何版本行、不改任何边** | 投影可指旧版是既有设计（回滚分叉，WP35 R2） |
| **编辑** | 追加新版本并前进投影（`append_edited_version`）。从影响角度看，它与回退**同构**：投影离开 D，指向另一个版本 | 接缝冻结 §5.12 |
| **影响（impact）** | 因投影离开 D，那些**依赖 D** 的东西不再对应「当前」 | — |

> 因此本包的核心函数 `traverse_dependents(start=D)` 对「回退」「编辑」「上游新版本」**一视同仁**：区别只在 D 是怎么来的（回退预览取投影；通用端点由调用方给 D）。这也是 WP34 不必知道「谁移动了指针」的原因（§3.3）。

### 3.2 影响分类（响应侧取值域，**不落库**）

**A. 下游版本节点**（遍历结果里的每个节点，`impactClass`）：

| 值 | 条件 | 含义 | 动作建议（仅提示，不自动执行） |
|---|---|---|---|
| `REVIEW_REQUIRED` | 该节点**是其实体的当前版本**（投影指向它）且依赖 D | 当前在用的成果建立在已离开的版本之上 | 复核 / 重生成 |
| `HISTORICAL` | 该节点**有投影但投影不指向它** | 本来就是历史版本，影响仅留痕 | 无 |
| `UNRESOLVED` | 无法判断当前性：实体类型无解析器（v1 仅 CONTENT、MEDIA；REPORT 视 WP33，见 OQ-34-12），或投影为 NULL | **不是 false**——缺失不填 0（§10） | 由调用方自行判断 |

**B. 导出行**（`exports.items[].exportImpact`；仅在回退预览与 `FROM_VERSION` 扫描中给出）：

| 值 | 条件 | 将发生什么 |
|---|---|---|
| `FROZEN_ON_DEPARTING` | `export_items.version_node_id = D` | 投影离开 D 后下一次扫描判 `INVALIDATED(VERSION_SUPERSEDED)` |
| `FROZEN_ON_DOWNSTREAM` | `export_items.version_node_id` ∈ 遍历所得的 CONTENT 节点集（即**上游**变化，内容本身未必变） | **仅提示「风险」**，不判失效（资格指纹未漂移；见 OQ-34-03） |
| `FROZEN_ON_TARGET` | `export_items.version_node_id = T`（仅回退预览） | 若其最近事件为 `INVALIDATED`，回退后下一次扫描将 `RESTORED`（信息项） |

**C. 不经边的影响（本包不建模，但被资格指纹捕获）**：图片资产（`media_renditions` 的重新加工）与内容之间**没有 `version_dependencies` 边**（`media_versions` 无 content 版本外键，仅 `media_items.content_item_id`）。它们引起的导出失效由 `ASSET_CHANGED`（§5.4）覆盖，不进入遍历图。图文段落错位属 WP30 `MEDIA_PARAGRAPH_REF_STALE` / WP33 对位检查，不在本包。

### 3.3 本包**不做**什么（边界）

· **不执行回退**（不移动投影）。依据：移动 `content_items.current_version_id` 必须改 `content/*.py` 根层（共享文件第 21 行，禁改）；并且全仓目前**没有**「恢复旧版本」的写入口（`grep rollback_to|restore` 在 content/media 零命中；WP29 说明明言只验并发冲突、不验回退，见 `AC-28验收标准_草案` §「局部重做/恢复旧版本」归 AC-13~15）。→ OQ-34-06。
· **不自动触发**扫描（无钩子进 content 写路径）。v1 仅显式 `POST` 与读时计算。→ OQ-34-05。
· **不改下载**：失效的导出仍可下载（ZIP 是历史事实，`zip_sha256` 不变）。「失效」的语义是**不再是当前可交付版本**，与 WP36 的「资格复验」同义。

## 4. 影响图遍历算法

### 4.1 图与边方向（逐字定义，测试按此断言）

```
version_dependencies 一行 = 有向边 E(parent → dependency)，含义「parent 用到了 dependency」
                            parent_version_id    = 下游（引用方，如内容版本 / 报告版本）
                            dependency_version_id = 上游（被引用方，如 Brief / 知识 / 基线 / 提示词版本）

依赖方向图 G_dep：沿 parent → dependency 走（link_dependency 的成环检测用的是这个方向）
影响图    G_imp：G_dep 的反向；从版本 X 出发，下一跳 = { parent | E(parent → X) }

深度 depth(n) = 起点到 n 的最短跳数；起点 depth = 0，不计入 nodes。
```

举例：`E(报告v1 → 内容v3, REPORT_INPUT)`、`E(内容v3 → 基线v2, …)`。从 `基线v2` 出发的影响图 = `{内容v3(depth1), 报告v1(depth2)}`；从 `报告v1` 出发 = `∅`（没人依赖报告）。

遍历键 = **`version_nodes.id`**，不是 `entity_id`（`ENTITY_TYPE_PLAN` 下 `entity_id` 可能是项目也可能是批次，R15；用节点 id 则无歧义）。
**`purpose` 不参与过滤**：所有边一律传播；每个节点附带到达它的边的 `purpose` 集合（排序、去重）原样透出（OQ-34-10）。

### 4.2 起点规则

| 入口 | 起点 D 的来源 | 禁止 |
|---|---|---|
| ② 通用 `GET …/versions/{versionId}/impact` | 调用方给的 `versionId`（必须属于路径项目，否则 404） | — |
| ① 回退预览 `GET …/rollback-impacts?entityType=CONTENT&entityId=…&targetVersionId=…` | **服务端**读 `content_items.current_version_id` 投影 = D；**不信**客户端给 D | **`ORDER BY version_no DESC`**；用 `MAX(revision_no)` 推断当前版 |
| ③ 扫描 `FROM_VERSION` | 调用方给的 `fromVersionId` | 同上 |

投影为 NULL（合法中间态，契约 §2.1）：回退预览返回 **409 `NO_CURRENT_VERSION`**，当前性判定返回 `UNRESOLVED`。**不回落末版**——这偏离契约 §2.1 的「投影为 NULL 时回落 `ORDER BY version_no DESC`」，理由：本包的结论会被当作「该不该复核」的依据，猜一个末版比承认未知更危险；且回落实现等于在本包再写一份「当前版本」读法（接缝冻结 §5.13 要求不另写）。→ OQ-34-07（请主线确认可偏离）。

全包静态断言：`impact/**` 源码不含 `ORDER BY version_no`、`MAX(version_no)`、`max_revision_no`（测试 T-START-04）。

### 4.3 算法（分层 BFS + 访问集合 + 上限）

```
traverse_dependents(fetch_dependents, start, *, max_depth=12, max_nodes=2000) -> TraversalResult

  visited  = { start: depth 0 }           # 访问集合：终止性的根本保证（理由同 dependency_reaches）
  frontier = [start]
  edges    = []                           # 仅用于 §4.5 的环检查与 purposes 汇总
  for depth in 1 .. max_depth:
      rows = fetch_dependents(frontier)   # 一次批量：WHERE dependency_version_id = ANY(frontier) AND parent 属于路径项目
      edges += rows
      new  = sorted({ r.parent } - visited.keys())   # 稳定顺序 ⇒ 截断结果确定
      if len(visited) - 1 + len(new) > max_nodes:    # 节点上限
          take = new[: max_nodes - (len(visited) - 1)]
          mark visited[take] = depth
          return result(complete=False, truncation="NODE_LIMIT", ...)
      mark visited[new] = depth
      if not new: return result(complete=True, ...)
      frontier = new
  # 走满 max_depth 仍有 frontier：多探一层，判断是「恰好走完」还是「被深度截断」
  if fetch_dependents(frontier) 产生任何未访问的 parent:
      return result(complete=False, truncation="DEPTH_LIMIT", ...)
  return result(complete=True, ...)
```

· `fetch_dependents` 由 `repository.py` 提供（SQL：`SELECT parent_version_id, dependency_version_id, purpose FROM version_dependencies vd JOIN version_nodes pn ON pn.id = vd.parent_version_id WHERE vd.dependency_version_id = ANY(:frontier) AND pn.project_id = :pid ORDER BY 1,2,3`，frontier 超过 500 个 id 时分块）。走 `ix_version_dependencies_dependency`；每层一次往返，总往返数 ≤ `max_depth + 1`，**与路径数无关**。
· `traverse_dependents` 是**纯函数**（`fetch_dependents` 注入），不碰数据库 ⇒ 毫秒级单测（与 `can_view_version` 同思路）。
· **为什么不用递归 CTE**：`UNION` 去重的 CTE 带不了 depth（带上会令同一 id 每层留一行）；而本包需要最短深度、层级截断与 `purposes`。DB 往返数以深度计、远小于节点数，可接受。

### 4.4 节点附加信息

遍历结束后**一次**批量补全（不在循环内逐个查）：
1. 节点元信息：`SELECT id, entity_type, entity_id, revision_no, project_id FROM version_nodes WHERE id = ANY(:ids)`；
2. 当前性（v1 解析器，裸 SQL，列名即对方契约）：
   · CONTENT：`SELECT cv.id, ci.current_version_id FROM content_versions cv JOIN content_items ci ON ci.id = cv.content_item_id WHERE cv.id = ANY(:ids)`；`ci.current_version_id = cv.id` → current；非 NULL 且不等 → historical；NULL → unresolved。
   · MEDIA：同形，`media_versions.media_item_id → media_items.current_version_id`。
   · REPORT：同形，`quality_report_versions.report_id → quality_reports.current_version_id`；**依赖 WP33 落地**（OQ-34-12）。
   · 其余类型（BRIEF / KNOWLEDGE / PROMPT / BASELINE / PLAN）：`UNRESOLVED`（未找到这些类型的统一投影；知识/提示词有「激活版本」概念但口径各异，不在本包臆造）。
3. `impactClass` 由 (1)(2) 派生；`byType` 计数由返回节点汇总。

### 4.5 环检测

· 写入侧已禁环；遍历仍须对「绕过 service 的脏环」自保。**终止性**由访问集合保证（环不产生新 id）。
· **报告**：遍历结束后，对 `edges` 中两端都在 `visited` 内的子集做 Kahn 拓扑排序；有剩余节点 ⇒ `anomalies += ["DEPENDENCY_CYCLE"]`，并给出 `cycleNodeCount`。**不抛错**（读路径不应因脏数据整体失败）。
· 起点自身在环上（存在 `E(start → x)` 且 `x` 可达 start）同样被捕获，因为 `start` 在 `visited` 内。
· 截断时（`complete=false`）「未发现环」**不构成无环结论**；文档与响应字段注释均写明（`anomalies` 为空只在 `traversal.complete=true` 时才有意义）。
· 区分菱形与环：菱形的第二条入边指向已访问节点但 Kahn 能排空；环不能。

### 4.6 规模上限与超限行为（初值，OQ-34-08 待主线确认）

| 常量 | 初值 | 依据 / 说明 |
|---|---|---|
| `MAX_TRAVERSAL_DEPTH` | 12 | 已知实体链层数约 6~7（BRIEF/KNOWLEDGE/PROMPT → BASELINE → PLAN → CONTENT → MEDIA/REPORT），取约 2 倍余量；**无仓内数据依据** |
| `MAX_TRAVERSAL_NODES` | 2000 | 单响应体与内存上界；**无仓内项目规模数据**（未找到依据） |

| `MAX_SWEEP_CONTENT_IDS` | 50 | 与 `exports.types.MAX_CONTENT_ITEMS_PER_EXPORT` 同值、各写一份、测试对账（平级不可互 import） |
| `MAX_SWEEP_ITEMS` | 500 | 单次扫描的导出行上限；超出 ⇒ 422，**不静默截断** |

超限行为（**不静默**）：

| 入口 | 行为 |
|---|---|

### 4.7 一致性与并发读

边与节点表**只追加**；单请求内多层读取即使跨越他人新增的边，结果也只会是真实图的某个**超集前缀**（不会出现不存在的边）。当前性用的是**可变投影**，在遍历结束后**一次**批量读，响应注明为「读取时刻」。不开 `REPEATABLE READ`（为一个建议性预览付快照代价不值得；写类入口的判定见 §9）。

## 5. 导出失效方案

### 5.1 「失效」的定义（对齐 R2/R8/R11）

> 一条导出行 `export_items`（一个 `(导出组, 内容, 冻结版本)`）**失效** = 按**当前**正文版本与正式图重算的资格指纹，**不等于**该行导出时冻结的 `eligibility_hash`。

· 不删除、不隐藏、不改 ZIP；`zip_sha256`、下载、核验端点行为不变。
· 失效**可恢复**：回退到被冻结的版本（或图的状态回到冻结时）后指纹回等 ⇒ `RESTORED`。
· 重算**算不出**（内容已无正文版本 / 配图位缺正式图：`ExportError`）⇒ 状态 `UNKNOWN`，**不是** VALID 也不是 INVALID，**不落库**（与 WP36「算不出 ⇒ 409，不降级成通过」同源）。

### 5.2 为什么新建失效记录表不违反 `export_items` 不可变（论证）

| # | 论证 | 证据 / 验证 |
|---|---|---|
| 1 | `trg_export_items_immutable` 是 `BEFORE UPDATE OR DELETE`。本包对 `export_items` **只做 SELECT**；失效事实写在**另一张表**，不改被冻结的那一行 | 静态扫描 `impact/**` 无 `UPDATE export_items` / `DELETE FROM export_items` / `INSERT INTO export_items`（T-EXP-02） |
| 2 | 本表对 `export_items` 有出向 FK。向子表 INSERT 时 PG 对被引用行取 `FOR KEY SHARE` **行锁**，这不是 UPDATE，不会触发 `BEFORE UPDATE` 触发器，也不产生新的行版本 | **⚠️ 未实测**（推断）。T-EXP-01：INSERT 事件前后读 `export_items` 行的 `xmin`，必须不变；触发器不触发（同事务内 INSERT 成功） |
| 3 | `ON DELETE RESTRICT`：只要有事件引用，`export_items` 行就删不掉——与「不可变」同向加固，不冲突（`export_items` 本就禁删） | T-EXP-03：对被引用行 `DELETE`，断言 sqlstate `23001`（不可变触发器先于 FK 拦下）；对无引用行同样 `23001` |
| 4 | 本表自身也不可变（`trg_export_validity_events_immutable`），追加写 | T-EXP-04 |
| 5 | 事实不复制：不在本表存 `project_id` / `content_item_id` / 冻结版本 / 冻结指纹，全经 FK 取得，所以**不存在**「本表与 `export_items` 说法不一致」的状态；仅 `observed_*` 是**新观测**，由一致性触发器与冻结值对账 | `ck_..._reason_paired` 等 + `trg_export_validity_events_consistency`（DDL 草案 §四） |
| 6 | 迁移只 `CREATE TABLE` 新表；不对 `export_items` 做任何 `ALTER` | DDL 草案 CHECKLIST 第 7 条；往返后 `export_items` 的列/约束/触发器 diff 为空 |
| 7 | 接缝冻结 §4.1「外键只指向已存在的表」：`export_items` 已存在（迁移 `e5a8c3b1d704`），WP34 迁移序在 WP33 之后 | 接缝冻结 §4.2 |

> 副作用（须主线知情）：这是一条**新增的跨包入向 FK**，与 WP36 `deliveries.export_item_id` 同类。测试夹具的 FK 闭包（`conftest.truncate_targets`）须覆盖——DDL 草案 §六。

### 5.3 数据模型（详见 `WP34-ddl-草案.py`）

`export_validity_events`（不可变、追加写）：`id` / `export_item_id`(FK) / `seq` / `transition`(INVALIDATED｜RESTORED) / `reason`(VERSION_SUPERSEDED｜ASSET_CHANGED，仅失效时) / `observed_version_id`(FK version_nodes) / `observed_eligibility_hash` / `scope_kind`(CONTENTS｜FROM_VERSION) / `source_version_id`(FK，仅 FROM_VERSION) / `created_by` / `created_at`。
当前态 = `export_item_id` 下**最大 `seq`** 那条的 `transition`；无事件 = VALID。触发器钉死：`seq` 从 1 连续、INVALIDATED/RESTORED 严格交替、首条必为 INVALIDATED、事件与冻结值对账。

### 5.4 判定函数（唯一实现点）

```
observe(content_item_id) -> Observed(version_id, eligibility_hash)  |  Unavailable(upstream_reason, message)
    # 只做一件事：转发 WP35 的只读接缝；ExportError → Unavailable（保留 reason 与原文，不吞、不降级）

derive(item, observation) -> (state, reason)
    Unavailable                                   -> (UNKNOWN, None)          # 不落库
    obs.hash == item.eligibility_hash             -> (VALID,   None)
    obs.version_id != item.version_node_id        -> (INVALID, VERSION_SUPERSEDED)
    else                                          -> (INVALID, ASSET_CHANGED) # 同一正文版本，图被重新加工
```

· 同一内容的多条导出行**共用一次观测**（先按 `content_item_id` 去重再调接缝）。
· `observed_version_id` 与 `observed_eligibility_hash` 必须**来自同一次读取**（同一快照）：这正是 §13 S2 要求新增「一次返回二者」的接缝、而不是让本包先调 `freeze_content` 再另算哈希的原因（两次调用之间若有并发编辑，会拼出一个「新版本 + 旧哈希」的假观测）。

### 5.5 扫描（写）与读时评估（读）

| | 读时评估 `GET …/exports/{groupId}/validity` | 扫描 `POST …/export-validity-sweeps` |
|---|---|---|
| 写库 | 否 | 是（仅状态**变化**时追加事件） |
| 权限 | `VIEW` | `DELIVER`（与导出同权，R：`ProjectAction.DELIVER` 注释「下载、交付…」） |
| 范围 | 一整个导出组 | `contentItemIds`（≤50）**或** `fromVersionId`（先遍历再映射到内容，见下） |
| 返回 | 逐行 `derivedState` + `recordedState` + `inSync` | 逐行变化 + 汇总计数 |

`FROM_VERSION` 映射：遍历结果里的 `CONTENT` 节点 → `version_nodes.entity_id` 即 `content_item_id`（§2.1 末行）；`D` 自己若是 CONTENT 也计入。再取这些内容在本项目下的全部 `export_items`（走 `ix_export_items_version` 或按 `content_item_id`）。

状态转移表（`recorded` = 最大 seq 的 transition，无事件视为 VALID）：

| recorded | derived | 动作 |
|---|---|---|
| VALID | VALID | 无（unchanged） |
| VALID | INVALID | 追加 `INVALIDATED`（reason = derived.reason） |
| INVALID | INVALID | 无（**不**为「原因变了」追加事件；响应里给出当前 derived.reason） |
| INVALID | VALID | 追加 `RESTORED` |
| 任意 | UNKNOWN | 无（计入 `unknown`，响应给 `unknownReason`） |

### 5.6 与 WP36 的关系

· WP36 在「标记交付」时**自己**重算比对（409），**不读**本表。本包的事件是**审计与列表视图**，不是 WP36 的前置。
· 两包都经由**同一个** `exports` 只读接缝取数；任何一方都不另写哈希/当前版本读法（§8）。
· WP36 是否应当读 `latest event = INVALIDATED` 作为快速拒绝：OQ-34-04。

### 5.7 方案对比（≥4 套，推荐 V2）

| 方案 | 做法 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| **V1 纯计算，不落库** | 只提供读时评估；与 WP36 R3 同款 | 零新表；零迁移风险 | 回答不了「何时失效、因何失效、是否来回翻过」；无列表/审计；用户已定前提要求有失效记录表 | 否（违背用户前提） |
| **V2 追加式事件表 + 派生当前态**（本设计） | 一张不可变表；最大 `seq` 为当前态；触发器钉连续与交替 | 不碰 `export_items`；可恢复；完整历史；并发靠 UQ(seq) | 取当前态需「每行取最大 seq」查询；多一个一致性触发器 | **推荐** |
| **V3 可变状态表** | `export_validity(export_item_id PK, state, reason, lock_version)` 原地更新 | 当前态 O(1)；列表简单 | 原地覆盖丢历史（翻来覆去无从追溯）；若补历史则变成两张表；可变表要 `lock_version`/ETag 面 | 否 |
| **V4 改 `export_items`** | 加 `invalidated_at` 列 / 放开不可变 | 最直观 | **违反** `trg_export_items_immutable`、接缝冻结 §1.1 第 24 行与 §8.4 ③；WP36 的冻结复制与 `eligibility_hash` 论证全部失效 | 否决 |

## 8. 与 WP36「复用同一函数」的约定

接缝冻结 §5.13 末句：WP34 与 WP36 复用同一函数、不另写第二份。落实为 **5 条可判据的约定**：

1. **唯一入口**：`impact/export_bridge.py` 是 `impact/**` 内**唯一** import `rednote.modules.exports` 的文件，只做转发 + `ExportError → Unavailable` 的语义换位（照 WP36 `export_bridge` 的做法与理由：保留原因与原文，不吞、不降级）。
2. **零实现**：`impact/**` 内不得出现 `hashlib`、`sha256`、`eligibility_hash(`、`ORDER BY version_no`、对 `media_renditions` 的任何查询。测试 T-REUSE-02 做源码扫描。
3. **同源对账**：桥接层返回的指纹与直接调用 `exports.service.current_eligibility_hash` **逐字节相同**（T-REUSE-01，照 WP36 `test_bridge_forwards_the_readonly_seam_and_does_not_reimplement_it`）。
4. **调用次数**：一次扫描对每个 `content_item_id` 至多调用接缝 **1 次**（T-REUSE-03，spy 计数）。
5. **接缝形态**：本包需要 `(version_id, hash)` 同快照二元组，现有 `current_eligibility_hash` 只返回哈希。→ §13 S2；**不得**自行调 `freeze_content` + `eligibility_hash` 拼装（该拼装体 = `current_eligibility_hash` 的函数体，等于第二份，且有跨调用快照分裂风险）。

| 场景 | 处置 | 测试 |

## 10. 缺失不填 0（NULL / 0 / 约数 三者分离）

| 位置 | NULL（未知/不适用） | 0（算过，确为零） | 约数（下界） |
|---|---|---|---|
| `isCurrent` | `null` = 无解析器或投影为 NULL | `false` = 有投影且不指向它 | — |
| `impactClass` | `UNRESOLVED` | `HISTORICAL` | — |
| `nodeCount` | — | `0` 且 `complete=true` = 确无下游 | `nodeCountIsLowerBound=true`（被截断） |
| `exports.items` / `count` | — | `[]` 且 `complete=true` | `countIsLowerBound=true` |
| `anomalies` | — | `[]` 仅在 `complete=true` 时才表示「无环」 | 截断时附注「未检出≠无」 |
| `derivedState` | `UNKNOWN`（算不出资格） | — | — |
| 扫描汇总 | `unknown` 单列 | `invalidated`/`restored`/`unchanged` 各自为精确数 | 无（写类遇截断直接 409，不产生下界数） |
| 事件表 | `reason` 在 `RESTORED` 时为 NULL（`ck_…reason_paired` 双向等价） | — | — |

**反例禁令**：不得把 `UNKNOWN` 折成 `VALID`（会让「没验证」读成「没问题」）；不得把截断后的 `nodeCount` 当精确值；不得把 `isCurrent=null` 序列化成 `false`。

## 12. 测试计划（用例清单，不写代码）

私有库 `rednote_test_wp34`；module 级 fixture 用 `create_all(tables=[export_validity_events])` + `ddl.all_trigger_ddl()`（先 DROP 后 CREATE，接缝冻结 §4.3）。约束类断言**必须断言 `sqlstate`**（§6.2-4）；不可变探针用「单事务 + SAVEPOINT + 整体 rollback」（§6.2-5）。API 测试 `follow_redirects=False`（G5）。造数照 `tests/test_exports_wp35.py` 的做法（不 import 该文件）。

**T-GRAPH（纯函数，无 DB）**
1. 线性链 A←B←C 从 A 出发：B depth1、C depth2。
2. 菱形（两条路径到同一节点）：节点只出现一次，depth 取最短。
3. 扇出：一个上游 N 个下游，全部 depth1。
4. 起点不在 `nodes` 内；零下游 ⇒ `nodes=[]`、`complete=true`、`nodeCount=0`（不是 null）。
5. **方向**：对 `E(parent→dep)`，从 dep 出发到达 parent；从 parent 出发什么都到不了。
6. 脏环（A↔B）：终止；`anomalies=[DEPENDENCY_CYCLE]`；菱形图**不**误报环。
7. 起点在环上（A→B→A）被报告。
8. 节点上限边界：恰好 `max_nodes` 个且无更多 ⇒ `complete=true`；`max_nodes+1` ⇒ `NODE_LIMIT`、`nodeCountIsLowerBound=true`、前缀确定（重复运行结果相同）。
9. 深度边界：恰好 `max_depth` 层且其后无更多 ⇒ `complete=true`；其后仍有 ⇒ `DEPTH_LIMIT`。
10. 往返次数 ≤ `max_depth + 1`（对 19 节点/36 边的菱形链+回边，WP11 同款图，不指数展开）。
11. `purposes` 去重排序。

**T-GRAPH-DB（真库）**
12. 批量反查走 `ix_version_dependencies_dependency`（`EXPLAIN` 断言 Index Scan/Bitmap，不是 Seq Scan，数据量放大后）。
13. 跨项目（含平台级 NULL）下游不被纳入；起点属别的项目 ⇒ 404 与「不存在」同形。
14. 与 `link_dependency` 写入的真实边互通（不手写 SQL 造边的一组用例）。

**T-START（起点）**
1. **回滚分叉**：内容 v1/v2/v3，投影指向 v1 ⇒ D=v1（不是 v3）。用 `MAX(version_no)` 的实现必须红。
2. 投影 NULL ⇒ 409 `NO_CURRENT_VERSION`（不回落）。
3. 客户端无法指定 D（①没有 `fromVersionId` 参数）。
4. 源码扫描：`impact/**` 无 `ORDER BY version_no` / `MAX(version_no)` / `max_revision_no`。

**T-ROLLBACK（①）**
1. 目标属别的内容 ⇒ 422 `TARGET_NOT_OF_ENTITY`；目标 = 当前 ⇒ 422 `TARGET_IS_CURRENT`；不存在 ⇒ 404；`entityType≠CONTENT` ⇒ 422。
2. 三类导出影响各一例：`FROZEN_ON_DEPARTING` / `FROZEN_ON_DOWNSTREAM` / `FROZEN_ON_TARGET`（后者含「最近事件为 INVALIDATED」）。
3. 下游含 REPORT 节点（造 `REPORT_INPUT` 边）⇒ `UNRESOLVED` 不是 `HISTORICAL`。
4. 预览**不写库**（事件表行数不变）。

**T-EXP（导出失效，真库）**
1. ★ `xmin`：INSERT 事件前后 `export_items` 行 `xmin` 不变，且 `export_items` 全表内容摘要不变。
2. 静态扫描：`impact/**` 无对 `export_items` 的写语句。
3. 对 `export_items` 行 `DELETE`/`UPDATE` ⇒ `23001`（有事件引用时亦然）。
4. 事件表 `UPDATE`/`DELETE` ⇒ `23001`。
5. 未改稿 ⇒ VALID，扫描不写事件。
6. 追加新正文版本 ⇒ `INVALIDATED(VERSION_SUPERSEDED)`。
7. 回退到被冻结版本（移动投影）⇒ `RESTORED`。
8. 同一正文版本、图重新加工出更高 `attempt_no` ⇒ `INVALIDATED(ASSET_CHANGED)`。
9. 算不出（无正式图 / 无版本）⇒ `UNKNOWN`，**不写事件**，`unknownReason` 透传。
10. 重复扫描幂等：第二次 `invalidated=restored=0`。
11. INVALID→INVALID（原因变化）不追加事件。
12. 同一内容多条导出行：接缝只调用 1 次（T-REUSE-03）。
13. 跨项目：项目 B 扫描项目 A 的内容 ⇒ 404；`FROM_VERSION` 起点属他项目 ⇒ 404。
14. `FROM_VERSION` 遍历被截断 ⇒ 409 `IMPACT_TRUNCATED` 且**零事件**。
15. 范围校验：空 / >50 / 重复 / 两种范围同给 / 命中行 >500。
16. 权限矩阵：非成员 404；具备 `DELIVER` 的成员可扫描；矩阵里若存在无 `DELIVER` 的角色则扫描 403 而评估（`VIEW`）可读（现矩阵 owner/collaborator 均有 `DELIVER`，该例是否可构造待落地时核对）。

**T-DB（DDL 与触发器，对照 `WP34-ddl-草案.py`）**
1. 表/约束/索引/触发器名与草案逐项一致（`pg_constraint` / `pg_indexes` / `pg_trigger`）；全部 ≤ 63 字节。
2. `reason_paired`、`scope_source_paired`、`observed_hash_shape`、`seq_positive`、取值域 CHECK 各一条反例（断言 sqlstate `23514` 与约束名）。
3. 触发器反例：首条为 RESTORED / seq 跳号 / 连续两条同 transition / INVALIDATED 指纹等于冻结值 / VERSION_SUPERSEDED 但版本未变 / ASSET_CHANGED 但版本已变 / RESTORED 未回到冻结值 ⇒ 均 `23514`。

5. 并发同 seq ⇒ 后到者 `23505`。
6. `downgrade` 不删 `rednote_reject_mutation`；往返后 `export_items` 无结构差异。

### 4. T-EXP-01 实测（真库，PG 17）

`test_t_exp_01_event_insert_does_not_touch_export_items_row`：
* `export_items` 上存在 `BEFORE UPDATE` 触发器 `trg_export_items_immutable`（`pg_trigger` 查得）；对同一行直接 `UPDATE` 被它以 `23001` 拒绝；
* 追加失效事件（INSERT 子表，FK 指向该行）成功；被引用行的 **`xmin` 前后相同**（一次运行：129760900 → 129760900），整行 md5 相同；事务内读同一行亦不变；
* 结论：推断成立——子表 INSERT 对被引用行只取 `FOR KEY SHARE`，既不触发 `BEFORE UPDATE`，也不产生新行版本。
* 另测 `test_t_exp_03`：有事件引用时 `DELETE`/`UPDATE export_items` 仍是 `23001`（不可变触发器先于 FK 拦下）。

### 5. 其他实测发现

* `version_dependencies` 上有 `trg_version_dependencies_scope`：非平台级（`project_id` 非空）节点之间的**跨项目边被 DB 拒绝**，只有平台级节点豁免。因此 `fetch_dependents` 的 `pn.project_id = :pid` 过滤的实际作用是排除平台级下游，而非他项目下游；测试按此重写（`test_graph_db_other_project_and_platform_dependents_excluded`）。
* REPORT「有表」情形用测试库内临时表 `quality_reports` / `quality_report_versions` 模拟，测试 `finally` 里 DROP；库中已有同名真实表时该例 skip，不会覆盖他表。
* 用 `drop_own_tables` 的 kept 语义：本表无入向 FK，夹具断言 `dropped ∪ kept == 本包表` 并对账跨包 FK 集合前后不变，不含「库名须含 wp34」自检。
* 本包不依赖 `batch.limits` 等迁移种子行，在无 GLOBAL 行的库里同样可过。
