## 0. 本包的一句话定位

**把"这份依赖清单"从"安装脚本里的一段补丁"变成"唯一的、被机械判据守着的真相"** ——
因为当前它有三个版本（`pyproject.toml` 写 7 个、`install.sh` 补 7 个、代码里注释说"已在 pyproject 锁定"），
**而这三者谁都不是权威，且没有任何东西会发现它们不一致。**

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让"这个项目需要哪些第三方包"**只有一个答案**，且这个答案**错了会有东西报红**。

拆开是三个彼此独立、但必须同时成立的问题：

| # | 问题 | 若不做会怎样 |
|---|---|---|
| P1 | **干净环境按 `pyproject.toml` 装完，`alembic upgrade head` 必须能跑通** | 新设备/CI/内网离线环境**按声明装完仍跑不起来**。实测：缺 `cryptography` 时迁移直接 `ModuleNotFoundError` 崩掉（`sync-kit` 演练记录），于是一条"照着文档做"的路径在**第一步就断** |
| P2 | **声明与代码必须一致，且不一致要报红** | 声明漏了 `httpx` ⇒ 生产安装（`pip install .` **不带 `[dev]`**）时 `platform/identity` 的 **`oidc.py` 顶层 `import httpx` 即崩**。这个失效不是"少个功能"，而是"服务起不来"，且**只在没装 dev extra 的环境出现** —— 本机永远发现不了 |
| P3 | **依赖清单必须是"可机械核对的事实"，不是"某个人记得补的一段脚本"** | `install.sh` 的 L203-260 那段补丁**本身就是证据**：它存在，说明有人知道声明不全。但它是**兜底**，不是**判据** —— 没有任何东西能回答"补丁装的那 7 个，是不是代码真正需要的全部？" |

**为什么 P1/P2/P3 必须同包做**：P1 是症状、P2 是根因、P3 是"同一件事会不会再发生"。
只修 P1（把包装上）不修 P3 ⇒ 下一个包新增 `import` 时，`pyproject` 会再漏一次，
而**漏的这一次依然不会报红**。这与本项目已现身 14 次的根因族完全同源。

**本包的产出边界**：它回答"依赖清单是什么、对不对、怎么保证以后还对不对"。
它**不建 wheelhouse**（WP46）、**不改任何业务代码逻辑**、**不新增任何迁移**。

### 1.2 核心用户是谁？

| 角色 | 规模 | 在本包做什么 |
|---|---|---|
| **新设备部署者 / 运维** | 1~3 人 | 按 `pyproject.toml` 装依赖 → 这一步必须**一次成功**，不能靠"记得跑补丁脚本" |
| **CI（门 1/门 2/门 3）** | — | `pip install -e "services/backend[dev]"` 之后跑迁移。它**从不读 install.sh**，因此**当前 CI 依赖的是"恰好 runner 里全都有"这个运气** |
| **WP46 内网打包** | — | 离线 wheelhouse 的输入清单 = 本包产出的依赖集。清单不全 ⇒ 内网装机缺包 ⇒ 又是"第一步就断" |
| **后续工作包的开发者** | — | 新增 `import` 时，有判据告诉他"该同步 pyproject 了" |

### 1.4 描述有哪些疏漏应当补充？理由是什么？

> 下面 3 条**全部来自本包勘察的磁盘实况**（命令与输出见 §4 证据），不是推演。

| # | 疏漏 | 为什么必须现在处理 |
|---|---|---|
| 1 | **代码注释在说谎，而且是 4 处** | `parsers/{office,pdf,image}.py` 共 **4 处**写着 `except ImportError as exc:  # pragma: no cover - 依赖已在 pyproject 锁定`。**实测这 4 个包（python-docx / openpyxl / pypdf / Pillow）在 pyproject 里一个都没有**。这正是判据纪律 #9："**声称自己有防线，比没有防线更危险**" —— 注释让读者以为依赖有保障，于是没人再复核 |
| 2 | **`httpx` 的作用域错了，不是"漏了"而是"放错位置"** | `httpx==0.27.2` **声明在 `[project.optional-dependencies].dev` 里**，而 `src/rednote/modules/identity/oidc.py:44` 是**顶层** `import httpx`（**生产代码，不是测试**）。⇒ `pip install .`（不带 `dev`）装完，**身份模块一 import 就崩**。本机/CI 都装 `[dev]`，所以**两边都测不出来** |
| 3 | **`starlette` 是传递依赖，代码却直接 import** | 5 处 `from starlette...`（`csrf.py` / `request_limits.py` / `errors.py` / `main.py`×2），但 `starlette` 只作为 `fastapi` 的传递依赖存在（实测 0.38.6）。**依赖传递依赖**在 fastapi 升级换掉 starlette 大版本时会**静默断裂**（且升级是 WP46 内网冻结后才会碰的事，那时已难回溯） |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **判据只比"总数"不比"作用域"** | 🔴 高 | 若把"运行时"与"测试"依赖混成一个集合，则 `httpx` 放在 `dev` 里也"通过" —— 而这正是 **P2 那个真实缺陷**。**判据漏掉它 = 判据没用** | 按**作用域分桶**：`src/` 顶层硬导入 → 必须属 `dependencies`；`tests/`/`tools/` → 可属 `dev`。两桶各判各的 |
| R2 | **判据做成"恒真式"** | 🔴 高 | 若写成"pyproject 里的包都装上了"，则**漏声明永远不触发**（漏的不在 pyproject 里，自然不参与比较）。参照 ISS-115：恒真判据与真判据**输出逐字相同**，"通过"与"根本没判"在输出上同形 | 判据方向必须是 **"代码用到的 → 声明里必须有"**（反向覆盖），并做**反向验证**：注入一处漏声明必须 `FAIL`，且**失败信息指向具体的包名与文件** |
| R3 | **AST 解析漏掉动态导入** | 🟠 中 | `importlib.import_module("xxx")` / `__import__` 扫不到 ⇒ 判判据有盲区 | 本仓实测：`src/` 下无动态导入（`grep importlib` 见证据）。判据**显式记录这个已知盲区**（写进工具 docstring），不做假保证 —— 不声称"100% 覆盖" |
| R4 | **别名映射表维护成本** | 🟠 中 | `import docx` 的发行名是 `python-docx`、`import PIL` 是 `Pillow`、`import pypdf` 是 `pypdf`。映射表若手写且不下沉判据，会漂移 | 映射表**落在判据脚本里**，并对**每一对名字**给出"发行名 ↔ 导入名"的双向断言（如 `docx → python-docx`）。**新增未映射的导入名必须报红**（不能静默跳过） |
| R5 | **改动 pyproject 触发 CI 缓存失效** | 🟢 低 | `cache-dependency-path: services/backend/pyproject.toml` ⇒ 改它会让 pip 缓存重建，门 1 变慢一次 | 可接受。这是**正确**的代价 —— 缓存本就该在依赖变化时失效 |
| R6 | **与 WP25 会话的文件冲突** | 🟢 低 | WP25 若在同一时间改 `pyproject.toml` | 实测 WP25 **零迁移、尚未落文件**；且本包改的是 `[project.dependencies]`，WP25 不碰依赖声明。**提交前 `git status` 复核** |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**：**无新表、无迁移**。改动集中在两个文件 + 一个新增工具：

```text
services/backend/pyproject.toml                    # 改：补全 dependencies
tools/quality/check_dependency_declarations.py     # 新：一致性判据（F2/F3）
.github/workflows/ci.yml                           # 改：门 3 挂判据（F4）
sync-kit/02-落地/install.sh                        # 改：兜底补丁降级为快照核对（F5）
```

**判据的三段式**（与 `check_test_db_isolation.py` 同构，便于维护者复用同一心智模型）：

| 段 | 扫描范围 | 判定 |
|---|---|---|
| ① | `services/backend/src/**/*.py` 的**顶层**硬导入 | 必须出现在 `[project.dependencies]` |
| ② | `services/backend/tests/**/*.py` + `tools/**/*.py` 的导入 | 必须出现在 `dependencies` **或** `[dev]` |
| ③ | `migrations/**/*.py` 的导入 | 同 ②（迁移由部署方执行，依赖随运行时安装） |

**接口**：

| 函数/常量 | 作用 |
|---|---|
| `MAPPING: dict[str, str]` | 导入名 → 发行名（`docx→python-docx` / `PIL→Pillow` / …）；**未映射的导入名报红** |
| `_declared_distributions(pyproject_path) -> set[str]` | 解析 TOML 取已声明发行名（规范化小写、`_`→`-`） |
| `_scan_imports(base) -> dict[str, set[Path]]` | AST 扫顶层硬导入，返回 `导入名 → 出处文件集` |
| `EXPECTED_CHECKS: int` | 防"崩溃伪装成通过"（ISS-43） |
| `main() -> int` | 三段判定 + `[PASS]`/`[FAIL]`，FAIL 时打印**包名 + 出处文件** |

**前端**：无。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**让"依赖清单"这件事从"三处各写一半、谁都不权威"变成"一处权威 + 一条判据守着它"** ——
而判据的方向必须是**"代码需要什么 → 声明里必须有"**，因为反向（"声明里有的都装上了"）对"漏声明"恒真。

### 2.2 用户画像

| 角色 | 最关心 | 本包怎么给 |
|---|---|---|
| 新设备部署者 | "照着文档做完就能跑" | `pyproject` 补全后，`pip install -e .[dev]` 一步到位，不必记得跑补丁 |
| CI | "别让我靠运气" | 判据进 CI ⇒ 漏声明在合并前就被拦 |
| WP46 内网打包 | "给我一份权威清单" | 判据扫描出的集合就是 wheelhouse 的输入 |
| 后续开发者 | "我加了 import，然后呢？" | CI 直接报"你没同步 pyproject"，并指出包名 |

### 2.3 核心功能清单（MVP）

| # | 功能 | 落点 |
|---|---|---|
| M1 | 补全运行时依赖并锁版本 | `pyproject.toml` |
| M2 | 修正 `httpx` 作用域（`dev` → 运行时） | `pyproject.toml` |
| M3 | 依赖声明一致性判据（三段 + 反向覆盖） | `tools/quality/check_dependency_declarations.py` |
| M4 | 反向验证（注入漏声明必须 FAIL） | 证据脚本内联 |
| M5 | CI 门 3 挂载 | `.github/workflows/ci.yml` |
| M6 | `install.sh` 兜底降级（职责唯一化） | `sync-kit/02-落地/install.sh` |

### 2.4 待补充项及理由

| # | 补充项 | 理由 |
|---|---|---|
| 1 | **`starlette` 显式声明** | 代码直接 `import` 传递依赖 = 隐式契约。显式声明它，把"fastapi 换了 starlette 大版本"从"静默断裂"变成"版本冲突，装不上" |
| 2 | **`httpx` 从 `dev` 提升为运行时依赖** | `oidc.py` 是生产代码的顶层导入。生产安装必须带它 |
| 3 | **判据白名单机制**（带理由） | `boto3`（M0 探针可选）/ `conftest`（本地模块非第三方）必须有落脚点，且白名单**逐条写理由**（与 `check_undefined_globals._IMPLICIT_GLOBALS` 同纪律） |
| 4 | **`EXPECTED_CHECKS` 常量** | 防"脚本中途抛异常 ⇒ 一条 CHECK 都没产生，却与全过计数相同"（ISS-43） |

### 2.5 砍掉清单

见 §1.5（wheelhouse / lockfile / 升级版本 / numpy / boto3 / 修测试库残留）。

### 2.6 技术风险评估（含应对）

见 §1.6 的 R1~R6。其中 **R1（作用域）与 R2（恒真）是本包必须当场闭合的两条**。

**约束 R2 的机制（唯一正确形态）**：

```python
# 错误形态（恒真）：声明里的包都装上了 → 漏声明永远不参与比较
for dist in declared:
    assert installed(dist)

# 正确形态（反向覆盖）：代码真正 import 的，声明里必须有
for imp, files in scan_imports(src):
    assert MAPPING[imp] in declared or imp in ALLOW, f"{imp} 未声明（出处：{files}）"
```

## 3. 阶段 3：多版本方案

### 方案 V1 —— 只补 `pyproject`，不建判据（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | 把 7 个包补进 `pyproject.toml` 完事 |
| 优点 | 最快（30 分钟）；立即解决 P1 |
| 缺点 | **P3 未解决** —— 下一个包新增 `import` 时照样漏，且**照样不报红**。这与本项目已现身 14 次的根因族（"覆盖范围由人写"）完全同源 |
| 适合 | 一次性脚本、不打算再改的项目 |
| 结论 | ❌ 不选。**它修的是症状** |

### 方案 V2 —— 用 `pip check` / `pipdeptree` 等现成工具（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | CI 里跑 `pip check`（校验已装包依赖自洽） |
| 优点 | 零自研；标准工具 |
| 缺点 | **方向完全不对**：`pip check` 校验的是"**已安装包的元数据是否自洽**"。本项目的缺陷是"**代码 import 了没声明的包**" —— `pip check` 对此**恒 PASS**（因为那些包也确实装上了，只是没在声明里）。另需新增工具依赖，与"减少自研"的偏好冲突但不解决根本问题 |
| 结论 | ❌ 不选。**它答的不是这道题** |

### 方案 V3 —— AST 反向覆盖判据 + 补全声明 + CI 挂载（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | ① 补全 `pyproject`（含 `httpx` 作用域修正）；② 新建 `check_dependency_declarations.py`：AST 扫代码硬导入，**反向**要求声明里必须有，按作用域分三段；③ 反向验证（注入漏声明必须 FAIL 且指向包名）；④ 挂 CI 门 3；⑤ `install.sh` 兜底降级 |
| 优点 | ① **判据方向正确**（"代码需要什么"是独立一侧，不会被漏声明绕过）；② **作用域分桶**直接命中 `httpx` 这个真实缺陷；③ 与 `check_test_db_isolation.py` **同构**，维护者复用同一心智模型；④ 白名单逐条给理由，与既有纪律一致；⑤ 零新依赖（只用标准库 `ast` + `tomllib`） |
| 缺点 | ① AST 扫不到动态导入（**显式记录为盲区**，见 R3）；② 别名映射表需维护（由 R4 的双向断言兜住） |
| 适合 | 本项目：有 CI、有 14 次同源根因前科、有 WP46 内网打包的下游需求 |
| 风险 | ①② 都有对应处置 |
| 结论 | ✅ **选它** |

### 方案 V4 —— 完整版：引入 lockfile + 依赖审计 + SBOM 生成（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | 在 V3 基础上加：`uv.lock` 锁全图 + `pip-audit` 漏洞扫描 + 自动生成 SBOM |
| 优点 | "能力最全" |
| 缺点 | ① **lockfile 是架构变更**（本仓已选 pip + `==`），应走 ADR；② `pip-audit` 需联网拉漏洞库，而 **ADR-10 受控出网、COST_LEDGER 禁出网**的同类约束意味着内网环境跑不了；③ **SBOM 是 WP46 的交付物**（§1.5 已砍），此处做了 =( WP46 越界) |
| 结论 | ❌ 不选。**三条增强里两条越界、一条违规** |

### 3.5 方案选择与理由

选 **V3**。核心理由：**验收命题本身（"顶层硬导入零漏声明"）要求的是一个反向覆盖证明，而 V3 是唯一一个把"代码需要什么"作为独立一侧、因而不被"漏声明"绕过的方案。**

三条否决理由，逐条对应：

| 方案 | 一句话否决 |
|---|---|
| V1 | 只修症状 ⇒ **同一件事会再发生，且不报红** |
| V2 | 方向反了 ⇒ `pip check` 对"代码 import 了没声明的包"**恒 PASS** |
| V4 | 三条增强里两条越界（SBOM 属 WP46）、一条违规（漏洞库需出网） |

本包"勘察磁盘实况"时发现：**判据自身就是它要消灭的病**。

| 复发 | 位置 | 症状 | 修法 |
|---|---|---|---|
| **第 5 次** | `check_dependency_declarations.py::_scan_imports` | 覆盖由 `rglob` / `ast.walk` 决定 —— 而 `rglob` vs `glob` 只差**一个字**。实测若写错：`src` 从 **174 文件掉到 0**（代码全在 `rednote/` 子目录下），判据**照样打印 `[PASS]`** | 用 `os.walk`（**独立实现**）逐范围对账 `rglob` 实扫文件数，不等即报红并指名范围 |
| **第 6 次** | `check_evidence_scripts.py` + `rerun_all_evidence.py` | 两个自检载体的收录 glob 全部以 `_evidence.py` 结尾 ⇒ **4 个 `collect_*code_review.py` 完全在覆盖外**，包括本包为 CI 门 3 新建的那个 | 扩为三约定（`collect_*_evidence` / `refresh_*_evidence` / `collect_*code_review`）；两载体交叉核对通过 |

**第 6 次的实测价值**：把 code_review 族纳入覆盖面后，**当场**抓到本包脚本里一处真问题（判据名里写了它要禁止的字面模式，被长度判据误判）—— 这正是"声称有防线"与"真的有防线"的区别（ISS-95）。这正是**第 4 次复发的附加教训**：*修完一个实例 ≠ 修完这族病*，要问"下一个同类工具会栽在哪儿"。

### 4.5 一处自查更正：我写下的假数字

本包 `check_dependency_declarations.py` 初版 docstring 里写的是「`src/` 实际顶层硬导入 **12** 个第三方包」，而**现场实测是 9 个**。

这个错数字**没有任何判据会去对账** —— 它安静地活在一段"讲为什么需要判据"的说明里，极具讽刺（这正是判据纪律第 6/9 条的复发：文档是唯一声称方时无判据）。

## 5. 阶段 5：Code Review（三遍法）

证据：`evidence/m3/dependency-declaration-code-review.log`（`RESULT=PASS checks=35 PASS / 0 FAIL`）。

三遍法 = **第一遍通读** → **第二遍把文档声称当"待验证假设"逐条证伪** → **第三遍只看判据自身是否恒真**。

| 遍 | 抓到的问题 | 严重度 | 处置 |
|---|---|---|---|
| 一 | `im, _n = mod._scan_imports(base)` 解包错误（返回值改 4 元组后未同步） | MAJOR | 修（`ValueError: too many values to unpack`） |
| 二 | 文档声称"覆盖范围已对账"，而 `[结构-3]/[结构-6]` 用**写死的函数名** `_scan_imports` 定位 | MAJOR | 新增 `_funcs_containing`，改由**磁盘**（遍历全部顶层函数体）决定"到哪儿找" |
| 三 | 判据名字符串里含 `len(a) >= len(b)` 字面量，被 `_REVISION_LENGTH_HACK_RE` 误判为"长度比大小的恒真判据" | MINOR | 改写判据名为自然语言；**这次假阳性本身证明了"把 code_review 族纳入覆盖面"的价值** |

**第三遍的一个副产品**：反向验证工具的变异 ⑥ 锚点因我重构 `_scan_imports` 而失效 → `rev-scan-narrowed-to-body` 报 FAIL。**这正是反向验证工具该做的事** —— 它检测到"脚本与代码已脱节"。
