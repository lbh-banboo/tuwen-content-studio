## 0. 本包的一句话定位

**把"一篇有正文的内容"变成"一篇有正文、且每一张图都能说出'画的是哪个产品的哪个部件、依据哪张参考素材'的内容"。**

M3 走到本包时，系统已经能回答"这批要产多少条、每条讲什么角度、正文写什么"（WP22 基线 + WP24 数量配置 + WP26 文案生成）。但 `content-feedback.html` 的预览里，**正文旁边还是空的** —— 而那条原型页面上写着「文案 + 静态图 · **6 张**」、「媒体一致性 通过 · **6 张图均对应正文段落**」。

本包要做的不是"调一次文生图 API"，而是**接住四条已经修好或已占位的管道，并把它们变成一组"可追溯、可重做、可目检"的静态图**：

| 已就位的东西 | 谁建的 | 本包怎么用 |
|---|---|---|
| `dispatch_call(repo, *, request, adapter, round_no)` —— 五步顺序（先落 `PREPARED` + 写 `ALLOWED` 留痕再发） | WP16 | 本包**原样调用**，不碰它的顺序 |
| `reserve_budget(repo, *, project_id, amount, ...)` —— 唯一预占入口 | WP25 | 本包**发出去之前**先预占（docstring 原话点名 WP27）；`PRICING_UNIT_IMAGE`（按张计）**已定义零消费** |
| `register_version(repo, *, entity_type="MEDIA", ...)` —— `ENTITY_TYPE_MEDIA` 在受控取值域里 | WP11 | 本包的每个媒体版本都注册成一条 `MEDIA` 节点（**全仓第 6 个 `*_node_paired` 触发器**） |
| `CAPABILITY_STATIC_IMAGE` / `DATA_CLASS_STATIC_IMAGE` | WP16 | 能力与数据类别**已定义、已在 `CAPABILITIES`/`DATA_CLASSES`/`FORBIDDEN_EGRESS_DATA_CLASSES` 的兄弟集合里，但业务代码零消费** —— 本包是**第一个消费者** |
| `PURPOSE_REFERENCE` / `PURPOSE_GENERATED`（`files/models.py`） | WP12 | 产品参考素材与生成图**两个用途已定义、跨文件零消费** —— 本包是**第一个消费者** |

**本包的产出边界**：它能回答"这篇内容配了几张图、每张图画什么、依据哪张参考素材、用的是哪个模型 profile、这一张重做花了多少钱"。它**不发外部请求**（WP16 的适配器发）、**不记账**（WP25）、**不写正文**（WP26）、**不做自检 8 类**（WP30）、**不做 Live 动态**（WP28）、**不做预览编辑**（WP29）。

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让系统的产出从**"可读的内容"**变成**"可交付的物料"** —— 而**图的正确性没有任何自动化手段能在发布前保证**，只能靠"每张图能追溯到一张产品参考素材"这件事本身。

拆开是四个彼此独立、但必须同时成立的问题：

| # | 问题 | 若不做会怎样 |
|---|---|---|
| P1 | **图必须"对齐段落"，不是"配几张好看的图"** | `content-feedback.html` 原话是「**6 张图均对应正文段落**」。若图与段落没有绑定关系，"重做某一张图"就无从下手（重做哪一段的代表图？），而 demo 的「单张媒体（重做按钮）」**直接依赖这个前提** |
| P2 | **产品一致性必须可判 —— 即"每张图能说清画的是参考素材里的哪个东西"** | AQ-03 的核心是「外观/型号/颜色与参考素材一致 ≥ 90%；**跨品牌事实混入 = 0**」（ADR-12）。而**判"一致"的唯一办法是把生成图对回参考素材**。若没有"这张图依据的是哪张素材"的记录，盲审只能靠人凭印象，AQ-03 也就测不成 —— 与 WP26 的 P3（证据绑定）**完全同构** |
| P3 | **出图前必须先算钱、后预占，超预算不出网** | 图片模型**按张计费**（`PRICING_UNIT_IMAGE`，WP25 已定义）。一批 50 篇 × 6 张 = 300 张，一次调用组就是一次真实花钱。若先生成后记账 ⇒ 超预算时钱已经花了 |
| P4 | **"媒体加工"必须做，且"预览与正式资产分开存"** | 技术选型表 §5 原话：「媒体加工 \| FFmpeg/ffprobe + Live 专用封装适配器 \| **预览与正式资产分开存**」。生成的原始图（供应商给的尺寸/格式）**不能直接当交付物**：小红书有尺寸与体积约束，ZIP 交付（WP35）需要确定的格式。**这条是修正清单里"含媒体加工"那四个字的具体所指** |

**为什么 P1 与 P2 必须同包做**：**"图对齐段落"与"图对齐参考素材"是同一张图上的两个绑定** —— 前者横向（内容内），后者纵向（对产品事实）。只有同时落库，才能回答"这张图重做时，是段落变了还是素材变了"。若分开做，重做一张图时**两个绑定各说各话**，而系统无法判断该沿用哪个。

**为什么 P2 与 P3 必须同包做**：**"哪张参考素材"会改变出网的数据类别**。ADR-10 的 E-2 行把 `STATIC_IMAGE` 的"数据类别（最小化）"写成**「批准的产品参考素材片段」** —— 也就是说，**参考素材是要出网的**。若在没定义"出网的是哪张素材、什么状态"的情况下先写出网逻辑，出网白名单就形同虚设（可能整份素材库都出去了）。

### 1.3 最小 MVP 应包含哪些功能？

| # | 功能 | 对应问题 | 验收映射 |
|---|---|---|---|
| F1 | **产品参考素材接入**：把"已批准"的参考素材挂到项目（`PURPOSE_REFERENCE` 的首次消费） | P2 | AQ-03 的对照来源 |
| F2 | **静态图生成**（`TASK_STATIC_IMAGE`）：按段落生成，每张图绑定 `content_versions` 的某一段 | P1 | 本包验收「静态图适配」 |
| F3 | **参考素材绑定**：每张图绑到**具体的**参考素材版本（不是"整个素材库"） | **P2（AQ-03 的地基）** | **AQ-03 产品一致性** |
| F4 | **媒体加工**：规格归一（尺寸/体积/格式）+ 预览资产与正式资产分开（`PURPOSE_GENERATED` 的首次消费） | **P4** | `content-feedback.html` 的预览；WP35 的 ZIP |
| F5 | **计费与预占接线**：按**张数**预估 + 预占，结果回来结算（`PRICING_UNIT_IMAGE` 的首次消费） | P3 | WP25 的接缝（docstring 点名） |

**F2 与 F4 必须是两件事**（生成 ≠ 交付）：

| 若"生成即交付" | 后果 |
|---|---|
| 供应商返回的原始图直接进 ZIP | 尺寸/体积/格式**由供应商决定**，WP35 的打包规则无从谈起；且小红书侧的上传约束（OP-64）变了要重新出一遍图 |
| 预览与正式不分 | 预览要的是"小、快、能看"（缩略图），正式要的是"原尺寸、可交付"。**技术选型表明确要求分开存** |
| 重做一张图 | 无法区分"重跑生成"与"只重新加工"——而后者几乎是零成本（FFmpeg 本地） |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（本包定义，协议原件不在本机 —— 见 §1.4 第 1 条）：

| 表 | 角色 | 可变性 |
|---|---|---|
| `media_items` | 媒体**身份**（一"内容 × 段落"位一条，跨版本不变） | **可变**（`lock_version` + 当前有效版本投影） |
| `media_versions` | 媒体**版本**（生成的图 + 段落绑定 + 参考素材绑定）。**`id` 同时 FK `version_nodes.id`** | **不可变**（触发器拦 UPDATE/DELETE） |
| `reference_assets` | **产品参考素材**（`PURPOSE_REFERENCE` 的落点）：型号/颜色/部件标注 + 素材来源 | **不可变**（一个新素材 = 一行；"停用"是新行而不是改行） |
| `media_renditions` | **加工产物**（预览 / 正式；尺寸/格式/体积）—— 技术选型表"预览与正式资产分开存"的落点 | **不可变** |
| `media_generation_contexts` | 生成上下文：钉住 `prompt_version_id` / `model_profile_id` / `task_kind` / 参考素材版本（OP-160 的同构） | **不可变** |

**关键设计判断：为什么"段落绑定"与"素材绑定"必须都在 `media_versions` 上**

| | 若只绑段落 | 若只绑素材 | 若两者都绑（推荐） |
|---|---|---|---|
| 重做一张图 | 不知道该对齐哪个产品事实 ⇒ 重做出来的图会漂 | 不知道该配哪一段 ⇒ 重做后段落对不上 | **两个坐标都在**，重做的输入确定 |
| AQ-03 可判性 | ❌ 无法对回参考素材 | ✅ | ✅ |
| 与 WP26 的关系 | WP26 的 P1（段落）断在半途 | WP26 的接缝没用上 | 接缝闭合 |

**为什么"加工产物"要独立成表**（而不是 `media_versions` 上两个 blob 列）

| | 若两列挂在版本表上 | 若独立表 |
|---|---|---|
| 加工规则演化 | 改一次规则 = 改不可变表（不可能） | 追加新 `rendition` 行 |
| "这张图的预览在哪" | 要读版本的某两列，且"没有预览"与"预览生成失败"在列上同形（都是 NULL） | `rendition` 行不存在 = 没生成；`state=FAILED` = 生成失败。**两者可分开** |
| 与 `blobs`/`file_objects` 的关系 | 两列各指一个 blob id，无法记尺寸/格式 | 每行可带 `width/height/bytes/format`，且**可被 FK 钉住** |

**接口**（本包定义的形状，协议原件不在本机）：

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/projects/{projectId}/reference-assets` | 登记一个产品参考素材（`PURPOSE_REFERENCE` 的入口） |
| `GET` | `/api/v1/projects/{projectId}/reference-assets` | 素材列表（按项目） |

### 2.4.1 ★ 跨包改动登记：`files` 模块新增 `store_generated_asset`（阻塞 B / B3 方案）

> **为什么单独起一节**：§2.4 上表是"待补充项"，而这一条是**已经发生的跨包代码改动**。
> 混在同一张表里会让"哪些是计划、哪些已落库"变得不可辨 —— 而本仓最贵的缺陷族
> 恰恰是"文档是唯一声称方，没有机械判据与它对账"（ISS-78/84/85/86/94/95/124）。

#### 缺口的事实

`media` 要把生成图存成正式资产，但**全仓唯一构造 `FileObject` 的地方**
（`files/repository.py:425` `insert_file_object`）此前**只有一个调用者**：
`files/service.py` 的 `complete_upload`（在 `complete_upload` 内部调用）。
即：**服务端没有"把已在内存里的字节直接落成 `file_object`"的公开路径**。

曾考虑过直接用网关的 `CapabilityResult.output_file_ids`，实测查清它**不是**本机的 `file_objects.id`：

| 事实 | 证据 |
|---|---|
| 全仓仅 2 处出现 | `gateway/types.py:235`（字段声明）、`gateway/adapters.py:103`（契约校验"SUCCEEDED 必须带 structuredOutput 或 outputFileIds 之一"） |
| `contracts/` 零命中 | 上游协议未定义其语义 |
| `provider_calls` 表**无任何输出列** | 列清单只有 `state` / `submitted_at` / `next_poll_at` / `request_evidence_ref` / `response_evidence_ref` / `status_unknown_reason` / `last_error_code` |
| `content` 侧只取当次事务内存中的 `structured_output` | `content/gateway_bridge.py:114` `_RecordingAdapter` |

⇒ 拿 `output_file_ids` 填 `media_versions.image_file_id` 只能得到**悬空外键**。

#### 四个方案与选型

| 方案 | 做法 | 结论 |
|---|---|---|
| **B1** | `media` 直调 `files.repository.insert_file_object` | ❌ 越过服务层，绕过 `object_key` 规则与物理去重 |
| **B2** | `media` 用裸 SQL 直插 `blobs` / `file_objects` / `project_file_links` | ❌ 把 `files` 的全部口径复制一遍（"同一事实两处实现"，违铁律 26），且 CHECK 约束要靠撞墙才知道 |
| **B3** | **`files.service` 新增 `store_generated_asset()`，由 `media` 走公开接缝** | ✅ **选定** |
| **B4** | 复用上传会话链路（建会话 + 传分片 + 完成） | ❌ 生成链路没有分片、预占、幂等状态机，强行套进去会让上传状态机被污染 |

#### 已落地的改动（`services/backend/src/rednote/modules/files/`）

| 文件 | 改动 | 性质 |
|---|---|---|
| `storage.py` | 新增 `STAGING_PREFIX` + `staging_key_for(purpose, token)` + `__all__` | **纯增量** |
| `service.py` | 新增 `StoredGeneratedAsset` + `store_generated_asset()` + `__all__` | **纯增量** |
| `service.py` | **`complete_upload` 一行未改** | 隔离性硬证据 |
| `repository.py` / `models.py` / `api.py` | **零改动** | 复用既有积木 |

`staging_key_for` 存在的理由不是"多一层封装"，而是
`LocalStorageBackend.write_part` 是**追加式**写（首块 `"wb"`、后续 `"ab"`）：
直接对最终 key 写，一旦该 key 已存在（同内容物理去重命中），
就会把新内容**追加**到旧内容后面 —— 产出一个大小对不上、
但在存储上与正常对象无法区分的坏对象。`assemble()` 内部用
`.{name}.assembling` + `replace()` 绕开了这一点，`write_part` 没有。

#### 口径与不变量（判据逐条对账，`tests/test_files_generated_asset.py` 17 条）

| 不变量 | 判据形态 |
|---|---|
| `object_key` 由**服务端**算 sha256 得出，不含用户输入 | 独立 `hashlib` 重算 + 独立拼 key 比对（**不复用被测对象的计算结果**） |
| 同内容两次 ⇒ 同一 `blob`、**两个不同** `file_id` | 成对断言（只断一个，实现可走另一条路而不红） |
| **物理去重真的跳过了重写** | 记录型探针：真实存储上"重写与不重写"结果完全相同（等价变异，首次变异实测全绿），只有数调用次数才可观测 |
| `GENERATED` **不占研究配额** | 对照组真跑一遍 `complete_upload(RESEARCH)` 证明配额**会**动，再断言生成后账面**完全不变** |
| 预览与正式互相不影响（R9） | 先 link 后 file_object 撤下预览，复验正式资产与其 link 均在 |
| 暂存区无残留**字节** | 只查文件不查目录（空目录零字节，断言它等于把判据变成实现细节的镜像） |

**刻意不做的事**（都登记为 OP，见 §2.4.2）：
本函数**不写 Outbox 事件** —— `EVENT_FILE_UPLOADED` 的语义是"用户上传完成，触发扫描"，
复用它会让下游扫描器把服务端产物当用户上传处理；宁可先不发，把该发什么登记为待定。
本函数**不调** `reserve_quota` / `finalize_reservation`。

## 3. 阶段 3：多版本方案

> 四套方案的**主要分歧点不是"要不要做媒体"，而是两件本包特有的判断题**：
> **① "每篇配几张图"这个数从哪来？**（§1.4 第 3 条：`form_items` 无该字段）
> **② 参考素材与生成图是同一种东西还是两种？**（§1.4 第 5 条：全仓无 media 表）
> 这两个判断**决定了表结构与接缝形态**，因此四套方案围绕它们分叉。

### 方案 V1 —— 最小可用：单表 `media_items`，媒体数写在生成请求里（**否决**）

**做法**：只建一张 `media_items`（图 + 段落下标 + 素材 id + blob id 全在一行）。"每篇几张"由**调用方在 `POST /media-generations` 的请求体里传**（`imagesPerContent`）。不区分预览/正式（生成什么就存什么）。参考素材复用 `file_objects`（`PURPOSE_REFERENCE`），不单独建表。

| 维度 | 评估 |
|---|---|
| 优点 | 表最少（1 张）、人日最短（≈5，落在修正清单下界）、"图对齐段落"能跑 |
| 缺点 | ① **"每篇几张"没有单一取数来源**（调用方随便传 ⇒ 违反 WP26 §9 第 26 条"同一个量只允许有一个取数来源"）；② **不可变性与"单张重做"冲突**（重做要改行，而图是历史）；③ **预览/正式不分**（技术选型表明确要求分开存）；④ 素材是一行 `file_object` ⇒ **无法标注型号/颜色**（那些列没处放）⇒ **AQ-03 直接判不成** |
| 适合场景 | 一次性的 demo，不做 AQ-03 |
| 风险 | 🔴 高。**它会在 AQ-03 上失败得毫无余地** —— "产品一致性 ≥90%"要求"生成图 ↔ 参考素材"可对照，而这条路连"素材的型号标在哪"都没回答 |
| 结论 | **否决** —— 它让本包唯一的核心验收（AQ-03）无法建立 |

### 方案 V2 —— 参考素材独立成表，但生成图与其共用一张表（**不推荐**）

**做法**：建 `reference_assets`（含型号/颜色/部件标注）+ `media_versions`（生成的图）。**预览与正式用同一行的两个 blob 列**。媒体数读 `runtime_settings` 的**新键**（如 `content.staticImageCount`）。

| 维度 | 评估 |
|---|---|
| 优点 | ① 素材有地方标型号/颜色 ⇒ **AQ-03 可判**；② 媒体数有单一来源（`runtime_settings`）；③ 表数少（2 张） |
| 缺点 | ① **预览与正式同行的两列** ⇒ "没有预览"与"预览失败"**在列上同形**（都是 NULL），且改加工规则**无处落**（行不可变）；② **与 WP24 的接缝仍不一致** —— WP24 §10.2 说本包读"形式配置的静态图张数"，而这条路读的是 `runtime_settings`，**两个来源并存**（除非把 WP24 那句话改掉，但那是跨包改文档，须登记）；③ 生成的图与素材**共用一张表**会让"素材被引用"与"图引用素材"两个语义混在一张表的两个方向上 |
| 适合场景 | 媒体数**确实是全局配置**（不随场景/形式变化）的场景 |
| 风险 | 🟠 中。主要风险是 ①（预览/正式的语义塌陷）：**"预览与正式资产分开存"是本项目的显式设计要求**，用一个 NULL 表达不了"分开" |
| 结论 | **不推荐** —— 差在"预览/正式双存"这一条，而那是技术选型表的白纸黑字 |

### 方案 V3 —— 5 张表 + 素材/生成图分离 + 段落与素材双绑定 + rendition 独立（**推荐**）

**做法**：即 §1.7 的数据结构。要点：

1. **`reference_assets` 与 `media_versions` 分开** —— 素材是"输入"，图是"输出"，**生命周期不同**（素材被多张图引用、跨内容复用；图属于某条内容）。
2. **`media_versions` 同时绑 `paragraph_ref`（段落）与 `reference_asset_id`（素材）** —— 两个坐标，R1/R4 的应对。
3. **`media_renditions` 独立** —— "预览 / 正式"是两行，`state` 可区分"没生成/生成中/失败/成功"，加工规则可重跑（`POST /media/{id}/renditions`）。
4. **媒体数**：**读 `plan_drafts.form_items` 的新字段**（若批准）**或** `runtime_settings`（若批准）—— **由老大拍板**（§3.7 第 1 点）。**无论选哪个，本包只留一条取数路径**（R3 判据）。
5. **`media_generation_contexts`** —— OP-160 的同构落点（钉住提示词版本/模型 profile/素材版本）。

| 维度 | 评估 |
|---|---|
| 优点 | ① AQ-03 可判（素材独立 + 型号标注 + 单素材绑定）；② 预览/正式双存（技术选型表）；③ 单张重做有落点（新媒体版本行）；④ 段落对齐是显式事实（不靠下标）；⑤ 与 WP26 的形态**完全同构**（身份表 + 不可变版本表 + 上下文表 + rendition 表）→ 复用率高、坑已知 |
| 缺点 | ① 表最多（5 张）+ 人日偏上界（≈8）；② **需要老大拍板"媒体数从哪来"**（否则本包会在两个来源间摇摆 —— 正是铁律 26 要防的） |
| 适合场景 | 本项目的实际场景（AQ-03 是硬验收） |
| 风险 | 🟠 中（可控）。主要风险是 ②，**用"请老大拍板"消解**；其余风险都有 R1~R10 的判据 |
| 结论 | **推荐** —— 它是四套里唯一同时满足"AQ-03 可判 + 预览正式双存 + 单张重做 + 段落对齐"的 |

### 方案 V4 —— 完整版：加素材版本化 + 相似度去重 + 出图缓存（**不选**）

**做法**：V3 + ① `reference_assets` 也版本化（素材本身有 `version_nodes` 节点）；② 生成前去重预检（"这张图与已有图相似度过高就复用"）；③ 出图缓存（同一"段落 + 素材 + 提示词版本"命中缓存不重复出图）。

| 维度 | 评估 |
|---|---|
| 优点 | 成本最优（缓存能省掉重复出图的钱）；素材可追溯（改素材影响谁可查） |
| 缺点 | ① **相似度去重需要真实模型 + 评测集** ← 挂起部分，**现在做就是"用假设实现"**（老大的红线原话：**WP28 期间不允许用假设字段实现**，本包同守）；② 素材版本化会让**素材表也进版本注册表** ⇒ 多一个 `*_node_paired` 触发器 + 多一套流动，而"素材改动影响谁"这个需求**目前没有任何消费者**（WP34 影响图读的是 `version_dependencies` 的边，素材是否入图未定）；③ 出图缓存与"幂等键"部分重叠（幂等已在 V3 里），缓存多出来的是"**不同内容、相同输入**也复用" —— 而不同内容本就不该共用同一张图 |
| 适合场景 | 媒体量非常大、成本敏感，且相似度判据已就位时 |
| 风险 | 🔴 高 —— **它把挂起部分（相似度）当成了本包的前置**，等于用一个不可验证的机制去省一笔尚未发生的钱 |
| 结论 | **不选** —— 明确登记为"待真实模型与评测集就位后评估"（并入 OP-203 同族） |

### 3.5 方案选择与理由

| 方案 | 表数 | AQ-03 可判 | 预览/正式双存 | 单张重做 | 段落对齐可靠 | 人日 |
|---|---|---|---|---|---|---|
| V1 | 1 | ❌ | ❌ | ❌ | 🟡（下标） | ≈5 |
| V2 | 2 | ✅ | ❌ | 🟡 | 🟡 | ≈6 |
| **V3** | **5** | ✅ | ✅ | ✅ | ✅ | **≈8** |
| V4 | 5+ | ✅ | ✅ | ✅ | ✅ | >10（含挂起项） |

**选 V3**。三条理由：

1. **AQ-03 是本包的叠加验收，不是"可选加分项"** —— V1 在它上面直接判不成，V2 差在双存。只有 V3 把"生成图 ↔ 参考素材"这条对照关系建成了**一等结构**。
2. **"预览与正式资产分开存"是技术选型表的显式设计要求** —— 这不是本包的自由发挥。V2 用一个 NULL 列表达它，**在语义上就输了**。
3. **V3 与 WP26 完全同构** —— 同样的"身份表 + 不可变版本表 + 上下文表"三件套，加上 rendition 表。本仓已交付 5 个同族包（WP18/20/22/23/26），**形态熟悉 = 坑已知 = 收口快**。V4 的额外两块（相似度、素材版本化）**都缺前置**。

### 四、设计决策（阶段 4 落地时定的，供后续包复用）

- **段号坐标系**：只在**空行**处切段（段内软换行不切、丢纯空白段、序号为过滤后连续下标从 0 起）；
  三处实现同口径 —— `content/schemas.py` / `knowledge/chunking.py` / `media/schemas.py`，
  判据 `tools/quality/check_paragraph_split_parity.py`（G1~G7 全绿）。
- **取数口径**：正文一律按 `content_items.current_version_id`**投影优先**，为空回落末版
  （不 `ORDER BY version_no DESC` —— 回滚后投影与末版会真实分叉）。
- **段落对位**：第 i 张配第 i 段；段落数不足 3 时多余张回落最后一段；
  **执行时按当时正文重算**，不读 `media_items.paragraph_ref` 快照（OP-198/OP-199）。
- **图片字节**：`ImageByteSource` 显式注入，**没有默认实现** ——
  宁可装配期就炸，也不要"看起来能跑"的假实现。
