## 0. 本包的一句话定位

**把"一条内容"从"只有一行计划"变成"有结构、有正文、有可追溯的生成依据"。**

M2 结束时，系统已经知道"这条内容该讲什么角度、该挂哪个场景、该带哪条证据"（WP22 的基线 + WP24 的十行清单 + `plan-detail.html` 的"结构：容量 → 单次用量推算 → 结论"）。但它**一个字都还没写出来**。

本包要做的不是"加一个大模型调用"，而是**接住三条已经修好的管道，并把它们变成一篇有依据、可追溯、可局部重做的内容**：

| 已修好的管道 | 谁修的 | 本包怎么用 |
|---|---|---|
| `dispatch_call(repo, *, request, adapter, round_no)` —— 五步顺序（先落 `PREPARED` + 写 `ALLOWED` 留痕再发） | WP16 | 本包**原样调用**，不碰它的顺序 |
| `reserve_budget(repo, *, project_id, amount, ...)` —— 唯一预占入口 | WP25 | 本包**发出去之前**先预占（docstring 原话点名 WP26） |
| `register_version(repo, *, entity_type="CONTENT", ...)` —— 受控取值域里已有 `CONTENT` | WP11 | 本包的每个内容版本都注册成一条 `CONTENT` 节点 |

**本包的产出边界**：它能回答"这篇内容的结构是什么、正文是什么、标题候选有哪些、每一个是依据什么生成的"。它**不发外部请求**（WP16 的适配器发）、**不记账**（WP25）、**不做自检**（WP30）、**不生成图**（WP27/28）。

## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正解决什么问题？

**一句话**：让系统的产出从**"计划"**变成**"可交付的内容"**，并且让**每一句话都能回答"我依据什么这么说"** —— 因为内容一旦发布就代表企业发声，而**没有任何人会在发布前逐句核对它有没有编造**。

拆开是四个彼此独立、但必须同时成立的问题：

| # | 问题 | 若不做会怎样 |
|---|---|---|
| P1 | **模型输出必须是结构化的，不能是自由文本** | 自由文本无法入库、无法局部重做（"仅标题"要怎么从一段散文里抠出标题？）、无法逐字段审。**demo 的 `content-feedback.html` 里"仅标题 / 仅正文 / 仅标签"三个按钮直接依赖这个前提** |
| P2 | **生成前必须先算钱、后预占，超预算不出网** | 外部模型调用**一旦发出就可能已计费**（WP25 §1.1 原话）。若先生成后记账，一批 50 篇跑完才发现超预算 ⇒ 钱已经花了 |
| P3 | **"这句话是依据哪条证据说的"必须可查** | AQ-01 的核心是"事实正确率"，而**判"正确"的唯一办法是把它对回证据**。若正文与 `brief_claims` 之间没有可查的绑定，盲审只能靠人凭印象，AQ-01 也就测不成 |
| P4 | **"改一版提示词影响了哪些历史生成"必须可查** | 这是 **OP-160** 原话指出的缺口，WP23 显式留给本包。没有它，"安全地改提示词"（OP-141/OP-152 的目标）就只有一半 |

**为什么 P1 与 P3 必须同包做**：结构化的意义不只是"好解析"。**能逐字段定值的输出，才能逐字段绑定证据** —— 「结论句用了哪条 claim」这个绑定只有在"结论句"是一个**字段**时才可能存在。若输出是自由文本，"证据绑定"就只能退化成"整篇引用了整份基线"，那种绑定等于没有绑定。

**为什么 P2 与 P1 必须同包做**：结构化输出会**改变预占金额的口径**。用户看到的`trial-plan.html` 计费表把**「文案生成」（≈86 千 tok）与「标题候选（2—3 个）」（≈9 千 tok）分开计** —— 也就是说，**这两件事是两次独立调用、两次独立预占**。若在没定义输出形状的情况下先写预占，预占的"数量"就是拍脑袋的。

### 1.3 最小 MVP 应包含哪些功能？

按"五块拼图"组织（对应 §1.1 的 P1/P2/P3/P4）：

| # | 功能 | 对应问题 | 验收映射 |
|---|---|---|---|
| F1 | **叙事蓝图生成**（`TASK_CONTENT_STRUCTURE`）：9 字段结构，从基线 + 计划行推导 | P1 | 本包验收「文案生成」的前半 |
| F2 | **正文生成**（`TASK_CONTENT_COPY`）：标题候选 + 正文 + 话题标签 | P1 | 本包验收「文案生成」的后半 |
| F3 | **标题候选层**：每篇 N 个候选 + 6 维评分 + 关键词/吸引点/风险说明 + 采纳 | P1 | `trial-plan.html` 的"标题候选（2—3 个）"计费项 |
| F4 | **证据绑定**：正文的每个事实段绑定到 `brief_claims` 的 claim | **P3（AQ-01 的地基）** | **AQ-01 事实正确率** |
| F5 | **生成上下文**（`generation_contexts`）：钉住本次生成用了**哪个提示词版本 / 哪个基线 / 哪个模型 profile** | **P4** | 闭合 **OP-160** |
| F6 | **计费与预占接线**：生成前 `estimate_cost` + `reserve_budget`，生成后把 `usage`/`cost` 交回 | P2 | WP25 的接缝（docstring 点名） |
| F7 | **幂等与重做**：同一篇内容的同一次生成不重复计费；"仅标题"重做只重做标题 | P1/P2 | demo 的"仅标题"按钮 |

**F1 与 F2 必须是两次独立调用**（不是一次调用出全部）：

`trial-plan.html` 的计费表把二者**分开列、分开计价**（¥154.80 vs ¥16.20），这不是排版巧合 —— 它反映的是**两个 `task_kind`**（`TASK_CONTENT_STRUCTURE` / `TASK_CONTENT_COPY`，WP23 已定义）。分开的理由：

| 若合成一次调用 | 后果 |
|---|---|
| 重做成本 | "只改标题"也要重跑整个长上下文调用（≈86 千 tok），而实际只需 ≈9 千 tok。**demo 的"仅标题"按钮会变成"整篇重做"** |
| 提示词演化 | 结构提示词与文案提示词是**两套**（历史文档里它们的提示词完全不同：一个输出 JSON 蓝图，一个输出小红书文案）。合成一次调用会让"改其一必改其二" |
| 计费口径 | 预占金额无法分开估，验收"预算并发预占"时测不出"局部重做只花局部钱" |
| 失败恢复 | 结构成功、文案失败时，重试会**重跑已成功的结构**（多花一次钱） |

### 1.5 哪些功能现在不该做？

| 砍掉 | 为什么 |
|---|---|
| **真实模型与适配器** | 本机无已审批的供应商、无 `model_profiles` 行、无真实适配器（WP16 交付的是 `StubAdapter`，**OP-130 未关闭**）。**处置与本仓已定的口径一致**（WP18 `GatewayDecomposer` 的原话）：交付**接线**，真实端到端验证登记为内网补做项。**交付一个"看起来能调"的假适配器比不交付更糟** —— 它会让"文案生成链路已验证"这句话变成假的 |
| **AQ-01 的评测结论** | AQ-01 的核心证据是"评测集盲审报告"，而评测集（≥30 正常 + ≥10 对抗）**全部 pending**（研发计划修正清单 §7 ⑩：WP04 已卡住，42 条全 pending）。本包**交付可验的部分**（证据绑定机制、结构化校验、幂等、预占接线），**AQ-01 的通过线判定显式登记为 `BLOCKED_ON_EXTERNAL`** |
| **12 个标题候选的"四组分类"作为强制约束** | 历史版本文档（`小红书素人感笔记全自动化工作流方案.md`）里"直接回答型 3 / 场景识别型 3 / 决策过程型 3 / 克制体验型 3"是**一份提示词的实现细节**，不是协议或验收的要求。**本包把它落成"提示词模板里的建议"而不是"数据库 CHECK"** —— 若落成 CHECK，等于把一份历史提示词的措辞变成对未来的硬约束。**本包只硬约束"候选数 N 的上下界"与"必须带关键词/吸引点/风险说明"**（后者是历史文档的硬规则，且可判） |
| **8 个角度候选 + 7 维 100 分评分** | 同上：这是历史文档里**角度生成提示词**的实现细节。本包的落点是"角度从 `plan_drafts` 的 `scene_items` / `pairings` 来"（WP24 已交付），**不从模型再生成一遍角度** —— 再生成一遍会与"十行清单已定稿、生成前定稿之后只走局部修订"（`plan-detail.html` 原话）冲突 |
| **正文的富文本 / 排版标记** | 小红书正文是纯文本 + 换行 + emoji。本包**不做 markdown 转换**、不做排版优化。demo 预览里正文就是纯文本段落 |
| **话题标签的独立生成** | demo 有"仅标签"重做按钮，但**标签是文案生成的一部分**（`TASK_CONTENT_COPY`），不是独立调用。**登记为本包取舍**：标签随正文一起重做（若要独立重做，需要第三种 `task_kind`，而 WP23 只定义了两种） |
| **首评 / 图片叠字的生成** | 历史文档有"图片叠字/正文/首评的职责分区表"，但**协议与验收都没有要求**，且首评依赖发布平台行为（属 WP36）。本包只产出**标题 + 正文 + 标签**三件 |
| **提示词模板的种子数据** | WP23 §1.4 已明确"未经交付 = 把 WP18/WP19 的硬编码文本搬进模板表"（**OP-161 未关闭**）。本包**不重复这件事** —— 本包只消费"激活版本"，不负责"有没有激活版本"。**没有激活版本时 fail-closed**（§1.4 第 6 条） |
| **生成内容的最终质量评级** | 那是 WP30（AI 自检 8 类）与 WP31（试产关口）。本包只产出内容与它自己的结构化校验结果 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 等级 | 后果 | 应对 |
|---|---|---|---|---|
| R1 | **结构化输出校验退化成恒真式** | 🔴 高 | `payload is not None` 恒真地放行 `{}`、`{"x":1}`、任意 JSON ⇒ **下游拿到的"正文"可能是空的**，而系统报成功。这是 WP23 §1.4-3（"判非空是假防线"）与 WP19 的 ISS-75 **同一形态** | 校验必须是**逐字段**的：9 个蓝图字段 + 3 个文案字段（标题/正文/标签）**各自存在**，且**类型正确**，且**取值在受控域内**（如 `conclusion_strength` ∈ 闭集）。**反例驱动**：判据必须包含"空 dict / 缺字段 / 类型错 / 域外值"四类**必须被拒**的用例 —— 只测"好输入能过"不构成判据 |
| R2 | **先生成后记账** | 🔴 高 | 外部调用一旦发出就可能已计费（WP25 §1.1）。后记账 ⇒ 超预算时钱已花 | 顺序**定死**：`estimate_cost` → `reserve_budget` → `dispatch_call` → 结果回来再结算。**判据**：额度为 0 的项目上，`dispatch_call` **一次都没有被调用**（不是"调用了但没用"）|
| R3 | **预占数量口径不唯一** | 🟠 中 | "这次预占几次调用"若两处算法不同 ⇒ 一次预占 10 次、实际调用 20 次 ⇒ 账面永远对不上 | 口径**只有一个函数**：`calls_for(kind, content_count)`，落在 `content/types.py`。`TASK_CONTENT_STRUCTURE` = 内容条数 × 1，`TASK_CONTENT_COPY` = 内容条数 × 1（标题候选与正文**在同一次调用内**，因为它们是同一段提示词的输出；demo 把它们分开**计价展示**是因为 token 量不同，不是两次调用）。**判据**：同一入参两次调用返回同一个数 + 全包只有这一处算法 |
| R4 | **证据绑定变成"整篇引用整份基线"** | 🔴 高 | 那种绑定**等于没有绑定**（每篇都绑全部 claim，AQ-01 无法定位到句）。这是"看起来有防线"的典型 | 绑定粒度**必须到段**：正文按 `paragraph_plan` 分段，每段绑**具体的** `brief_claims.id`（至少一条，可为空但必须显式标 `null` + 理由）。**判据**：构造一条正文，断言"绑定的 claim 数 < 基线全部 claim 数" —— 若相等，说明在做整篇引用 |
| R5 | **幂等缺失导致重复计费** | 🔴 高 | 同一篇内容的同一次生成被重试 ⇒ 两次真实调用、两次真实花钱，而用户只看到一条内容 | `CapabilityRequest.idempotency_key` 由**内容版本号 + task_kind**派生（不是随机），与 `brief/decomposer.py` 的 `f"brief-decompose:{file_id}"` 同款。网关侧"找到既有调用 → 不重发"是 WP16 已验证的语义。**判据**：同一 key 连调两次，断言**只产生一次真实派发** |
| R6 | **没有激活提示词版本时静默用空模板** | 🔴 高 | 生成出**没有系统指令**的内容 ⇒ 内容可能越界、可能不符合业务约束，而**系统报成功** | fail-closed：查不到 `task_kind` 的激活版本 ⇒ 抛错**不调用网关**。理由与 WP23 的"新建模板工具集为空集（`PLATFORM_DEFAULT_TOOLS = ()`）"**同一取向** —— **默认必须是最小的那一档** |
| R7 | **顶层 import 网关导致依赖树变重** | 🟠 中 | `content/` 在"没有模型通道"的部署里也会被 import（要拿 `UnavailableGenerator`）；顶层 import 会让每个请求都拖着网关的适配器与策略树 | **本地导入**（函数内 `from rednote.modules.gateway.service import dispatch_call`），与 `brief/decomposer.py:551` 的注释原话一致："`gateway` 是重模块 …… 顶层 import 会让每个请求都拖着网关的依赖树" |
| R8 | **`UNKNOWN` 被当成失败而重发** | 🔴 高 | 重发 = **再买一次**，且真实结果可能已经成功 | 继承 WP16 的取值域语义：`CALL_TERMINAL_STATES = {SUCCEEDED, FAILED}`，`UNKNOWN` **不在其中**且**在 `CALL_IN_FLIGHT_STATES` 里**（"一律不得重新派发"）。本包在 `state != SUCCEEDED` 时**一律不产出内容**，把处置交给任务框架 |
| R9 | **内容版本与 `version_nodes` 分叉** | 🟠 中 | 注册表说有一版、领域表说没有（或反之）⇒ 溯源图断链，而两边各自看着正常 | 闭合 **OP-88 的 `CONTENT` 一半**（正向：`content_versions.id` 必须有节点且 `entity_type='CONTENT'` 且 `entity_id` 匹配；反向：`CONTENT` 节点必须配对领域行）。**延迟触发器**（`DEFERRABLE INITIALLY DEFERRED`）——因为 `register_version` 内部用 SAVEPOINT + 重试取号，**不暴露"节点行何时落库"的控制权**（WP18 已实测） |
| R10 | **正文里出现基线没有的事实（编造）** | 🔴 高 | 这是 **AQ-01 要测的头号问题**（"阻断级事实错误（参数/功效/竞品混入）= 0"）。而模型天然会补全 | ① **提示词侧**：给模型的是"可用的 claim 清单"，并明确"清单外的事实不许写"；② **结构侧**：`plan-detail.html` 的原话是硬约束 —— "含待补信息的行 …… 生成时可退化为产品说明结构，**但不允许把空白补成使用经历**"，这条落成 `narrative_blueprints.limitation` 的必填；③ **可查侧**：证据绑定（F4）让 WP30 的自检与 AQ-01 的盲审**有东西可对**；④ **本机不可验**：模型是否真的编造需要真实模型 + 评测集，登记为 `BLOCKED_ON_EXTERNAL` |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构**（5 张新表；可变性按用途分三类）：

| 表 | 角色 | 可变性 |
|---|---|---|
| `content_items` | 内容条目**身份**（一项目一条内容，跨版本不变） | **可变**（`lock_version` + 当前有效版本投影） |
| `content_versions` | 内容**版本**（标题 / 正文 / 标签 / 采纳的标题候选 / 证据绑定）。**`id` 同时 FK `version_nodes.id`** | **不可变**（触发器拦 UPDATE/DELETE） |
| `narrative_blueprints` | **叙事蓝图**（9 字段结构），生成正文的输入。`id` 同时 FK `version_nodes.id` | **不可变** |
| `title_candidates` | 标题候选（每批 N 个 + 6 维评分 + 关键词/吸引点/风险说明） | **不可变**（"采纳哪一个"记在 `content_versions` 上，不改候选行） |
| `generation_contexts` | 生成上下文（**OP-160 落点**）：钉住 `prompt_version_id` / `baseline_id` / `model_profile_id` / `task_kind` | **不可变** |

**关键设计判断：为什么"采纳标题"记在 `content_versions` 上，而不是给 `title_candidates` 加一个 `adopted` 列**

| | 若给候选加 `adopted` 列 | 若采纳记在内容版本上 |
|---|---|---|
| 表可变性 | `title_candidates` 变成**可变表** ⇒ 失去"候选历史不可篡改" | 候选表**纯不可变**，与 `version_nodes` 同级 |
| "这一版用了哪个标题" | 要**反查两张表**（候选表的状态 + 内容版本），且两者可能分叉 | **一处** —— 内容版本的 payload 里直接有 `adopted_title_candidate_id` |
| 采纳两次 | `adopted=true` 可被写两次（无状态可判），与 WP25 §3 V2 的"重复释放检测不了"**同一形态** | 不同版本各记各的，**天然不会冲突** |

这与 WP25 的"账面 / 明细分表"是**同一种判断**：**把"历史事实"与"当前选择"分开**，历史表不可变，选择只出现在新的版本行上。

**为什么蓝图与内容版本分成两张表**（而不是 `content_versions` 里一个 JSONB 列）

| | 若合成一张表（蓝图塞 JSONB） | 若分两张表 |
|---|---|---|
| "仅标题"重做 | 无法只重做标题 —— 蓝图与文案在同一行，改一行要整车重写，**且蓝图是不可变的历史** | 蓝图行不动，只追加新的 `content_versions` 行 |
| 蓝图独立审阅 | 蓝图被埋在内容版本的 JSON 里，无法单独查 | 可单独查"这 10 条的蓝图分别是什么"（`plan-detail.html` 那一屏要的正是这个） |
| Schema 演进 | JSONB 无 CHECK 能力，字段漂移**无人发现** | 9 个字段各有列与 CHECK，字段缺失在**写入时**就报错 |
| 与"注册表不是万能 JSON 仓库"的一致性 | 违反该原则（`versions/models.py` docstring 明写） | 与 `brief_claims`（WP18，事实 claim 独立成表）**同构** |

**接口**（本包定义的形状，协议原件不在本机 —— 见 §1.4 第 1 条）：

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/projects/{projectId}/content-generations` | 发起一次生成（结构 或 文案 或 两者）—— 预占 + 入队 |
| `GET` | `/api/v1/projects/{projectId}/contents` | 内容列表（按项目） |
| `GET` | `/api/v1/contents/{contentId}` | 单条内容详情（含当前版本、蓝图、候选、证据绑定、生成上下文） |
| `GET` | `/api/v1/contents/{contentId}/versions` | 版本历史 |
| `POST` | `/api/v1/contents/{contentId}/regenerations` | 局部重做（`scope` ∈ 标题 / 正文 / 标签 / 整篇 —— 对齐 demo 的五个按钮） |
| `POST` | `/api/v1/contents/{contentId}/title-adoptions` | 采纳一个标题候选 |

**前端消费面**（demo 实测，本包是它的后端来源）：

| demo 位置 | 本包提供什么 |
|---|---|
| `trial-plan.html` 计费表「文案生成」/「标题候选（2—3 个）」**分开计价** | 两个 `task_kind` 的独立预估与预占 |
| `trial-plan.html` 清单一列「**叙述角度**」 | 本包**读** WP24 的 `pairings` / `scene_items`，不在本包再生成角度 |
| `plan-detail.html`「结构：容量 → 单次用量推算 → 结论」「证据：150g 规格 + 建议单次用量」 | `narrative_blueprints.paragraph_plan` + `evidence_beats` |
| `plan-detail.html`「未补齐前不得写成亲历体验 …… 生成时可退化为产品说明结构」 | `narrative_blueprints.limitation` 的必填 |
| `content-feedback.html` 手机预览的**标题 / 正文 / 标签**三段 | `content_versions` 的三件产出 |
| `content-feedback.html` 重做范围：**仅标题 / 仅正文 / 仅标签 / 单张媒体 / 整篇** | `regenerations` 的 `scope`（媒体那一项归 WP27/28） |
| `content-feedback.html`「AI 自检 8 类」 | **不是本包**（WP30）。本包只提供它要读的内容与证据绑定 |
| `content-feedback.html`「标记已通过」在有阻断事实问题时报"无法标记" | **不是本包**（WP31）。本包只保证"有没有阻断事实问题"**可判** |

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**"计划 → 内容"这一步，真正的难点不是调模型，而是让模型产出"能逐字段追责"的东西。**
调模型是 WP16 已解决的事（`dispatch_call` + 出网策略 + 留痕 + 幂等）；本包要解决的是**把一次不透明的文本生成，拆成一组可校验、可绑定证据、可局部重做、可对账的结构化产物**。

### 2.2 用户画像

| 画像 | 一天里的真实动作 | 本包要支持的 |
|---|---|---|
| **运营 A（主要使用者）** | 拿到 10 条内容 → 逐条看 → 对不满意的点"仅标题"重做 → 觉得可以了标记 → 提交下一步 | 局部重做只重做那一部分、花费可预期、重做产生新版本而旧版本可查 |
| **运营 B（背靠背审核者）** | 按 AQ-01 逐条核对"这句话依据哪条证据" | 每段的事实绑定**可查**（不是"整篇引用了基线"） |
| **管理者** | "这批花了多少""改了提示词影响哪些内容""为什么这篇没生成出来" | 按 `task_kind` 分别计费；`generation_contexts` 可按 `prompt_version_id` 反查；失败有明确错误码 |
| **下一个包的开发者（WP27/29/30/31/33/35）** | 要接正文、要对齐段落、要自检、要判过关、要查重、要打包 | 内容版本的 payload 形状**定死且有 schema_version**；证据绑定**可直接读** |

## 3. 阶段 3：多版本方案

### 方案 V1 —— 一次调用出全部自由文本（**否决**）

| 维度 | 说明 |
|---|---|
| 做法 | 一次大提示词，模型直接吐出一段可发布的小红书文案。不拆结构、不拆标题，落库就是一列 `text` |
| 优点 | 最少代码；一个 `task_kind`；一天可交付；提示词最简单 |
| 缺点 | ① **P1 直接失败**：demo 的"仅标题 / 仅正文 / 仅标签"三个按钮**无从实现**（无法从散文里可靠抠出某一部分）；② **P3 失败**：无法逐段绑定证据 ⇒ **AQ-01 无从测**；③ 验收"文案生成"退化成一个"能不能调通"的检查；④ 局部重做 = 整篇重做，**每次都花 ¥154.80 而不是 ¥16.20** |
| 适合 | 单次人工试用，不进生产 |
| 风险 | 无技术风险，但**没有做需求** —— 它把"结构化生成"降级成了"调一次模型" |
| 结论 | ❌ 不选。**它省掉的"结构"，恰好是证据绑定与局部重做共同的必要条件** |

### 方案 V2 —— 结构化但单表：内容表里一个 JSONB（**不推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | 一张 `contents` 表，`payload JSONB` 里塞蓝图 + 标题候选 + 正文 + 标签。有校验但没有独立表 |
| 优点 | 表少（1 张）；Schema 演进灵活；开发快 |
| 缺点 | ① **"仅标题"重做无法表达"蓝图不动"** —— 蓝图与文案同在一行，新版本要么整车重写（蓝图被重复生成、多花钱），要么在 JSON 里手工保留（无判据）；② **蓝图的 9 个字段没有列级 CHECK** ⇒ 字段漂移无人发现（与 `versions/models.py` docstring「注册表不是万能 JSON 仓库」**同一反对理由**）；③ **`OP-160` 的要求落不了** —— 它点名 `generation_contexts.prompt_version_id`，一个 JSONB 列里的 `prompt_version_id` 无法建索引、无法做影响面分析（那正是 OP-160 要的能力）；④ `OP-88` 的注册表配对需要"领域表有 `id`"，JSONB 行没有独立 `id` |
| 适合 | 原型、字段还会大改的阶段 |
| 风险 | **R4（证据绑定）与 R9（注册表分叉）在此方案下无法防御** |
| 结论 | ❌ 不选。**它省掉的"独立表"，恰好是 CHECK、索引与 OP-88 配对的落脚点** |

### 方案 V3 —— 5 张表 + 蓝图/文案两段式 + 段级证据绑定 + 生成上下文（**推荐**）

| 维度 | 说明 |
|---|---|
| 做法 | `content_items`（身份，可变）+ `content_versions`（不可变，正文/标签/采纳标题/证据绑定）+ `narrative_blueprints`（不可变，9 字段列级 CHECK）+ `title_candidates`（不可变，6 维评分）+ `generation_contexts`（不可变，钉提示词/基线/模型）。生成分 **2 次调用**（`TASK_CONTENT_STRUCTURE` → `TASK_CONTENT_COPY`），每次**先 `estimate_cost` + `reserve_budget` 再 `dispatch_call`**。校验**逐字段**（反例驱动）。闭合 `OP-88` 的 `CONTENT` 一半 |
| 优点 | ① **P1 被结构性满足**：每个可重做的部分都是一张表/一组列 ⇒ "仅标题"= 只追加新的 `content_versions` 行，蓝图行不动；② **P3 可判**：段落级绑定到 `brief_claims.id`，AQ-01 与 WP30 都有东西可对；③ **`OP-160` 直接闭合**：`generation_contexts.prompt_version_id` 有索引，影响面分析可做；④ **与已交付的形态同构**：`brief_claims`（WP18，用 JSONB 存 `applicability` 但独立成表）、`baseline_items`（WP22 快照独立成表）、`prompt_versions`（WP23 不可变 + 延迟触发器）——**没有一处是新发明的**；⑤ 计费口径可分（两次调用分别预占） |
| 缺点 | ① 表多（5 张）；② 两段式让"生成一条内容"变成两次派发，**失败恢复要处理"结构成功但文案失败"**（本包按"结构已落库、只重试文案"处理）；③ 段级绑定要求模型输出里带段标记，**提示词更复杂** |
| 适合 | 本项目：有 AQ-01 的定量验收、有"局部重做"的产品形态、有 OP-160 的影响面要求、API 双实例 |
| 风险 | ②③ 都有对应处置（结构版本可复用 + 提示词模板控制）。剩下的是**模型真的按要求输出**，那部分 `BLOCKED_ON_EXTERNAL` |
| 结论 | ✅ **选它** |

### 方案 V4 —— 完整版：加生成缓存 + 跨内容去重预检 + 提示词 A/B（**不选**）

| 维度 | 说明 |
|---|---|
| 做法 | 在 V3 基础上加：① 生成结果缓存（同输入直接复用）；② 生成前跨内容相似度预检（提前避免重复）；③ 提示词 A/B 分流 + 效果对比 |
| 优点 | "能力最全"；成本更低、质量更可控 |
| 缺点 | ① **缓存的口径无法定义**：模型输出是**非确定性**的，而"同输入"的判据本身（提示词 + 基线 + 模型 + 温度的规范化摘要）需要先定死 —— 而"复用缓存"会让"重生成"变成"拿到同一篇"，**与 demo 的"重生成"语义直接冲突**；② **去重预检是 WP33 的职责**（`方案 V3` 与 WP33 的"重复检查"重叠，提前做会造出第二份相似度实现）；③ **A/B 需要评测集**（AQ-01 的 42 条全 pending），现在建分流只会产生**无法判读的数据** |
| 适合 | 无。三条增强分别与"重生成语义"、"WP33 职责边界"、"评测集不可得"冲突 |
| 风险 | 引入一个**语义矛盾**（缓存 vs 重生成）与两个**越界**（去重归 WP33、A/B 依赖不可得的外部输入） |
| 结论 | ❌ 不选 |

### 3.5 方案选择与理由

选 **V3**。核心理由：**验收本身（"文案生成" + AQ-01）要求的是"产出的每一句话都能追回依据"，而 V3 是唯一一个把"可追责"落成表结构与列级约束的方案。**

三条否决理由，逐条对应：

| 方案 | 一句话否决 |
|---|---|
| V1 | 没有结构 ⇒ **"仅标题"与"证据绑定"都无从落地**（没做需求） |
| V2 | 没有独立表 ⇒ **CHECK、索引、OP-88 配对、OP-160 影响面全都没有落脚点** |
| V4 | 三条增强分别与"重生成语义"、"WP33 职责边界"、"评测集不可得"冲突 |

**与 WP25 的 PM 判断一致**：WP25 选 V3 的理由是"**验收标题本身要求一个并发正确性证明，而 V3 是唯一把正确性放在单条 SQL 语句里的方案**"。本包选 V3 的理由同构：**验收标题本身要求"事实可追责"，而 V3 是唯一把追责落成表结构而非"文档里的承诺"的方案。**

### 4.2 五张表

| 表 | 列 | CHECK | FK | 可变性 |
|---|---|---|---|---|
| `content_items` | 12 | 3 | 3 | **可变**（`lock_version`；本包唯一的身份行，`current_version_id` 投影在这里推进） |
| `content_versions` | 15 | 9 | 6 | **不可变**（`trg_content_versions_immutable`） |
| `narrative_blueprints` | 14 | 18 | 2 | **不可变**（`trg_narrative_blueprints_immutable`） |
| `title_candidates` | 9 | 7 | 1 | **不可变**（`trg_title_candidates_immutable`） |
| `generation_contexts` | 13 | 1 | 9 | **不可变**（`trg_generation_contexts_immutable`） |

**本包 CHECK 总数 38 / FK 总数 21 / 17 个声明索引（库内 5 表共 22 条，另 5 条为 `pk_*`）/ 7 个触发器（6 挂本包表 + 1 挂共用表 `version_nodes`）**，全部由 `wp26-content-generation.log` 的 S1~S18 逐条实测。

**4 张不可变 + 1 张可变**的分法：只有 `content_items` 是"身份行"（它承载投影字段 `current_version_id`，必须能推进），其余 4 张是**历史事实**（版本 / 蓝图 / 候选 / 上下文）—— R5 要求"冲正不靠改旧行"，所以它们只有 INSERT。

**4 条延迟 FK / 2 条非延迟 FK 的分界口径**：延迟的 4 条全部落在**两个环**上 ——
环 1（`content_items.current_version_id` → `content_versions`）、环 2（`content_versions.generation_context_id` → `generation_contexts`），
每一环的**两向各 1 条延迟 FK**（正向引用 + 回落引用）。分界是"**两表行是否在同一事务里互相依赖**"：
`content_versions.content_item_id` 与 `title_candidates.content_version_id` 是**必然先后顺序**（先有内容行才有版本行；先有版本行才有候选行），
延迟它们**等于放弃一条免费检查**。这条负向边界由 `NON_DEFERRED_FOREIGN_KEYS` 判据钉住（RG-121 / RG-124）。

**`content_versions` 等 4 张表的残留只能用 `TRUNCATE` 清**：不可变触发器拦的是**行级** UPDATE/DELETE，而 `TRUNCATE` 不触发行级触发器。
这不是漏洞 —— 生产代码零 `TRUNCATE` 路径，它只是测试夹具的清空手段；该前提本身有一条单独用例（RG-123：`test_truncate_bypasses_immutable_triggers`），
这样 30+ 用例因"清不干净"失败时，**第一句**就指向清空机制坏了，而不是分散指向各自实现。

### 5.2 ★ CRITICAL-1：R4 的证据绑定防线**只写在 docstring 里**（ISS-177，**本包唯一 CRITICAL，未修**）

**现场**：`repository.claim_scope` 的 docstring 逐字写着"**服务层据此拒绝（`REASON_BASELINE_NOT_READY`）**"，
而 `REASON_BASELINE_NOT_READY` 在 `service.py` 的抛点为 **0**。⇒ `execute_generation` 在"基线没有 Brief / 没有 claim"时
返回 `(frozenset(), 0)` 后**不拒绝、直接放行** ⇒ `validate_bindings` 的"绑满"规则分母为 0 而**不启用**，
且模型可以绑 0 条通过 ⇒ **R4 静默降级为"不判绑定"**。

```
CHECK OK   [CR-1 CRITICAL-1] 现状钉住：claim_scope docstring 声称=True（repository.py:[237]） 服务层抛点=0 处
CHECK OK   [CR-1 CRITICAL-1b] total_claim_count 在 service.py 无任何守卫（出现 5 处，守卫 0 处）
```

这是 **ISS-95 形态**："**声称自己有防线**"比"没有防线"更危险 —— 而本条更隐蔽，因为它**声称得极其具体**
（连拒绝时该抛哪个常量名都写出来了），读代码的人会以为已经接线。

**⚠️ 判据自带"修复后会变红"的设计**：`[CR-1 CRITICAL-1]` 断言的是**缺陷现状**，
它 `ok=True` 的含义是"**现状与 CR 报告一致**"，不是"代码没问题"。**修好之后它会变红** ——
那是设计，逼着修复者同步 CR 报告与登记册；否则证据会**静默地继续声称缺陷存在**（ISS-143 的变体）。

**为什么本轮不修**（用户显式拍板）：本轮授权范围是"只登记 ISS + 报告 + 证据 + 简化 + 回填"，**不改任何业务代码**。
`service.py` / `api.py` / `repository.py` 全程只读，13 个业务文件的**字节哈希**在开工与收尾两次核对一致。
⇒ 修复与 **TESTS-1**（`execute_generation` 零覆盖）**必须同批做**：否则修了也没有判据。

### 7.3 4 对真重复：判定保留 + 升降为判据

判据：同一被调方**恰出现 2 处**、且两处 **kwargs 键序列完全一致**、且键数 ≥ 3。命中 **4 对（全部落在 `service.py`）**：

| # | 被调方 | 处 ① | 处 ② | 键数 |
|---|---|---|---|---|
| 1 | `insert_version` | `926`（生成路径 `_apply_copy`） | `1477`（采纳路径） | **13** |
| 2 | `advance_projection` | `692`（生成路径） | `1500`（采纳路径） | 6 |
| 3 | `register_version` | `915`（生成路径） | `1464`（采纳路径） | 5 |
| 4 | `ContentVersionSummary` | `1184`（`read_version_history`） | `1517`（采纳路径） | 10 |

两条路径的分工清楚：**生成**（模型产物 → 落版本）与**采纳**（上一版复用 → 落版本）。它们**共用同一套落库原语**，kwargs 必然同形。

**为什么不合并（三条理由，按重要性排序）**：

| # | 理由 |
|---|---|
| ① | **合并会把"字段来源分歧"藏进一层间接 —— 而它现在是显式的。** 以 `insert_version` 为例：生成路径的 `title/body/tags` 来自模型产物，采纳路径来自上一版；`adopted_title_candidate_id` 在生成路径恒为 `None`、采纳路径是 `candidate_id`。抽 helper 要先把 8 个分歧字段打包成一层中间结构 ⇒ "**这一版是从哪儿来的**"从两处显式实参变成一个参数 |
| ② | **与 WP25 `[C35]` 同构的风险：字段求值顺序会随参数书写顺序静默改变。** 两处 kwargs 的书写顺序决定**哪个字段的错误先被报**，而"两个字段同时非法"才现形 —— 单独非法的用例**全都照样绿** |
| ③ | **收益只是少写几行 kwargs，而 `repository.insert_version` 的 13 个关键字就是那 13 个库列。** 本项目既有判例（WP24 / WP25）："参数一一对应数据库列，包成 dataclass 只会在调用处多一层构造" |

**但"判定不合并"不等于"不需要检查"** —— 既然承认是复制，就必须把"两份保持同步"变成**可机械检查**的事，
否则下一次只改一处不会报红，而读者会以为两处等价（ISS-95）。⇒ 新增 **9 条判据**（全部落在 `tools/m3/collect_wp26_code_review.py`）：

| 判据 | 断言 | 为什么需要它 |
|---|---|---|
| `[C36]` ×4 | 每对**恰 2 处** + **键序列一致** + **键数 ≥ 4** + **键数等于登记值** | 主判据。"≥4"是防某处被删成空调用而两边"一致" |
| `[C36b]` | 上表**由磁盘反算**与 `_REPEAT_SITES` **相等** | ★ 铁律 14：清单是**人写的**，必然漂移。**本判据当场抓到了自己漏掉 1 对** |
| `[C36c]` | 每对**实参确有分歧** | 反向事实：若两处实参也逐字相同，那才是"可安全合并的重复"，本节结论需重写 |
| `[C37]` | 手写 `None if X is None else str(X)` **恒 12 处** | 扫描器**抓不到**的重复形态（每处 ≤1 行） |
| `[C37b]` | **逐行 `search` 会欠计**（`findall`=12 / `search`=9，差 3） | 把"口径差"本身钉住 —— 否则读者无从知道为什么不是 9 |
| `[C38]` | 三处未使用 import 逐处核实（非 import 用法 = 0） | 把"哪些可删"变成机械事实（本轮不改） |

### 7.4 ★ `[C36b]` 当场抓到了人写清单的漏洞（本包最值得记的一条）

第一版 `_REPEAT_SITES` 只写了 **3 对**。`[C36b]` 报红：

第 4 对（`ContentVersionSummary`，10 字段）**与前三对同型**：一处源是 `row.*`、一处源是 `new_version.*`。

### 7.5 ★ `[C37]`：重复度扫描器**抓不到**的一种真重复

`None if X is None else str(X)` 出现 **12 处**（`api.py` 10 / `handlers.py` 1 / `service.py` 1）。
**抓不到的原因**：每处最多一行，而 `scan_dup.py` 只比较"归一化体 ≥ 6 行"的函数 ⇒ 12 个半行表达式**不构成"函数体相似"**。
这是**扫描口径**造成的盲区，不是阈值问题（调低阈值也抓不到"半行"）。

**判定：保留。** 三处的理由各不相同：

| 点 | 为什么 |
|---|---|
| `api.py` 的 10 处 | 全在"响应装配"里（`_context_view` / `_version_view` / 内联 dict）。职责是**让 `types.py` 的 10 个 id 逐字段可见**（`_context_view` docstring 明写"10 个 id 逐字段给"）。写成 `_opt_str(x)` 之后，函数会从"**协议形状的说明书**"变成"数据搬运机" —— 读代码的人再也看不出线上返回了哪 10 个字段 |
| `handlers.py:203` 的 1 处 | **必须保持手写**：注释写着"**为 None 时如实留空，不拼 `'None'` 字符串**" —— 这一行是**语义声明**，抽成 helper 会让"这里为什么允许 None"只存在于 helper 名里 |
| `service.py:943` 的 1 处 | **必须保持手写**：它是 JSONB 序列化的**唯一落点**，docstring 论证了"为什么存字符串而不是 UUID 对象"（`json.dumps` 对 `uuid.UUID` 直接报 `TypeError`） |

> **`[C37b]` 的由来（一次真实的欠计）**：第一版用**逐行** `search` 得 **9** 处，整文件 `findall` 得 **12** 处。
> 差的 3 处（`api.py:665` / `770` / `1085`）是**条件与两分支各占一行**的写法 —— 逐行匹配时 `None` 单独占一行，**连 `if` 都看不到**。
> ⇒ **"逐行 grep"在格式化代码上会欠计多行表达式**，而看不见时**不报错**（与"中文路径下 `grep` 静默失败"同类）。

### 7.6 刻意不动的（共同判据）

### 7.7 ★ 扫描器自身的反向验证（判据的判据）

**"永远通过的判据比永远失败的更危险"。** 一个恒绿的扫描器会输出与"真的干净"**完全一样**的结果。
本包做了**两轮**反向验证，**每一轮都抓到了一条真缺陷**：

| 轮 | 脚本 | 断言数 | 抓到的 |
|---|---|---|---|
| ① 扫描器轮 | `/tmp/wp26/reverse_scan.py` | **15 条 0 FAIL** | **扫描器的一个真实盲区**（见下） |
| ② 新增判据轮 | `/tmp/wp26/reverse_c36.py` | **22 条 0 FAIL** | **我自己反向操作选错对象**（2 条） |

**① 抓到的盲区**：第一版注入写成 `WP26_REVERSE_PROBE_SYMBOL = 1`（模块级**变量**赋值）—— **没被报出**。
查因：`_module_defs()` 只收集 `FunctionDef / AsyncFunctionDef / ClassDef`，**不收集模块级 `Assign`**。
**处置**：注入改成**函数定义**（那才是本扫描器口口声称覆盖的形态），并**另加一条判据把盲区本身钉住**：

```
OK   ★ 盲区已钉住：模块级**变量**赋值不被本扫描器覆盖（如实登记，非恒绿）
```

> 没有这一步，我会把一个**探测手段选错**读成"扫描器恒绿" —— 而真相是"**覆盖范围比我以为的窄**"。
> **判据纪律第 3 条**：文档说"有判据"，必须能**当场指出脚本里哪个函数**覆盖什么、**不覆盖什么**。本包把"不覆盖什么"也写成了判据。

**② 抓到的两条（都是我的错）**：

| 错误 | 现场 | 修法 |
|---|---|---|
| 变异锚点**不唯一** | 第一版选 `title=new_title,` —— 它出现 **2 次**（生成 `1481` + 采纳 `1505`）⇒ "只改一处"这个**前提就不成立** | 改用采纳路径独有的 `adopted_title_candidate_id=candidate_id,`（出现 1 次） |
| 变异**改的是值不是键** | 第一次改的是 `candidate_id` → `candidate_id_x`（实参**值**），而 `[C36]` 断言的是 **kwargs 键序列** ⇒ 判据照样绿 | 改成**改键名** `adopted_title_candidate_id=` → `adopted_candidate_id=`。⇒ **反过来证明 `[C36]` 的断言精确**（只看键名，不看值） |

> **共同形态**：**反向验证脚本自身也会写错，而它写错的样子像"判据不灵"**（与 WP25 §五 ③ 的 ISS-171"尺子没涨被读成东西坏了"同族）。
> 处置也一样：**先怀疑尺子**。两轮共 37 条断言，其中 **5 条**一开始报红、**全部**是我这边的问题（1 条盲区 + 1 条锚点 + 1 条改错对象 + 2 条连带）。

**③ 未做反向验证的一项（如实登记，不假装做过）**：`scan_dup.py` / `scan_dup2.py` 的相似度扫描器**没有**做"注入真重复 → 看它报红"。
理由：它的 165 对命中**全部是假阳性**，而注入**真**重复需要真的往 `service.py` 里复制十几行（**会改变生产代码，与"零改动"冲突**）。
它的**有效性**目前由 `[C36]` 系列独立承担（`[C36]` 已验证能报红），而相似度扫描器**只用于发现候选、不进入任何判据** ⇒ 这一缺口**不影响任何结论**。

### 8.6b ★ 同一条判据的**第三个**入口也有病：OP 引用的编号位数写死（ISS-187）

**现象**：跑 `audit_consistency.py` 时，同一份输出里 §1 与 §7 对「OP 条数」给出**两个互相矛盾的读数** ——
§1 打印 `OP 条数 实测 188 OK`，§7 紧接着打印 `登记册已定义 OP 89 条`。

**根因**：§7（`check_op_references_resolve`，即「文档引用的 OP 编号必须真实存在」这条防线，
专治 ISS-172 那类幽灵引用）把编号位数**写死成 3 位**（`OP-\d{3}`），
而本项目 OP 编号**从 2 位起步**（OP-01…OP-99）、过百后才变 3 位。
实测登记册：3 位表格行 **89** 条（OP-100~OP-188）+ 2 位表格行 **99** 条（OP-01~OP-99）= 合并唯一 **188** 条。

⇒ 前 99 条编号在**定义侧与引用侧同时失明**；引用侧实测 3 位口径抓到 80 个编号、
2~3 位口径抓到 **126** 个 ⇒ **46 处双位数引用从未被核对过一次**，而 §7 每次都说「幽灵引用 0 处」。

**性质 = ISS-115 的对称形态**：那次是「恒真式伪装成判据」（永远为真），这次是「**恒不命中**」——
漏掉的形态与"判过了"在输出上逐字同形。**尤须记的是**：WP25 收口时踩到的三次真幽灵
（OP-172 / OP-173 / OP-174）**全落在双位数编号段** ⇒ 这条判据**从建立起就对自己最该盯的那一半数据失明**，
它当时报绿**不能证明**那三次是被它抓住的，只说明**它没机会报错**。

**处置（不停在改数字，改工具）**：两条正则放开为 `\d{2,3}`（引用侧带 `(?!\d)` 负向前瞻 ——
否则 `OP-1888` 会被截成 `OP-188`、**造出假编号**）；**落地前先探针验真**（两遍对跑确认
放开后新增暴露的**真**幽灵 = 0）；新增**同源对账判据**（§7 定义侧取数必须与 §1 的 `OP-\d+` 逐条相等）。

**反向验证（实测记录）**：把定义侧正则改回写死 3 位 ⇒ 立即报 **47 处**（1 条同源对账 + **46 处**
双位数引用被误判为"幽灵"），精确复现旧缺陷的后果；边界实测 `OP-1888` 在旧口径被截为 `OP-188`、
新口径正确不匹配。

## 9. 本包新增的铁律（值得沉淀）

承接《待定项与问题登记册》§4.4（G1~G7）与 WP25 的第 16~18 条，本包新增 **7 条**（**第 19~25 条**），全部来自**判据/工具自身或环境假设**的缺陷而非功能缺陷。

### 第 19 条 —— "我扫过、没人用"必须写明扫的是哪个范围

> 凡下"零消费 / 零引用 / 不存在"这类**否定性结论**，必须在同一句里写明**扫描范围**；
> 范围不是"全仓"时，该结论**不得跨出这个范围使用**。

**现场（ISS-175）**：本包往共享表 `version_nodes` 挂反向触发器时，依据是"`ENTITY_TYPE_CONTENT` 零消费" ——
而那个结论**只扫了 `src`**。`ENTITY_TYPE_CONTENT` 恰是 WP11 测试的 **8 类样本实体之一** ⇒
不收窄守卫就会**破坏 WP11 既有 2 例**（"别的包的进度被本包阻塞"）。

**与第 14 条的关系**：第 14 条管的是"**覆盖范围由人写** ⇒ 必须改由磁盘决定"；
本条管的是"**覆盖范围即使已由磁盘决定，也必须把范围写出来**" ——
因为磁盘范围**不等于**全仓范围，而否定性结论的**传播**不看范围。

### 第 20 条 —— "拆成两个 `task_kind`"若只体现为"两次调用"，就还没有拆开

> 判断两个阶段是否真的拆开，看"**前者的产物是不是后者的输入、且前者能否作为资产被复用**"，
> 而不是看"代码里调了几次"。

**现场（本包 §1.3）**：`TASK_CONTENT_STRUCTURE` 与 `TASK_CONTENT_COPY` 若只落在"调用两次"，两者仍共享同一份上下文与同一条失败恢复路径 ⇒
结构成功而文案失败时会**重跑结构**（多花钱）。**本包真正拆开**：蓝图（`narrative_blueprints`）是**独立表 + 不可变**，
文案生成**以蓝图 id 为输入**，且"仅标题"重做**只重跑文案那一次**。

### 第 21 条 —— 结构化校验的判据必须包含"必须被拒"的四类输入

> 只测"好输入能过"的校验器，与"没有校验器"在判据覆盖度上**没有区别**（都只证明了恒真的那一半）。

**现场（R1 / §1.6）**：四类必拒 —— **空 dict / 缺字段 / 类型错 / 域外值**。
本包三个校验器（`validate_bindings` / `validate_title_candidates` / `validate_copy`）**各自都有四类必拒用例**，
且每处 `SchemaViolation` **必带 `reason=`**（`[C6]` 判据守着 —— 四类拒绝必须**可区分**，
否则"四条规则"会退化成"一个报错"）。

### ★ 第 22 条（本包实测，**最值钱的一条**）—— "范本注释"不是证据，DDL 属性只能查 `pg_constraint`

本包编码期要给"循环外键"定延迟口径，第一反应是照抄范本 `brief/models.py`。
那一行的注释白纸黑字写着（第 168 行）：

> `# 当前草稿。**与 brief_drafts.brief_id 构成循环外键**（两者都延迟）。`

**照抄它就错了。** 实测 `rednote_wp26` 的 `pg_constraint`：

| 约束 | 注释声称 | 实测 |
|---|---|---|
| `fk_briefs_draft_id_brief_drafts` | 延迟 | `deferrable=true` ✅ 与注释一致 |
| `fk_brief_drafts_brief_id_briefs` | 延迟 | **`deferrable=false`** ❌ **与注释矛盾** |

**代码是对的，注释是错的。** 而这条注释错得很危险：它教人去"两条都延迟"，
而那会**削弱防线** —— 非空的那一侧延迟之后，`content_versions` 就能先插
"指向不存在内容的孤儿版本行"（该用例在 v3 探针里实测报 `23503`，**正确行为**）。

本包据此得到的口径（`models.py` docstring 五 / 七）：**延迟的是 3 条环 FK，不是 4 条**，
且"环 1 的 `content_item_id` 必须留 IMMEDIATE"要写成**负向判据**钉住。

**推广**：凡"某个 DDL 对象具备某属性"这类断言，**唯一可信来源是该对象在当前库里的实际状态**
（`pg_constraint` / `pg_trigger` / `pg_index`），而不是：
- ❌ 同类模块的注释（本条）
- ❌ ORM 的 `deferrable=` 参数（那只是"意图"，要 `create_all` 或迁移落地后才成事实）
- ❌ 文档里抄来的表格

这与 ISS-95「"声称自己有防线"比"没有防线"更危险」是同一族，但**更隐蔽** ——
ISS-95 是"没人验证过"，本条是"**有人验证过、验证错了、还写下来当范本**"。

### ★ 第 23 条（本包阶段 7 实测）—— 判据化的分界是"**变了会不会静默**"

> 一份"机器扫描出 N 个问题"的记录，**不是每一项都值得判据化**，也不是都不值得。
> 分界判准：**这项数字变化时会不会报错？**
> **会静默变化 ⇒ 判据化**；**变化时肉眼可见 ⇒ 命令即证据**。

**现场（§7.8）**：本包阶段 7 的扫描结果里，**长函数计数 / 嵌套深度 / 死标记 / 参数个数**这几项
变化时**肉眼可见**（长函数从 10 个变 12 个不会静默）⇒ 保持"命令即证据"；
而**"两处 kwargs 是否还同步" / "手写转换是否被悄悄合并" / "未使用 import 是否还是三处"**这三项
**变了不报错** ⇒ 全部判据化（`[C36]`~`[C38]`，9 条）。

**为什么这条值钱**：它给出了一个**可执行的分界标准**，而不是"全都判据化"（成本爆炸、且会造出第二套口径）
或"全都不判据化"（WP25 的 ISS-171 就是这么坏的）。
**与铁律 14 同向**：让机器只管住**人会漏的那部分**。

### ★ 第 24 条（本包新增判据第一次运行就抓到自己的错）—— **人写清单必须与磁盘反算并列成两条判据**

> 只要判据里出现一个**人写的清单**（函数名列表 / 包号列表 / 站点列表），
> 就必须**另有一条判据从磁盘反算同一个集合，并断言两者相等**。
> 清单是**人给的假设**，反算判据是**机器给的否决权** —— 缺了后者，清单的漂移**不报错**。

**现场（§7.4，`[C36b]`）**：`_REPEAT_SITES` 是人写的真重复清单，第一版写了 **3 对**。
`[C36b]`（磁盘反算）**第一次运行就报红**，抓出我漏了第 4 对 `ContentVersionSummary`（10 字段）。
**磁盘不会漏，我会漏。**

**与既有纪律的关系**：这是第 14 条（覆盖范围由磁盘决定）的**判据化落地形态**。
第 14 条说"改由磁盘决定"，本条补上"**怎么知道改对了**" —— 答案是
**"人写一份 + 机器反算一份 + 断言相等"**，而不是"人不再写清单"（人写清单有价值：它承载**意图**）。

### 第 25 条 —— **"关闭条件"不是愿望，是一条要能当场跑起来的命令**

> 凡写下"某待定项在本包闭合"，必须同时给出**可执行的验证方式**（跑哪条命令、它输出什么）；
> 若给不出，**正确写法是"机制就位、判据未做"并推进状态到 `IN_PROGRESS`，而不是 `CLOSED`**。

**现场（ISS-184）**：本包文档 §3.6 为 **`OP-160`** 写下的关闭条件是"证据 = `test_content_wp26.py` 里
『按 `prompt_version_id` 反查历史生成』的用例通过"。收口核实发现：**该用例不存在** ——
`test_content_wp26.py` 与全 `tests/` 目录对 `prompt_version_id` **零命中**，
反查函数 `service.read_generation_contexts_by_prompt_version` **无任何测试引用**。
而**机制四件套**（表 / 列 / `ix_generation_contexts_prompt_version` 索引 / 反查函数）**都真实存在**，
于是"交付物清单"看起来完整 —— **缺的是把它们串起来跑一次的那条用例**。

**为什么这条比"漏做功能"更危险**：该声称写在**关闭条件**里。若有人照它关闭 `OP-160`，
等于**用不存在的证据关闭一条待定项**，而后来的读者会以为"这条验过了"。
这是 **ISS-84 原话**在 WP26 的现身：**判据是「有代码路径 / 有测试 / 有落库行」，不是「我建了能承载它的表」**；
也是 **ISS-95（"声称有防线"比"没有防线"更危险）**的**第 N 次**现身。

**与第 19 条的关系**：第 19 条管"**否定性结论**必须写明扫描范围"（我扫过、没人用）；
本条管"**肯定性结论**（已闭合）必须能当场跑起来"。一否一肯，同一条原则的两面：
**结论的强度越大（越绝对），它需要的证据就越具体。**

**落地动作**：把该用例列入**下一包清理项**（§7.9，与 ISS-177 / ISS-178 同批），
并把"关 `OP-160`"的前置改为"**这条例用通过**" —— 即**先把判据补齐，再谈关闭**。

### ★ 第 26 条（本包收口审计轮实测，**判据自身有三条入口**）—— 同一个量只允许有一个取数来源

> 当一个判据内部**多处**需要从同一份事实里取**同一个量**（条数 / 编号集 / 文件列表），
> 必须只有**一处取数**。一旦出现第二处（哪怕只是"顺手再写一条正则"），
> 它们迟早会因为「一处后来放宽了、另一处没跟上」而给出**互相矛盾的读数** ——
> 而更糟的是，**旧的那一份仍在输出一句理直气壮的「0 处」**。

**现场（ISS-185 / ISS-186 / ISS-187，同一天同一份文件里的三条）**：
`tools/m1/audit_consistency.py` 的三条判据**各自**在自己的"取数口径"上有病：

| 缺陷 | 形态 | 后果 |
|---|---|---|
| **ISS-185** | §2b 同一字段的**多条声明正则**，一条**恒不命中**（入口从未接上）+ 一条**无锚点**（抓到正文里的局部叙述） | 判据的绿与红都不足采信；报了一次**假红** |
| **ISS-186** | §4 声明路径只认**连写**形态，**换排版**（目录与文件名分写）即完全不被命中 | 与它要消灭的缺陷（ISS-124）**同形**，而它全程静默 |
| **ISS-187** | §7 把**编号位数写死成 3 位**，而编号**从 2 位起步** | §1 报 188 / §7 报 89，**同一次运行自相矛盾**；46 处引用（37%）**从未被核对**，而它每次说「0 处」 |

**为什么这条比前面三条更该记**：三者**全都发生在「判据自己的取数口径」上**，
而不在被检查的内容里。⇒ **判据自身有缺陷时，它的 PASS 与 FAIL 都不构成任何结论。**
本轮能发现它们，靠的不是重跑，而是**逐条把每条正则的命中次数与取值打出来看了一遍**
（**命中 0 次的"防线"必须当作不存在** —— ISS-185 的正则自引入起一次都没匹配过）。

**两个可直接复用的动作**：
1. **对每条正则做「命中计数」自检**：命中 0 次 = 该入口从未接上（不是"没有缺陷"，是"没在看"）；
2. **对同一事实的两处取数做「不等即报红」对账**：不是靠人定期比对，而是让它们**互相判红**（§7 已加）。

**与第 14 条的关系**：第 14 条管"**覆盖范围**由人写 ⇒ 必须改由磁盘决定"；
本条管"**取数口径**有多份 ⇒ 必须合并成一份，且多份时必须互相对账"。
前者是"范围"，后者是"读数"——**范围对了，读数仍可能量错**（ISS-187 的编号位数就是纯读数问题）。

> **本节的真正教训（写给下一个包）**：
> ① **"要不要新开一条 OP"的判据是"册里有没有一条已覆盖同一事实的条目"**，不是"附录 A 里写了几条"。
> 本包 8 条里 **3 条**（A2/A6/A7）在写下时就**已经指向**既有 OP，新开编号会让同一事实有**两个声称方**。
> ② **"期望时机"不是自由创作区**：它是给人看的说明，但一旦进入登记册就是**受控取值**。
> 凡是"还没定"的时机，正确写法是 `待产品定模型` 这类**已在白名单里的兜底表述**，
> 而不是发明一个新里程碑名（`前端对接前`）—— 后者会**静默**让分桶脚本 FAIL，
> 而 FAIL 的信息是"未归类 1 条"，**看不出**是哪一条、更看不出它本该归哪个桶。
