### 0.3 三条实测结论（**本包的核心防线靠它们选型，必读**）

WP22 的三条核心不变量都不是"加个字段"能解决的。落盘前对**防线层次**做了实测，
结论直接决定 §2 的设计。

#### 实测 1：跨表不变量，**CHECK 表达不了**

AC-24「跨品牌事实不得迁移」的本质是「**子行引用的资产，其品牌必须与基线所属品牌一致**」。
这是**跨表条件**。实测：

```
试 1  check ((select brand_id from asset where asset.id = asset_id) = 1)
      → ERROR: cannot use subquery in check constraint   (FeatureNotSupported)

试 2  alter table snapper add column brand_id int
      check (brand_id = (select brand_id from asset where ...))
      → ERROR: cannot use subquery in check constraint   (FeatureNotSupported)

试 3  退而求其次：冗余列 + check (brand_id > 0)
      → 写入成功。子行声称 brand=10，父行真实 brand=20，**无任何报错**。
```

**结论**：`CHECK` 只能管**本行**。把品牌冗余成一列后，CHECK 只能保证"非空 / 取值合法"，
**保证不了"与父行一致"** —— 这与 ISS-75（判据建立在数据库已保证的事上 → 恒真）是同一族：
一个恒真的判据从不报错，它只是让防线看起来存在。

**替代路径的实测**（`_wp22_probe` 探针，已回收）：

```
试 4a  对照组（同品牌写入，该过）→ 通过 ✅
试 4b  反例（跨品牌写入，该拦）→ 被拒 ✅  sqlstate=23514
```

**因此本包的选择**：跨表不变量落**延迟约束触发器**，且活性验证**必须成对**
（对照组 + 反例）—— 只跑反例的话，一个"一律 RAISE"的坏守卫也会全绿（WP20 铁律原文）。

#### 实测 2：协议里的「**同事务**」是**可强制的**，不是约定

协议原文（经 WP19 §6 转述）：「步骤 3 创建 baseline 时**同事务**生成 step approval」。
"同事务"三个字，能不能落成数据库级保证？

```
试 1  布尔冗余列 + check (has_approval)
      → 实测：has_approval=true 而 approval 表里一行都没有，CHECK 全绿 ✗
      （声称方与事实方分离 —— 又一次同族）

试 2  CONSTRAINT TRIGGER ... AFTER INSERT ... DEFERRABLE INITIALLY DEFERRED
      函数体：select count(*) from approval where baseline_id = new.id；=0 则 RAISE(23514)

试 2a 反例：只插 baseline，不插 approval → COMMIT 被拒 ✅  sqlstate=23514
试 2b 正例：**同一事务**先插 baseline 再插 approval → 通过 ✅
试 2c 反例：只有 baseline 的裸事务 → 被拒 ✅
```

**结论**：`CONSTRAINT TRIGGER` + `DEFERRABLE INITIALLY DEFERRED` 在 **COMMIT 期**校验，
因此"同事务"可以成为**硬约束**。同时它带来两个附带好处：

1. **顺序不再是必须猜对的事** —— 触发器延迟到提交，实现方不必猜"节点行何时落库"
   （与 WP18 `brief_*` 的 5 个延迟触发器同一条理由）；
2. **跨事务补批准这条路被物理封死** —— 这是"事后补一张批准单"这种绕过的唯一入口。

#### 实测 3：部分唯一索引的**静默退化**

AC-08 说基线不可原地修改 → "修改"必然是"新增一版 + 旧的转 `SUPERSEDED`"。
这与"每个项目同时只能有一个 `ACTIVE` 基线"合起来，要求一个**部分唯一索引**。实测：

```
试 1  create unique index uq_bl_active on bl (project_id)          ← 漏写 WHERE
      插 project=1 的 ACTIVE：成功
      插 project=1 的 SUPERSEDED（历史基线）：**被拒** ✗ duplicate key
      → 误拦。这不报错，它只是让「基线只能创建一次」——
        而这条约束与 AC-08 **直接冲突**，症状迟一步（第二次创建基线时）才出现。

试 2  create unique index ... on bl (project_id) **where state = 'ACTIVE'**
      插 ACTIVE + SUPERSEDED：都成功 ✅
      再插第二个 ACTIVE：被拒 ✅  sqlstate=23505

试 3  pg_indexes.indexdef 逐条核对：
      CREATE UNIQUE INDEX uq_bl_active ON ... USING btree (project_id)
        WHERE (state = 'ACTIVE'::text)
```

**结论**：索引**存在**与索引**带 WHERE** 是两个不同的断言
（WP20 铁律原文：「部分索引的 `WHERE` 必须逐条核对（少了 `WHERE`，唯一约束会静默退化）」）。
本包的证据脚本必须**逐条打印 `indexdef`** 并把 `WHERE` 子句当判据，不能只数索引条数。

## 1. 阶段 1：需求追问（8 问）

### 1.1 这个需求真正要解决什么问题？

**一句话：把"运营心里确认过的东西"变成一份「带版本号、不可被后续动作改掉、且能被下游钉住引用」的快照。**

G2 出口给了两个否定式分句（执行计划 §8.2 原文）：
**「跨品牌事实不串」「基线固定不被污染」**。两者都是**否定式**，
而否定式约束的共同特征是：**做不到不会报错，只是有一个口子一直开着**。
这正是本包全部设计的出发点 —— 但更关键的是，这两个分句**不是同一件事**：

| 分句 | 它在防什么 | 它防的是**谁的**动作 |
|---|---|---|
| **跨品牌事实不串** | A 品牌的内容用上 B 品牌的事实 | **知识选择**（横向：跨品牌） |
| **基线固定不被污染** | 已批准的基线被后来的知识变更**悄悄改掉** | **时间推进**（纵向：跨版本） |

**第二条才是最容易做错的那条，因为它反直觉**：

> 运营在 9-15 批准了基线（当时事实 v7）。9-20 知识库把「氨基酸表活占比」从 62% 更正为 60%。
> `knowledge_assets.active_version_id` 指向新版本 —— **这是 WP20 的正确行为**（知识就该更新）。
> 而基线 BL-v3 里存的是"事实 v7"的**引用**。若基线存的是**指针**而不是**快照**，
> 那么 9-20 之后生成的每一篇内容都会用上 60%，而运营批准的是 62%。
> **基线被污染了，且没有任何人做了"修改基线"这个动作。**

所以验收原文（原型 L33 转述 AC-08）的措辞是「**不可原地修改的基线快照**」——
"**快照**"两个字是本包的核心：基线必须**钉住版本号**，不能钉住"当前生效的"。

**为什么这句话是「本包」的验收，而不是 WP20 的**：WP20 已把**知识的版本与生效**
做完了（`knowledge_publications` 事件流 + `active_version_id` 投影 + 5 表 30 CHECK）。
但**"某一版知识被批准进某条基线"这件事在 WP20 里无处安放** ——
WP20 交付后，基线只是一个 `projects.active_baseline_id` **空列**
（`projects/models.py` L226 的注释原文就写着"WP11/WP22 填充"）。
**把"运营批准的那一版"变成一份可引用、不可污染的快照，是本包的工作。**

**反面：这个包不做「内容生成」，也不做「审核规则的执行」。**
基线里的"审核规则 v5（9 阻断 · 14 提醒）"（原型 L61）在本包**只被快照，不被执行** ——
规则的**判定**归 WP30（自检与审核）。本包交付的是**基线**，不是**判定**。
同理，"必须提及 / 禁止提及"（原型 L233~262）在本包是**基线内容**，
它在生成时的**检查**归 WP26/WP30。

**为什么现在做（而不是等 M3）**：三个已交付的包**各留了一个指向本包的坑**，且都已登记：

| 遗留 | 来源 | 内容 |
|---|---|---|
| **OP-151** | WP19 §6 | `/step-approvals` 端点协议里**未定义形状**，全库无实现；协议原文说"步骤 3 创建 baseline 时**同事务**生成 step approval" → 自然归属是 WP22 |
| **OP-88 的 `BASELINE` 那一半** | WP11 §2.4 | `versions/models.py` L67 已定义 `ENTITY_TYPE_BASELINE`，但**反向触发器**（`BASELINE` 节点必须配对 `production_baselines` 行）**尚无子表可挂** —— 与 WP18 闭合 `BRIEF` 半边、WP20 闭合 `KNOWLEDGE` 半边**同构，这是第三半** |
| **`active_baseline_id` 空列** | WP11/WP22 交接注释 | `projects.models` L226~229 明写"WP11/WP22 填充"。**本包交付前，这个列永远为空** |

**OP-88 的这一半是本包最硬的约束**：它不是"缺个功能"，而是
「一个已定义的类型**永远不可能有实例**」—— `ENTITY_TYPE_BASELINE` 声明了却没有生产者。
本包把 `production_baselines` 建出来，`BASELINE` 这个 entity_type 才第一次真实存在。

| 角色 | 规模 | 在这个包里的动作 | 关键诉求 |
|---|---|---|---|
| **运营** | 约 50 人 | 逐条确认事实 / 处置冲突 / 选择人群场景 / 确认表达边界 → 点"确认信息并创建基线" | **"我批准的是哪一版，事后要能查"**；**"批错了能重来（但不能偷偷改）"** |
| **运营负责人** | 1 人 | 在阻断项未处置时**必须**被拒；审批 step approval | **"系统不能让我在明知有冲突时放行"** |
| **WP26 文案生成**（下游代码） | 代码 | 按项目取**生效基线**，组装动态上下文 | **拿到的是钉死的那一版**，不是"当前最新的" |
| **WP30 AI 自检**（下游代码） | 代码 | 读基线的表达边界（必须提及 / 禁止提及 / 禁用话术） | 边界**来自基线快照**，不来自"当前知识" |
| **WP31/WP32 试产与批产** | 代码 | 按基线推进八步 | **存在阻断项时必须被拒**（AC-09 的落点） |
| **WP42 知识回写** | 代码 | 回写产生新知识 → 触发基线影响检查 | **不修改生产基线**（原型 `content-feedback.html` L348 原文：「不修改生产基线 —— 基线变更需回到步骤 3 创建新版本」） |
| **审计/事后追溯的人** | — | 查"这篇内容用的是哪版基线" | **八步记录里要能定位到基线版本** |

**主用户是运营 + 下游代码（WP26/WP30/WP31/WP32）**，
**关键决策人是运营负责人**（"阻断项未处置不得推进"这条否决权的持有者），
**验收的受害者是运营自己**（基线被污染时，第一批看到错内容的还是他们）。

> **一个容易忽略的用户**：**半年后查事故的人**。
> AC-24 明写"保存实际选用条目、版本、片段与**未纳入原因**"（原型 L102）。
> 「未纳入原因」这个字段在**当天**看起来毫无价值 —— 它在事故复盘时才第一次被读。
> 而如果创建基线那天没存，半年后**无法补**：当时的判断依据已经不存在了。

### 1.3 最小 MVP 应包含哪些功能？

**MVP 的判据是 G2 的两个否定式分句能各自闭环**（不是"表建齐了"）：

| G2 分句 | MVP 必须有的 | 落点 |
|---|---|---|
| **跨品牌事实不串** | 基线项引用知识时，**品牌必须与基线一致** | `baseline_items` 上的延迟约束触发器（实测 1） |
| **基线固定不被污染** | 基线存**版本号快照**，不存"当前生效的" | `baseline_items` 记录 `knowledge_version_id`（钉死版本），而非 `asset_id` |
| **（AC-09）阻断项未处置不得推进** | 「有阻断项就拒绝创建基线」必须是**数据库级**的 | `information_drafts` 状态 + 延迟触发器（实测 2 同款） |

**MVP 的具体功能清单**：

1. **四张表**：
   - `information_drafts` —— 审核工作区（可变，**一个项目一份**，与 `brief_drafts` 同构）
   - `production_baselines` —— 基线（**不可变**，`id PK/FK version_nodes`）
   - `baseline_items` —— 基线内的条目（**不可变**，含"实际选用条目 / 版本 / 片段 / 未纳入原因"）
   - `step_approvals` —— 跨步骤批准（**不可变**，步骤 1/2/3 通用，闭合 OP-151）
2. **一个纯函数**：`context_order.py` 的**动态上下文组装顺序** —— PRD §15.4 的 5 项
   优先级是**规则**，必须可单测（不碰数据库）
3. **一组延迟约束触发器**（WP22 的三条不变量，全部 COMMIT 期校验）：
   - 基线创建时**必须有**对应 step approval（实测 2）
   - 基线项引用的知识**不得跨品牌**（实测 1）
   - **存在阻断项时不得创建基线**（AC-09）
4. **一个部分唯一索引**：每个项目同时只有一个 `ACTIVE` 基线（实测 3）
5. **`BASELINE` 的 OP-88 反向触发器**：挂在共用表 `version_nodes` 上，
   用 `WHEN (NEW.entity_type = 'BASELINE')` 收窄（与 WP18/WP20 那两个并存）
6. **端点**：基线创建 / 查询 / 列表 + 审核工作区的读写 + `step-approvals`
   （**数量与形状待协议原文复核**，见 §2.4 的 OP-171）
7. **`projects.active_baseline_id` 的填充**：创建基线事务里同时更新该列（WP11 交接的坑闭合）

**不放进 MVP**（划界理由见 §1.5）：
- **审核规则的执行**（9 阻断 / 14 提醒的判定）—— 归 WP30
- **动态上下文的实际组装与裁剪** —— 归 WP26（本包只交付**顺序规则**）
- **知识回写对基线的影响分析** —— 归 WP34/WP42（本包只保证基线**不被改**）
- **真实研究资料的语义选用** —— 依赖 OP-154（研究语义检索）+ 真实数据
- **前端** —— 本仓 `apps/` 目录不存在（盘点 L14），30 个原型页面是**独立的 HTML demo**

### 1.4 描述有哪些疏漏应当补充？理由？

原始描述只有一句：「信息草案 / 冲突处理 / 批准基线」。**至少 10 处疏漏**：

| # | 疏漏 | 为什么必须补 | 落点 |
|---|---|---|---|
| 1 | **"信息草案"到底是什么？它和 `brief_drafts` 是什么关系？** | 名字极像，作用完全不同。`brief_drafts` 是**解构前的工作区**（WP18，运营改字段与结论）；`information_drafts` 是**审核工作区**（WP22，运营处置冲突与选用范围）。**混为一谈会让两个工作区的状态互相覆盖** | `information_drafts` 独立表 + `project_id` **唯一**（一个项目一份草稿）；docstring 显式写明与 `brief_drafts` 的分工 |
| 2 | **"冲突处理策略"是什么策略？有哪些种类？** | 原型只给了**一个**冲突样例（氨基酸表活占比：Brief 称 62% vs 研究资料 R-014 称 ≥60%，且**被 4 条试产内容引用**）。真实冲突至少有四类：来源冲突 / 时效冲突 / 跨品牌冲突 / 事实与限制冲突。不分类就会做出"一个备注框" | 受控的冲突类型 + **处置动作**（采纳其一 / 标记区间表述 / 升级为阻断 / 停用场景）。冲突**不落独立表**（它是草稿内容的一部分，与 WP18 的 issues 同款判断） |
| 3 | **基线快照要存什么？原型给了 9 项，但它没说存的是"值"还是"引用"** | 这是**本包最容易做错的一处**（§1.1 的核心）。存"引用" → 基线会被知识更新污染；存"值" → 丧失了溯源（AC-24 要求"保存实际选用条目、版本、片段"） | **两者都要**：`baseline_items` 同时存 `ref`（指向哪条知识的哪一版）与 `snapshot`（当时的实际文本/值）。**只有 `ref` 会被腐化，只有 `snapshot` 会断溯源** |
| 4 | **"未纳入原因"没有落点** | AC-24 原文要求「保存实际选用条目、版本、片段与**未纳入原因**」（原型 L102）。若只存"纳入了什么"，"**为什么没纳入**"就永远查不到 —— 而它正是半年后复盘时唯一想知道的事（§1.2 的"容易忽略的用户"） | `baseline_items` 加 `inclusion`（INCLUDED / EXCLUDED）+ `exclusion_reason`；**排除项也要落行**，不能只是"没有那一行" |
| 5 | **基线被替代（SUPERSEDE）与创建新版本，是同一件事还是两件？** | AC-08 说"修改将创建新版本"；原型 L130 说"基线 BL-v2 **被替代**"。若把替代做成"就地改状态"，则"BL-v2 曾经生效过"这件事从数据里消失（与 WP20 状态投影问题**同构**） | 基线**不可变**（`production_baselines` 上是 `guard_immutable`）；"被替代"是**新基线的创建** + 旧基线 `superseded_by_id` 指向新基线。**状态由关系算出，不是一列** |
| 6 | **`step_approvals` 批准什么？谁能批？批了改什么？**（OP-151 原文） | 协议只说"步骤1与步骤2通过它完成"，**没给形状**。而实测 2 已证明"同事务"可以硬约束化 —— 那就必须现在定形状，否则触发器无从写起 | 见 §2.3 决策 4：**批准的对象是「步骤 + 版本」的组合**，不是"一个项目"。理由：八步里每一步批准的产物不同（步骤 1 批准 Brief 版本，步骤 3 批准基线版本），只记"批了"无法回答"批的是哪一版" |
| 7 | **"至少有一个可生产场景"这条完成条件，判据是什么？** | 原型 L154 说"5 个场景可生产"，L196~204 又有一个"已停用"的场景（熬夜党急救，原因"无对应事实支持"）。**"可生产"的定义没有任何地方给出** | 定义为**可派生的判据**：场景状态 `PRODUCIBLE` 且**至少引用一项已确认事实**。停用场景落 `EXCLUDED` 并带原因 —— 于是"可生产场景数"是**算出来的**，不是运营手填的（避免第二个真值来源） |
| 8 | **"阻断项已处理"的判据是"数量为 0"还是"没有那种类型的行"？** | 这是本项目**踩过 10 次**的形态（ISS-78/84/85/86/94/95 同族）。若写成"`blocking_count = 0`"，那个 count 若由别处维护就会与事实脱节；若写成"没有 OPEN 状态的 BLOCK 冲突"，则**它是派生的**，不需要 count 列 | 判据写成**对明细行的否定式**：`NOT EXISTS (... state <> 'SETTLED')`。**不落 `blocking_count` 列**（第二个真值来源） |
| 9 | **基线与 Brief 版本、知识版本的关系** | 原型 L56 说基线绑定"Brief v2 已批准"、L58 说"事实 v7 · 风格 v4"。但**"已批准"这个状态由谁定义**？Brief 的批准状态在 WP18（`brief_versions`），知识版本在 WP20。基线引用它们时，**引用的是版本号还是"已批准"这个事实**？ | 基线**钉版本号**（`brief_version_id` / `knowledge_version_id`），**同时**在创建时校验"被引用的版本确实处于已批准/生效状态"。**校验在创建时做一次，之后不再重复** —— 否则基线会随被引用对象的状态变化而"失效"（那正是"被污染"的另一种形式） |
| 10 | **`active_baseline_id` 与 `active_version_id` 的关系** | 两个名字都叫 active，层级不同：`projects.active_baseline_id` → 某个**基线实体**；`production_baselines` 是版本化实体（`id PK/FK version_nodes`）→ 它自己**也有版本**。**"生效的那一版基线"与"生效基线"是两个 id** | 显式区分：`projects.active_baseline_id` 存**版本节点 id**（`version_nodes.id`，与 `knowledge_assets.active_version_id` 同构）；基线实体本身另有一个 id。**两个 id 都叫 active 是本包最容易写错的地方**（WP19 W4 的教训：两个 id 的语义差异会让错误信息指向错误的地方） |

**另有 3 处需要显式登记（不是疏漏，是外部依赖/空缺）**：

| # | 空缺 | 处置 |
|---|---|---|
| 11 | **协议 `/step-approvals` 的形状从未定义**（OP-151） | 本包按 §2.3 决策 4 定义形状，但**这是本包自己定的**，不是协议原文。登记进 OP-151 的收口结论：**协议需回填该定义** |
| 12 | **规格源原件（研发计划 01~04 / PRD / 协议 03）全部不在本机** | §0.1 已声明。登记 **OP-171**（挂靠 OP-164 的适用范围扩容），原件到位后复核本包全部回溯口径 |
| 13 | **"5 个启用场景 / 21 份选用研究资料"这类数字没有真实数据源** | 原型里的数字是**演示数据**。本包验证的是**机制**（能否记录选用与未纳入），不是**数量**。登记进 OP-171 的复核清单 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 后果 | 应对 |
|---|---|---|---|
| **R1** | **基线存"指针"而不是"快照" → 被知识更新悄悄污染** | **本包最危险的一条**。它不是"做错了"，而是"当时对了、后来变错"。没有任何报错，症状是"生成的内容用了运营没批准的数值"（§1.1 的例子） | `baseline_items` **同时**存 `ref`（版本 id）与 `snapshot`（当时的值）；**测试要构造"批准后知识更新"这个时序并断言基线不变** —— 这是本包唯一需要**跨时间**的测试 |
| **R2** | **跨品牌不变量退化成"列非空"** | 实测 1 已证：冗余列 + CHECK 在品牌不一致时**静默通过**。看起来有防线，实际是恒真判据（ISS-75 同族） | 跨表不变量落**延迟约束触发器**；活性验证**成对**（对照组 + 反例） |
| **R3** | **"同事务"实现成"先建基线、稍后补批准"** | 实测 2 已证：若无 COMMIT 期校验，"补批准"这条绕过路径是开放的。而它**不报错** —— 数据库里最终看起来是一致的（有基线、有批准），只是**中间有一段时间不一致**，且那个窗口里的推进是不合法的 | `CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED`（实测 2 已验证有效） |
| **R4** | **部分唯一索引漏 `WHERE`，唯一约束静默退化** | 实测 3 已证：漏写后**不报错**，只是让"基线只能创建一次"。而它与 AC-08（不可原地修改）**直接冲突**，症状在"第二次创建基线"时才出现 | 证据脚本**逐条打印 `indexdef`** 并把 `WHERE` 子句当判据（不是数索引条数） |
| **R5** | **`blocking_count` 这类聚合列成为第二个真值来源** | 本项目**已踩 10 次**（ISS-78/84/85/86/94/95 同族）。若落一个 count 列，它与明细行脱节时**不报错**，只会让"存在阻断项"这个判断失效 → 基线可以被非法推进 | **不落 count 列**。判据一律写成对明细行的否定式（`NOT EXISTS (...)`），且**同一判据在两个地方出现时必须调用同一个函数** |
| **R6** | **`information_drafts` 与 `brief_drafts` 混淆** | 两个工作区如果共用一个状态机或一张表，会出现"审核时改了字段、解构结果被覆盖"的双向踩踏；而两边都**读起来正常工作** | 独立表 + 独立服务；`information_drafts.project_id` **唯一**（一个项目一份，与 `briefs.project_id` 同构）；docstring 显式写明分工 |
| **R7** | **两个 `active` id 语义混淆**（`projects.active_baseline_id` vs 基线实体 id） | WP19 W4 的教训原文：「两个 id 的语义差异，错误信息会指向错误的地方」。写错时会报"缺少节点"，而真因是"传错了 id" | 参数名显式体现语义：`baseline_version_id` vs `baseline_id`；docstring 给出两者的关系图 |
| **R8** | **`ENTITY_TYPE_BASELINE` 的反向触发器与 WP18/WP20 的两个互相干扰** | 三个 `WHEN` 收窄的触发器挂在**同一张共用表 `version_nodes`** 上。若 `WHEN` 写错或漏写，会让每次 `BRIEF`/`KNOWLEDGE` 版本注册都白跑一次函数（轻则性能，重则误拦） | `WHEN (NEW.entity_type = 'BASELINE')` 收窄；**测试要验证另两个 entity_type 注册不受影响**（跨包回归） |
| **R9** | **历史证据的跨包影响** | 新增迁移推进 `alembic_version`；新增触发器与索引会改变全局计数 | 证据脚本**不用等式判据**（ISS-44/64/71/83/87 已现身**八次**）；本包自己的逐个断言，总数用 `>=` |
| **R10** | **基线的不可变性与"探针残留"** | `production_baselines` 若不可变，探针数据**物理删不掉**（本项目的不可变表已验证：连自己的残留都删不掉）。共享库上跑测试会让它**只涨不减** | 测试用**未提交事务**（夹具与服务层共用同一 `Session`，结束无条件 `rollback()`）—— WP19 W3 已验证这是"零写入/零残留"唯一成立的形状 |

## 2. 阶段 2：方案设计

### 2.1 需求本质

**这个包交付的不是"一个审核界面"，而是「两条不变量 + 一个可强制的原子性」。**

| 不变量 | 来源 | 为什么它是本质 |
|---|---|---|
| **快照而非指针** | AC-08 原文「不可原地修改的基线快照」 | 它是**跨时间**的约束：做不到时**当天完全正常**，问题在知识更新后才显现（R1）。所以它必须有**同时存 ref 与 snapshot** 的结构性保证，不能只靠"读的时候注意一下" |
| **不跨品牌** | G2 出口「跨品牌事实不串」+ AC-24 | 它是跨表的否定式约束。实测 1 已证 **CHECK 表达不了** → 必须落触发器，且判据要能**区分两种实现**（ISS-82：顺序调用构造的判据恒真） |
| **同事务** | 协议原文（OP-151） | 实测 2 已证它**可以**从约定升级为硬约束。不做这一步，绕过路径（先建后补）**不报错地**长期开放 |

由此推出本包的设计重心**不是功能数量，而是「防线的可验证性」**：

```
第 1 层  部分唯一索引         —— 每项目一个 ACTIVE 基线（本包建，实测 3）
第 2 层  不可变触发器         —— 基线 / 基线项 / 批准 三者不可原地改（本包建）
第 3 层  延迟约束触发器       —— 跨品牌不得引用（AC-24 落点，实测 1）
第 4 层  延迟约束触发器       —— 基线必须有同事务批准（实测 2）
第 5 层  延迟约束触发器       —— 存在阻断项不得创建基线（AC-09）
第 6 层  OP-88 反向（BASELINE）—— 节点必须配对子表行（闭合第三半）
第 7 层  服务层断言           —— 纯函数派生完成条件（readiness.py，与 API 预检同源）
```

**七层里第 3、4、5 层是三个 AC 的落点，第 6 层是 OP-88 的落点。**
每一层都必须有**成对活性验证**（对照组 + 反例），而不是"我建了它就说明它生效"。

### 2.2 用户画像与使用场景

**主场景：运营完成步骤 3 —— 审核信息并创建基线。**

```
输入：项目 X（品牌 A / 产品 P）
     ↓
① 审核工作区（information_drafts）
     逐条事实：已确认 11 / 冲突 1 / 待确认（非阻断）
     人群场景：5 个可生产 / 1 个已停用（无事实支持）
     表达边界：必须提及 3 / 禁止提及 5 / 禁用话术 5
     研究资料：21 份选用 / 3 份未支持未纳入（**带未纳入原因**）
     ↓
② 处置冲突（唯一的阻断项）
     源：Brief v2 P.5 称「氨基酸表活占比 62%」
         研究资料 R-014 品牌官方页称「≥60%」
     动作：采纳区间表述「≥60%」+ 记录依据
     ↓
③ 完成条件预检（readiness.py，与后端拒绝判据**同一个函数**）
     ① 阻断问题已处理 ✅  ② ≥1 可生产场景 ✅  ③ 运营明确点击确认 ✅
     ↓
④ 创建基线（单个事务，四件事**原子**发生）
     钉住：Brief v2 / 知识 事实 v7 · 风格 v4 / 规则集 v5 / 21 份研究资料
     写  ：production_baselines + baseline_items（含未纳入项）
     写  ：step_approvals（**同事务**，实测 2 的触发器会校验它）
     写  ：projects.active_baseline_id ← 新基线版本节点 id
     ↓
输出：基线 BL-v3 + 完整审核记录 + 可被 WP26/WP30 钉住的快照
```

**次场景：知识更新后，基线不被污染（R1 的验证场景）。**

```
9-15  创建基线 BL-v3，钉住 事实 v7（氨基酸表活占比 62%）
9-20  WP20 把该事实更正为 60% → knowledge_assets.active_version_id 指向 v8
      （**这是 WP20 的正确行为，知识就该更新**）
9-21  读 BL-v3 的 baseline_items
      期望：**仍是 62%**（snapshot），且 ref 仍指向 v7（未跟随 active_version_id）
      若读到 60% → **基线已被污染**，而这期间没有任何人做过"修改基线"这个动作
```

**关键：这个场景是本包唯一需要「跨时间」的测试。**
它无法用"插入后立即查询"验证 —— 必须**构造出那个时间点**
（新建一个知识版本并激活），然后断言基线不变。
这正是 ISS-82 的教训在时序维度的映射：没有可控替身造出"那一刻"，判据就是恒真的。

### 2.3 核心设计决策

#### 决策 1：基线项**同时**存 `ref` 与 `snapshot`

**实测依据见 §1.6 R1。** 取舍：

| 维度 | 只存 `ref`（指向版本） | 只存 `snapshot`（当时的文本） | **两者都存（采用）** |
|---|---|---|---|
| 知识更新后 | **被污染**（读到新值） | 正确（读到批准值） | 正确 |
| 溯源能力（AC-24） | ✅ 能追到版本与片段 | ❌ 断了 | ✅ |
| "未纳入原因"可解释性 | 部分 | 部分 | ✅ 完整 |
| 存储成本 | 最小 | 中 | 中（多一列） |
| 失败模式 | **静默**（R1） | 无法回答"这条来自哪一版" | — |

**为什么"只存 ref"是不可接受的**：它的失败是**静默且延迟**的 ——
创建基线当天一切正常，运营的批准也真实存在，但基线已经不是一个"快照"了。
验收原文用的词是「快照」（原型 L33 转述 AC-08），不是「引用」。

#### 决策 2：跨表不变量落**延迟约束触发器**（实测 1）

**实测依据见 §0.3 实测 1。** 守卫伪码：

```
BEFORE INSERT ON baseline_items
  SELECT a.brand_id, a.product_id, a.project_id INTO p
    FROM knowledge_assets a WHERE a.id = NEW.knowledge_asset_id
  -- 基线的 scope 决定了允许的引用范围：
  --   BASELINE_BRAND   → 只允许 GLOBAL 或 brand_id 相同的知识
  --   BASELINE_PRODUCT → 只允许 GLOBAL 或同品牌同产品的知识
  IF 违反 THEN RAISE ... USING errcode = '23514'
```

**为什么要用触发器而不是 CHECK**：实测 1 已证 PG **直接拒绝** CHECK 里的子查询
（`cannot use subquery in check constraint`）。这不是风格选择，是类型系统的硬约束。

**为什么不用"冗余列 + CHECK"折中**：实测 1 试 3 已证它**恒真** ——
冗余列与父行不一致时 CHECK 不会报错。这与 ISS-75（判据建立在数据库已保证的事上）同族：
一个恒真的判据从不报错，它只是让防线看起来存在。

#### 决策 3：`snapshot` 存的不是"美化后的文本"，而是**原样的可追溯负载**

**为什么**：如果 `snapshot` 是我们自己拼的一句话，那它**本身就成了一个新的真值来源** ——
半年后无法判断"这个值是从哪来的"。因此 `snapshot` 存**结构化负载**
（值 + 单位 + 限定条件 + 来源片段 id），与 WP20 的 `knowledge_versions.structured_payload`
**同构**。这样：

- 它足够稳（不会因知识更新而变）；
- 它仍可溯源（内含来源片段 id，能回到原文）；
- 它**不引入新语义**（只是把当时的版本内容复制一份，不重新解释）。

#### 决策 4：`step_approvals` 批准的对象是「**步骤 + 版本**」的组合（**本包定义，闭合 OP-151**）

OP-151 原文说协议**没给形状**。本包必须现在定，理由：实测 2 的触发器要校验
"基线在 COMMIT 时有对应批准" —— **没有形状就写不出校验**。

**定义**：

| 列 | 含义 | 为什么 |
|---|---|---|
| `project_id` | 项目 | 批准是项目内的事 |
| `step_no` | 步骤号（受控 1..8） | 八步里步骤 1/2/3 都用它（OP-151 原文） |
| `subject_kind` | 批准对象的类型（`BRIEF` / `RESEARCH` / `BASELINE` / …） | **关键**：只记"批了"无法回答"批的是哪一版" |
| `subject_version_id` | **版本节点 id** | 与 `version_nodes.id` 同构 → 能钉住具体那一版 |
| `decision` | `APPROVED` / `REJECTED` | 拒绝也要留痕（"曾经被拒过"是审计信息） |
| `decided_by` / `decided_at` / `reason` | 谁、何时、为什么 | W4 教训：语义要显式 |
| `superseded_by_id` | 被哪条新批准替代 | **不可变表的"撤销"靠新增，不靠改写**（决策 5 同款） |

**为什么"步骤 + 版本"而不是只有"步骤"**：Brief 出了 v2 之后，步骤 1 的"已批准"
指的是 v2 已批准，而不是"步骤 1 曾经被批过"。只记步骤会让"这一步批的是哪一版"
在数据里**没有答案**，而八步闭环的验收恰恰要回答它（AC-08~09 证据 = 「固定版本」）。

**这是一条本包自定的形状，不是协议原文** —— 已登记进 OP-151 的收口结论（§2.4）。

#### 决策 5："基线被替代"用**新的行 + 关系**表达，不用"就地改状态"

AC-08（不可原地修改）与原型 L130（"基线 BL-v2 **被替代**"）合起来，
要求"替代"这个动作**不改变旧基线的内容**。

**做法**：

- `production_baselines` 上是 `guard_immutable`（ORM 事件 + 数据库触发器**双重**守卫，
  与 `brief_versions` / `knowledge_versions` 同款）；
- 新基线的 `supersedes_id` 指向旧基线；
- 旧基线的 `superseded_by_id` —— **这一列不能存在**，因为它意味着"改写旧行"。

**替代关系用单向 FK 表达**：新行记 `supersedes_id`，
"谁替代了 BL-v2"通过**反向查询**得到（`WHERE supersedes_id = BL-v2.id`）。
这与 WP20 的"状态由事件流投影算出，不是一列"是**同一条原则**：
若在旧行上存 `superseded_by_id`，就必须 UPDATE 旧行 —— 而它是不可变的。

**"当前生效的是哪一个"由谁回答**：`projects.active_baseline_id`（投影列，
与 `knowledge_assets.active_version_id` 同构）。它是**可重建的**
（从"未被替代的最新基线"算出来），服务层提供 `rebuild_active_baseline()` 并可测试
"增量维护与全量重算一致"（与 WP20 `rebuild_active_version` 同款，**同一处实现**）。

#### 决策 6：`readiness.py` 是完成条件的**唯一来源**，API 预检与后端拒绝**调用同一个函数

AC-09 的验收证据是「**非法推进被拒**」。而原型 L169~174 显示前端**也会**预检
（"1 项阻断待处置"按钮是灰的 / 可点击但提示）。

**风险**：前端预检 + 后端拒绝是**同一判据的两处实现** —— 它们会漂移，
且漂移时**不报错**（前端说可以、后端说不行 = 用户看到"点了没反应"）。
这与本项目"同一事实只能有一处实现"的铁律（WP19 R4 / WP20 `_project_asset`）正面对撞。

**处置**：`readiness.py` 的 `step3_readiness()` 是**纯函数**，输入是明细行，
输出是三条完成条件各自的状态与原因。**API 的预检端点和创建基线的服务层都调它**，
测试断言"两处调用的是同一个函数"（不只是"结果相等"—— 与 WP19 §6 的
`test_gap_categories_come_from_wp18_constant` 同款断言）。

#### 决策 7：**不落任何** `*_count` 聚合列

**依据**：本项目**已踩 10 次**（ISS-78/84/85/86/94/95 同族）。
"审核项 42 · 已处置 41 · 待处置 1"（原型 L45）这类数字**必须从明细算**。

**为什么这条要单独列为一个决策**：它的诱惑力极大 ——
原型上明明白白写着这些数字，落一列是"最直接"的实现。
但一旦落列，它与明细脱节时**不报错**，只会让 AC-09 的"存在阻断项"判断失效。
而 AC-09 的失效意味着**基线可以被非法推进** —— 本包最严重的后果。

### 6.1 二十九处活性验证（本仓最多）

`evidence/m1/wp22-baseline.log`：**74 PASS / 0 FAIL**。为什么这个包需要最多？因为本包**绝大多数防线都是"做不到也不报错"的形状**：

| 防线 | 失效后的症状 | 会报错吗 |
|---|---|---|
| 部分唯一索引漏写 `WHERE` | 退化成"每项目只能有一条基线" → 与 AC-08 冲突 | **不会**（第二次创建时才炸） |

| `trg_baseline_items_cross_brand` 的 `IS DISTINCT FROM` 写成 `<>` | NULL 比较→`IF` 视为 false → 跨品牌**静默通过** | **不会** |
| `trg_*_no_blocking` 没建 | 有未处置阻断项也能建基线（AC-09 失效） | **不会** |
| `fk_*_supersedes_id` 忘了 `DEFERRABLE` | 替代链写入顺序一变就失败 | 多数时候是**测试与线上行为分叉** |

—— 一个"见谁都拒"的触发器能让所有"被拦"判据全绿，而系统已经完全不可用。
29 处分五组：基线的创建与批准（1~4）/ 不可变保护（5~6）/ OP-88 节点一致性（7~10）/

### 7.1 判据口径的修正：为什么用"代码行"而不是"逻辑行"

沿用 WP21 确立的口径（逐行过滤空行/`#` 注释/docstring 块），
而不是 WP23 的 AST 首尾行差 —— 后者把 docstring 一起算进去，
而本项目的 docstring 密度是**刻意的**（每条判据都要能回答"为什么不那样做"）。
**砍注释不会让代码变简单**，只会让下一个接手的人重新踩一遍。

### 7.2 一次**看起来很像真问题**的假警报（值得单独记）

AST 扫描器报 `ddl.py::_scope_match_case` 嵌套 **5 层**、`service.py::_require_item_scope`
嵌套 **4 层**。核实后：**实际都是 2 层**。

根因：`elif` 在 AST 里落进 `orelse` 字段，是一个**嵌套的 `If` 节点** ——
朴素遍历会把"同一层的第 N 个分支"算成"第 N 层嵌套"。两个函数都是 `if/elif`
分支选择器（scope 匹配规则表、范围判据表）。

> **若照它去拆函数，会把一个一眼可读完的分支表拆成多个片段函数** ——
> 而那个表的价值恰恰是"能一眼看完所有分支"。
> **扫描器的口径必须先验证再用。**

**扩范围时判据抓到它自己**（值得单记，是"判据的判据"缺口）：

`check_test_db_isolation.py` 一进 CI 就被自己的第二段扫到，而它的
`_is_dsn_literal()` 要判前缀 `"postgresql://"` —— **前缀常量天生就是 DSN 字面量**，
于是判据自报违规（`[FAIL] 发现 2 处违规`，两处都是它自己的判定行）。
更早还暴露过一处同族假阳性：`"postgresql+psycopg"`（一个**驱动名**，
没有 `://`）也被当成 DSN。

修法**不是加白名单**（判据自己进白名单会让它成为法外之地），
而是让判据**按位置**豁免：`x.startswith("postgresql://")` 里的字符串是
**模式**，不是**连接地址**。用 `id()` 而非行号定位 ——
**同一行混用时只豁免模式**（实测：`s.startswith("postgresql://x") and
s == "postgresql://rednote@h/db"` 只豁免前一个，后一个照报）。

> **这一轮的最强教训**：**"覆盖范围"是整条链上最脆的一环**。
> 判据会守代码，但"判据管到哪"没有人守：
> 一条早退（B）、一次硬编码（C）、一份手工名单（D）都能在**不报错**的前提下
> 让防线缩水。ISS-104/105 是这条病的第一批，本轮 A~D 是第二批 ——
> 同一族缺陷在同一个仓库里**两轮复发**，说明它不是疏忽而是结构问题：
> **凡"覆盖范围"由人写（名单、glob、目录判断），就必须另有一条判据去对账它。**

### 8.8 二次复核：复核"证据脚本的迁移判据"又抓到一族三个缺陷（ISS-115~ISS-117）

**触发**：8.3.1 那一轮把两条跨包护栏补进 CI 门 3 之后，收口并未结束 ——
本轮回头**复核"证据脚本自己是否可信"**，方法是对每个 helper 跑**区分度矩阵**
（构造 4 个真实场景，看它给出的 True/False 是否与真实链序一致）。

**结果：三个缺陷，分属同一族（"判据/防线自身失效"）的不同形态。**

#### ISS-115（MAJOR）—— 12 个脚本的"不早于"判据是**恒真式**

| 项 | 内容 |
|---|---|
| 现象 | 12 个证据脚本（WP11~WP18 / WP20~WP23）的 `_revision_is_at_least` 写成 `len(current) >= len(introduced)` |
| 根因 | 本项目**全部 16 个 revision id 都是 12 位十六进制**（`ebc05dfca16b` 等），于是 `current != introduced` 时该式**恒为 True** |
| 性质 | ISS-44 揭示"不能用 `==`"之后，修法选了"比长度"来表达先后 —— **而长度不是顺序**。它把"永远失败"换成了"永远通过"，**比原缺陷更隐蔽：永不失败，因此永不报警** |
| 为何没人发现 | 输出行印的是 `CHECK OK  迁移 head 不早于本包引入的版本`，与真判据的输出**逐字相同**。"通过"与"根本没判"在输出上同形 |
| 第二层真因 | 自检器 `check_no_exact_revision` 当时只认 `version == EXPECTED_REVISION` —— 既不认 `head ==` / `rev ==` 这类改名写法（ISS-105 同族），也认不出恒真式本身 |
| 第三层（**这才是能"躲过门禁"的真因**） | WP21 的 `_uses_check_pattern` 用 `"failures" in text` 当判据，而 WP21 全文明写 `sum(1 for c in checks if not c)`，**没有 `failures` 这个词** → 被判为"非 CHECK 模式" → `check_expected_checks` 与 `check_no_exact_revision` 对它**双双早退**。**整条检查链对 WP21 从未执行过**，不是正则漏网 |
| 处置 | 12 个脚本改为沿**真实迁移链按位置比较**：`ScriptDirectory.walk_revisions(base='base', head='heads')` 取 `chain`，再比 `chain.index(current) <= chain.index(introduced)`；认不出的 revision 一律判否（fail-closed）。自检器同步加固**四处**（见下） |

**实测区分度矩阵（旧 vs 新）**：

| current | introduced | 期望 | 旧 len 法 | 新链序法 |
|---|---|---|---|---|
| `ebc05dfca16b` | `cedfe85c1bf9` | True | True | True |
| `cedfe85c1bf9` | `ebc05dfca16b` | False | **True（错）** | False |
| `ebc05dfca16b` | `185ec01bed91` | False | **True（错）** | False |
| `185ec01bed91` | `ebc05dfca16b` | True | True | True |

→ 旧实现 4 个场景错 2 个，新实现错 **0** 个。

**自检器四处加固**：

| # | 加固点 | 从 → 到 |
|---|---|---|
| 1 | `_uses_check_pattern()` | `"failures" in text` → `_CHECK_DECL_RE.search(text) and "EXPECTED_CHECKS" in text`（按**结构特征**，不按某个变量恰好叫什么名） |
| 2 | 新判据 `_REVISION_LENGTH_HACK_RE` | 按**行为**拒绝任何 `len(x) >= len(y)` 形态 —— 长度不是顺序 |
| 3 | `check_no_exact_revision()` 的等式判据 | `version\s*==\s*…` → 不限定左操作数名（覆盖 `head ==` / `rev ==` 两种改名写法） |
| 4 | 新增**死代码判据** | 声明了版本常量却没有一处 `_revision_is_at_least(...)` 调用 → 报红 |

**一处踩过的弯路（值得记）**：加固 2 的第一版想用"找 `print` 语句 + 括号配平"来定位 RESULT 行，
结果把 **13~16 个脚本集体误报** —— 本仓的 RESULT 有**两种出口**：一半直接 `print(...)`，
另一半先拼进 `lines = [...]` 再统一落盘（`collect_wp13` 等），**语句里根本没有 `print` 这个字**。
最终改为按**行为**判断：RESULT 标记附近的代码窗口里同时出现"期望"与 `EXPECTED_CHECKS`。

#### ISS-116（MAJOR）—— WP19 的 helper **参数传反**，且错误路径永不触达

| 项 | 内容 |
|---|---|
| 现象 | `_revision_is_at_least` 调的是 `script.walk_revisions(current, introduced)` |
| 根因 | `walk_revisions` 的真实签名是 **`(base, head)`**（降序产出 head→base）。参数传反后**方向整体反转** |
| 实测 | 4 个场景**错 3 个**：`185ec0→ebc05d` 期望 True 得 False；`ebc05d→185ec0` 期望 False 得 True；`7a4c1e→ebc05d` 期望 True 得 False |
| 为何长期"通过" | 该包读的**固定验证库** `rednote_verify_wp19` 的 head **恰好停在引入点** → 走 `current == introduced` **短路分支直接返回 True** → 出错的代码路径**永不执行**（ISS-82 同族：两种实现给出相同结果） |
| 为何本轮会漏掉它 | 批量修恒真判据时，**修复名单写的是"12 个脚本"（靠记忆列举）**，而 WP19 的 helper 形状不同、不在名单里 → 它带着传反的参数继续输出 `CHECK OK`。**修复名单本身没有任何判据** |
| 处置 | helper 重写为与其余 12 个脚本同口径，删除 `current == introduced` 短路分支与 `try/except` 静默兜底；注释内嵌 4 场景区分度矩阵 |
| 复跑 | `RESULT=49 PASS / 0 FAIL（共 49 条，期望 48 条）`，`rc=0` |

#### ISS-117（MINOR）—— 同一编号被两条不同缺陷共用

登记册里 `ISS-111` = 「`check_evidence_scripts.py` 的一条早退使反向验证脚本完全不在自检范围」
（属 v1.16.1 的"覆盖范围靠记性"四连，且被 README 与变更行引用）；
而 **12 个脚本的注释把上面的恒真判据标为 ISS-111** —— 该条在登记册里**查无此条**。
两条缺陷的根因、范围、严重度全然不同，共用一个编号。

**根因**：编号由 append-only 顺序分配，注释里的引用是**手写**的，两处独立演化。
`log_issue.py --check` 只校验编号**连续与唯一**，**不校验引用语义相符** —— 是判据缺口（ISS-95 族）。

**处置**：恒真判据补登为 **ISS-115**；12 个证据脚本 + 自检器 + WP19 注释共 **14 处**引用由 `ISS-111` 改为 `ISS-115`。

#### 本轮新增的判据：`check_revision_helper_implementation`

**为什么"函数存在 + 函数被调用 + 不用长度法"三条还不够** —— 本仓实测三种形态：

| # | 形态 | 后果 | 原有判据 |
|---|---|---|---|
| 1 | 定义了但从不调用 | 死代码，那条判据没生效 | 已有（死代码判据） |
| 2 | 调用了，内部写 `len(a) >= len(b)` | **恒真**，永久绿灯（ISS-115） | 已有（长度法判据） |
| 3 | 调用了，内部 `walk_revisions(current, introduced)` **参数传反** | **方向全错**（ISS-116） | **本轮新增** |

新判据对**函数体**（不是全文）做三条断言：
① 不得用**位置参数**调 `walk_revisions`（顺序靠记性）；
② 必须含 `walk_revisions(base=..., head=...)`（自解释，不可能传反）；
③ 必须含 `chain.index(...)`（按真实链上位置判断）。

**反向验证 5/5 全过**（在临时副本上做，不动真树）：

| 用例 | 期望 | 实测 |
|---|---|---|
| 基线：正确实现 | 全绿 | PASS |
| 变异 1：位置参数传反（ISS-116 原形） | 报红且定位准确 | PASS |
| 变异 2：恒真长度法（ISS-115 原形） | 报红且定位准确 | PASS |
| 变异 3：未取真实链（直接 `return True`） | 报红且定位准确 | PASS |
| 还原后 | 重新全绿（无残留） | PASS |

**一处调试弯路**：反向验证脚本第一版"3 个变异全没抓到" —— 根因是它跑的是**真树**的自检器
（`REPO_ROOT` 由 `__file__` 推导），变异写在副本里、真树那份根本读不到。改为跑沙箱内的副本后即全过。
**教训**：验证"判据能否抓到错"时，必须先确认**被判据读到的确实是被变异的那份文件**。

#### 本轮沉淀（三条，已并入 §9 铁律族）

1. **判据必须能区分两种实现**（判据纪律第 7 条）。当"通过"与"根本没判"在输出上同形时，它就不是防线。
   凡用「长度 / 数量 / 字母序」表达顺序的地方，先问：**这个度量在真实数据上有没有区分度？**
2. **修复一族的缺陷时，"修复名单"本身必须要有判据。** 本轮名单写的是"12 个脚本"（靠记忆列举），
   必然漏掉形状不同的第 13 个（WP19）。这与 ISS-104/105/111/114 是**同一族第三次复发** —— 属结构问题而非疏忽。
3. **编号是弱引用。** 注释里写"见 ISS-NN"是**手工维护**的引用，必须有一条判据去对账它的**语义**；
   只断言"编号存在"会放过 ISS-117 这种「存在但指错」。

| 实验 | 结果 |
|---|---|
| 隔离库 `rednote_test_wp22`（`expired=0` 干净态）跑**全量** | **1539 passed** ✅ |
| 同一隔离库**种入 9 条过期残留**（`scope='s'`、`expires_at = now() - 1 day`）后**单跑该用例** | **`assert 10 == 1` FAIL** ❌ |

即它不是「偶发」，而是**数据量依赖的必红** —— 会在某个时间点之后从「一直绿」突变成
「一直红」，而代码一行没改。之所以看起来像偶发：**失败运行自己把过期记录删掉了**
（那条全表 `DELETE` 在断言失败**之前就已提交**，实测探针跑完后 `decoy 剩余 = 0`、
`total 从 20 降到 6`），于是它**自愈了下一次运行**。

处置（方案 B，不改生产语义）：断言改为**存在性 + 下界** —— `assert removed >= 1`，
保留本用例真正关心的两条（临时记录被删、永久记录未被误删）。
**反向验证 3/3**，且校验了**红的形状**：

| 错误实现 | 期望 | 实测 |
|---|---|---|
| 甲 误删永久记录（`or_(expires_at IS NULL, ...)`） | 第②条断言红 | PASS（`AssertionError`） |
| 乙 清理失效（下界放宽 100 年） | 第①条断言红 | PASS（`AssertionError`） |
| 丙 删全表（连未到期也删） | 第②条断言红 | PASS（`AssertionError`） |
| 正确实现 | 绿 | PASS（1539 passed） |

⚠️ 前两次构造的「错误实现」**红的形状是错的** —— 分别因 `or_` 未导入（`EXIT=4` 收集错误）
与 `key = '\x00never\x00'`（PG 拒 NUL 字节，`DataError`）而红。**若只断言「退出码非 0」，
这两次都会被误判成「判据有效」** —— 这是本轮新增的沉淀（§9 铁律 18）。

已按 ISS-59 的教训**把源头在每个包各过一遍**：全仓 grep `.delete()` 仅此一处全表 DELETE；
另两个全局扫描（WP12 `expire_stale_sessions` / WP13 `reclaim_expired_leases`）的断言
早已是「大 limit + `>= 1` + 本实体核对」形态，未发现同类漏网。

## 9. 本包新增的铁律（值得沉淀）

1. **"跑现象"得出的排除才叫排除，"读代码"得出的排除是一次无判据的声称。**
   三遍法的 `[INFO]` 段落里写"`newest_baseline_of` 的子查询写法正确（刻意选暴露式）"，
   而那条子查询是**同行自比恒假**（MAJOR-4）。它经全量 pytest 才暴露。
   **动作**：凡在审查里写"已排除/无问题"，后面必须跟一条**可复现的命令**（探针用例名 / 测试名）。

2. **三遍法（含真库探针）不是终点。** 本包三遍法过完、6 条 MAJOR 已修、
   探针全绿之后，**跑全量 pytest 又炸出 3 条 MAJOR**，其中 1 条正是被"排除"过的。
   **"逐文件读"看不见跨文件的口径不一致**（MAJOR-6 服务层 vs DDL 两处口径）——
   这类缺陷只能由**跨文件对账判据**或**端到端运行**抓住。

3. **只有一条防线的缺陷，在错误路径上表现为 500 而不是 4xx 时，那条防线就不是防线。**
   MAJOR-2：部分唯一索引本该是"最后一道保险"，实际成了"唯一的一道"，
   于是可读的 409 退化成裸 500。**判据**：凡数据库约束承担"业务规则拒绝"职责的地方，
   服务层必须**先**给可读错误码 —— 否则约束一响就是 500。

4. **同一模块内两条同类字段的处理必须对称。** MAJOR-1 的根因不是"漏了校验"，
   而是 `knowledge_version_id` 有类型交叉核对、`brief_version_id` **没有** ——
   所以没人觉得缺了什么。**动作**：新增同类字段时，先找出模块里已有的同类字段，逐条对齐。

5. **"部分更新"语义必须逐个字段核对"无条件写"与"仅非 None 写"。**
   MAJOR-3：一个 `values["brief_version_id"] = brief_version_id` 无条件写，
   把运营几小时的设置**静默清空**（HTTP 200）。而该函数自己的 docstring 就写着不能这样。
   **更隐蔽的是**：`Optional` 字段**无法区分"未提供"与"显式 null"**，
   只有 `model_fields_set` 能区分 —— 而服务层/仓储层**都没读它**。

6. **`elif` 不是嵌套层。** AST 扫描器报"嵌套 5 层"是**看起来很像真问题的假警报**
   （`orelse` 里的 `If` 节点）。若照它拆函数，会把一个一眼可读完的分支表拆碎。
   **扫描器的口径必须先验证再用** —— 否则你会"修"一个不存在的问题，
   而真正的问题被这个假警报挤掉了注意力。

7. **注释与文档字符串会骗过子串判据。** 审查脚本第一版 9 条 FAIL，
   其中 3 条同一根因：**被测文件的 docstring 里逐字写着它们的反例**（讲解"不要这样写"）。
   **机械证明**：把 `sans_doc()` 关掉，2 条判据立刻重现 FAIL。
   **动作**：文本判据先剥离注释/文档字符串；结构判据一律走 AST。

8. **注释声称"已登记"= 一次声称，而不是一次登记**（**ISS-95 第二次现身**）。
   本包 4 处注释写着"已登记待定项 / 已登记 / 已知取舍"，
   收口时登记册里**一条都没有** —— 比不写更糟，因为所有人（包括下一个接手的人）
   会以为有人看着。**动作**：收口时 grep 全部"已登记/已知取舍/待定项"字样，
   逐条去登记册找那一行；找不到就补登记或删掉声称。

9. **"测试 docstring 声称已登记"是本条最坏的形态**（**ISS-109**）。
   两条测试写着"这是已登记的口径问题（收口时记入登记册）"，
   而它们当时**按现状断言**，把缺陷**钉成了预期行为** ——
   后来人看到绿测试，会认为"这是有意为之"。
   **动作**：测到已知缺陷时，测试必须**断言它现在的错误表现 + 注释里给出登记编号**，
   而不是只写"已知问题"。

10. **建表路径有两条时，必须有一条判据比较它们**（**ISS-106/107**）。
    迁移建表 与 夹具 `create_all` 建表，此前**没有任何判据比较产物** ——
    于是"夹具把别的包的外键拆掉"（1511 条全绿）与"模型漏写 deferrable 被夹具治愈"
    两个真实缺陷**同时静默通过**。

11. **环境约定没有机械判据 = 没有约定**（**ISS-108**）。
    "测试库物理隔离：`REDNOTE_TEST_DATABASE_URL` 覆盖"这条约定写在接缝文档里，
    被破坏了 10 次而无人发现。判据必须是 **AST 数据流**（DSN 字面量必须流向隔离变量），
    而不是"文件里出现过 `environ.get` 就算合规"。

12. **永远失败的判据等于没有判据**（`alembic check`，**ISS-110**）。
    `prompt_templates ↔ prompt_versions` 的循环 FK 让 `alembic check` 恒失败 →
    本仓"模型与迁移一致"这件事**实际上没有任何机械判据**（因为谁也不会看一条永远红的命令）。
    与 ISS-108 同族：**声称有防线 / 放着一条红命令不管，都比明确说"这里没有防线"更糟。**

13. **永远通过的判据比永远失败的更危险**（**ISS-115**）。第 12 条说"永远失败 = 没有判据"，
    而本条是它的**镜像且更坏**：12 个脚本把"不早于"写成 `len(a) >= len(b)` ——
    本项目全部 16 个 revision id 都是 12 位十六进制，于是 `a != b` 时该式**恒真**。
    它的输出行与真判据**逐字相同**（`CHECK OK  迁移 head 不早于本包引入的版本`），
    "通过"与"根本没判"在输出上同形。**动作**：凡用「长度/数量/字母序」表达"顺序/先后"的地方，
    先问这个度量在**真实数据**上有没有区分度 —— 有区分度才叫判据。（与判据纪律第 7 条同族）

14. **修复一族的缺陷时，"修复名单"本身必须要有判据**（**ISS-116**）。
    修 ISS-115 时名单写的是"12 个脚本"（**靠记忆列举**），必然漏掉形状不同的第 13 个（WP19：
    它调 `walk_revisions(current, introduced)` 而真实签名是 `(base, head)`，参数传反，
    4 个场景错 3 个；又因固定验证库的 head 恰好停在引入点、走 `current == introduced` 短路，
    错误路径**永不执行**）。**动作**：批量修复的名单要由**命令现场生成**（glob/grep），
    并由"枚举全部同类文件"的判据对账 —— 否则名单就是一个自由文本。

15. **编号是弱引用**（**ISS-117**）。注释里写"见 ISS-NN"是**手工维护**的引用，会与
    append-only 的编号分配**独立演化**：同一编号 `ISS-111` 被两条毫不相干的缺陷共用，
    其中一条在登记册里**查无此条**。`log_issue.py --check` 只校验编号**连续与唯一**，
    **不校验引用语义相符**。**动作**：注释/文档里的登记编号引用，需要一条判据对账其**语义**
    （只断言"编号存在"会放过这种「存在但指错」）。（与判据纪律第 9 条同族）

16. **判据只证明"读得到"，不证明"还成立 / 不矛盾"**（**ISS-118 / ISS-120**，同一族的两个形态）。
    收口审计里 `_collect_facts()` 从 `evidence/m1/*.log` 读计数，而 `check_readme()` 判据是
    `str(value) in readme` —— 两者都只证明"某个数字在某个文件里写着"，**不证明这个数字还成立**
    （证据整体过期：日志停在 10:15、`main.py` 10:53 又改），**也不证明没有互相打架的声明**
    （README 开头写 110、看板写 119，门禁两处都放行）。
    **动作**：① 凡判据从文件读事实，都要问一句"**这个文件凭什么是现在的？**"——
    本包新增 §4 `check_evidence_freshness()`（证据生成时间 vs 被证据代码 mtime），
    且**在 CI 里响亮跳过**（checkout 重置 mtime，必然假红；"永远被静默跳过"与没有判据无从区分）；
    ② 凡"同一事实在 ≥2 处出现"，判据必须**收集全部出现点再比对**（§2b
    `check_readme_internal_consistency()`），不能用 `in` 判存在性。

17. **「重跑直到绿」是把偶发失败藏起来的动作**（**ISS-122**，根因指向 **ISS-121**）。
    `backend-pytest.log` 被一次 flaky 失败覆盖成 `RESULT=1 failed, 1538 passed` 后，
    当时的处置是"重跑一次就好了"—— 于是这个 flaky 下次再红也没人会知道；
    而 `_collect_facts()` 的正则 `RESULT=(\d+) passed` 匹配不上红行，退化成哨兵 `-1`，
    报出的是「声明 [1539] 不含实测值 -1」——**把"证据那次跑挂了"与"值不一致"压成同一个信号**。
    **动作**：① 解析失败与取值不符是**两种故障**，用 `None` / 可选值表示"没解析出来"，
    不用 `-1` / `0` / 空串这类哨兵（哨兵会让报错信息误导排查方向）；
    ② 新增 §5 `check_evidence_self_report()`：读证据的 `EXIT=` 行，非 0 即 FAIL 并**点名 flaky 用例**，
    让红运行在证据里留下不可掩盖的痕迹 —— 对全表操作断言精确计数（`removed == 1`）
    把判据建在**外部状态**上，单跑必过、全量偶发，只有这类判据能让它持续暴露。

    > **更正（ISS-123）**：上面末句里的"偶发"是**当时的定性，已被推翻**。
    > 本轮用决定性实验证明它是**数据量依赖的必红**，且**失败运行自己把过期记录删掉了**，
    > 从而自愈了下一次 —— 这才是它"看起来偶发"的机制。详见 §8.9 与第 18 条。

18. **反向验证必须校验"红的形状"，不能只断言退出码非 0**（**ISS-121 → ISS-123**）。
    本轮为 `delete_expired_idempotency` 的断言修复做反向验证，前**两次**构造的"错误实现"
    红是红了，但**红得不对**：一次 `or_` 未导入（补丁锚点只改了 `import` 行的一半），
    红的形状是 **`EXIT=4` 收集错误**（`NameError`，用例根本没跑）；一次用
    `key = '\x00never\x00'` 造"永不匹配"，触发 **`DataError`（PG 拒 NUL 字节）**。
    **只断言"退出码非 0"的话，这两次都会被判成"判据有效"** ——
    而那两次根本没有证明被断言的行为。这与第 12/13 条的"永远失败/永远通过"是同一族：
    **红/绿本身不是信号，"红在哪一行、因为什么红"才是信号。**
    **动作**：反向验证的判据必须是「**具体断言失败**」（这里要求 `AssertionError`
    且失败行是那一条 `assert`），而不是「退出码 != 0」；
    构造"永不匹配"这类替身时，值本身也必须是**目标类型域内的合法值**
    （NUL 字节不是合法 PG text，用它成功只会证明 PG 拒绝，不证明本用例的设计意图）。
    **附带一条反味教训**：第一次实验（"去掉 `expires_at IS NOT NULL`"）**跑绿了** ——
    因为 SQL 里 `NULL <= now()` 为 NULL（非真），该条件对 DB 本就冗余。
    **一个"错误实现"跑绿，说明这个变异根本没改变语义**，要换变异而不是换结论。
