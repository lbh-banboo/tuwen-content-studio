## 1. 阶段 1：需求追问（superpower-workflow 强制 8 问）

### 1.1 这个需求真正要解决什么问题？

**把"我们知道的关于产品/品牌的事"变成一种"能被引擎精确取用、能被追责、且换版时不会读错"的资产。**

三个定语一个都不能省：

- **能被精确取用** —— 规格源 §277 原文最后一句：**"重要事实可以从数据库精确获取；
  不能因索引延迟读取错误旧事实"**。这句话直接否掉了一个很自然的做法：
  "知识 = 一堆向量，检索就是相似度查询"。因为**相似度查询在索引未就绪时会返回旧结果**，
  而"我们的产品不能宣称某个功效"这种事实，读错了就是一次违规。因此本包必须提供
  **一条不经过索引的精确读取路径**（`knowledge_assets(product_id, category, active_version_id)`
  的部分索引，见 DDL 草案 §三）。
- **能被追责** —— 规格备注两处："全员可管理"与"AI 创建待确认，**不直接生效**"。
  前者意味着任何运营都能改知识（权限面很宽），因此"谁在什么时候把哪个版本变成生效版本"
  必须是**一条不可改的事件**，而不是某一列上的当前值。后者意味着 AI 的建议
  与人的决定要在结构上分开。
- **换版时不会读错** —— 验收原文「生效版本与旧引用并存」。旧引用指的是：
  一份 3 个月前生成的内容引用了知识的 v2，而现在 v5 生效。
  **那份内容不能被追溯地"改成"引用了 v5**，同时它也不能因为 v5 生效就读不到 v2。
  这要求版本是**只追加**的、生效关系是**事件流**。

**本包真正的难点不是"怎么写 CRUD"**（那是标准模式），而是
**"怎么让『当前生效的是哪一版』这件事只有一个来源"**。
最容易埋下的坑是：写入侧（发布事务）与读取侧（详情接口）各算一遍状态 ——
两边一旦有微小差异，就会出现"刚发布完，返回 ACTIVE，紧接着读回却显示别的状态"。
本包把状态判定收敛到一个 `_project_asset()`（见 §4，主 agent 补），
**两处调用同一个函数**。

### 1.2 核心用户是谁？

| 用户 | 何时用 | 关心什么 |
|---|---|---|
| **WP21 切块与索引**（下游代码，最高优先） | 知识发布后 | 该给哪个版本切块；换 embedding 模型时哪些版本要重算 |
| **WP22 信息草案 / WP26 文案生成**（下游代码） | 步骤 3~7 | **精确事实**（`FACT` 类、按 `product_id` 查）—— 不经过向量索引 |
| **WP23/WP41 反馈与实验**（下游代码） | 收到反馈时 | 往 `knowledge_proposals` 写候选（本包只建表 + 决策） |
| **运营（前端）** | 日常 | 列表（筛选/分页）、详情（内容/来源/历史/范围）、建与改 |
| **任何组织内成员（前端）** | 生成内容时 | "全员可查" —— 知识是组织级资产，不是项目私有 |
| **审核人 / 管理者** | 处理 AI 候选时 | 候选的内容、范围、依据；接受或驳回 |
| **AI（模型）** | 产出候选时 | 六类各自的结构化字段规格（`schema.py`），不能只写散文 |

**"全员可查"与"全员可管理"是两个不同的面**：读只需登录（`CurrentUserDep`），
写需要 `OrgAction.KNOWLEDGE_MANAGE`（运营与管理者的权限矩阵最后两行）。
这不是项目级权限 —— 一条 `GLOBAL` 范围的知识本就跨项目。

### 1.3 最小 MVP 应包含哪些功能？

1. 五张表（`knowledge_assets` / `knowledge_versions` / `knowledge_publications` /
   `knowledge_chunks` / `knowledge_proposals`）+ 30 条 CHECK + 15 条 FK + 11 条显式索引
2. 六类知识的结构化字段规格（`schema.py`）：每类的必填字段、归一化、校验
3. 创建（建 asset 同时建 v1，**草稿态**）+ 加版本（不改原文）
4. 发布事务（锁 asset → 校验 → 插 publication 事件 → 切换 `active_version_id` →
   写索引 Outbox 事件），四个动作**同一个事务**
5. 状态投影（纯函数）：从 publication 事件流算出 `DRAFT / ACTIVE / INDEXING /
   SUPERSEDED / ARCHIVED`，以及每版本的状态
6. 列表（筛选 + 游标分页）+ 详情（内容/来源/历史状态/可用范围）
7. 引用摘要（谁引用了这条知识，**受项目可见性过滤**）
8. AI 候选的列表与决策（ACCEPT / REJECT）
9. 四层测试：纯函数 / 服务层 + 真库 / **数据库约束活性** / HTTP

### 1.4 描述有哪些疏漏应当补充？理由是什么？

| 疏漏 | 补充 | 理由 |
|---|---|---|
| 数据结构只写 `versions` 有 `body`/`structured_payload`，没说"按什么规格校验" | 加 `schema_version`（当前恒为 1） | 六类字段规格会演进。没有它，"该按哪版规格校验这份 payload"成了不可知的事，而**旧版本不能重写** |
| 没说驳回要不要理由 | `decision_reason` 列 + `ck_*_reject_needs_reason` | "为什么这条 AI 建议被否了"若只存在聊天记录里，三个月后没人能回答 |
| 没说决策时刻存哪 | `decided_at` 列 | `updated_at` 会被任何后续写入刷新，不能当决策时间 |
| 没说"归档"的语义边界 | `ck_*_archived_implies_had_version` | 从未生效过的草稿被归档 = 一条没人见过的东西出现在"归档可追溯"列表里，让该列表失去意义 |
| 没说 `sequence` 的唯一性 | `uq_publications_asset_sequence` | 这才是**真正的**并发串行化点（不是 ETag，见 api docstring 第二节） |
| 没说六类的"范围"约束差异 | `ck_*_fact_requires_concrete_scope` | `FACT` 不许是 `GLOBAL`。一个全局事实在下游会被不加区分地写进任何产品的文案 |
| 没说 `GLOBAL` 能不能带限定列 | `ck_*_scope_global_has_no_qualifier` | "全局"却带着 `product_id`，说明它其实只对一个产品有效 —— 那是 `PRODUCT`，不是 `GLOBAL` |
| 没说 `chunks` 是否可重建 | 明确**不加**不可变触发器 | 它是 (版本内容, 切块器版本) 决定的**物化结果**，可重算。加锁会让 WP21 无法实现"换模型不混向量" |
| 没说 `If-Match` 到底怎么处理 | 接收并校验、不强制（缺省放行）；已登记 | 协议写了它但语义不匹配（见 §1.6 风险 4） |

### 1.5 哪些功能现在不该做？

| 不做的事 | 归属 | 理由 |
|---|---|---|
| **`knowledge_chunks` 的生产**（切块 + embedding） | **WP21** | 本包**只建表**。切块粒度、overlap、embedding 模型选型与维度是一整套策略，不是标准模式 |
| **`POST /knowledge/searches` 语义检索** | **WP21** | 需要 embedding。协议 §9 共 10 行，本包做 9 行（第 8 行留给 WP21，已登记待定项） |
| **`proposals` 的产生**（AI 创建候选） | **WP23 / WP41** | 依赖反馈与实验数据，本包不生产。表建好、决策做完 |
| **`proposals` 的 `source_feedback_id` / `source_experiment_id` 外键** | 不在本包 | 那两张表属于后面的包，现在建 FK 会指向不存在的表 |
| **投影结果物化成只读列** | 后续 | 当前状态是算出来的（见 §1.6 风险 2）。物化是一处优化，不是本包验收要求 |
| **六类各自的专用接口**（如"按事实查"的专用端点） | 后续 | 协议只给了一个通用列表接口 + `category` 筛选。精确读取路径已在 repository 层备好，等 WP22 真要用再定接口形状 |

**判断法**（本项目通用）：按「**有没有设计空间**」划，不按「表在哪一章」划。
表定义完整就是标准模式 → 本包建；涉及一整套策略 → 留给它的包；
只有列名、真正消费者在后面 → **不建**（死表）。

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 后果 | 应对 |
|---|---|---|---|
| 1 | **发布不是原子操作** | 事件插了但 `active_version_id` 没切 → 投影算出"已发布但没生效"的幽灵态 | 锁 asset（`SELECT ... FOR UPDATE`）→ 校验 → 插事件 → 切列 → 写 Outbox，**同一事务**。测试层③用原生 SQL 绕过 ORM 验事件范围约束 |
| 2 | **状态判定有两个来源** | 写入侧返回 `ACTIVE`、读取侧读回 `INDEXING`（本包**实测踩到过**：写入侧写死 `index_ready=True`） | 收敛到唯一的 `_project_asset()`，`publish` 与 `asset_view` 都调它。测试层②有一条专门断言"发布返回的 `assetState` 等于紧接着读回的 `state`" |
| 3 | **`KNOWLEDGE` 节点与版本行失配**（OP-88） | 版本树里有节点但没有版本行（或反之）→ 跨包的版本注册机制读到孤立节点 | 6 个触发器，其中 2 个是 `DEFERRABLE` 一致性触发器。**活性测试成对**：该拦的拦 + **该过的过** |
| 4 | `If-Match` 语义不匹配 | 强制 428 会逼前端为"追加事件"先读一次 asset，而那个 ETag 描述的是**另一个对象**（`active_version_id`） | 接收并校验、不强制。真正的并发保护是 `sequence` 唯一约束 + 重试。已登记待定项 |
| 5 | **列表按 `state` 筛选无法下推 SQL** | 状态是投影算出来的，带筛选时需先取一批、投影、再过滤 → 深翻页时性能退化 | 本包接受（已登记待定项）。收口方向：把投影物化成只读列 |
| 6 | **`CREATE TRIGGER` 不幂等** | 测试夹具重复建表时第二遍报 `DuplicateObject`，整层测试红 | 夹具用幂等三步：`DROP TRIGGER IF EXISTS` → `CREATE OR REPLACE FUNCTION` → `CREATE TRIGGER` |
| 7 | **不可变表物理删不掉** | 探针残留无法清理，污染后续用例的"全表 0 行"判据 | 探针取判定用 `SET CONSTRAINTS ALL IMMEDIATE`（不 `commit`）；零残留判据用**与运行前基线差分** |
| 8 | **`entity_type` 取值跨包冲突** | 用错值会让别的包的节点被本包触发器拦下 | 严格用 `KNOWLEDGE`（本项目已按包划分：`BRIEF`=WP18 / `KNOWLEDGE`=WP20 / `BASELINE`=WP22 / `PROMPT`=WP23） |

### 1.7 数据结构、接口、前端、后端怎么拆？

**数据结构（5 表 / 53 列 / 30 CHECK / 15 FK / 11 显式索引 / 6 触发器）**

```
version_nodes (WP11 共用，本包不改结构，只加 1 个触发器)
   ↑ id                       ↑ id
knowledge_assets ──────→ knowledge_versions ──→ knowledge_chunks
   ↑ asset_id                (不可变)              (可重建，非不可变)
   ├── knowledge_publications (不可变，事件流)
   └── knowledge_proposals    (AI 候选)
```

**接口（9 个端点）**

| 方法 | 路径 | 成功码 | 权限 |
|---|---|---|---|
| GET | `/knowledge/assets` | 200 | 登录 |
| POST | `/knowledge/assets` | 201 | `KNOWLEDGE_MANAGE` |
| GET | `/knowledge/assets/{id}` | 200 | 登录 |
| POST | `/knowledge/assets/{id}/versions` | 201 | `KNOWLEDGE_MANAGE` |
| POST | `/knowledge/assets/{id}/publications` | 200 | `KNOWLEDGE_MANAGE` |
| GET | `/knowledge/assets/{id}/versions` | 200 | 登录 |
| GET | `/knowledge/assets/{id}/references` | 200 | 登录 + **项目可见性过滤** |
| GET | `/knowledge/proposals` | 200 | 登录 |
| POST | `/knowledge/proposals/{id}/decisions` | 200 | `KNOWLEDGE_MANAGE` |

**后端分层（本包 11 文件 / 约 5000 行）**

| 层 | 文件 | 职责 |
|---|---|---|
| 取值域 | `types.py` | 六类 category、scope、action、state、状态常量、值类型 |
| 规格 | `schema.py` | 六类 FieldSpec + 归一化 + 必填判据 + scope 违规判定 |
| 纯函数 | `projection.py` | 事件流 → 状态。**零 I/O，可独立单测** |
| 表 | `models.py` | 5 表 + 约束 + 索引 |
| 触发器 | `ddl.py` | 6 触发器 DDL + 幂等 + `consistency_items()` 供 downgrade |
| 存储 | `repository.py` | 只做访问，不做业务判定 |
| 业务 | `service.py` | 唯一对外入口；`_project_asset()` 是状态判定的唯一来源 |
| 端点 | `api.py` | 9 端点 + pydantic 请求/响应模型 |
| 接线 | `dependencies.py` / `__init__.py` | 依赖注入 + router 导出 |

**前端要处理的三种状态**：`DRAFT`（可加版本）、`ACTIVE`（生效中）、
`INDEXING`（**已生效、索引处理中** —— 这不是错误，是可显示的正常态，规格源 §277 明写）。
另外 `SUPERSEDED` / `ARCHIVED` 出现在版本级与资产级的历史视图里。

## 2. 阶段 2：方案设计

### 2.1 需求本质（一两句话）

**让"当前生效的是哪一版知识"成为一个由不可改事件流算出的、可追责的、且与检索索引解耦的事实。**

### 2.2 用户画像

- **主用户：运营**（每天都在用）——关心"这条知识现在是什么状态、改过几版、谁改的"。
  他不关心向量、不关心事件流，但他需要"归档了还能查"这件事真的成立。
- **次用户：下游代码**（WP21/22/26）——关心"给我一条按 `product_id` 精确取用的、
  当前生效的 `FACT`"。它要求读到的**永远是当前生效版本**，且不能因为索引延迟读到旧的。
- **边缘用户：管理者**——只在处理 AI 候选时出现（接受/驳回），但他是"不直接生效"
  这条规矩的**执行者**，因此他的决定必须落成可审计的列。

### 2.3 核心功能清单（MVP）

1. 五张表 + 完整约束（30 CHECK / 15 FK / 11 索引）
2. 六类结构化字段规格 + 校验（**"禁止无结构散文替代事实字段"**）
3. 建（草稿）/ 加版本 / 发布（4 个动作一个事务）
4. 状态投影（纯函数）+ 版本状态投影
5. 列表（筛选+游标分页）/ 详情 / 版本列表
6. 引用摘要（**受权限过滤**）
7. AI 候选列表 + 决策
8. 6 个触发器（含 OP-88 双向）
9. 四层测试（169 条）

### 2.4 待补充项及理由

见 §1.4 的表格（9 条疏漏及理由）。三条最实质的：
`schema_version`（规格演进的可追溯性）、`decision_reason` + `decided_at`（决策可审计）、
`ck_*_fact_requires_concrete_scope`（下游误用的结构性防护）。

### 2.5 砍掉清单

见 §1.5 的表格（6 项）。两条最实质的：
**切块与 embedding 全部留给 WP21**（本包只建表）、
**`POST /knowledge/searches` 留给 WP21**（登记为待定项）。

### 2.6 技术风险评估（含应对）

见 §1.6 的表格（8 条）。前三条是必须靠测试兜住的：
**发布原子性**、**状态判定单一来源**、**OP-88 双向一致性**。

## 3. 阶段 3：多版本方案

### 方案 V1 —— 五张表 + 基础 CRUD，发布只是"改一个列"（**否决**）

- **做什么**：建五张表，通 `GET /knowledge/assets`、`POST /knowledge/assets`、
  `GET /knowledge/assets/{id}`。发布 = `UPDATE knowledge_assets SET
  active_version_id = :new`。不建 `knowledge_publications` 表
  （或建了但没人写）。状态直接存在列上（`state varchar`）。
- **优点**：两天能完，接口立刻能联调，前端可以先做列表和详情。
- **缺点**：**验收原文「归档可追溯，生效版本与旧引用并存」两条都没落点**。
  - 「归档可追溯」：`UPDATE` 覆盖 `active_version_id` 之后，
    "上一版是什么、谁切的、什么时候切的"**全丢了** —— 唯一痕迹是
    `updated_at` 被刷新了，而它分不清"改了标题"和"发布了新版本"。
  - 「生效版本与旧引用并存」：没有事件流就无法回答"3 个月前那份内容
    当时引的是哪一版"。而"并存"这件事**不能事后补** —— 丢失的历史补不回来。
- **适合场景**：无。它把本包的核心验收项（版本与事件的语义）整块省掉了。
- **风险**：**最危险的一种交付** —— 表建了、端点通了、测试能绿，
  但两条验收项都没达成，且**数据一旦产生就无法补救**。
  这与 §1.3 里 V1 的问题同源：看起来完成了，实际上把不可逆的部分做错了。

### 方案 V2 —— 事件流齐，但一致性只在服务层校验（**不推荐**）

- **做什么**：五张表齐、发布事务齐（锁 → 校验 → 插事件 → 切列 → 写 Outbox）、
  状态投影齐。但六类字段规格、范围约束、事件范围一致性
  **全部只写在 `service.py` 的 `if` 里**。不建触发器、不加 CHECK。
- **优点**：实现直观，规则集中在 `service.py` 一处，改起来方便；
  错误信息天然可读（不必从 `sqlstate` 反推）。
- **缺点**：**"当前生效的是哪一版"退回成纪律要求**。绕过 service 的写入路径
  至少有四条：数据回填脚本、手工 SQL 修数据、将来某个批量导入端点、
  以及"某天有人重构 `publish` 时移动了那个判断的位置"。每一条都能写出
  "发布事件引用了别人的版本"这种数据，而**数据库不会拦**。
  更实质的是三条本包核心约束在服务层**判不了**：
  - **`FACT` 不许 GLOBAL**：需要一次跨表或跨字段的联合判断，
    而服务层的 `if` 只看到手头这个 draft。运营从 CSV 批量导入时最容易漏。
  - **事件引用的版本必须属于本 asset**：这不是"校验一个字段非空"，
    是校验"两个不同表的行之间的归属关系"。绕过 service 就没了。
  - **OP-88**（`KNOWLEDGE` 节点与版本行必须配对）：这是**跨包**的版本树
    不变量。WP11 的注册机制、WP22/WP23 的包都会写 `version_nodes`。
    只在 WP20 的 service 里判，等于对其它包的写入路径没有任何保护。
- **适合场景**：一次性脚本、无下游依赖的内部工具。
- **风险**：静默的数据污染。一颗"全局事实"会在 WP22 生成信息草案时
  被不加区分地当成对所有产品都成立 —— 而它已经写进发给客户的内容里了。

### 方案 V3 —— 约束/触发器全部沉到数据库层，状态由事件流投影，OP-88 双向闭合（**推荐**）

- **做什么**：
  1. **六类字段规格两层**：`schema.missing_required_fields()` 给可读的
     领域错误（测试能断言文案、能列出缺哪个字段）+ 数据库 CHECK
     管住绕过 service 的写入（`structured_payload` 必须非空对象、
     `ck_*_fact_requires_concrete_scope`）。两边同一判据。
  2. **范围与限定列双向**：`scope=PRODUCT` 必须有 `product_id`；
     `scope=GLOBAL` 不许带任何限定列；`scope=BRAND/PROJECT` 同理。
     六条 CHECK 互不重叠地覆盖"范围"—"限定列"的四个取值。
  3. **发布原子性**：锁 asset → 校验 → 插事件 → 切列 → 写 Outbox，
     **同一事务**。事件范围一致性由延迟触发器
     （`trg_knowledge_publications_asset_scope`）在提交时刻兜住。
  4. **状态单一来源**：`_project_asset()` 是唯一的状态判定函数，
     `publish`（写入侧）与 `asset_view`（读取侧）都调它。
     **这修掉了一个实测踩到的缺陷**：写入侧曾写死 `index_ready=True`，
     导致"发布返回 ACTIVE、紧接着读回 INDEXING"。
  5. **`INDEXING` 是一等状态**：规格源 §277 明写"索引尚未完成时知识状态
     显示『已生效／索引处理中』"。它是**可显示的正常态**，不是错误。
     判据 = 生效版本存在但 `knowledge_chunks` 无行。
  6. **OP-88 双向闭合**：
     - 正向：`trg_knowledge_versions_node_consistency` —— 版本行的 `id`
       必须有节点、节点必须是 `KNOWLEDGE`、`entity_id` 必须等于 `asset_id`。
     - 反向：`trg_version_nodes_knowledge_paired`（挂**共用表**
       `version_nodes`，`WHEN entity_type='KNOWLEDGE'`）—— 节点必须配对版本行。
     - 两处都 `DEFERRABLE INITIALLY DEFERRED`（插入顺序由版本注册机制
       与应用共同决定，不可猜）。
  7. **生效版本归属**：`trg_knowledge_assets_active_scope` 保证
     `active_version_id` 指向的版本确实属于本知识 —— 否则投影会算出
     "别人的版本是本知识的当前版本"。
  8. **不可变性按证据判据划分**：`knowledge_versions` 与
     `knowledge_publications` 不可变（它们是业务证据）；
     `knowledge_chunks` **不可变**（它是可重建的物化结果，
     加锁会让 WP21 无法实现"换模型不混向量"）。
  9. **候选不直接生效**：`knowledge_proposals` 的
     `PENDING ⇔ 无确认人` 双向 CHECK + `REJECTED` 必须带理由。
- **优点**：
  - 两条验收项各有**结构性保证**（不靠自觉、不靠测试覆盖运气）；
  - **跨包写入路径也受保护** —— OP-88 的两个触发器对任何写
    `version_nodes` 的代码生效，包括 WP22/WP23；
  - "全局事实"、"事件引用别人版本"、"生效版本张冠李戴"
    这三类**静默污染**在数据库层被拦，绕过 service 也进不去；
  - 状态判定只有一个来源，**写入侧与读取侧不可能不一致**
    （这条有专门的 HTTP 用例锁定）；
  - 延迟触发器让"插入顺序"不再是必须猜对的事 —— 这与 WP11 的
    版本注册机制（内部有 SAVEPOINT + 重试，不暴露节点行何时落库）兼容。
- **缺点**：不变量分散在三处（构造器/schema / CHECK / 触发器），
  改动时要同时想清楚"这条判据属于哪一层"；
  延迟触发器在事务提交时才报错，错误定位比即时 CHECK 稍难
  （应对：错误消息里带具体 `id` 与原因，见 DDL 草案 §5.1 的函数体）。
- **适合场景**：本项目（有下游依赖、有验收项、有不可逆的数据沉淀）。
- **风险**：**反向触发器挂在共用表 `version_nodes` 上**。
  若不做收窄，它会把别的包的合法中间态（尚未建 asset 的节点）判成
  "孤立节点"而拦下 —— 这是**本包实测推翻第一判断**的一处
  （详见 DDL 草案 §5.2）。应对：函数里加
  "`entity_id` 在 `knowledge_assets` 里存在时才要求配对"的前置判断，
  并写**成对**的活性测试（该拦的拦 + 该过的过）。

### 方案 V4 —— V3 之上再加：投影物化列 + 状态筛选下推 + 语义检索 + 影响分析（**不选**）

- **做什么**：把投影结果物化成 `knowledge_assets.state` 只读列
  （由事件写入时同步刷新），让 `state` 筛选能下推 SQL；
  接通 `POST /knowledge/searches`；版本变更时自动算出受影响的内容版本。
- **优点**：更接近"生产级"。列表按状态筛选在深翻页时不再退化；
  语义检索是协议 §9 的第 8 行，做了就更完整。
- **缺点**：
  - **物化列引入第二个状态来源** —— 而这正是本包 §1.6 风险 2 要消灭的东西。
    物化列必须靠触发器或应用同步维护，任何一处漏刷就产生
    "投影说 A、物化列说 B"。**本包为它付出的代价正是 V3 的核心优点**。
  - **语义检索需要 embedding**，而切块、模型选型、维度、HNSW、
    "换版不混向量"是 **WP21 的整包内容**。在这里做等于把 WP21 的核心
    设计在一个没有它的上下文的包里边做边定 —— 而它一旦定错，
    重做的是向量库。
  - **影响分析依赖完整的版本依赖图**，而本批只有 `BRIEF` 与
    `KNOWLEDGE` 两类实体落地，图是残缺的 → 算出的"影响"会**漏报**，
    而漏报比不报更危险（WP18 §3 已对同类问题给出过同样的判断）。
- **适合场景**：WP21 与 WP22 落地之后、有真实负载数据时。
- **风险**：现在做会在没有真实负载、没有完整依赖图的情况下把形状定死，
  且引入一个与投影竞争的状态来源。

### 另外两个被考虑但未列为方案的方向

| 方向 | 为什么不做 |
|---|---|
| **不建 `knowledge_publications`，在 `knowledge_versions` 上加 `is_active` 布尔** | 需求与数据结构 02 §12 都明写"**恢复通过新事件，不篡改旧状态历史**"。布尔列表达不了"这一版曾经生效过又被打回"的历史，也无法回答"谁在什么时候切的"。更实质的是：它会让"归档可追溯"退化成"看当前布尔值"，而**归档的价值恰恰在于它是历史** |
| **`knowledge_chunks` 也做不可变表** | 看起来更保守，实际是**错的**。`chunks` 是 (版本内容, 切块器版本, embedding 模型) 决定的物化结果，可重算。加锁会让 WP21 无法实现"换 embedding 模型时重切同一版本的块"，也就是无法实现规格源要求的"不混新旧向量"。**判据是"这行是不是一次业务的证据"，不是"这张表重不重要"** |

### 选择与理由

**选 V3**。理由与本项目前十三轮一致：**验收项与不变量必须落在结构上，不落在纪律上**。

两条验收原文逐条对照：

| 验收原文 | V3 的落点 |
|---|---|
| **归档可追溯** | 归档 = 追加一条 `ARCHIVE` 事件（不改旧版本、不删行）；`knowledge_publications` **不可变**；`ck_*_archived_implies_had_version` 保证只有生效过的知识能归档；恢复 = 追加 `RESTORE` 事件而不是改历史状态 |
| **生效版本与旧引用并存** | 版本**只追加**（`knowledge_versions` 不可变）；`active_version_id` 是**投影列**（由事件流算出，不是就地改写的状态）；`trg_knowledge_assets_active_scope` 保证它指向本知识的版本；`GET /knowledge/assets/{id}?versionId=` 提供**读任意历史版本**的路径 |

V1 的问题是**没有事件与版本语义**（两条验收项都没落点，且不可补救）；
V2 的问题是**把跨越两个表的归属关系交给纪律**（服务层判不了 OP-88 与事件范围）；
V4 的方向都对，但每一件都依赖本批不存在的上游，且物化列会**反噬 V3 的核心优点**
—— **显式登记而不是假装做了**。

## 4. 收口阶段：它真的这样运行吗

本节全部结论来自**实测**，不是设计意图的复述。运行环境：本机 PG（`rednote_verify_wp20`
为收口时新建的**干净库**，从 bootstrap 跑到 head；`rednote_test_wp20` 为分支测试库）。

### 4.1 落迁移：为什么必须换库验

收口第 2 步是把 DDL 草案落成 alembic 迁移。第一次尝试直接对分支测试库
`rednote_test_wp20` 跑 `alembic revision --autogenerate` —— **产出空迁移**
（`upgrade()` 与 `downgrade()` 都是 `pass`，日志无任何提示）。

**根因**：按接缝协议 §4.1，并行分支用模块级夹具 `create_all(tables=[...])`
在**同一个库**里建了自己那 5 张表。于是 autogenerate 比对 metadata 与库，
发现"表已在"→ 判无差异。**"建表这件事在库里已经发生过，但在迁移链里没有发生过"**
—— autogenerate 只比对终态，不关心终态是谁建的。

**处置**：只取 autogenerate 给出的 `revision` 与 `down_revision`，
`upgrade`/`downgrade` 按 DDL 草案手工写全；然后**新建 `rednote_verify_wp20` 空库**，
从零跑 `upgrade head`。登记 **ISS-70**。

> **判据：建表脚本的正确性只能在"什么都不存在"的起点上验。**
> 分支测试库已有所建的表，在那里跑 `upgrade head` 会"成功"而掩盖空迁移。

### 4.2 迁移双向可逆（干净库实测）

| 检查 | 结果 |
|---|---|
| `upgrade head`（空库，从 bootstrap 起） | ✅ 一次成功 |
| 建出的结构 | ✅ 5 表 / 53 列 / 30 CHECK / 2 UNIQUE / 15 FK / 11 显式索引 / **6 触发器** |
| 部分索引 `WHERE` 未退化 | ✅ `ix_knowledge_assets_fact_lookup` 的 `WHERE` 在 |
| 延迟外键 | ✅ 2 个（`condeferrable`） |
| `downgrade -1` | ✅ 成功 |
| **零残留**（本包对象） | ✅ 5 表 0 残留 / `trg_knowledge_*` 0 残留 / 挂共用表的 `trg_version_nodes_knowledge_paired` 0 残留 / `rednote_check_knowledge_*` 函数 0 残留 |
| **不误删**（别人的对象） | ✅ 共用函数 `rednote_reject_mutation` 存活 / WP18 的 4 个 `rednote_check_brief*` 存活 / `version_nodes` 表存活 |
| re-`upgrade head`（可重入） | ✅ 结构回到 30 CHECK / 6 触发器 |

**downgrade 归属判据**（本包实测的第三个不可混淆点）：
三类要分开 ——
① 挂**本包表**上、由**本包建**的触发器（5 个）→ 删；
② 被本包引用、由**别人建**的共用函数（`rednote_reject_mutation()`）→ **不删**；
③ 挂在**别人表**（WP11 的 `version_nodes`）上、但由**本包建**的触发器
（`trg_version_nodes_knowledge_paired`）→ **要删**。
`ddl.consistency_items()` 就是为第 ③ 类准备的（它只列本模块自己的函数与触发器）。

### 4.3 接 `main.py` 与契约导出

- `main.py` 补两处：import + `include_router(knowledge_router, prefix=resolved.api_prefix)`。
- `migrations/env.py` 补一行 models import（否则 autogenerate 看不到本包的表）。
- 契约重新导出（**一次覆盖 WP18 + WP20**）：**37 paths / 44 operations**，
  `--check` EXIT=0。

### 4.3.1 「库里有表」≠「迁移链记录过这些表」（ISS-74）

收口第 2 步在**新建干净库**上验通过后，第 6 步（在默认库跑全量）又暴露一处缺口：

```
$ (默认库 postgres) alembic upgrade head
psycopg.errors.DuplicateTable: relation "knowledge_assets" already exists
```

**根因**：默认库的 5 张表**早就存在**（分支期间 pytest 夹具 `create_all` 建的），
而 `alembic_version` 停在 WP18 的 `19441cc26ce9`。**「表的存在性」有两个来源** ——
测试夹具与迁移 —— 前者不推进版本记录，后者推进。
这与 ISS-70 是**同一根因的两面**：一面让 autogenerate 产出空迁移，
另一面让迁移执行必失败。

**最隐蔽的一点**：全量 pytest 在默认库上是**绿的**（夹具会 `create_all` 把缺的补上）
—— 这个缺口**测试永远发现不了**。

**处置**：先证明结构等价，再只推进版本记录。

| 步骤 | 命令/判据 | 结果 |
|---|---|---|
| ① 证明结构等价 | 导出两库全部列/约束/索引/触发器/函数的 DDL，`diff` | **57 行 0 差异** |
| ② 只推进版本记录 | `alembic stamp ebc05dfca16b`（**不执行任何 DDL**） | 表 5 / 触发器 5+1 / CHECK 30 / assets 99 行 —— **全部未变** |
| ③ 验幂等 | 再跑 `upgrade head` | 无操作、无报错 |

> **判据：同一个迁移必须在两种来源的库上都验** —— 干净库（表由迁移建）
> 与已有表库（表由夹具/回填建）。只验干净库会漏掉"表已存在"这一整类失败。
>
> **`stamp` 是"承认既成事实"的工具，不是修复工具。** 用它之前必须先证明
> "结构确实等价于目标版本"，否则 stamp 就是在**掩盖结构漂移** ——
> 而那种掩盖比报错危险得多。登记 **ISS-74**（MAJOR / CLOSED）。

### 4.4 跨包回归：两次抓到真问题

收口第 11 步是**复跑全部历史证据脚本**（wp10~wp20）。这一步**不是形式** ——
它在 WP18 收口时抓到 WP17 的证据失效（ISS-64），在本包收口时**又抓到 WP18 的证据失效**：

```
wp18-brief.log: CHECK FAIL 不可变触发器总数（5 原有 + 3 本包）: 10   ← 期望 8
```

而同一时刻 WP20 自己 53 条全绿、全量 pytest 1040 全绿 —— **没有任何一处真的坏了**。

**根因**：WP18 把"不可变触发器恰好 8 个"写成了等式判据。这个 8 是它当时的快照
（原有 5 + 本包 3），而本包合法新增了 2 个（`knowledge_versions` /
`knowledge_publications`）→ 变 10。**要守的不变量是"我建的 3 个还在、
保护没有被削弱"，却被写成了"全项目恰好 8 个"。**

**修法**：拆成两条 —— ① 本包那 3 个**逐个**断言（`== 3`，这才是真正要断言的）；
② 总数用 `>= MIN_IMMUTABLE_TOTAL`（要守的是"不少于"）。登记 **ISS-71**。

> **同类根因在本项目已现身五次**：ISS-44（"恰好停在某迁移版本"）、
> ISS-64（否定式判据写成全契约范围）、WP17 的解析表判定、WP12 的残留判定、
> 本条的等式基数。形态完全同源。
> **判据：历史证据只能断言"我建的还在"，不能断言"全项目恰好有 N 个"。**
> 且**只有复跑全部历史证据脚本能发现它** —— 单跑当轮永远是绿的。

### 4.7 一处需要留意的判据手感

**`knowledge_chunks` 刻意不是不可变表** —— 它是 (版本内容, 切块器版本,
embedding 模型) 决定的**可重建物化结果**。加锁会让 WP21 无法实现
"换 embedding 模型时重切同一版本的块"，即无法实现规格源要求的"不混新旧向量"。

**判据是"这行是不是一次业务的证据"，不是"这张表重不重要"。**
（对外看，`chunks` 比 `proposals` 重要得多，但不可变性判的是前者。）

## 5. 状态判据为什么必须单一来源（本包最实质的一处修复）

分支阶段实测到一个**写入侧与读取侧不一致**的缺陷：

```
publish(...)  → asset_state = "ACTIVE"
asset_view(...) → asset_state = "INDEXING"     ← 同一个 asset，紧接着读
```

**根因不是"哪一边算错了"，而是同一判据存在两处实现**：`publish` 里构造事件流时
硬编码 `index_ready=True`（意图是"刚发布完就是生效的"），而 `asset_view` 是按
`knowledge_chunks` 有没有行判断。知识刚发布、chunk 还没切（切块属 WP21），
读取侧算出的就是 `INDEXING`。

**修法**：抽出唯一投影函数 `_project_asset(repo, *, asset) -> (投影结果, chunk 数)`：

1. 先以 `index_ready=True` 投影一次 → 拿到**哪一版生效**（`active_version_id`）；
2. 按该版本的真实 chunk 数决定是否以 `index_ready=False` **重新投影**。

`publish`（写入侧）与 `asset_view`（读取侧）都调它。修完有一条 HTTP 用例专门锁定
"**写端点返回的状态 == 紧接着读回的状态**"。

> **判据：如果同一个事实在代码里有两处实现，那它们迟早会不一致**，
> 而症状是"写入返回 A、读取返回 B"这种最难查的形式（两边看起来都对）。
> 登记 **ISS-66**（MAJOR / CLOSED）。

另：`INDEXING` 是**一等状态**，不是错误。规格源 §277 明写"索引尚未完成时知识状态
显示『已生效／索引处理中』"。判据 = 生效版本存在但 `knowledge_chunks` 无行。

## 6. OP-88 在本包的闭合

OP-88（WP11 留的"延迟约束检查 `entity_type`/`entity_id` 与子表一致"）由 WP18 补上
`BRIEF` 那一半，**本包补上 `KNOWLEDGE` 那一半，两半对称**：

| 方向 | 触发器 | 判据 | 挂在哪 |
|---|---|---|---|
| 正向 | `trg_knowledge_versions_node_consistency` | 版本行的 `id` 必须有节点、节点必须是 `KNOWLEDGE`、`entity_id` 必须 == `asset_id` | `knowledge_versions` |
| 反向 | `trg_version_nodes_knowledge_paired` | `entity_type='KNOWLEDGE'` 的节点必须配对版本行 | **共用表 `version_nodes`** |

两处都 `DEFERRABLE INITIALLY DEFERRED`（插入顺序由版本注册机制与应用共同决定，
不可猜）。

**反向判据必须收窄** —— 这是本包实测推翻第一判断的地方：
WP11 的测试夹具把 `BRIEF` 当默认参数且不写 `briefs` 行，若不收窄，
WP11 整批测试会在提交时集体炸。收窄判据 = "`entity_id` 在 `knowledge_assets`
里**真实存在**时才要求配对"。

**活性验证必须成对**（该拦的拦 + **该过的过**）：一个永远 `RAISE` 的触发器
也能让"正向拦、反向拦"两条全绿。本包的证据脚本对两处都给了对照组。

## 9. 本包新增的铁律（值得沉淀）

1. **`include_router` 的 `prefix=` 必须与测试里 URL 字面量成对**。
   漏一边 → 整层静默 404，且报错形式是 `KeyError: 'data'`（拿到错误信封）
   而不是"路由不存在"，极难一眼看出。定位手法：跑一条用例**打印真实响应体**。
2. **临时补偿代码必须有退出机制**（"什么情况下它该消失"）。
   为收口前状态写的补挂逻辑，收口后要**自动失效**（探测 + 跳过），
   不能等收口方记得回来删。
3. **历史证据只能断言"我建的还在"**，不能断言"全项目恰好有 N 个"
   （同一根因第五次现身）。
4. **阈值型防线的阈值本身也要维护** —— 长期小于实测值就不是防线而是装饰。
5. **JSON 响应里的 id 是字符串**，跨 HTTP 边界的断言两侧必须同类型。
6. **测 CHECK 必须同事务先建外键目标行**，否则先撞 23503（测试假绿）。
7. **`knowledge_chunks` 刻意不是不可变表**（判据是"是不是业务的证据"）。
