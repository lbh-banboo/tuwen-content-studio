## 3. 数据库隔离（并行必需的硬条件）

两个分支**必须使用各自的独立测试库**，否则会互相污染（WP16 ISS-50 的同类问题：
一个分支造的数据被另一个分支的全局扫描捞走，产生偶发红）。

| 分支 | 测试库 DSN | 环境变量 |
|---|---|---|
| **A** | `rednote_test_wp18` | `REDNOTE_TEST_DATABASE_URL=postgresql+psycopg://rednote@localhost:5432/rednote_test_wp18` |
| **B** | `rednote_test_wp20` | `REDNOTE_TEST_DATABASE_URL=postgresql+psycopg://rednote@localhost:5432/rednote_test_wp20` |

**已验证的前提**：本机 PG（17.10 Homebrew）支持 `CREATE DATABASE`，且
`tests/conftest.py` 的 `_test_database_url()` 已经支持用 `REDNOTE_TEST_DATABASE_URL`
覆盖默认库 —— **无需改 conftest**。

建库命令（主 agent 已建好，分支只需使用）：

## 4. 迁移的并行协议（最容易出事的地方）

迁移是**唯一仲裁资源**：`migrations/versions/` 是一条单链，`down_revision` 必须
首尾相接。两个分支各生成一个迁移文件，会得到**两个都指向同一父节点**的分叉。

**协议**：分支**不生成迁移文件**，改为提交**DDL 草案**：

```
docs/m2/WP18-ddl-草案.py      # 分支 A 产出
docs/m2/WP20-ddl-草案.py      # 分支 B 产出
```

草案内容 = 一张建表清单，含：
- 表名、列名、类型、可空性、默认值
- 全部 `UniqueConstraint` / `CheckConstraint` / `Index`（含部分索引的 `WHERE`）
- 外键指向（**只指向已存在的表**；指向对方模块的表 = 越界，报告主 agent）
- 触发器需求（若有）

由**主 agent** 按以下顺序串行落成真迁移：

1. WP18 迁移（`down_revision = 55e35f7a4cb9`）
2. WP20 迁移（`down_revision = <WP18 的 revision>`）

每次 `autogenerate` 后必过 **G2 三件事**（删探针表 drop / 重写 downgrade / 补 postgresql 导入）。

### 4.1 分支的测试怎么建表（关键机制，别自己发明）

分支**不生成迁移文件**，但测试又必须有表。**不要**去改 `env.py` 或往
`migrations/versions/` 里放文件 —— 那会让另一个分支的 `alembic upgrade head`
撞上 "Multiple head revisions are present"（两个分支各一个头）。

**正确做法**：分支在自己的测试文件里，用一个 **module 级 fixture** 建**自己那几张表**。
本项目的既有模式是 `session_scope(_make_settings())` 自开 session（见
`tests/test_versions_wp11.py` 的 `_make_settings()` / `_create_user()`），
**没有现成的 `engine` fixture** —— 用 `get_engine(settings)` 拿：

```python
import pytest
from rednote.platform.base import Base
from rednote.platform.configuration import Settings
from rednote.platform.database import get_engine, reset_engines

def _make_settings() -> Settings:
    """与 tests/test_versions_wp11.py 同款：DSN 从环境变量取，缺省本机。"""
    import os
    dsn = os.environ.get(
        "REDNOTE_TEST_DATABASE_URL",
        "postgresql+psycopg://rednote@localhost:5432/postgres",
    ).strip()
    return Settings(database_url=dsn, environment="test")


@pytest.fixture(scope="module", autouse=True)
def _ensure_own_tables() -> None:
    """只建本模块的表 + 自己的触发器。

    为什么用 create_all 而不是迁移：
      · 迁移是共享单链，两个分支各生成一个会分叉（见 §4）；
      · create_all 只建 tables=[...] 里列出的表，不碰别人的；
      · FK 目标表（version_nodes / projects / users 等）已由迁移建好，
        create_all 只发 FK 约束、不会尝试创建被引用表。

    为什么要先 reset_engines()：conftest 的 _isolate_settings_cache 是
    autouse 的 function 级 fixture，module 级 fixture 拿到的 engine
    可能已被上一轮清掉 —— 重取一次最稳。
    """
    reset_engines()
    settings = _make_settings()
    engine = get_engine(settings)
    from rednote.modules.brief import models as _m  # noqa: F401  触发注册

    Base.metadata.create_all(engine, tables=[
        _m.Brief.__table__, _m.BriefDraft.__table__, _m.BriefVersion.__table__,
        _m.BriefClaim.__table__, _m.BriefIssue.__table__,
    ])

    # 不可变表的触发器：与迁移里用的是**同一份来源**（modules/<包>/ddl.py），
    # 这样主 agent 落迁移时直接引用它，不会出现两份不一致的 DDL。
    #
    # ⚠️ 必须先 DROP 再 CREATE —— **CREATE TRIGGER 不是幂等的**。
    #    本机实测：直接 CREATE 会报
    #    `DuplicateObject: trigger "trg_..." for relation "..." already exists`
    #    （迁移已建过，create_all 建表是幂等的但触发器不是）。
    from sqlalchemy import text
    from rednote.modules.brief import ddl as brief_ddl
    with engine.begin() as conn:
        # 元组形状（已核实 modules/parsing/ddl.py）：
        #   (表名, 函数 DDL, 触发器 DDL, 触发器 DROP, 函数 DROP)
        # 用前四个；最后一个（函数 DROP）是 downgrade 用的，**别在这里执行**。
        for _table, _func_ddl, _trigger_ddl, _drop_trigger, _drop_func in (
            brief_ddl.all_trigger_ddl()
        ):
            conn.execute(text(_drop_trigger))   # 幂等关键
            conn.execute(text(_func_ddl))
            conn.execute(text(_trigger_ddl))
    yield
```

> **已实测验证**（主 agent 在 `rednote_test_wp18` 上用 WP17 的等价结构跑过）：
> `create_all(tables=[...])` 幂等、不误建别人的表；
> `DROP → CREATE OR REPLACE FUNCTION → CREATE TRIGGER` 顺序幂等；
> 跑完 `pg_trigger` 里 5 个 `trg_*_immutable` 都在。

> **触发器 DDL 的形状**（已核实，别猜）：本项目既有实现是
> `all_trigger_ddl() -> list[tuple[str, str, str, str, str]]`，
> 五元组 = `(表名, 函数DDL, 触发器DDL, 触发器DROP, 函数DROP)`
> —— 见 `modules/parsing/ddl.py` 与 `modules/versions/ddl.py`。
> 底层函数在 `platform/immutability.py`：
> `immutable_trigger_ddl(table) -> (函数DDL, 触发器DDL, 触发器DROP, 函数DROP)`，
> `immutable_trigger_name(table) -> f"trg_{table}_immutable"`。
>
> **直接复用 `platform.immutability`**，不要自己写触发器 SQL ——
> 所有不可变表共用同一个函数 `rednote_reject_mutation()`，
> 自己写一份会在 downgrade 时撞 "cannot drop function ... because other objects
> depend on it"（WP11 踩过、WP16 差点再踩）。

**收尾**：分支跑完测试**不必删表**（自己的独立库，只有自己在用）。
主 agent 收口时把两个库都 `DROP DATABASE` 重建。

### 5.1 WP11 版本注册（`modules/versions/service.py`）

```python
def register_version(
    repo: VersionRepository,
    *,
    entity_type: str,                    # 受控取值，见下
    entity_id: uuid.UUID,
    payload: Mapping[str, Any],          # 会被 canonical_payload_hash 摘要
    project_id: uuid.UUID | None = None,
    created_by: uuid.UUID | None = None,
    schema_version: int = MIN_SCHEMA_VERSION,   # = 1
    revision_no: int | None = None,      # None = 追加到末尾（max+1）
) -> RegisteredVersion
```

**`entity_type` 受控取值**（`modules/versions/models.py` 的 `ENTITY_TYPES`，有 CHECK 兜底）：

| 常量 | 值 | 谁用 |
|---|---|---|
| `ENTITY_TYPE_BRIEF` | `"BRIEF"` | **WP18** |
| `ENTITY_TYPE_KNOWLEDGE` | `"KNOWLEDGE"` | **WP20** |
| `ENTITY_TYPE_BASELINE` | `"BASELINE"` | WP22（不在本批） |
| `ENTITY_TYPE_PROMPT` | `"PROMPT"` | WP23（不在本批） |
| `ENTITY_TYPE_PLAN` / `_CONTENT` / `_MEDIA` / `_REPORT` | 同名字符串 | 后续工作包 |

**关键语义（别猜，已实测）**：
- `revision_no=None` 时**不是幂等的**（OP-91）：一次超时重试会写出两个
  「内容摘要相同、修订号不同」的版本。需要幂等就显式传 `revision_no`。
- 同一修订号重复注册：摘要一致 → 返回既有节点 `created=False`；
  摘要不同 → 409 `INVALID_TRANSITION`。
- **子表 `id` 同时 FK `version_nodes.id`**，注册表与具体表**必须同一事务插入**
  （数据结构 02 §5）。
- **OP-88 的闭合点**：本批两个包都是"第一个领域版本表落地"，
  因此**延迟约束检查 `entity_type`/`entity_id` 与子表一致**这一项，
  由本批负责实现（原登记为「WP18 / WP29 落地时补」）。

### 5.2 WP17 解析片段读取（`modules/parsing/repository.py`）

```python
class ParseRepository:
    def list_segments(self, parse_run_id: uuid.UUID) -> list[SourceSegment]  # 按 segment_no 升序
    def get_run(self, run_id: uuid.UUID) -> ParseRun | None                  # populate_existing=True
    def latest_run_for_file(self, file_id: uuid.UUID) -> ParseRun | None
```

**下游必须显式处理 `state='PARTIAL'`** —— 它**不是** `SUCCEEDED` 的变体：

| state | 含义 | 下游该做什么 |
|---|---|---|
| `SUCCEEDED` | `parsed_units == total_units`，全部解析出 | 正常消费 |
| `PARTIAL` | `0 < parsed_units < total_units`，**有页没解出来** | **必须把缺失暴露出来**，不得当成完整输入 |
| `FAILED` | `total_units` 为 NULL / 0，或 `parsed_units == 0`，或有文件级错误 | 不得消费 |

`SourceSegment` 的定位字段（`position` JSONB）是**受控构造**，`kind` 决定必填字段；
`bbox` 已归一化到 0~1。**不要自己拼 position 字典**。

## 6. 分支必须遵守的铁律（G1~G7 + 本项目高频坑）

| # | 铁律 | 与本批的关系 |
|---|---|---|
| **G1** | 改已有文件前先盘点、先读再改 | 分支只写自己目录，天然规避大部分 |
| **G2** | autogenerate 后必查三件事 | **分支不生成迁移**，由主 agent 执行 |
| **G3** | localhost 调用显式 `NO_PROXY='*'` | 跑测试必用 |
| **G4** | 清理用 `find -delete` | 分支一般用不到 |
| **G5** | `follow_redirects=False` | 写 API 测试时 |
| **G6** | 测试准备数据自开 session 并 commit | 必用 |
| **G7** | `class X(BaseModel, Generic[T])` | 新增泛型响应模型时 |

**本项目高频坑（分支最容易踩的五条）**：

1. **`pytest` 不要再加 `-q`**（`addopts` 已有，叠加成 `-qq` 会把汇总行压掉而退出码仍为 0）
2. **JSONB 字面量一律 `cast(:pos as jsonb)`**（`text()` 把 `{"page":1}` 里的 `:1` 当绑定参数）
3. **裸 SQL 改状态后读回要 `populate_existing=True`**（identity map 里是陈旧副本）
4. **约束测试必须断言 `sqlstate`**（只 `pytest.raises` 无法区分"真的拦住了"与"因为别的原因报错"）
5. **不可变表的测试探针要"单事务 + SAVEPOINT + 整体 rollback"**（否则 commit 后删不掉）

**分支的完成定义**（主 agent 验收时逐条核）：
- 自己模块的测试**全绿**（在自己的独立库上）
- 无未使用导入、无零调用符号、**无"声明了但一行都没实现"的常量**（WP17 阶段 7 的新形态）
- `docs/m2/WP<NN>-*.md` 的 §1~§3 写完（8 问 + 疏漏补全 + 砍掉清单 + ≥4 套方案 + 推荐）
- `docs/m2/WP<NN>-ddl-草案.py` 提交（若本包建表）
- **明确报告**：哪些接口是你假设存在的、哪些地方你改了主意
