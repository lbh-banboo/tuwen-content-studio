### 0.3 一条**推翻前轮拍板**的实测结论（必读）

上一轮（WP20 收口时）对 OP-44 的拍板是：「**维度放 profile 表，列用无维度 `vector`**」。
**本包实测推翻了这个方案的可行性**：

```
postgres=# create table _p3 (v vector);
postgres=# create index on _p3 using hnsw (v vector_cosine_ops);
ERROR:  column does not have dimensions
```

**根因**：pgvector 的 HNSW 索引必须在**列声明处**知道维度，运行时维度不足以建索引。
这是类型系统的硬约束，不是配置问题。**"列无维度"与"要建 HNSW"不可兼得**。

实测了全部替代路径（pgvector 0.8.6 / PG 17.10）：

| 方案 | 建 HNSW | 多维度共存 | 查询命中索引 | 结论 |
|---|---|---|---|---|
| 无维度 `vector` 裸列 | ❌ `column does not have dimensions` | ✅ | — | **不可行** |
| 无维度 + **每 profile 部分索引** `WHERE profile_id=X` | ✅ | ✅ | ✅ `Index Scan` | **采用** |
| 无维度 + 表达式索引 `(v::vector(1024))` | ✅ | ✅ | ✅ `Index Scan` | 可行，但维度写死在表达式里 |
| 无维度 + 声明式分区（子表建索引） | ❌ 继承列仍无维度 | — | — | 不可行 |
| 固定维度 `vector(1024)` | ✅ | ❌ | ✅ | 简单，但换维度要 `ALTER` 列 + 重建全部索引 |

**老大已拍板：采用「无维度 + 每 profile 部分索引」。** 理由：它最贴 ADR-15
（ADR-15 明写「超出后**按 embedding profile 分区**」，这条是同一语义在索引层的落地），
且「换模型 = 新建 profile + 新建索引」与 ADR-15 的切换流程**逐字对应**。

### 0.4 第二条实测结论：**维度守卫拦不住同维度混用**

ADR-15 要求负向测试「尝试向旧 profile 索引空间写入新模型向量应被拒绝」。
实测发现**仅靠维度守卫会漏掉最危险的那一类**：

```
profile1 绑定 bge-m3@v1 / 1024 维
写入 bge-m3@v2 的 1024 维向量  →  通过（维度相同，守卫无感）
```

只有把 **`model_version` 一并纳入守卫**才拦得住（实测 `sqlstate=23514`）。
这正是 ADR-15 说的「混用的危害不是报错而是**静默劣化**」——
**维度相同的混用连报错都没有**，检索会返回语义无关的结果，表现为「AI 答非所问」。

**本包的设计结论**：守卫必须同时校验 **`model_version` 与 `dimensions` 两项**，
且负向测试要**两个方向都覆盖**（异维度混用 + 同维度混用）。

## 1. 阶段 1：需求追问（8 问）

### 1.1 这个需求真正要解决什么问题？

**一句话：让知识库从「一个能存能查的库」变成「一个能被模糊召回、且召回时不串品牌的库」。**

验收原文「**近似品牌案例不串事实**」——这句话的结构值得拆开看，
它把 WP21 的**全部工作**装进了一个**否定式**里：

| 分句 | 含义 | 为什么是本包的核心 |
|---|---|---|
| **近似品牌案例** | 检索要能召回**语义相近**的案例，而不是关键词匹配 | 这是 embedding 的存在理由。WP20 已提供**精确读取路径**（`ix_knowledge_assets_fact_lookup`，按 `product_id + category` 直取）—— 缺的正是**模糊召回** |
| **不串事实** | 召回结果**不能跨品牌** | 这是**范围过滤**的存在理由。而它是**否定式**：做不到不会报错，只会让 A 品牌的内容用上 B 品牌的事实 |

**为什么这句话是「本包」的验收，而不是 WP20 的**：WP20 已把范围**落成数据**
（`scope` 四值 + `SCOPE_REQUIRED_COLUMN` + `FACT` 必须有具体范围 + 反向 CHECK
`scope <> 'GLOBAL' OR 三个限定列全 NULL`）。但**数据层有范围 ≠ 检索时按范围过滤** ——
WP20 交付后，范围只是一组**没人读的列**。**让范围在召回路径上真正生效，是本包的工作。**

**反面：这个包不做「知识库问答」。** 没有 LLM 生成环节，没有 prompt 组装，
没有引用校验。本包交付的是**检索**（召回候选 chunk），不是**答案**。
按 `agent-craft` 的模式库：文档问答 = **Chaining（检索 → 重排 → 生成 → 引用校验）**，
而 WP21 只做 Chaining 的**第一环**。后续环节归 WP26（文案生成）与 WP30（自检）。

**为什么现在做（而不是等 M3）**：
三个已交付的包**都留了指向本包的坑**，且都已登记：

| 遗留 | 来源 | 内容 |
|---|---|---|
| **OP-146** | WP20 §1.5 | `POST /knowledge/searches` 未实现（协议 §9 共 10 行，WP20 做 9 行） |
| **OP-149** | WP20 §1.6 | `INDEXING` 状态的判据是「生效版本无 chunk 行」，而 **chunk 的生产者不存在** → **WP20 交付后所有已发布知识都停在 `INDEXING`** |
| **OP-154** | WP19 §2.4 | 研究文件的语义检索（WP19 的 `research-files` 是**列表**，不是**检索**） |

**OP-149 是本包最硬的约束**：它不是「缺个功能」，而是「**已交付的一个状态永远无法到达终态**」。
本包把 chunk 生产者接上，`INDEXING → ACTIVE` 这条路径才第一次真实存在。

> 它的代价在**下一次换模型**时才支付，而那时已经没人记得当初怎么建的索引。

### 1.3 最小 MVP 应包含哪些功能？

**MVP 的判据是验收原文「近似品牌案例不串事实」两个分句能各自闭环。**

| 验收词 | MVP 必须有的 | 落点 |
|---|---|---|
| **近似** | 语义检索要真的按**向量距离**排序 | `chunk_embeddings` + 每 profile 部分 HNSW 索引 |
| **品牌案例** | chunk 要能回指到**哪条知识、哪个品牌** | `knowledge_chunks` → `knowledge_versions` → `knowledge_assets` 的链（WP20 已建） |
| **不串事实** | 检索**必须**按 `scope` 过滤 | 见 §2 核心设计：范围谓词**下推到 SQL**，不是取回来再筛 |

**MVP 的具体功能清单**：

1. **两张表**：`embedding_profiles`（模型与维度的**绑定**，是「索引空间」的身份）+ `chunk_embeddings`（向量）
2. **一个纯函数切块器**：`chunk_text()` —— 由 (文本, 切块器版本) 决定，**可重算**，不碰数据库
3. **一个端点**：`POST /knowledge/searches`（协议 §9 第 8 行，**逐个对应，不多不少**）
4. **范围过滤**（本包的核心，不是附属）：`scope` 四值 → SQL 谓词的**唯一来源**派生
5. **混用守卫**（ADR-15 硬约束）：`model_version` + `dimensions` **双项**校验
6. **Outbox 消费者**：`knowledge.index_requested` → 切块 + 写向量；`knowledge.index_removed` → 删索引
   （**这一条闭合 OP-149**：`INDEXING → ACTIVE` 首次真实可达）

**不放进 MVP**（划界理由见 §2）：
- **真实 embedding 模型的调用** —— 见 §1.4 疏漏 #3：本机没有模型，OP-44 未定
- **重排（rerank）** —— `CAPABILITY_RERANK` 在 WP16 已定义，但本包只做召回
- **知识库问答（生成 + 引用校验）** —— 属 WP26/WP30
- **索引容量实测校准**（ADR-15 判据 1/4）—— 需要 200 万量级数据，本机不可能
- **HNSW 参数调优**（`m` / `ef_construction`）—— 需要真实负载

### 1.4 描述有哪些疏漏应当补充？理由？

原始描述只有一句：「切块 + embedding + 范围过滤 + 检索」。**至少 8 处疏漏**：

| # | 疏漏 | 为什么必须补 | 落点 |
|---|---|---|---|
| 1 | **切块粒度、overlap、切块器版本，一个都没定** | 「切块」两个字背后是一整套策略。不定义就会做出「按固定字数硬切」，而真实风险是**切断了事实的限定条件**——「续航 18 小时」与「（实验室条件下）」被切到两个 chunk，召回时只拿到前半句 | `chunking.py` 的纯函数 + `CHUNKER_VERSION` 常量；**切块器版本进 chunk 的判据**（重切时靠它判断要不要重算） |
| 2 | **`locator` 的形状是什么？** | WP20 只要求它是 `jsonb object`（`jsonb_typeof(locator) = 'object'`），**形状留给 WP21 决定**（`models.py` L491 原文：「形状由 WP21 的切块器决定」） | 定义 `locator = {start, end, unit, versionId}`；`unit` 区分「字符区间」与「结构化字段路径」（`structured_payload` 的切块没有字符位置） |
| 3 | **embedding 模型与维度（OP-44）未定，怎么办？** | 这是本包最大的外部依赖。若把维度写死成 1024 列类型，将来换 1536 维模型要 `ALTER` 列 + 重建全部索引 | **维度放 `embedding_profiles.dimensions` 列**（数据而非 schema）；`chunk_embeddings.embedding` 用**无维度 `vector`**；索引按 profile **分别建**（§0.3 实测） |
| 4 | **「范围过滤」的谓词从哪来？** | `scope` 四值已由 WP20 定义，但「什么范围对谁可见」的映射**没有任何地方定义过**。散写会产生「列表接口与检索接口各一套口径」 | `scope_filter.py` 的**唯一来源**派生：`scope_visibility_predicate(scope, subject)` 纯函数，检索与列表共用 |
| 5 | **「不串事实」是「不过滤就不行」还是「过滤了更好」？** | 若是后者，它会退化成一个「默认全返回」的实现，而**验收看起来是通过的**（因为没有断言能证明它过滤了） | 它必须是**硬约束**：范围谓词**下推到 SQL**；测试要断言「跨品牌的一条**确实不在结果里**」，且**反向验证**（去掉谓词后测试必须红） |
| 6 | **`POST /knowledge/searches` 的请求/响应形状？** | 协议 §9 第 8 行的**原文不可得**（§0.1）。不定义就无从实现 | 按 WP20 已实现的 9 个端点的既有形状推断（`data` + `meta` 信封、camelCase、分页用 `platform.pagination`）；**显式登记 OP-164 待原件复核** |
| 7 | **`INDEXING → ACTIVE` 谁来触发？（OP-149）** | WP20 的 `_enqueue_index_event` 已写 `knowledge.index_requested` 事件，但**没有消费者**。不接上，所有已发布知识永远停在 `INDEXING` | 本包实现该事件的消费者：切块 → 写 chunk → 写向量 → 状态自然转 `ACTIVE`（**因为 `ACTIVE` 的判据就是「有 chunk 行」**） |
| 8 | **换 embedding 模型时，旧向量怎么办？** | ADR-15 的硬约束：「换模型 / 换版本时，必须创建新的索引空间（新 profile），**禁止在旧索引空间中混入新模型产生的向量**」 | 守卫触发器（`model_version` + `dimensions` **双项**，§0.4 实测）；切换流程的 5 步在 `embedding_profiles.state` 上表达 |

**另有 2 处需要显式登记（不是疏漏，是外部依赖/空缺）**：

| # | 空缺 | 处置 |
|---|---|---|
| 9 | **真实 embedding 模型不可得** | 本机无模型服务（ADR-10 E-4：embedding 默认不出网）。本包用 WP16 既有的 **`StubAdapter`** 做**确定性替身**（同文本 → 同向量），使检索管线**可端到端验证**；真实模型接入登记为 **OP-165**，依赖 OP-44 与内网模型服务 |
| 10 | **ADR-15 判据 1/4（阈值校准、空间估算）需要 200 万量级数据** | 本机不可能构造。本包交付**度量口径**（按 profile 计数、容量查询）与**外推公式**；实测校准登记为 **OP-166**，待真实负载 |

### 1.5 哪些功能现在不该做？

| 不做 | 理由 |
|---|---|
| **真实 embedding 模型调用** | 模型未选型（OP-44）、本机无服务（ADR-10 E-4 默认不出网）。做出来是一个「连不上任何东西的适配器」 |
| **重排（rerank）** | `CAPABILITY_RERANK` 已定义，但重排是**召回之后的第二环**，本包只做第一环。且没有真实模型时重排无法验证 |
| **知识库问答（生成 + 引用校验）** | 属 WP26（文案生成）与 WP30（自检）。本包交付**检索**，不交付**答案** |
| **索引容量实测校准**（ADR-15 判据 1） | 需 200 万 chunk 真实数据。本机构造出来也测不出真实 IO 特征 |
| **HNSW 参数调优**（`m` / `ef_construction`） | 需真实查询负载。用默认值 + 登记待调 |
| **跨 profile 检索与结果合并** | ADR-15 明写「跨 profile 的检索需要应用层路由与结果合并逻辑（**若业务需要**）」。当前业务只按当前活跃 profile 检索 |
| **多模态 embedding（图片/视频）** | 规格源未提。知识是文本类（六类 category 全是文本） |
| **研究文件的语义检索**（OP-154） | 它需要把 `research_files` 也纳入切块 —— 那是**另一条数据链**（`file_objects` → `source_segments`）。本包先做**知识**这条链；OP-154 **保持 OPEN**，理由：两条链的切块源不同（知识是 `knowledge_versions.body`，研究是 `source_segments.text`），混在一个包会让切块器多一个分支而收益不明 |

### 1.6 这个系统有哪些技术风险？

| # | 风险 | 后果 | 应对 |
|---|---|---|---|
| 1 | **范围过滤退化成「取回来再筛」** | 逻辑上「过滤了」，但 HNSW 的 `limit k` 是**过滤前**取的 → 若同品牌只有 2 条而 `k=10`，会返回 8 条跨品牌的。**不报错，看起来正常** | 谓词**下推到 SQL 的 `WHERE`**（与部分索引的 `WHERE` 对齐）；测试断言「跨品牌的一条**确实不在**结果里」+ **反向验证**（去掉谓词必须红） |
| 2 | **同维度混用拦不住**（§0.4 实测） | 检索静默劣化（答非所问），**无任何错误信号** | 守卫**双项**校验（`model_version` + `dimensions`）；负向测试**两个方向** |
| 3 | **`chunk_embeddings` 与 `knowledge_chunks` 的生命周期不一致** | 重切块后旧向量仍在 → 检索召回**已不存在的 chunk**（或旧文本） | 向量表的 FK 指向 `chunk_id` 且 `ON DELETE CASCADE`；重切是「先删旧 chunk（级联删向量）再写新」 |
| 4 | **`embedding_profiles` 的 state 机缺失** | 「新 profile 就绪前旧 profile 仍可用」（ADR-15 切换流程第 3 步）无法表达 → 切换期检索中断 | `embedding_profiles.state` ∈ {ACTIVE, DEPRECATED}；检索**必须**指定 profile 或取 ACTIVE 的那个；切换期两个 profile 并存且都可用 |
| 5 | **`FACT` 类知识的召回被范围过滤过度收紧** | WP20 已保证 `FACT` 必须有具体范围（不允许 `GLOBAL`）→ 一条 `PRODUCT` 范围的事实只对**同产品**可见。若检索方传的 subject 缺 `productId`，该事实**永远召不回** | 检索请求**必须**携带 subject（`brandId`/`productId`/`projectId`）；缺字段时的行为要**显式**（本包：只召回 `GLOBAL`，并在响应里报告 `scopeFilterApplied`） |
| 6 | **历史证据的跨包影响** | 新增迁移推进 `alembic_version`；新增 HNSW 索引与触发器会改变全局计数 | 证据脚本**不用等式判据**（ISS-44/64/71/87 已现身**八次**）；本包自己的逐个断言，总数用 `>=` |
| 7 | **`vector` 类型在 autogenerate 里被渲染成 `NullType`** | G2 铁律已记录：`wp05_vec_probe.embedding` 被渲染成 `sa.NullType()`。本包新增 `vector` 列会**再次**触发 | 迁移**手工写全** `upgrade`/`downgrade`，从 autogenerate **只取 `revision` 与 `down_revision`**（ISS-70 同款处置） |
| 8 | **测试夹具 `create_all` 建不出 HNSW 索引** | 索引 DDL 在 `models.py` 的 `Index(..., postgresql_using="hnsw")` 里，`create_all` 会执行它，但**部分索引的 `WHERE` 与表达式**可能不被正确渲染 | 与触发器同款处置：索引 DDL 放 `ddl.py` 的 `all_index_ddl()`，测试夹具与迁移**同源**调用（G2 铁律 5） |
| 9 | **pgvector 未装时整个迁移失败** | `deploy/dev/initdb/01_init.sql` 已用 `DO $$ ... EXCEPTION` 包裹（WARNING 而非中断）。但**迁移里 `CREATE EXTENSION` 若失败会中断整条链** | 迁移**不建扩展**（扩展由 initdb 负责，已在 M0 处理）；迁移只建表与索引，并在文档写明「前置条件：pgvector 已装」 |
| 10 | **`INDEXING → ACTIVE` 的消费者与 WP20 的 `_enqueue_index_event` 不同事务** | 事件投递成功但消费失败 → 知识永远停在 `INDEXING`（**这正是 OP-149 的现状**） | 消费者要**幂等**（重复消费不产生重复 chunk —— `UQ(version_id, chunk_no)` 天然保证）；失败时事件留在 outbox 待重试（WP13 已有机制） |

## 2. 阶段 2：方案设计

### 2.1 需求本质

**这个包交付的不是「一个检索接口」，而是「三条不变量」。**

| 不变量 | 来源 | 为什么它是本质 |
|---|---|---|
| **不串事实** | 验收原文 | 它是**否定式**。否定式约束的特征是：**做不到不报错，只是有一个口子一直开着** —— 所以它必须有**数据库层与 SQL 层的兜底**，不能只靠 service 层的自觉 |
| **换版不混用** | ADR-15 硬约束 | 混用的代价**不在切换当天支付**。ADR-15 原文：「混用的危害不是报错而是**静默劣化**」—— 且 §0.4 实测证明**同维度混用连报错都没有** |
| **可重建** | WP20 划界 | `knowledge_chunks` 与 `chunk_embeddings` 都是「由 (版本内容, 切块器版本, embedding 模型) 决定的**物化结果**」。WP20 刻意**不给 chunk 加不可变触发器**，理由原文：「加锁会让 WP21 无法实现『换模型不混向量』」 |

由此推出本包的**设计重心不是功能数量，而是「防线的层次」**：

```
第 1 层  数据库 CHECK        —— FACT 必须有具体范围（WP20 已建）
第 2 层  数据库 CHECK        —— GLOBAL 不带任何限定列（WP20 已建）
第 3 层  数据库守卫触发器     —— profile 的 model_version + dimensions 双项（本包建）
第 4 层  部分 HNSW 索引       —— 每 profile 一个索引空间（本包建）
第 5 层  SQL 范围谓词         —— 下推到 WHERE，与索引 WHERE 对齐（本包建）
第 6 层  服务层断言           —— 检索结果逐条核对范围（本包建，防御性）
```

**六层里第 5 层是验收的落点，第 3 层是 ADR-15 的落点。** 两者都必须有**活性验证**
（试写 / 反向验证），而不是「我建了它就说明它生效」。

### 2.2 用户画像与使用场景

**主场景：WP26 生成内容时检索相关知识。**

```
输入：Brief（项目 X / 品牌 A / 产品 P）
     ↓
检索请求：{ query: "除湿机 静音 卧室", subject: {brandId: A, productId: P, projectId: X},
            category: ["FACT", "SCENE"], limit: 8 }
     ↓
范围过滤：GLOBAL 的全部可见；BRAND=A 的可见；PRODUCT=P 的可见；PROJECT=X 的可见
         其余（BRAND=B / PRODUCT=Q / PROJECT=Y）**一条都不返回**
     ↓
输出：8 条 chunk + 各自的来源（assetId / versionId / chunkNo / 距离）
```

**次场景：AI 负责人换 embedding 模型。**

```
1. 建新 profile（新 model_version）→ state=ACTIVE，旧的转 DEPRECATED
2. 为全部生效版本重算向量（写进新 profile）
3. 检索按 profile 路由 —— 切换期两个 profile 都能查
4. 新 profile 质量确认后，把检索默认 profile 切到它
5. 旧 profile 保留到确认无需回滚
```

**关键：第 3 步「两个 profile 都能查」是 ADR-15 的明文要求**，
而它要求 `chunk_embeddings` **同时容纳两个 profile 的向量**（同一 chunk 两行）——
这正是 `UQ(chunk_id, profile_id)` 而非 `UQ(chunk_id)` 的理由。

### 2.3 核心设计决策

#### 决策 1：向量列用**无维度 `vector`** + **每 profile 部分索引**

**实测依据见 §0.3。** 取舍：

| 维度 | 无维度 + 部分索引（采用） | 固定维度 `vector(1024)` |
|---|---|---|
| 换维度模型 | **只加一个 profile + 一个索引** | `ALTER COLUMN TYPE` + 重建全部索引 |
| 与 ADR-15 的对应 | 「按 profile 分区」**逐字对应** | 无对应 |
| 索引数量 | 每 profile 一个 | 一个 |
| 新增 profile 的成本 | 一次 DDL（`CREATE INDEX ... WHERE profile_id=X`） | 零 |

**为什么新增 profile 的一次 DDL 是可接受的**：ADR-15 明写换模型是「一次真实的计算与时间成本」
（全量重算向量），一次 DDL 相对于全量重算是**可忽略**的。

#### 决策 2：混用守卫必须**双项**校验

**实测依据见 §0.4。** 守卫伪码：

```
BEFORE INSERT ON chunk_embeddings
  SELECT model_version, dimensions INTO p FROM embedding_profiles WHERE id = NEW.profile_id
  IF NEW.model_version <> p.model_version THEN RAISE (23514)
  IF vector_dims(NEW.embedding) <> p.dimensions THEN RAISE (23514)
```

**为什么要冗余存 `chunk_embeddings.model_version`**（它可以从 profile 推出）：
因为**守卫需要一个可比较的列**。若只比 profile 自己的值，`NEW` 里没有任何东西能证明
「这个向量是哪个模型产的」—— 守卫会退化成恒真（ISS-75 的同族错误：
**判据不能建立在数据库已保证的事上**）。冗余这一列是**为了让守卫有东西可比**。

#### 决策 3：范围谓词**下推到 SQL**，与部分索引的 `WHERE` 对齐

```python
def scope_visibility_predicate(subject: ScopeSubject) -> ColumnElement[bool]:
    """范围可见性的**唯一来源**。

    四值映射（与 WP20 的 SCOPE_REQUIRED_COLUMN 一一对应）：
      GLOBAL  → 恒真（不限品牌/产品/项目）
      BRAND   → asset.brand_id = subject.brand_id
      PRODUCT → asset.product_id = subject.product_id
      PROJECT → asset.project_id = subject.project_id
    """
```

**为什么必须下推**：HNSW 的 `LIMIT k` 是在**索引扫描时**取的。
若先取 `k` 条再在 Python 里筛，同品牌只有 2 条时 `k=8` 会返回 6 条跨品牌的 ——
**逻辑上「过滤了」，实际没过滤**。下推到 `WHERE` 后，HNSW 在**过滤后的集合**上取 `k`。

⚠️ **一个必须显式承认的取舍**：pgvector 的 HNSW 在 `WHERE` 存在时可能**退化为精确扫描**
（因为 HNSW 的近似搜索要求「无过滤的 k 近邻」）。这是**正确性优先于性能**的选择：
本规模（远未到 200 万）下精确扫描完全可接受，且**正确性没有替代品**。
已登记为待定项（**OP-167**），待 ADR-15 的容量实测时一并评估。

#### 决策 4：`FACT` 的范围收紧是**有意的**，且要显式报告

WP20 保证 `FACT` 不允许 `GLOBAL`。后果：一条 `PRODUCT` 范围的事实
**只对同产品可见**。若检索方没传 `productId`，这条事实**永远召不回**。

**处置**：请求**必须**携带 `subject`；缺字段时**只召回 `GLOBAL`**，
并在响应的 `meta` 里报告 `scopeFilterApplied` 与 `subject` ——
**让「为什么没召回」是可诊断的**，而不是静默返回空。

#### 决策 5：用**确定性替身**验证检索管线（OP-165）

本机无真实 embedding 模型。若不验证，本包交付的是「一段没跑过的代码」。

**处置**：复用 WP16 的 `StubAdapter` 模式，提供 `DeterministicEmbeddingStub`：
- 输入文本 → 稳定哈希 → 派生**单位向量**（同文本必同向量，不同文本距离可预测）
- 用它端到端验证：切块 → 写向量 → HNSW 检索 → 范围过滤 → 返回

**关键：替身不是 mock。** 它产出**真实的 `vector` 类型值**、走**真实的 HNSW 索引**、
执行**真实的 SQL**。唯一被替代的是「文本 → 向量」这一步的**数值来源**。
这样检索管线（索引、距离、排序、范围过滤）是**真的被测过的**。

## 3. 阶段 3：多版本方案（4 套 + 推荐）

### V1 最快上线版

| 项 | 内容 |
|---|---|
| **定位** | 1~2 天。把「能检索」这条链打通，其余全部后置 |
| **做法** | 固定维度 `vector(1024)` 单列 + 单一全局 HNSW 索引；切块按固定 500 字硬切；范围过滤**在 Python 里做**；embedding 用 stub |
| **优点** | 最快；代码量最小；HNSW 直接可用 |
| **缺点** | **范围过滤是假的**（取 k 条再筛，同品牌不足时返回跨品牌）；换维度模型要重建列；无混用守卫 |
| **适合场景** | 只做演示、不接真实数据 |
| **风险** | **验收原文「不串事实」直接不满足**。这是把「有口子」做成了「设计如此」 |

### V2 稳定可扩展版 ⭐ **推荐**

| 项 | 内容 |
|---|---|
| **定位** | 长期维护。三条不变量各有独立防线，全部可验证 |
| **做法** | 无维度 `vector` + **每 profile 部分 HNSW**；切块器纯函数 + 版本号；范围谓词**下推 SQL** 且与索引 `WHERE` 对齐；混用守卫**双项**；Outbox 消费者闭合 OP-149；embedding 用确定性替身 |
| **优点** | 与 ADR-15 **逐字对应**；换模型是「加 profile + 加索引」；六层防线各有活性验证；检索管线**端到端真跑**（真 `vector` 值 + 真 HNSW + 真 SQL） |
| **缺点** | 每新增 profile 一次 DDL；范围谓词下推可能让 HNSW 退化（OP-167）；工作量最大 |
| **适合场景** | 本项目当前阶段（M2，要接 M3 的 WP26/WP30） |
| **风险** | 主要风险在 OP-167（性能）与 OP-165（真实模型未接）—— 两者都不影响**正确性**，且都已登记 |

### V3 个人开发版

| 项 | 内容 |
|---|---|
| **定位** | 单人完成，效率优先 |
| **做法** | V2 的全部，但**砍掉**：Outbox 消费者（改为手动触发切块）、容量统计、`embedding_profiles.state` 切换流程；embedding 直接调本机模型 |
| **优点** | 少写约 30% 代码；不碰 outbox 接缝 |
| **缺点** | **OP-149 仍不闭合**（`INDEXING` 永远不到 `ACTIVE`）；换模型没有安全切换流程 |
| **适合场景** | 只有一个 profile、永不换模型 |
| **风险** | 「永不换模型」在本项目**已被 ADR-15 明确否定**（ADR-15 的存在前提就是会换版） |

### V4 完整生产级版

| 项 | 内容 |
|---|---|
| **定位** | 生产级，含真实模型与容量实测 |
| **做法** | V2 + 真实 embedding 适配器 + 200 万量级容量实测 + HNSW 参数调优 + 跨 profile 检索合并 + 重排 |
| **优点** | ADR-15 七条判据**全部**可判 |
| **缺点** | **本机做不到**：无模型（OP-44/OP-165）、无 200 万数据（OP-166）、无重排模型 |
| **适合场景** | M0 出口之后、有真实环境与负载时 |
| **风险** | 现在做等于把「测不了的东西」写进代码，而**未经验证的实现比明确未实现更危险**（技能原文） |

### 推荐：**V2**，理由

1. **只有 V2 同时满足三条不变量**。V1 直接违背验收原文；V3 违背 ADR-15 的前提；V4 现在做不到。
2. **V2 的每条防线都有活性验证的落点**。范围谓词 → 反向验证；混用守卫 → 双向负向测试；
   部分索引 → `pg_indexes.indexdef` 逐条核对 `WHERE`；切块器 → 纯函数单测。
3. **V2 的代价是可支付的**：每新增 profile 一次 DDL，相对于 ADR-15 明写的「全量重算向量」可忽略。
4. **V2 明确登记了做不到的部分**（OP-164~169），没有把「测不了」伪装成「已完成」——
   这正是 ISS-84（把「我提供了一把锁」写成「我已经把门锁上了」）的反面。

**请老大确认 V2。**

## 5. 阶段 5：Code Review（三遍法）

完整记录见 `evidence/m1/wp21-code-review.log`（**24 PASS / 0 FAIL / 24 checks**）。

### 5.1 一遍：结构（10 条判据全绿）

关键几条不是"文件存在"，而是**方向正确**：

| 判据 | 为什么它比"文件存在"强 |
|---|---|
| `scope_filter` **不 import ORM 模型** | 这条实测的是"纯函数层能不能被单测直接调用" —— 若它 import 了 `models`，纯函数单测就得起数据库 |

### 5.2 二遍：逐行（6 条判据全绿）

| 判据 | 实测 |
|---|---|
| 两条检索 SQL 的**值**全走绑定参数 | `:limit` / `:q` / `:profile_id`；f-string **只**用于别名与维度等非输入值 |
| `hnsw.ef_search` 用 `SET LOCAL` | 若用 `SET`，会话级设置会被**连接池复用** → 检索质量随请求顺序变化（一个不报错的错） |

### 5.3 三遍：边界与加固（8 条判据全绿）

最要紧的一条：**新增 scope 取值有自检守卫，且守卫在测试里被真实调用**

### 5.4 MAJOR 级发现一条（已修正措辞 + 登记）

**`embedding_service.search` 的 docstring 说"权限在 `search_api.py` 的依赖里判"，

## 7. 阶段 7：代码简化

完整记录见 `evidence/m1/wp21-simplify.log`。处理 **4 处**，刻意不改 **5 类**。

### 7.1 判据口径的一处修正（本包对 WP23 的改进）

WP23 用 AST 首尾行差（`end_lineno - lineno`）算函数长度，**把 docstring 与注释一起算进去**。
本包改为**逐行过滤**（去空行、`#` 注释行、docstring 块）= **真正在执行的语句行数**。

同一批 6 个函数的两种口径对比：

| 函数 | 逻辑行口径 | **代码行口径** | 差 |
|---|---|---|---|
| `chunk_text` | 78 | **56** | −22 |
| `mixing_guard_ddl` | 68 | **68** | 0 |
| `create_profile` | 59 | **50** | −9 |
| `ingest_version` | 56 | **48** | −8 |
| `handle_index_event` | 56 | **54** | −2 |
| `search` | 52 | **47** | −5 |

**这张表本身就是一条判据**：逻辑行口径报 6 个函数"超长"，代码行口径只有 3 个。
差额全是**解释性文本** —— 本项目 docstring 密度是刻意的（每条判据都要能回答
"为什么不那样做"）。**砍注释不会让代码变简单**，只会让下一个接手的人重新踩一遍。

### 7.2 处理的四处

| # | 位置 | 是什么 | 为什么它是缺陷而不只是啰嗦 |
|---|---|---|---|
| 1 | `search_api.search_knowledge` | 删除与服务层**重复的 mode 校验** | **不是"多一层防御"，是同一判据的两处实现**，且两处**已经分叉**：端点是 `sorted(SEARCH_MODES)` 的 Python 列表表示，服务层是 `SEARCH_MODE_LIST_SQL` 的 SQL 字面量表示。ISS-47 同族 |
| 2 | `indexing.handle_index_event` | `IndexingOutcome` 的"不处理"构造**三处逐字重复** → 抽 `_not_handled()` | 6 个字段**全部无默认值** → 漏填报 `TypeError`，但**填错不报**。三份里只要一份把 `handled` 写成 `True`（复制粘贴最易犯），症状是"结论说处理了、实际什么都没做"，而 outbox 会据此把事件标记为已消费 |
| 3 | `scope_filter.assert_scope_values_covered` | 让 `SCOPE_QUALIFIER_COLUMNS` 与自检函数**互钉** | 常量与函数内部各写一份"哪些列是限定列"，而自检**只校验函数那一份** → 常量写错**没有任何东西会发现**。ISS-78/84/85/86 同族 |

端点用例走完整链路，服务层拦下它同样返回 422，**看起来一样**。

### 7.4 「低引用」符号必须逐条人工核实（**不是按扫描结果删**）

本次扫描出 10 个"引用 ≤ 1"，核实结果是 **1 删 / 9 留**。留的 9 个里有 **3 类扫描器看不见的正当引用形态**：

| 形态 | 例子 |

| **装饰器注册** | `@router.post(...)` 引用 `search_knowledge` / `SEARCH_RESPONSES` —— 扫描器看不到装饰器这条边，**删了端点直接消失** |
| **同文件调用** | `search_api._envelope`、`chunking` 的三个私有小函数 |
| **框架持有** | FastAPI 的路由表 |

**新增观察（登记为 ISS-93）**：扫描器把 `EmbeddingProfileDraft` 报成"引用 1 次"，
而它**实际零引用** —— 那"1 次"是**定义行自身**（计数器的减一逻辑按 `(文件名, 行号)`
匹配，而 md 文档里提到该符号名的那一行既没被算进引用、也没被当作定义行排除）。
**结论：引用计数是启发式，不是判据**，凡以它为依据删代码必须补一次语义级复核。

## 9. 本包新增的铁律（值得沉淀）

1. **「契约在字符串层面对齐」不等于「在真实执行层面对齐」**（ISS-88）：
   把一段**编译出的 SQL 片段**嵌进另一段**手写 SQL** 时，两边的表名/别名必须**真库跑一次**才算验证过。
   字符串断言（`assert "a.brand_id" in sql`）在这里是**零信息量**的。
   动作：凡 `str(predicate.compile(...))` 交给别的 SQL 用的地方，补一条真库 `EXPLAIN` / 执行判据。

2. **顺序敏感的代码，串行测试等价性会让错误实现完全隐身**（ISS-89）：
   凡 docstring / 注释里出现"顺序很重要""必须先 X 再 Y"，就配一条**断言调用顺序**
   的测试（记录替身被调用的序列），并做反向验证。
   **这类缺陷没有别的发现途径** —— 它不报错、结果一样、只看终态一辈子也看不出来。
   （同族：ADR-15 的"换版不混用"，代价要到**下一次换模型**才支付）

3. **写「查询计划命中某索引」这类判据前先回答两问**（ISS-90）：
   （a）**数据量够不够让优化器真的需要索引？** 不够时它选 Seq Scan 是**正确行为**，
   判据会把正确行为判成失败；（b）**我有没有用 `enable_*` 削弱条件？**
   削出来的计划不构成证据。
   另外：**凡是「命中 X」类正判据都要配一条负判据**（改一处让它本该不命中），
   否则恒真的正判据无人能发现。附带：造数据量要有**阈值实测**（本包 2000 行 = 实测阈值 1000 的一倍余量）。

4. **证据脚本自己清理前置，就必须自己准备前置**（ISS-91）：
   否则它**只能跑一次** —— 而"只能跑一次"在第一次跑时完全看不出来。
   动作：写完证据脚本**连跑两次**，这是最便宜的暴露方式。

5. **「全局扫描 + 默认 limit + 断言我造的那条在里面」这根因已第 4 次现身**（ISS-92）：
   修跨包污染**必须把源头在每个包各过一遍**，不是只修报红的那个包。
   两个变体：① 失败可能是 **flaky** 而非稳定红 —— "第二次跑绿了"不等于修好了；
   ② 断言"全局计数 == 0"的用例必须**先清场**，与"调用处传大 limit"是**两件不同的事**。

6. **引用计数是启发式，不是判据**（ISS-93）：
   它至少有三个盲区 —— 把定义行自身算进去、看不见装饰器注册的边、看不见同文件调用。
   凡以"零引用/低引用"为依据删代码，必须补一次**语义级复核**
   （逐个判断命中行的性质：定义 / 调用 / 装饰器 / 文档提及 / 同文件）。

7. **简化扫描器的判据口径必须是「代码行」而非「逻辑行」**（§7.1）：
   `end_lineno - lineno` 会把 docstring 与注释算进去 —— 本项目 docstring 密度高，
   于是 6 个函数被误报"超长"，实际只有 3 个。**砍注释不会让代码变简单。**

8. **本轮一致性最强的一条（本包六条 ISS 里有四条同源）**：
   **"两类实现各自都自洽"是最难抓的一类缺陷。**
   ISS-88（字符串对齐 vs 执行对齐）、ISS-89（串行等价）、ISS-90（判据区分的是统计状态）、
   ISS-93（计数器的减一逻辑）—— 四条都是"看起来有判据，实际判据在测别的东西"。
   这与判据纪律第 7 条（判据必须能区分两种实现）是同一条，
   但本包给出了**三种工程化的落地形态**：真库执行、断言调用序列、正负判据成对。

9. **设计稿里的符号名必须与落盘名同一次核对**（§8.6，本包自纠）：
   §1.7 的三个名字在落盘时两个改名、一个被删。
   **设计文档与代码之间没有任何机械对账** —— 动作：落盘后回头把设计稿的
   每个符号名 grep 一遍，找不到就改文档或删符号，**不许两边并存**。

10. **统计视图必须能从明细列反推，否则它只是"另一个手写副本"**（ISS-94/95）：
    登记册 §3.1（按责任方）与 §3.2（按时机）两张表都**只有人工写的数字** ——
    §3.1 的「条数」与自己的「编号」列都对不上（9 行里 5 行），§3.2 更声称
    "规则见 §3.2 脚本"而那个脚本**从未存在**。
    动作：凡"按某维度汇总"的表，**汇总列必须由明细列机械派生**，
    并配一条会 FAIL 的核对；`合计相等` 不算 —— 它掩盖行间互借，
    逐行核对才算。兜底桶必须是**白名单**，且"未归类"要能判 FAIL，
    否则新增取值静默消失而合计那行照样自洽。
    **强度判断**：ISS-95 比 ISS-94 更严重 —— 它不只是没防线，
    还**写了一句话声称自己有防线**，把"没有"包装成"可复核"。
