## 2. 演练一：备份恢复（④）

判据：`tools/quality/check_backup_restore_drill.py` · `EXPECTED_CHECKS = 21`（静态 1 + 动态 14 + 队列 6）

> ⚠️ 21 条里的最后 6 条（`queue:*`）是 2026-10-08 补的 —— 原 15 条在队列表上
> 犯了一个恒真式缺陷，见 §2.6。

### 2.1 判据形状 —— 两库都从零点建，逐项比相等

```
库 A（源）：  createdb → CREATE EXTENSION vector → alembic upgrade head
              → 造种子数据（SEED_USERS / SEED_VERSION_NODES）
              → pg_dump -Fc --no-owner --no-acl（含 manifest：指纹 / 行数 / 摘要 / sha256）
库 B（目标）：createdb → CREATE EXTENSION vector → pg_restore
        ↓
三重比对：① 结构指纹（6 类对象）② 行数（逐表）③ 业务摘要（payload_hash 集合）
        ↓
注入破坏反向验证：删一个触发器 → 指纹必须变；删一行 → 行数必须变
```

**为什么必须造种子数据**：空库对账是 `0 == 0`，恒真（ISS-115）。不造数据的话
这条判据永远绿而毫无信息 —— 正是 ISS-110 骂的那种"绿灯"。

**指纹覆盖 6 类对象**（`backup_pg.py::FINGERPRINT_CLASSES`）：表 / 列 / 约束 / 索引 / 触发器 / 函数，
全部取自 `information_schema` 与 `pg_catalog`，**不读模型代码** —— 比的是"库里实际有什么"，
不是"我们认为库里该有什么"。类别数另有判据单独断言（铁律 14：少比一类会静默发生）。

### 2.4 ★ 第 1 次为什么红 —— 一次"判据自身的缺陷"

第 1 份 JSON 是**旧版实现**的产物，字段是 `fingerprint_equal: false`（整体一次比对，不等）。
第 2 份起字段变成 `object_sets_equal` / `definition_text_equal` / `normalizer_no_over_collapse`
（外加详细 `fingerprint` 对象）。这不是"备份后来变好了"，而是**判据换了比较口径**。

根因（`tools/ops/backup_pg.py` docstring §"为什么定义文本必须规范化"，2026-10-07 实测）：

```
pg_dump 把 CHECK 约束反解析成 SQL 文本 → pg_restore 再解析回来，
PG 解析器会把数组字面量的强制转换位置改写：

  源库：  actor_kind::text = ANY ((ARRAY['SERVICE'::varchar, ...])::text[])
  目标库：actor_kind::text = ANY (ARRAY[('SERVICE'::varchar)::text, ...])
```

两者**语义完全等价**（都是 text 对 text），但**文本不等** ⇒ 裸比 DDL 文本**必然假红**。
PG 的定义文本没有规范形式，这是"反解析 / 重解析的规范化迁移"，不是备份出错。

修法：把一层拆成两层，并对规范化本身的副作用上锁 ——

| 层 | 比什么 | 强度 |
|---|---|---|
| `objects_sha256` | 对象**身份三元组**（名字 + 归属 + 类型）排序后集合摘要 | **硬断言**（严格、稳定、无需规范化） |
| `defs_sha256` | 定义文本经 `normalize_def()`（去空白 → 去 `::类型` → 去冗余括号）后 | 软信号 + 反向验证 |

⚠️ 规范化**必然损失灵敏度**（`col::text='1'` 与 `col='1'` 会变同形）⇒ 另加
`normalizer_no_over_collapse`（断言去重后的定义数量**不下降**）+ 注入破坏反向验证。
**两者缺一，规范化就成了"把判据调绿"。**

> **这条演进本身就是本项目的核心教训**：判据报红的原因可能不是被测对象有问题，
> 而是**判据用错了比较口径**。同一形态在本仓已出现过多次（恒真式 ISS-115、
> 假红/假阴 ISS-137/198）。

### 2.5 结论（本机可验部分）

- ✅ `pg_dump -Fc` → `pg_restore` 能恢复出**逐项相等**的库：身份集合、规范化定义文本、
  行数、业务摘要四项全等（第 2~5 次，连续 4 次稳定复现）。
- ✅ 判据**不是恒真式**：自带注入破坏反向验证（删触发器 / 删行必须让对应项报红）。
- ⚠️ 首跑红（第 1 次）的归因已定位到判据口径，**不是备份缺陷**；证据保留，不抹除。
- ❌ **RTO 达标未证**（空库口径，见 §5）。

### 2.6 ★ 队列对账（异常矩阵第 ⑭ 项）—— 一次"判据在自己的表上犯了它自己写下的罪"

计划 §4.2 的本机三项验收（行数/digest 一致、`promtool check`、**队列对账脚本通过**）里，
队列对账是本节补齐的第三项。

#### 2.6.1 本仓的「队列」是什么 —— 先查清再动手

`jobs/dispatch.py` 的模块 docstring 写明：

> 本机没有 RabbitMQ（内网才有 3 节点）

⇒ 队列 = **PostgreSQL 表**，两层：

| 层 | 表 | 角色 |
|---|---|---|
| 事件层 | `outbox_events` | 事务性发件箱，投递前先落库 |
| 任务层 | `jobs` / `job_attempts` / `idempotency_records` | 任务、尝试、幂等 |

> ⚠️ **命名冲突**：本仓另有三处也叫"对账"，都不是这里 ——
> `billing/reconciliation.py`（费用与用量分叉）、`files/repository.py:179`（配额账面重算）、
> `research/service.py:469`（`reconciled` 字段）。本节指队列表。

#### 2.6.2 ★ 动手前先量出判据的真实缺口：`0 == 0`

`check_backup_restore_drill.py` 逐表比对全部 67 张表，但原 `drill_db.seed()` **只造
`users` 与 `version_nodes`** ⇒ 四张队列表全是 0 行 ⇒ 那四表的
`compare:row-counts-equal` 比的是 `0 == 0`。

**备份即使丢掉全部队列内容，恢复后仍会报「行数相等」。**

这正是该脚本 docstring 自己写下的 ISS-115（*"空库对账是 `0 == 0`，恒真"*）——
**判据在自己的队列表上犯了它自己写下的这条罪**。

行数相等本身也**极弱**：`UPDATE outbox_events SET published_at = now()` 不改行数，
但它正是「未投递事件被错标为已投递」⇒ 永久跳过 ⇒ **丢任务**。
⇒ 队列对账必须逐列比内容摘要，不能只比条数。

#### 2.6.3 落地：6 条新判据

判据条数 `15 → 21`（静态 1 + 动态 14 + 队列 6）：

| 判据 | 断言什么 | 挡住哪种失效 |
|---|---|---|
| `queue:seed-present-in-source` | 源库四张队列表都非空 | 回退到 `0 == 0` |
| `queue:states-match-model` | 种子覆盖 ORM 全部状态 | 半个恒真式（某态从未被验） |
| `queue:column-digests-equal` | 逐列摘要两库相等 | 内容变了但行数没变 |
| `queue:not-empty-after-restore` | 恢复后队列表非空 | 备份丢了队列内容 |
| `queue:publish-triad-present` | 投递三形态都在 | 只造一种形态应付判据 |
| `reverse:queue-digest-detects-content-change` | 注入 UPDATE 后摘要必须变 | 判据对内容变化不敏感 |

**逐列摘要的稳定算法**（`drill_db.queue_digest`）：
逐列点名（不 `select *`）→ 每列 `coalesce(expr::text, '\x00')`（**用 `\x00` 区分 NULL 与空串**）
→ 按行内容排序（不按 UUID）→ `sha256`。任何一格不同 ⇒ 摘要不同。

**状态覆盖从 ORM 真值派生**：`drill_db.py` 刻意不 import `rednote.*`，
所以判据用 `_read_model_states()` 真读 `JOB_STATES` / `ATTEMPT_STATES` / `IDEMPOTENCY_STATES`，
**读取失败直接抛，不 `except: return {}`** —— 否则 `set(model) - set(seed)` 恒为空，
`queue:states-match-model` 恒绿。

种子规模（实测读数）：jobs **9**（覆盖 9 态全）/ attempts **4**（覆盖 4 态全）/
outbox **6**（2 已投递 + 2 未投递 + 2 退避重试）/ idempotency **4**（`IN_PROGRESS` + `COMPLETED`
× 永久/七天过期两形态）。

#### 2.6.4 反向验证：6 条"声称自己有防线"的判据必须逐个报红

`tools/quality/collect_queue_reconcile_reverse_evidence.py` · **7/7 PASS**（证据
`evidence/m5/wp47-queue-reconcile-reverse.log`）：

| 编号 | 注入 | 报红的 pytest |
|---|---|---|
| R0 | 基线未变异 | `14 passed` |
| R1 | 种子摘掉一个 job 状态 | `test_queue_seed_covers_every_state_of_the_model` |
| R2 | 种子行数缩到不够走完状态 | `test_queue_seed_row_counts_cover_every_state` |
| R3 | `QUEUE_TABLES` 与 `QUEUE_DIGEST_COLUMNS` 脱钩 | `test_queue_digest_covers_every_declared_queue_table` |
| R4 | 列项从二元组退化成字符串 | `test_queue_digest_columns_are_declared_as_pairs` |
| R5 | 反向验证被改名 | `test_reverse_injection_checks_are_still_declared` |
| R6 | 磁盘逐字还原 | `14 passed`（回绿） |

两条设计要点：

- **锚点必须 `src.count(old) == 1`** —— 否则 R1~R5 全绿可能只是因为**一个都没改上**。
  「判据没报红」与「变异根本没生效」必须区分开。
- **注入用 UPDATE 而非 DELETE** —— DELETE 已由行数判据覆盖；队列这块必须用
  「行数不变但内容变化」才能证明逐列摘要比行数**多抓到了什么**。

> ★ 写这个脚本时踩到一次真坑：`pyproject.toml` 的 `addopts` 里**已有 `-q`**，
> CLI 再传一次叠加成 `-qq`，**把 `14 passed in 0.03s` 汇总行一起吞掉** ——
> 当时首版靠"过滤含 passed 的行"收集读数，收集到空字符串**却仍判 PASS**。
> 这与纪律第 11 条同形（「没东西可查」被当成「查过了没问题」）。
> 本仓 `tools/m1/collect_wp10_evidence.py::_pytest_result()` 早写过同一个坑的解法。
> ⇒ 三重防护：不传 `-q` + 优先抓汇总行 + **抓不到就 fail-fast**。

#### 2.6.5 结论

- ✅ 队列对账从 `0 == 0` 变成真对账：真库实测 `RESULT=PASS checks=21/21 failures=0`。
- ✅ 6 条新判据**逐个注入破坏都报红**（7/7），判据自己能证明在干活。
- ✅ 异常矩阵第 ⑭ 项「备份恢复队列对账」由「尚未测」转为**本机已验**。

## 3. 演练二：回滚（⑤⑥）

判据：`tools/quality/check_rollback_drill.py` · `EXPECTED_CHECKS = 24`（静态 3 + 动态 19 + 反向 2）

### 3.1 判据形状 —— 一个私有库上的六幕剧

```
[幕 1] 建到 head → 指纹 FA                                   ← 基准态
[幕 2] 注入破坏（DROP 一个索引）→ 指纹必须变 → 建回来 → 必须复原   ← 证明"指纹相等"是灵敏的（ISS-110）
[幕 3] 单步回滚 downgrade -1 → 版本落位、被回滚对象真的变了 → 再 upgrade → 指纹复原
[幕 4] 存量数据阻断回滚：插一条"上版本不允许"的行 → downgrade 必须失败
       且必须原子（版本不动 / 行不丢 / 约束不半改）→ 删行后必须能回
[幕 5] 升级失败注入（两种粒度）：
       ① 运行中**第一条**迁移失败 → 版本纹丝不动 + 它已建的对象整体回滚
       ② 运行中**最后一条**迁移失败 → 版本推进到上一条已提交的迁移 + 其对象存活
[幕 6] 反向验证：把 transaction_per_migration 翻成 False，同场景同注入，
       只差一行 ⇒ 落点**必须不同**（run 起点 vs 上一条已提交）
```

**为什么幕 5 必须两种粒度**（判据纪律第 4 条的应用）：只做 ① 的话，
`transaction_per_migration = True` 与 `False` 的观测**完全一样**（整个 run 只有一条迁移，
失败后版本都回起点）⇒ 那条判据测不出它想测的东西。必须让 run 里**两条迁移、后一条失败**才能区分：
`True` ⇒ 停在第一条（已提交，运维可"回到上一个已发布版本"）；`False` ⇒ 停在 run 起点（前一条的成果也丢）。

**覆盖范围一律由磁盘/系统表决定**（铁律 14）：回滚目标版本 = 解析 `migrations/versions/*.py`
的 `revision`/`down_revision` 建链；被回滚隔离的取值域 = 比 head 态与回退态
`pg_get_constraintdef` 的字面量集合之差；建表顺序 / 后置对象 = AST 解析目标迁移的
`op.create_table` / `op.drop_constraint`。**推导不出来就报 FAIL 并说明"无法构造注入"，
不允许退化成"跳过这一条"**（ISS-143）。

### 3.4 首条迁移失败耗时 vs 回滚预算

| 口径 | 实测 | 回滚预算 | 占比 |
|---|---|---|---|
| 首条迁移失败耗时最大 | **16.85 s** | 28800 s | **0.059 %** |
| 最小 | 1.56 s | 28800 s | 0.0054 % |

⚠️ 16.85 s 与 1.56 s 相差 **10.8 倍**，且三次的 `dump_seconds` 也出现过 0.143 ↔ 9.565 的波动
（§2.2 第 3、4 行）。这是**本机负载抖动**（并行会话 / 磁盘缓存），不是机制差异 ——
所以这些数字只能作"上界量级"参考，**不能当性能基线**。

### 3.5 结论（本机可验部分）

- ✅ 单步回滚、升级失败注入（两种粒度）、数据阻断回滚三条路径**全部按预期落位**。
- ✅ 幕 6 A/B 证明幕 5② **不是恒真式**（两臂落点确实不同）。
- ✅ `chain_length = 20`，说明 `ISS-79`（`rednote_reject_mutation()` 被触发器依赖导致
  `downgrade base` 失败）修复后整条链可逆 —— 该链的**全链往返**由另一条判据
  `check_migration_roundtrip.py`（门 3 同门）覆盖，两者刻意不重叠：
  前者答"整条链可逆吗"，本条答"生产升级失败时能不能退回"。
- ⚠️ 与备份恢复同款：预算断言在本机是弱判据。
- ❌ **未覆盖**（脚本 docstring 已显式登记为盲区，不做假保证）：
  ① 数据迁移的正确性（本仓迁移全是 DDL，无数据搬运）；
  ② head 之前的中间版本（只演练 head 与 head-1 两步）；
  ③ **"磁盘满 / 超时 / 被 kill" 类失败**——其语义（进程被杀 ⇒ 连接断开 ⇒ 服务器回滚当前语句）
     与"名字冲突 / 依赖缺失"这类确定性失败**不同**，本机无法稳定复现 ⇒ 内网待跑。
