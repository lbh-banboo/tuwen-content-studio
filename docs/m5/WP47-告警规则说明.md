## 0. 本包一句话结论

**计划 §4.2 的验收原文「告警规则 `promtool check` 通过」单独使用时完全不设防** ——
本机实测（2026-10-08）：

```
$ promtool check rules /tmp/mutated_rules.yml    # 规则里指标名被拼错
Checking /tmp/mutated_rules.yml
  SUCCESS: 6 rules found
EXIT=0
```

而 Prometheus 对"引用不存在的指标"**同样不报错**（表达式静默返回空向量），
告警永不触发、**没有任何日志提示**。

⇒ 本包交付的不是"6 条告警规则"，而是
**「一条能证明这些规则引用的指标真实存在」的判据**（10 条）+ **它自己的反向验证**（8 条变异）。

## 1. 现状：可抓的指标只有 5 个

WP47① 在 `/metrics` 暴露的指标（本次实测 `# TYPE` 行）：

| # | exposition 名 | 类型 | 来源 |
|---|---|---|---|
| 1 | `rednote_build_info` | gauge | WP47① 本仓代码（`platform/observability/metrics.py`） |
| 2 | `python_info` | gauge | `prometheus_client` 默认 REGISTRY |
| 3 | `python_gc_collections_total` | counter | 同上 |
| 4 | `python_gc_objects_collected_total` | counter | 同上 |
| 5 | `python_gc_objects_uncollectable_total` | counter | 同上 |

⚠️ **`ProcessCollector` / `PlatformCollector` 在 macOS 上不注册**
（`prometheus_client` 对不支持的平台主动禁用）⇒ **进程 CPU / 内存 / 文件句柄本机抓不到**。
这也是判据的集合必须**从真实输出派生**、不能写死名单的原因之一：
写死会以为"进程指标应该有"，然后整批规则判红或静默失效。

⚠️ **`collect()` 的名字 ≠ exposition 里的名字**（`metrics.py` docstring 已记录）：
`Counter("python_gc_collections_total")` 在 `collect()` 里是 `python_gc_collections`，
exposition 里才是 `python_gc_collections_total`。
⇒ **告警规则必须写 exposition 名**（带 `_total`）。照抄 `collect()` 的名字会让规则永不触发。
判据 D2 比对的正是 exposition 名（`# TYPE` 行），与 Prometheus 抓到的同一口径。

## 2. 计划列的五条业务告警：本轮**故意不写**

计划 §4.2 任务 ② 点名要"队列积压、任务失败率、预算异常、磁盘、备份失败"。
本轮**一条都没写**，理由是它们的埋点在代码里**还不存在**：

| 计划要求的告警 | 埋点现状 | 缺什么 |
|---|---|---|
| 队列积压 | **零埋点** | RabbitMQ 埋点（ADR-11 C2），代码里无任何 AMQP 指标 |
| 任务失败率 | **零埋点** | job 状态机埋点（WP13/14），代码里无成功率/失败计数 |
| 预算异常 | **零埋点** | 账本/预算埋点（M2），代码里无预算占用指标 |
| 磁盘 | **不适用** | 需 `node_exporter`，ADR-11 C6 组件清单里**没有列它** |
| 备份失败 | **零埋点** | `tools/ops/backup_pg.py` 当前无Prometheus 出口 |

**写这五条就是写五条永不触发的假告警** —— 违反本项目纪律
「声称有防线比没有防线更危险」（ISS-95）。
它们登记在 §5「待补清单」，随埋点落地**逐条增补**。

⚠️ **增补时只能新增、不能重命名**：改名会让既有告警静默失效（同 §0 的机制）。

## 3. 本轮实际交付的 6 条告警（全部基于真实可抓的指标）

| 组 | 告警名 | 表达式要点 | severity | 阈值来源 |
|---|---|---|---|---|
| 抓取 | `RednoteApiDown` | `up{job="rednote-api"} == 0` for 2m | critical | ADR-11 C8 双实例 |
| 抓取 | `RednoteApiAllDown` | `sum(up{job="rednote-api"}) == 0` for 1m | emergency | 同上 |
| 构建 | `RednoteBuildInfoMissing` | `absent(rednote_build_info)` for 5m | warning | 无阈值，纯存在性 |
| 构建 | `RednoteVersionSkew` | `count(count by (version) (rednote_build_info)) > 1` for 10m | warning | ADR-11 C8 要求双实例一致 |
| 运行时 | `RednoteGcUncollectableHigh` | `python_gc_objects_uncollectable_total > 1000` for 5m | warning | ⚠️ **工程判断值，待内网校准** |
| 运行时 | `RednoteGcCollectionBurst` | `rate(python_gc_collections_total[5m]) > 10` for 10m | warning | ⚠️ **工程判断值，待内网校准** |

**为什么只有这几条**：它们是当前 5 个真实指标 + Prometheus 内置 `up` 能支撑的**全部**有意义的规则。
按 ADR-11「单节点验证不得当生产证据」，这 6 条只能读作**"机制可用"**，不是"阈值正确"。

⚠️ 阈值 1000 / 10 **无 ADR 依据**（ADR-11 只给了 RPO ≤ 24h / RTO ≤ 8h），
是本轮显式给出的工程判断，列入 §5 待校准清单。

## 4. 判据设计：三层递进

| 层 | 判据 | 覆盖 | 缺陷 |
|---|---|---|---|
| 语法层 | **D1** `promtool check rules` | YAML 合法、PromQL 可解析 | ❌ **不校验指标是否存在**（§0 实测） |
| 语义层 | **D2** 悬空指标名对账 | 每个 `expr` 引用的名字 ∈ 真实输出 ∪ 内置 |补 D1 的洞 |
| 结构层 | D0/D3~D8 | 文件存在、配置可加载、白名单不腐烂、条数、字段齐备、路径不漂移 | — |

### 4.1 D2 为什么必须"从真实输出取集合"

若写死名单 `{"up","python_gc_*","rednote_build_info"}`：
新增埋点后规则引用了它、名单没跟上 ⇒ 判据或误报或放过。
⇒ 集合一律**运行时渲染一次真实 exposition 再取`# TYPE` 名**。

### 4.2 写这条判据时踩的三个坑（都是假红，方向相反）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `m`、`api`、`rednote` 被判成悬空指标 | `[5m]` 的单位、标签值 `{job="rednote-api"}` 被当标识符 | 引入 `_RANGE_SELECTOR` / `_LABEL_MATCHER`，**顺序不能反**（先 range 后标签） |
| 2 | `version` 被判成悬空指标 | `count by (version)` 的**无引号分组标签名** | 引入 `_GROUP_LABEL`，只抹`by/without/on/ignoring` 后的括号 |
| 3 | D4 报"5 处泄漏" | **D4 的前提就是错的**：原写法是"忽略名单里的词不得出现在规则里"，但 `sum`/`rate`/`by` **本来就该出现** | 改为**集合相交**检查（白名单不得与真实指标名相交，防"给真指标开后门"） |
| 4 | D5 报 4 个陌生键 | 我漏登记合法的**组级**键 `groups`/`name`/`interval`/`rules` | 补进白名单 |

⚠️ **判据自己的白名单不完整，也是一种假绿来源**：
它会让人习惯性忽略 D5 输出，真陌生键混进来也没人看（这与 D4 的教训同族）。

### 4.3 反向验证抓出的真缺陷：R④（规则文件被删 ⇒ D2 仍绿）

首版判据在规则文件整体缺失时：
D1~D8 里只有总`RESULT=FAIL`，而 **D2 报绿** —— 因为文件没了就没有告警可扫，
D2 的循环体**一次都没执行**，空集合"无悬空"。

⇒ **「没东西可查」被当成「查过了没问题」**，与 ISS-143「没跑与跑失败同形」同族。

**修法**：新增 **D0「规则文件必须存在且非空」并放在所有扫描之前**（fail-fast）；
同时给 D2 加断言 —— `exprs` 为空时**不得判绿**。

这是本包**唯一一条真缺陷**，其余 7 条变异首版即通过。

## 6. 复现方式

```bash
brew install prometheus# 3.15.0，提供 promtool

cd <repo>
promtool check rules deploy/monitoring/rules/*.yml     # => SUCCESS: 6 rules found
promtool check config deploy/monitoring/prometheus.yml  # => is valid prometheus config file

python tools/quality/check_alerting_rules.py# 10/10 PASS
python tools/quality/collect_alerting_rules_reverse_evidence.py  # 8/8 PASS
```

⚠️ 判据依赖 `promtool` 在 PATH。缺失时判据**报红**而非跳过 ——
一个"跑不了所以绿"的判据等于没有判据（同ISS-143）。
