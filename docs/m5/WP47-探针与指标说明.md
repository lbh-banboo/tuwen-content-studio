## 1. 阶段 1：需求追问（8 问）

### 1.1 这个需求真正要解决什么问题？

**表面需求**：加三个端点 + 让日志带上下文。

**本质需求（三层，逐层收窄）**：

| 层 | 问题 | 本轮回答 |
|---|---|---|
| L1 运维可用性 | 编排平台/网关怎么判断"这个实例该不该接流量"？ | 探针必须**语义正确**（liveness 不碰库、readiness 才碰库）—— 这一层**已解决**（WP06/WP07） |
| L2 可观测性 | 出故障时，运维**看什么**判断"哪里坏了"？ | 需要一个机器可读的指标出口（`/metrics`）—— 这一层**缺失**，是本轮主体 |
| L3 可追溯性 | 一条请求贯穿 API → Worker → DB，排障时怎么**串起整条链**？ | 日志必须每条带 `requestId`（已有单源，但**未接进日志**）—— 这一层**半缺** |

**关键判断：本需求的真实交付物不是"三个端点"，而是"可观测面的最小闭环"。**
端点是载体。若只建端点而探针语义错（例如 liveness 去连库），交付的是"能通过检查的假绿灯"
—— 那比没有端点更坏（ISS-110 的形态）。

### 1.2 核心用户是谁？

| 用户 | 关心什么 | 对设计的影响 |
|---|---|---|
| **编排平台 / 反向代理**（k8s kubelet、hyproxy health check） | `/healthz` 200 → 存活；`/readyz` 200 → 接流量 | 路径必须在**根**（惯例）、**必须快**（有超时）、**必须不依赖库**（liveness） |
| **Prometheus**（ADR-11 C6，仅运维面） | `/metrics` 返回合法 exposition 格式 | Content-Type 必须是 `text/plain; version=0.0.4`；指标名/标签必须合法 |
| **值班运维 / 排障人** | 日志里能 grep 出一次请求的完整轨迹 | 每条日志须带 `requestId`；**格式必须稳定**（不能因为加了字段就破坏既有日志解析） |
| **本包后续（WP47 ② 告警规则）** | 指标名要从现在就固定下来 | 指标名是**契约**（告警规则引用它）⇒ 命名要在本包定死，不能 WP47 ② 再改 |

**明确不是用户**：终端业务用户。ADR-11 C6 写明「**仅运维面**」⇒ 这三个路径**不对用户网段开放**，
也不应出现在给前端生成 SDK 的契约里（见 §2.2 决策 D3）。

### 1.3 最小 MVP 应包含哪些功能？

**MVP 判据：拿掉任何一项，"可观测面最小闭环"就断了。**

| # | MVP 项 | 拿掉会怎样 |
|---|---|---|
| M1 | `GET /healthz`（根路径，`include_in_schema=False`）→ 复用现有 liveness handler | 编排平台要写长路径 `/api/v1/health`；惯例不符，网关配置易错 |

| M4 | 集中式 logging 配置（`dictConfig`）+ 每条日志注入 `requestId` | **L3 层整层缺失**；`main.py:513` 继续是空承诺 |

### 1.4 描述有哪些疏漏应当补充？理由？

计划原文的任务 ① 只有一句话，以下 **7 处疏漏**必须补，否则交付物会缺关键面：

| # | 疏漏 | 理由（为什么必须补） |
|---|---|---|
| S1 | **没说别名路径是否入契约** | 入或不入，是**契约语义**的决策，且影响 71 paths 的计数与 CI 门。不写清楚 = 交付时两可 ⇒ 必然争议。ADR-11 C6「仅运维面」已给出答案方向 |
| S2 | **没说 `prometheus_client` 如何引入** | 本仓唯一权威是 `pyproject.toml` 的 `dependencies`，且有 AST 反向判据守着。不说 = 合并前报红 |
| S3 | **没说指标名/标签的命名口径** | 指标名是**跨包契约**（WP47 ② 告警规则引用它）。后改 = 告警规则集体失效，且**不报错** |
| S4 | **没说 `/metrics` 的暴露面控制** | `/metrics` 会泄露进程信息（版本、GC、连接数）。ADR-11 C6 说"仅运维面"，但代码层**没有任何访问控制** —— 若网关配置漏了，它就是公网可读。必须**显式登记**这个约束落到谁头上 |
| S5 | **没说日志格式是否变化** | 加字段有两条路（改动 `format` 字符串 vs 只塞 `extra`）。前者会让既有日志解析器全挂 ⇒ 必须**明确选后者** |
| S6 | **没说 `jobId`/`contentId` 怎么进日志** | 原文写"日志只带 requestId/jobId/contentId"，但 jobId/contentId **不是请求级常量**（一次请求可涉及多个 job/content），它们是**业务操作级**的。混进请求中间件是设计错误 —— 必须**显式说明为什么本轮不做**（§1.5 C3） |

## 2. 阶段 2：方案设计

### 2.1 需求本质说明

> **本包要交付的是"可观测面的最小闭环"，不是三个端点。**

闭环 = **探针（编排可判活）→ 指标（Prometheus 可抓）→ 日志（人能串链）** 三段。
三段中两段已有（探针语义、requestId 单源），一段缺失（`/metrics`），
而"已有"的部分**没有被接成闭环**（requestId 没进日志）。

**因此本包的工作量主要在"接线"，不在"造新东西"。** 这个判断直接决定了方案选择：
**凡是重写既有能力的方案，都是错的方向**（§3 会把它们列出来并说明为什么不选）。

### 2.2 五个设计决策（本包的设计空间全在这五处）

| # | 决策 | 取值 | 理由 | 反向验证方式 |
|---|---|---|---|---|
| **D1** | 别名路径的**实现位置** | 在 `main.py` 的 `create_app()` 里注册，**不新建模块** | 别名复用的 handler 属 `modules/health/`；在 `main.py` 注册可让"这是给编排平台的一个根路径入口"这件事在装配处一眼可见；且不动 `health/api.py`（既有 12 条测试的行为面零变化） | 若改动 `health/api.py` 的既有路由，`test_health.py` 的 `test_health_endpoint_is_not_under_bare_path`（L115-119，断言 `GET /health` 是 404）**必须仍绿** |
| **D2** | `/metrics` 的实现位置 | 新建 `platform/observability/metrics.py`（**platform 层**，不是 module） | 它**没有业务实体**、被所有模块共享、且将来 WP47 ② 要给它加业务指标 ⇒ 放 platform 才有正确归属（与 `pagination.py` / `errors.py` 同级） | 若放在 `modules/health/`，WP47 ② 加业务指标时会出现"业务模块 import health 模块"的倒挂依赖 |
| **D3** | 新路径**是否入契约** | **全部不入**（`include_in_schema=False`） | ① ADR-11 C6 明文「**仅运维面**」② 契约为前端生成 SDK；给前端一个 `metrics` 方法是荒谬的 ③ 保持 71 paths 不变 = **零破坏性变更风险** ④ 有先例：`/`（`main.py:421`）与 `/api/v1/dev/auth/login` 均 `include_in_schema=False` | 契约 `--check` 必须 **exit 0 且 paths 仍为 71**；新增一条测试断言 `/metrics` **不在** `app.openapi()["paths"]` 里 |
| **D4** | 日志注入方式 | **只加 `extra` 字段 + 在 `format` 末尾追加 `requestId` 占位**，**不改**既有格式结构 | 见 S5/R7：改格式 = 打断既有全部日志解析。追加占位是**加法**，既有 grep 仍能命中 | 断言配置前后 `logging` 的既有 handler 未被清空；断言输出的日志行**仍能被既有正则匹配**（模拟既有解析器） |
| **D5** | 指标注册的**幂等性** | 注册函数先查 registry 再注册；**不在模块顶层裸建指标** | `create_app()` 在测试中被反复调用（conftest 有 4 个 fixture 各建一次）；顶层裸建必然在第二次 import/rebuild 时炸 `Duplicated timeseries`（R6） | 专门一条测试：连续两次调用注册函数**不抛异常**；并断言 registry 里该指标**只有一个**实例 |

### 3.0 四套方案总览

| 方案 | 定位 | 探针 | `/metrics` | 日志 | 契约变更 | 人日 |
|---|---|---|---|---|---|---|
| **V1 最窄接线版** | 只接线，不造新东西 | 根路径别名复用 | 默认 registry 直出 | dictConfig + requestId Filter | 零 | 0.5 |

### 3.1 V1 最窄接线版

**做法**：在 `main.py` `create_app()` 内注册三个根路径路由，handler 直接复用
`modules/health/api.py` 的两个函数 + `platform/observability/metrics.py` 的一个函数；
日志配置放 `platform/observability/logging_config.py`，`dictConfig` + 一个 `RequestIdFilter`。

| 维度 | 评价 |
|---|---|
| **优点** | ① 改动面最小（新增 2 文件 + 改 `main.py`/`pyproject.toml`）② 既有 12 条测试**零影响**③ 契约零变更 ④ 与"本包工作量在接线"的判断一致 ⑤ 最容易做**反向验证**（每处改动都能被注入破坏） |
| **缺点** | ① 指标只有 Python 默认那几个（`python_info` + GC），**业务价值低** —— 但业务指标本就属 ② ② 根路径别名写在 `main.py` 会让该文件继续变长（已 511 行） |
| **适合场景** | 当前 —— 阶段目标是"骨架 + 接线 + 判据"，业务指标留给 ② |
| **风险** | 低 |

### 3.2 V2 独立运维模块版

**做法**：新建 `modules/ops/`（含 `api.py` / `metrics.py` / `logging_config.py`），
探针别名与 `/metrics` 都在此模块；独立 `CollectorRegistry`（不用默认 registry），
并自建一组 `rednote_build_info` 之类的元信息指标。

| 维度 | 评价 |
|---|---|
| **优点** | ① 运维面与业务面在**目录结构**上分开，符合 ADR-11 C6 的"仅运维面"② 独立 registry 可与默认 registry 隔离，避免第三方库的指标混进来 |
| **缺点** | ① **归属错误**：`modules/` 在本仓语义是"业务竖切片"（每个模块有自己的表/服务/端点），而探针与指标**没有业务实体、没有表**（对照：`modules/health/` 之所以在 `modules/` 下，是因为它是 WP06/WP07 的"最窄可跑通链路"**竖切片**，是本仓第一个模块）。为运维面新造一个"没有实体的 module"会破坏 `modules/` 的语义 ② 独立 registry 的代价：`prometheus_client` 的**自动进程指标**（GC/process）默认注册在 `REGISTRY`，用独立 registry 就得**手工搬**，否则 `/metrics` 连内存都不报 ③ `platform/observability/` 才是与 `pagination.py`/`errors.py` 同级的正确归属 |
| **适合场景** | 若将来运维面真的膨胀到需要自己的服务层/配置（目前没有） |
| **风险** | 中（目录语义漂移，且是本仓**结构惯例**层面的漂移，reviewer 容易漏） |

### 3.3 V3 业务前缀入契约版

**做法**：`/api/v1/healthz`、`/api/v1/readyz`、`/api/v1/metrics` 三条**全部写进契约**，
与既有 71 paths 并列。

| 维度 | 评价 |
|---|---|
| **优点** | ① 探针路径可被工具（swagger-ui、契约 diff）读到 ② 与既有 `/api/v1/health` 风格统一 |
| **缺点** | ① **与 ADR-11 C6 直接冲突**（「仅运维面」的东西进了对外的产品契约）② `/api/v1/metrics` 会被前端 SDK 生成器产出 `getMetricsApiV1MetricsGet()` 之类的**给前端看的方法**，语义误导 ③ 契约从 71 → 74 paths，**属对外可观测的变更**（虽非破坏性，但需走契约评审）④ 最有价值的一点"可被工具读到"其实**不成立** —— 编排平台读的是 k8s 配置、Prometheus 读的是 scrape config，二者都不读 OpenAPI |
| **适合场景** | 若本系统把"运维面"也当作对外契约的一部分（当前 ADR 明确不是） |
| **风险** | 中（契约污染 + 与 ADR 冲突需解释） |

### 3.4 V4 完整可观测版

**做法**：V1 + OpenTelemetry（span/trace 注入日志与响应头）+ JSON 结构化日志 +
全部 5 类业务指标（队列积压/任务失败率/预算异常/磁盘/备份失败）+ Grafana 看板。

| 维度 | 评价 |
|---|---|
| **优点** | 一步到位，AC-30 的告警面全覆盖 |
| **缺点** | ① **越界**：业务指标是计划 §4.2 任务 ② 的范围；OTel 属 ADR-11 S7（运维侧最后接）② 业务指标**依赖业务侧埋点**（读 MQ、读账本、读备份状态）—— 而队列/备份的执行体尚未交付（WP13 任务队列已交付，但备份状态在 ③ 里）③ JSON 日志会打断既有解析（C5）④ 单包人日 3+ 且需多人日的前置 |
| **适合场景** | M5 收尾统一做可观测面时（②+③ 都到位后） |
| **风险** | 高（范围失控是 M5 的最大风险 —— 计划 §6 风险 4「运维量低估」已预警） |

### 3.6 推荐：**V1 最窄接线版**（已请老大确认，三处设计空间全选推荐项）

**推荐理由（三条，按重要性）**：

1. **正确性优先于丰富度。** 本包唯一可能造成生产事故的风险是 R1（liveness 混进连库）。
   V1 的"复用既有 handler"从结构上让 R1 不可能发生 —— 不是"小心不写错"，
   而是"没有可写错的地方"。V2/V3 都重新实现了 handler，把 R1 从"结构上不可能"降级成"靠 review 保证"。
2. **归属正确。** `platform/observability/` 与 `errors.py`/`pagination.py` 同级 ——
   它是平台能力，不是业务竖切片。V2 的 `modules/ops/` 会破坏 `modules/` 的既有语义。
3. **与 ADR-11 C6 一致，且把契约风险降到零。** 71 paths 不变 = 零破坏性变更，
   也不需要契约评审；同时 `/metrics` 不进契约恰好阻止了"前端 SDK 里出现 metrics 方法"这个荒谬结果。

**若要偏离 V1，只有一种情况值得**：如果老大认为"业务指标现在就要有"
（那么应把 V4 拆成"V1 + 指标埋点"两包，而不是把 V4 整包做完 —— 见 §3.4 风险）。

**已确认记录**（2026-10-08，老大拍板）：

| 设计空间 | 选定 | 备选 |
|---|---|---|
| 探针路径名 | **新增根路径别名**（保留既有两条不动） | 只登记差异 / 别名入契约 / 迁移改名 |
| `/metrics` 形态 | **根路径 + 不入契约 + 引入 `prometheus_client`** | 零依赖手写 exposition / 入契约 / 本轮跳过 |
| 日志范围 | **补集中配置 + 接上悬空的 `get_request_id_for_logging`** | 再加 jobId/contentId / 只清理悬空函数 / 本轮不做 |

### 8.3 CR-2 判据：本包最贵的一条结论

**首版判据反向验证失败**（去掉锁仍绿）。查明**不是"Barrier 位置放错"，而是判据形态选错**：

> **确定性复现竞态**与**"有锁时不阻塞"在逻辑上互斥**。
> 对齐必然要求两线程**同时进入临界区**，而锁的定义就是**禁止**这件事 ——
> 有锁时 `Barrier` 永远凑不齐第二人，**判据自己把正确实现 deadlock 死**。

⇒ 并发类缺陷的判据**不能是"复现它"**，必须是**"断言那条不变量"**。
`threading.Lock.locked()` 是可查询的事实，不需要任何时序配合。

改后两条**成对**判据（缺一不可 —— **范围对 ≠ 互斥真**）：

| # | 判据 | 抓不到的坏实现 |
|---|---|---|
| 1 | 查/建/set 三步都在锁内（记账探针 + `lock.locked()`） | — |
| 2 | 锁真互斥（主线程持锁 ⇒ 工作线程被挡住，用 `Event` 而非 sleep） | 不阻塞的假锁（判据 1 会**绿**：假锁 `locked()` 仍为 True） |

**四变异反向验证**（坏实现按类别穷举，非只测一种），每条断言 4 件事：
退出码非 0 / 输出含**期望判据名** / 含**该判据自己的断言消息** / 还原后源码**逐字**一致。

    基线（未变异）                          GREEN ✔
    [M1] 完全去掉锁                          RED ✔ @主判据
    [M2] 锁范围只覆盖"建"                    RED ✔ @主判据
    [M3] 换成不阻塞的假锁                     RED ✔ @互斥判据
    [M4] "set" 移出锁外                      RED ✔ @主判据
    => 4/4 RED，"红的形状"逐条校验通过

M3 当场抓出**脚本自身**的缺陷：注入辅助类时把锚点先吃掉了，**变异根本没生效**
却被误当成"红了" ⇒ 纪律「先确认被判据读到的确实是被变异的那份文件」，**脚本自己也得守**。

原"两线程并发不抛异常"那条**保留但降级为"补充观测、非判据"**，
docstring 写明它为何无法保证复现。生产缺陷确实由它先发现 ——
但**"发现过" ≠ "守得住"**。

### 8.4 收口期撞上判据自身的第三次失效（ISS-206）

跑 `audit_consistency.py` 收口时，它报：

```
README 对「OP 条数」有互相矛盾的声明：[188, 193]
```

而 README 的真声明只有一处（`全部 196 条待定项`）。**188 不在任何声明行里。**

#### 188 是什么

是 README「问题记录」行里**引述 ISS-185 修复过程的那段文字**中的引文：

> ① `OP 条数` 的第二条 … **恒不命中**（README 从头到尾写「全部 188 条待定项」，星号位置不符…）

**登记 ISS-185 的过程本身，把被修的旧句式抄回了 README。**

#### 这是同一条正则的第三次失效

| 次 | 形态 | 判据当时输出 |
|---|---|---|
| ① | 死正则（ISS-185） | `声明 [188] / 实测 188` —— 看着正常 |
| ② | 误伤局部叙述（ISS-185） | 假红 `{8, 188}` |
| ③ | **误伤引文**（ISS-206） | 假红 `{188, 193}` |

三次都是「锚点不够紧」，而**收紧锚点有极强的工作方向**：
每收一次，报红就少一次。⇒ 这条判据最可能的演化路径是
**一路收到永不命中**，而那正是形态 ① ——
**"死"看起来和"过"完全一样**。

三次失效是同一递进：**裸词 → 加句式 → 加行首**。
每一级只能排除一批干扰；**只有最后一级能排除"引文"** ——
因为引文与声明的差异不在**词形**，在**位置**。

#### 处置：改工具，不改数字

引文是历史记录，**改它等于篡改史实**（与删证据文件同性质）。
⇒ 把 `ISS 条数` / `OP 条数` 的第一条来源正则收紧为：

```
^\|\s*`docs/待定项与问题登记册\.md`\s*\|[^\n]*?全部\s*(\d+)\s*条待定项
```

即「行首 + 登记表文件名 + 该行内出现计数句式」。前两级缺一不可：
只锚行首会连「问题记录」行的说明文字一起吃进来。

#### 配套反向验证（`tools/quality/collect_readme_decl_anchor_reverse_evidence.py`）

7 条变异。**R④ 是本脚本存在的核心理由**：

| # | 变异 | 期望 | 证明的失效面 |
|---|---|---|---|
| R0 | 副本基线 | 每条来源都活、每计数取值 = 单值 | 没绿在"没命中"上 |
| R① | 真声明 OP 数字改错 | 取值 `[193, 999]` ⇒ 报红 | 锚点**看得见**真声明行 |
| R② | 真声明 ISS 数字改错 | 取值 `[205, 777]` ⇒ 报红 | 同上，覆盖 ISS 那条来源 |
| R③ | 单元格内再塞同句式引文 | 仍 `[193]` ⇒ **不**报红 | ISS-206 形态复发必须挡得住 |
| R④ | **删掉真声明整行** | 第 1 条来源命中数 = 0 | **锚点没收窄成永不命中** |
| R⑤ | 还原保证 | 磁盘 README 逐字未变 | 变异只在内存副本上做 |
| R⑥ | 可重复性 | 连续两轮结果一致 | 变异没偷偷依赖迭代序 |

**R①~R③ 全绿而没有 R④，这套论证是不完整的** ——
「锚得对」与「锚得死」在真实工作区里表现**完全一样**（都是一组干净的单值）。

#### 写这个脚本时自己踩的三个坑

1. **R② 的红形状是假的**：token 写成 `" 条开发过程问题记录"`（带前导空格），
   `str.replace` 把分隔空格一起吃掉 ⇒ 造出 `205777` 这个不存在的数。
   判据确实报红了，但**报的是假红**。⇒ 断言从 `777 in got` 收紧为
   `got == [205, 777]`。与 CR-2 那条纪律同源：**不只查"报没报红"，
   还要查"红成什么形状"**。
2. **R⑥ 无限递归**：`run_cases()` 里调 `run_cases()` ⇒
   `RecursionError` 炸在 `Path.resolve`。改用 `_round` 参数控制深度。
3. **D1 判据当场报红（它是对的）**：脚本首版只 `print`，靠人手 `| tee` 落盘
   ⇒ `check_evidence_scope.py` 的 D1（"收进来的都是真证据脚本"）报红。
   一个不落盘的脚本只能靠人手出证据，而**人手恰恰是铁律 14 要消灭的东西**。
   改为 `EVIDENCE.write_text(...)` 自落盘后回绿。
