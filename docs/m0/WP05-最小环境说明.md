## 3. 未完成的部分（有明确原因，不是"大概可以"）

### 3.1 `--verify` 阶段尚未产出（本机环境阻塞，需人工终端配合）

按验收流程，写入后需重启 PostgreSQL 再跑 `--verify`。重启这一步在本机被**自动化执行环境**挡死，
四条路径全部失败（原始报错见 `WP05-smoke.log` [7]/[7b]/[7c]/[7d]/[7e] 节）：

| 路径 | 结果 |
|---|---|
| `brew services restart postgresql@17` | `Error: Operation not permitted @ apply2files - /Users/<user>/Library/LaunchAgents/homebrew.mxcl.postgresql@17.plist` —— 无法写 LaunchAgents |
| `pg_ctl -D /opt/homebrew/var/postgresql@17 start` | postgres 进程被拒 `unlink`/`rename`（`Operation not permitted`），checkpoint `PANIC` → 进入 crash recovery 循环 |
| `postgres -D /opt/homebrew/var/postgresql@17`（前台直启） | 同上，逐条 PANIC 于 `pg_logical/replorigin_checkpoint.tmp` |
| `launchctl bootstrap gui/$UID <plist>` | `Bootstrap failed: 5: Input/output error` |

**关键对照**：本机以 brew/launchd 方式启动的 postgres 在 `22:35:33` 做过一次**完全正常**的关闭
（`database system is shut down`，无任何 `Operation not permitted`），且此前已稳定运行三周。
→ 结论：该限制来自**自动化执行环境**（不排除本机安全软件/沙箱策略），**不是 PostgreSQL 或数据目录的问题**。

**已完成的安全处置**（避免反复 crash recovery 放大风险）：

- 已用 `kill -QUIT` 终止循环中的 postmaster，确认无 postgres 残留进程；
- 已把崩溃残留的 `postmaster.pid` 重命名为 `postmaster.pid.wp05-stale-*`，
  避免人工启动时撞 `FATAL: lock file "postmaster.pid" already exists`。

**待人工执行（在普通终端里，不要在自动化环境里做）**：

```bash
brew services start postgresql@17
# 或： /opt/homebrew/opt/postgresql@17/bin/pg_ctl -D /opt/homebrew/var/postgresql@17 -l /opt/homebrew/var/log/postgresql@17.log start
```

起来之后：

```bash
cd "/Users/<user>/内容运营AI Native/rednote-production"
/Users/<user>/.workbuddy/binaries/python/envs/default/bin/python \
  tools/m0/wp05_smoke/smoke.py --verify --backend fs \
  --report evidence/m0/WP05-smoke-verify.json 2>&1 | tee -a evidence/m0/WP05-smoke.log
```

> 预期：`--verify` 会取 `smoke_meta` 里 `created_at` 最新的一行（即 V3 那次写入），
> 读回本地对象并重算 SHA-256 与库中 `content_digest` 比对。若通过，则"重启后元数据与文件不丢"的
> **PG 腿**与**本地目录腿**成立；对象存储腿仍需内网 MinIO 重跑。
> **注意**：这次重启前 PG 经历了一次异常关闭（crash recovery），因此该次校验实际上还额外覆盖了
> "崩溃恢复后数据仍在"这一更强的情形 —— 但**必须以实际跑出的结果为准**，未跑出结果前本项记为「未完成」。

| **G0-21** | 备份小样可恢复（至少数据库 dump 恢复一次） | ① `docker exec rednote-dev-postgres pg_dump -U rednote -Fc rednote > /backup/rednote.dump`；② 在独立库/独立实例 `pg_restore`；③ 比对 `smoke_meta` 行数与 `content_digest` 一致；④ MinIO 侧补一次对象备份恢复小样 | dump/restore 命令与校验输出 |
| 附加 | 版本口径落地 | 确定 MinIO 生产 digest、Keycloak 具体补丁 tag，回写 `docker-compose.yml` 注释与 §5 版本表 | 更新后的 `docker-compose.yml` |

> 本编排里 MinIO 用 `latest` 是 dev 特权，**内网落地前必须换成 digest**。

## 5. 本机复现命令（可原样重跑）

```bash
cd "/Users/<user>/内容运营AI Native/rednote-production"
PY=/Users/<user>/.workbuddy/binaries/python/envs/default/bin/python

# 依赖（已装：psycopg 3.3.5 / boto3 1.43.98）
$PY -m pip install "psycopg[binary]" boto3

# 初始化 SQL 干跑（不留副作用）
psql -h localhost -p 5432 -U rednote -d postgres -v ON_ERROR_STOP=1 -X \
  -c "BEGIN;" -f deploy/dev/initdb/01_init.sql -c "ROLLBACK;"

# 冒烟写入（fs 降级替身）
$PY tools/m0/wp05_smoke/smoke.py --write --backend fs \
  --report evidence/m0/WP05-smoke-write.json

# 重启 PostgreSQL（务必在普通终端执行）
brew services restart postgresql@17

# 冒烟校验
$PY tools/m0/wp05_smoke/smoke.py --verify --backend fs \
  --report evidence/m0/WP05-smoke-verify.json
```
