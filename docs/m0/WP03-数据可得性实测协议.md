# WP03 · 数据可得性实测协议

> 目标：把「小红书笔记后台到底能拿到哪些字段」从猜测变成**事实**，产出逐字段的「自动 / 导入 / 人工 / 不可得」清单，作为 G0-10、G0-11 的判定凭据。
> 执行方：后端B / 产品 ｜ 必需资源：**企业自有或已获授权的账号 + 该账号可见的真实笔记** ｜ 时限：W1 D3–D5
> 配套文档：`WP03-指标口径与导入模板.md`（口径与缺失表示）、`templates/metric_import.template.csv`（导入模板）、`tools/m0/wp03_data/validate_import.py`（校验工具）

---

## 0. 本协议要回答的问题与不回答的问题

**要回答**：对每一个字段，用**我方有权访问**的账号与后台，实测「能不能拿到、拿到什么口径、以什么形态拿到」。

**不回答**：
- 不回答「公网上看得到点赞数，所以后台也能拿到点赞数」——两者是不同数据面，禁止互相推定。
- 不回答「平台文档说有什么接口」——本项目**不假设存在任何可用的官方开放接口**。
- 不回答「怎么绕过限制拿到」——见 §5 合规红线，遇到限制的处理是**停止并记录**。

### 关键前提（不可违反）

1. **小红书对普通企业基本不开放笔记后台数据接口。** 本工作包的默认预期是「大部分字段不可自动获取」，实测若印证此预期，属于**预期内结果**，不视为缺陷（研发执行计划 V2.0 决策 D3）。
2. **不得臆造平台侧 API 名称、接口路径、字段名。** 本协议所有涉及平台的描述统一表述为「平台侧字段待实测确认」。
3. **不得把公网可得数据推定为后台可得数据。** 笔记详情页对所有人可见的点赞/收藏/评论计数，与「该账号后台是否提供该数据、口径是否一致」是两个独立问题，必须分开实测。
4. **不得在 M0 阶段写采集代码。** 本工作包只产出协议、模板、记录工具与实测结论。

## 1. 四种可得性等级（G0-10 的判定词表）

| 等级 | 代码 | 定义 | 判定门槛 |
|---|---|---|---|
| **自动** | `AUTO` | 存在官方开放接口或官方授权通道，且**用真实账号实测成功取得该字段** | **未经实测不得标自动**（G0-11）。仅有文档、仅有他人经验、仅有公网页面可见，一律不得标自动 |
| **导入** | `IMPORT` | 无法接口直取，但可从后台**手工导出**（文件下载）或**截图后识别**，经人工确认后入库 | 必须实测确认「导出/截图」这一动作在该账号权限下可完成 |
| **人工** | `MANUAL` | 既不能接口直取也不能导出，只能由人**用眼看、用手填** | 必须说明人工读取的位置（哪个页面、哪块区域）与耗时量级 |
| **不可得** | `UNAVAILABLE` | 在当前账号权限与合规前提下，**无法以任何方式获取** | 必须写明「不可得的原因」：无该功能 / 无该权限 / 平台不提供 / 我方无权访问 |

**等级判定规则**：

- 一个字段的等级必须**绑定账号权限**记录。同一字段在不同账号类型下可能不同等级，不得只写一个等级而不写前提。
- 等级为 `AUTO` 的字段，必须在「实测结论」列附**证据引用**（截图/导出文件名/日志路径）。
- 等级为 `UNAVAILABLE` 的字段，必须同时确认「是否有替代路径」——替代路径写进 `WP03-数据可得性说明.md`，但**替代路径不改变该字段的等级**（不能因为"人工也能填"就把不可得改写成人工；人工可填说明等级本来就是 `MANUAL`）。
- 等级留空 = **未测**。G0 评审前，留空必须变成四等级之一，或明确标注「未测（原因 + 补测计划）」（M0 执行手册 §4）。

## 2. 逐字段实测表

**填表规则**：
- 「预期可得性」列**统一预填「未知」**——这是刻意的，防止实测者被预期带偏（确认偏误）。
- 「实测结论」列**留空待回填**，只能填 `AUTO / IMPORT / MANUAL / UNAVAILABLE / 未测`。
- 「平台可能口径」列全部是**假设**，表述为「平台侧字段待实测确认」；实测后若发现口径与假设不同，**以实测为准**并在此列加「实测修正」备注。

## 3. 测试方法

### 3.1 前置条件（缺一不可，缺则本工作包只能产出"未测"）

| # | 前置条件 | 状态 |
|---|---|---|
| P1 | 企业自有或已书面授权的账号（KOC 本人授权 / 企业自有账号） | 待回填 |
| P2 | 该账号名下有**已发布**的真实笔记（≥1 条，建议 ≥3 条覆盖不同形态） | 待回填 |
| P3 | 若测商品链接跳转：该笔记挂有商品组件/链接，且该账号有权查看该组件数据 | 待回填 |
| P4 | 若测投流：该账号有已投流笔记，且账号主体有权查看投流后台 | 待回填 |
| P5 | 执行人具备该账号的合法登录权（**不得借用、不得购买、不得共享账号**） | 待回填 |
| P6 | 记录工具就绪：`templates/metric_import.template.csv` + `validate_import.py` | ✅ 已就绪 |

> P1–P5 未满足时，本协议**不具备执行条件**，应如实记为「未测（缺企业侧账号授权）」并写明补测计划。**禁止**用他人账号、公开笔记或第三方数据源替代。

### 3.2 指标类字段试取动作

| 步骤 | 动作 | 记录内容 |
|---|---|---|
| S0 | **固定观测时刻**：为每次试取记录精确到分钟的观测时间（用于快照的 `observed_at`） | 观测时间（含时区） |
| S1 | 登录授权账号，进入笔记数据查看位置（**平台侧具体入口待实测确认**，实测时如实记录入口名称） | 入口路径、页面标题、截图 |
| S2 | 逐字段读取 F01–F05，**原样抄录平台显示值**（含「1.2 万」这类约数写法，不得自行换算成 12000） | 每个字段的原始显示字符串 |
| S3 | 对每个字段判断：是否有「导出 / 下载 / 明细」类按钮 | 按钮是否存在、导出文件名、导出格式（CSV/XLSX/图片） |
| S4 | 若存在导出：执行导出，检查导出文件是否含该字段、是否为精确值 | 导出文件路径、字段清单、值样例 |
| S5 | 若不存在导出：对显示区域截图，评估 OCR 可行性（数字/中文/单位是否可辨） | 截图路径、OCR 可辨性结论 |
| S6 | 商品链接跳转（F06/F07）：确认点击次数与人数是否**分别**可读、是否提供统计窗口（如近 7 天 / 累计） | 两个值、窗口说明、组件标识 |
| S7 | 评论正文（F05）：尝试读取前 N 条评论，确认是否可读到正文、是否有条数上限、是否含评论时间 | 可读条数、字段完整度、是否需翻页 |
| S8 | **重复观测**：间隔 ≥1 小时后对同一笔记再取一次，判断「累计值 / 窗口值」性质 | 两次取值对比、增量是否单调 |

**S8 是必需步骤**：累计值与窗口值在单次观测下无法区分，若误判为累计值，后续汇总会系统性失真。

### 3.3 发布登记类字段试取动作

| 步骤 | 动作 | 记录内容 |
|---|---|---|
| T1 | 从笔记分享入口取链接（F09），记录完整 URL 原文 | 原始 URL 字符串 |
| T2 | 用**另一个已登录账号**访问该链接，确认链接可访问性 | 可访问 / 需登录 / 不可访问 |
| T3 | 尝试从链接中识别笔记标识（F10）：观察是否存在稳定、唯一、不含跟踪参数的标识段 | 标识候选、是否稳定（对同笔记多次取链接是否一致） |
| T4 | 取短链后再展开，比对是否与长链指向同一标识（需求 §12.1 要求归一） | 短链原文、展开结果、是否同一标识 |
| T5 | 发布时间（F11）：记录页面显示的时间形态（绝对时刻 / 相对时间）与后台是否提供精确时间 | 显示形态、是否可换算为绝对时刻 |
| T6 | 是否投流（F12）：在**投流后台**（若有权限）查找该笔记的投放记录 | 能否查到、查到哪些字段 |
| T7 | 发布状态（F14）：构造/观察一次「不可访问」情形，区分「无法访问」与「确认删除」 | 平台提示原文、判定依据 |
| T8 | **负向测试**：对一条**非本账号**的公开笔记，重复 T1–T5，记录哪些字段在无权限下拿不到 | 无权限下的字段可得性 |

> T8 的价值在于区分「平台不提供」与「我方账号无权限」——这两种原因对应完全不同的后续动作（前者放弃，后者可申请权限）。

## 5. 合规声明（红线 · 不可违反）

1. **只验证自身有权访问的数据。** 仅使用企业自有账号或已获书面授权的账号，仅访问该账号有权访问的页面与功能。
2. **不做未授权爬取。** 不编写、不使用任何针对平台的爬虫；不通过非官方客户端、非官方协议、逆向接口等方式取数。
3. **不绕过平台风控与访问限制。** 不尝试绕过登录校验、验证码、频率限制、访问控制。**明确禁止**：更换 IP、更换账号、切换设备指纹、使用代理池、伪造请求头、重放 token 等任何规避手段。
4. **遇到访问限制立即停止并记录。** 处理动作是「停止该字段的试取 → 记录平台提示原文与发生时间 → 该字段记为 `UNAVAILABLE` 或「未测」→ 评估替代路径」。**不是**「换个方式再试一次」。
5. **不批量抓取隐私数据。** 评论正文试取只取**必要条数**（建议 ≤20 条/笔记）用于判断字段结构，不落库、不外传、不分析评论者身份。
6. **不做高频请求。** 同一账号的试取动作按人工节奏进行，不进行并发、循环、压测式访问。
7. **不把实测数据用于协议之外的用途。** 试取所得样本仅用于本工作包结论，不得进入业务库或用于演示。
8. **越界即停。** 任何执行人对「这个动作是否合规」存疑时，**先停再做**，并向技术负责人确认。

> 违反上述任一条 = M0 红线事件，须在 G0 评审会上如实报告。

## 6. 判定与升级路径

### 6.1 G0-10 / G0-11 判定

- **G0-10 通过** = F01–F14 每行「实测结论」均有值（四等级之一，或「未测（原因+补测计划）」）。
- **G0-11 通过** = 所有标 `AUTO` 的字段均有真实账号实测成功证据。**若没有任何字段标 `AUTO`，G0-11 天然通过**（空集满足条件），但必须在说明文档中显式写出「无字段标自动」这一结论。

### 6.2 全部不可得时的处置（对应研发执行计划 V2.0 决策 D3）

若 F01–F14 全部为 `UNAVAILABLE`：

1. **不阻塞上线。** D3 已拍板：第 8 步数据回收以「人工录入 + 表格导入 + 截图 OCR 确认」为**第一版常态路径**，自动采集仅作为验证通过后的增强。无自动渠道属于**预期内结果**（风险 R1 已降级为已接受的产品形态）。
2. **产品行为按"明确不可得"设计**：界面必须显示「该字段当前不可自动获取」+ 引导至导入路径，**不得静默留空、不得显示 0 冒充数据**。
3. **回写需求**：按执行计划 §5.3 / 硬伤 🔴3 的处置，将渠道清单结论回写需求说明 §1.3。
4. **保留未来接入位**：数据模型保留 `source_type` 字段，未来若出现合规渠道，可作为新增来源接入，不改表结构。
5. **如实上报**：在 G0 评审会上明确「Q3 的结论是全不可得」，由老大决定是否追加验证。**禁止**为了凑 G0 通过而虚报可得性（M0 执行手册 §5 红线 2、3）。

### 6.3 部分可得时的处置

- 可得字段按等级接入；不可得字段走人工/导入路径。
- **不得因为"部分字段能自动拿"就宣称"数据自动回收已打通"**——口径、时间差、覆盖度必须一并说明（需求 §12.4 要求显示时间差，不声称整行同一时刻完整采样）。
