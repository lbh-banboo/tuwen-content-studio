# WP02 · Live 图链路验证协议（首发硬要求）

> 目标：在真机上证明「生成的动态素材 → 交付包 → 手机相册识别为实况 → 小红书成功发布且保持 Live 效果」全链可行，或证明不可行并给出决策。
> 执行方：AI/测试 ｜ 必需资源：iPhone（≥2 代） + Mac + 小红书账号 + 真实网络 ｜ 时限：W1–W3 日

## 1. 核心原则

1. **纸质推断一律无效**：Apple Live Photo 由静止图 + 配对动态资源组成，「下载两个文件到相册就自动成为实况」是常见错误推断，必须真机验证。
2. **四环节独立判定**：动态生成 / 标准资产封装 / 传到目标手机并被识别 / 在平台发布且保持效果——任一环节失败即整体不可用，不允许"基本可行"结论。
3. **失败要留证据**：失败链路的报错、相册表现、平台提示都要记录，供后续决策辅助工具是否立项。

## 2. 目标设备矩阵（G0-09 锁定）

| 设备 | 型号 | 系统版本 | 小红书版本 | 结论 |
|---|---|---|---|---|
| 主设备 | 待回填 | 待回填 | 待回填 | ☐ |
| 副设备（较小/较大屏或旧一代） | 待回填 | 待回填 | 待回填 | ☐ |
| 对照：Android（若业务需要） | 待回填 | — | 待回填 | ☐ 不适用可略 |

> 记录规则：结论必须绑定**具体版本号**。升级系统或 App 后需重测受影响环节（`live_profiles` 表按此设计为版本化配置）。

## 3. 四条候选链路（[待实测] 假设，非结论）

| 链路 | 做法 | 前置条件 | 判定 |
|---|---|---|---|
| **L1** | 生成配对素材（静帧 + 动态）→ Mac「照片」导入 → iCloud 照片同步 → iPhone 相册 → 小红书发布 | Mac + iCloud 开启 | ☐ |
| **L2** | 自制封装（写入配对标识/元数据）→ 隔空投送到 iPhone → 相册识别为实况 → 发布 | 封装格式正确 | ☐ |
| **L3** | 第三方工具把动态片段转换为实况 → 相册 → 发布 | 工具可用性/合规 | ☐ |
| **L4** | 内部辅助导入工具（自研）| 需立项 + 签名 + 分发能力 | ☐ 需决策 |

## 4. 单条链路验证步骤（逐条执行，逐条留证）

| 步 | 动作 | 记录内容 |
|---|---|---|
| S1 | 准备静帧（JPG/HEIC，竖版 3:4）+ 动态（MOV，时长/帧率/编码记录） | 素材规格、文件大小 |
| S2 | 封装为可识别实况资产 | 封装工具与命令、输出文件名与结构 |
| S3 | 传输到目标手机 | 传输方式（AirDrop/iCloud/其他）、耗时、是否需额外 App |
| S4 | 相册检查 | 是否显示"实况"角标；长按是否播放；动态是否流畅 |
| S5 | 小红书发布 | 发布是否成功；发布后详情页是否仍为实况；是否被压成普通图/视频 |
| S6 | 他人视角复核 | 另一账号查看该笔记，确认实况效果对观看者可见 |
| S7 | 批量验证 | 10 张打包 ZIP → 解包 → 批量导入 → 抽查 3 张发布 |
| S8 | 异常记录 | 任何报错、降级、静默转静态的情况 |

## 7. 判定与升级路径

- 任一链路 S5 + S6 通过 → **Live 可行**，记录为 `live_profiles` 首个 VERIFIED 配置。
- 全部链路失败：
  1. 先判定是否属于"封装格式不对"这类可修复问题（改封装再测一轮）；
  2. 仍失败 → 评估 L4 自研工具（须回答：签名与分发是否具备、企业是否批准）；
  3. L4 不可行 → **Live 硬要求未达**，升级老大做范围决策，**禁止默认降级为静态图**（需求 §13.3 明确禁止静默降级）。
