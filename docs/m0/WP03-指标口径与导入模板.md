## 1. 口径规范化（六条硬口径）

以下六条是**不可混用**的口径约束。违反时 `validate_import.py` 会报出口径违规告警。

### 口径 1：阅读量与曝光量**不得混加**

- 需求 §12.3 明文：「浏览／阅读量 —— 保留平台原字段与口径，**不与曝光量混加**」。
- 系统为两者设**独立字段**：`VIEW_COUNT`（阅读/浏览）与 `IMPRESSION_COUNT`（曝光）。
- **禁止**把「阅读 + 曝光」的和写进任一字段；**禁止**把一个混合口径值同时填进两个字段。
- 若平台只提供一个混合口径字段：按**实测到的口径**登记到最贴近的字段，并在 `note` 写明「口径含曝光，未拆分」。**不得**自行拆分成两个数。
- 汇总时 `VIEW_COUNT` 与 `IMPRESSION_COUNT` **分别求和，不得相加成"总触达"**。

### 口径 2：点赞数支持约数（如「1.2 万」）

- 需求 §12.3：「点赞数 —— 非负整数；**支持来源仅提供约数的情形**」。
- 约数必须**保留原值字符串**：`raw_value` 原样存平台显示值（如 `"1.2 万"`，含空格与单位），`value` 存**规范化后的数值**（如 `12000`），`precision` 标 `APPROXIMATE`。
- **不得**把「1.2 万」伪装成精确的 `12000`（即：约数不得标 `EXACT`）。
- **不得**丢弃原值只存数值（丢原值 = 丢失精度信息，后续无法判断阈值跨越）。
- 约数跨越业务标签阈值（50 / 100，需求 §12.5）无法明确判断时，标 `PENDING` 待确认，**不得**强行判定标签。

### 口径 3：评论计数与评论条数分开

- 需求 §12.3：「评论数 —— **评论计数与已导入评论条数分开**」。
- `COMMENT_COUNT` = 平台给出的评论**计数**（口径待实测确认，可能含或不含折叠/审核中评论）。
- `COMMENT_TEXT` = **实际导入的评论正文**，一行一条，逐条登记；其"条数"由行数自然得出，**不写进 `COMMENT_COUNT`**。
- **禁止**用导入条数覆盖平台计数；**禁止**用平台计数推断导入条数。
- 差值（平台计数 − 已导入条数）是正常现象，由界面提示，不在本层强行抹平。

### 口径 4：点击次数与点击人数分开

- 需求 §12.3：「商品链接跳转 —— 保留**点击次数／人数**、组件或链接标识与统计窗口」。
- `LINK_CLICK_PV` = 点击**次数**（同一人多次点击重复计）。
- `LINK_CLICK_UV` = 点击**人数**（同一人多次点击只计一次）。
- **两者不得相加、不得互相替代、不得只填其一而不说明**。
- 点击类指标**必须**写明统计窗口（`metric_scope` 不得为 `UNKNOWN`）；若平台未提供窗口说明，填 `UNKNOWN` 并同时记告警，由运营确认。
- 「组件或链接标识」记在 `note`。

### 口径 5：统计窗口必须随值登记

- 同一指标在「累计」与「近 7 天」两种窗口下的值**不可比较、不可相加**。
- `metric_scope` 必须显式填写；汇总只对**同一 `metric_scope`** 的值求和（需求 §12.4：「项目汇总只对口径一致的指标求和」）。
- 单次观测**无法**区分累计值与窗口值 → 实测协议要求做二次观测（§3.2 S8）。

### 口径 6：每个指标有自己的观测时间

- 需求 §12.4：最新视图按**指标**选择最新有效观测值，因此**每个指标可有不同时间**。
- 系统**必须显示时间差**，**不声称整行是同一时刻的完整采样**。
- 因此 `observed_at` 是**行级**字段，不是表级字段。
- 汇总必须同时显示**覆盖笔记数**与**时间范围**。

## 2. 指标字典（metric_code 词表）

| metric_code | 中文名 | 值类型 | 单位 | scope 要求 | 可否求和 |
|---|---|---|---|---|---|
| `VIEW_COUNT` | 阅读/浏览量 | 整数 | 次 | 累计或窗口 | 仅同 scope 内 |
| `IMPRESSION_COUNT` | 曝光量（**隔离字段**） | 整数 | 次 | 累计或窗口 | 仅同 scope 内，**不与 VIEW 相加** |
| `LIKE_COUNT` | 点赞数 | 整数 | 个 | 累计或窗口 | 仅同 scope 内 |
| `FAVORITE_COUNT` | 收藏数 | 整数 | 个 | 累计或窗口 | 仅同 scope 内 |
| `COMMENT_COUNT` | 评论计数 | 整数 | 条 | 累计或窗口 | 仅同 scope 内 |
| `COMMENT_TEXT` | 评论正文 | **文本**（value 留空） | — | 不适用 | **否**（不参与求和） |
| `LINK_CLICK_PV` | 商品链接点击**次数** | 整数 | 次 | **必须明确窗口** | 仅同 scope 内 |
| `LINK_CLICK_UV` | 商品链接点击**人数** | 整数 | 人 | **必须明确窗口** | 仅同 scope 内 |
| `NOTE_URL` | 笔记链接 | **文本**（value 留空） | — | 不适用 | 否 |
| `NOTE_ID` | 平台笔记标识 | **文本**（value 留空） | — | 不适用 | 否 |
| `PUBLISHED_AT` | 发布时间 | **文本**（value 留空，ISO8601 写 raw_value） | — | 不适用 | 否 |
| `IS_PROMOTED` | 是否投流 | 整数 `1`=是 / `0`=否 | — | 不适用 | 否 |
| `PROMOTION_INFO` | 已知投流信息 | **文本**（value 留空） | — | 不适用 | 否 |
| `PUBLISH_STATUS` | 发布状态 | **文本**（value 留空） | — | 不适用 | 否 |

**文本类指标**（`value` 必须留空，内容写 `raw_value`）：`COMMENT_TEXT`、`NOTE_URL`、`NOTE_ID`、`PUBLISHED_AT`、`PROMOTION_INFO`、`PUBLISH_STATUS`
**数值类指标**（`value` 必须为非负整数）：其余全部。

> 本词表**只描述我方内部口径**，不代表平台侧存在同名或同口径字段。平台侧字段、口径、统计窗口**一律待实测确认**（见实测协议）。

### metric_scope 词表

| metric_scope | 含义 |
|---|---|
| `CUMULATIVE` | 累计值（自发布起） |
| `LAST_24H` | 近 24 小时窗口值 |
| `LAST_7D` | 近 7 天窗口值 |
| `LAST_30D` | 近 30 天窗口值 |
| `LAST_90D` | 近 90 天窗口值 |
| `NOT_APPLICABLE` | 不适用（文本类指标使用） |
| `UNKNOWN` | 窗口未知（**会告警**，需运营确认后才可用于汇总） |

### source_type 词表

| source_type | 含义 | 对应可得性等级 |
|---|---|---|
| `MANUAL` | 人工录入 | 人工 |
| `CSV_IMPORT` | CSV 文件导入 | 导入 |
| `XLSX_IMPORT` | XLSX 文件导入 | 导入 |
| `SCREENSHOT_OCR` | 截图识别后人工确认 | 导入 |
| `AUTO_API` | 自动采集（**须有实测证据引用**） | 自动 |

## 3. 缺失表示规范

### 3.1 核心原则：缺失不填 0

需求 §12.3 明文：「**缺失不填 0**」。

- `0` 是一个**合法的真实观测值**（如某笔记确实 0 点赞）。
- 「拿不到」与「真的是 0」是两件事，混用会导致汇总系统性偏低/偏高，且无法事后区分。

### 3.2 NULL 与 0 的区别

| 情形 | `value` | `raw_value` | `availability` | 说明 |
|---|---|---|---|---|
| 真的观测到 0 | `0` | `"0"` | `ACQUIRED` | 有效观测值，参与汇总 |
| 字段不存在（平台不提供） | 留空 | 留空 | `NOT_PROVIDED` | 不参与汇总，界面提示"平台未提供" |
| 无权限查看 | 留空 | 留空 | `NO_PERMISSION` | 不参与汇总，界面提示"无权限" |
| 该笔记不适用该指标 | 留空 | 留空 | `NOT_APPLICABLE` | 不参与汇总，界面提示"不适用" |
| 试图获取但失败 | 留空 | 可保留错误信息 | `FETCH_FAILED` | 不参与汇总，保留失败原因 |
| 有值但待确认（如约数跨阈值） | 可填 | **必填** | `PENDING` | 不参与汇总，等人确认 |
| 已获取 | 必填 | **必填** | `ACQUIRED` | 参与汇总 |

**判定规则**：`value` 有值 ⟺ `availability = ACQUIRED`（`PENDING` 为唯一例外，允许带值但必须同时保留 `raw_value`）。

### 3.3 六种字段状态（availability 词表）

严格对应需求 §12.3 「字段状态区分」：

| 代码 | 中文 | 含义 | 是否参与汇总 |
|---|---|---|---|
| `ACQUIRED` | 已获取 | 成功取得该字段的有效值 | ✅ 是 |
| `NOT_PROVIDED` | 未提供 | 平台不提供该字段 | ❌ 否 |
| `NO_PERMISSION` | 无权限 | 我方账号无权查看 | ❌ 否 |
| `NOT_APPLICABLE` | 不适用 | 该笔记/该类型不适用此指标（如无商品组件则点击量不适用） | ❌ 否 |
| `FETCH_FAILED` | 获取失败 | 尝试获取时失败（网络/超时/接口错误），**保留失败原因** | ❌ 否 |
| `PENDING` | 待确认 | 有候选值但需人工确认（如约数跨阈值、来源冲突） | ❌ 否（确认后转 `ACQUIRED`） |

**汇总口径**：只有 `ACQUIRED` 参与求和；其余五种一律排除，且界面**必须显示排除原因分布**（需求 §12.2：展示最后成功采集时间、当前来源和失败原因）。

### 3.4 约数必须保留原值字符串

- `raw_value` 存**平台原样显示值**，一个字符都不改：`"1.2 万"`、`"约 300"`、`"1.5k"`、`"100+"`。
- `value` 存**规范化数值**（可参与计算的近似值），`precision=APPROXIMATE`。
- **禁止**把 `raw_value` 丢失只留 `value`。
- **禁止**把约数的 `raw_value` 改写成精确值（如把 `"1.2 万"` 改写成 `"12000"`）。
- `raw_value` 为中文单位约数时，`value` 必须在**同量级**（校验工具会检查量级一致性）。

### 3.5 冲突与修订

- 同一指标同一时刻、不同来源给出冲突值时：**两个值都保留**，标 `PENDING`，由运营确认（需求 §12.4：「未经确认保留冲突提示」）。
- **不覆盖原始证据**：人工修正创建**修订记录**，原记录保留（需求 §12.4）。
- 累计值下降（如点赞数变少）时：**保留原值并提示核对**，**不强制抹平**（需求 §12.4）。

## 4. 三条导入路径

需求 §12.2：「第一版**必须**提供人工录入、CSV/XLSX 导入和截图识别后确认。自动回收仅接入经验证可用且具备相应访问条件的渠道。」

| # | 路径 | source_type | 操作方式 | 人工确认点 |
|---|---|---|---|---|
| 1 | **CSV / XLSX 导入** | `CSV_IMPORT` / `XLSX_IMPORT` | 从后台导出文件或运营手工填表 → 上传 → 系统校验 → 预览差异 → 确认入库 | 上传后**必须预览**：字段映射、缺失行、口径告警、重复行 |
| 2 | **截图 OCR 后确认** | `SCREENSHOT_OCR` | 上传后台截图 → OCR 提取候选值 → **逐值人工确认或修正** → 入库 | **OCR 结果一律不得直接入库**；`PENDING` 起始，人确认后转 `ACQUIRED` |
| 3 | **人工录入** | `MANUAL` | 运营在界面逐字段填写 → 系统校验 → 入库 | 缺失项必须选状态（六态之一），**不得留空** |

### 4.1 三条路径的共同要求

1. **一律形成快照**：写入即产生快照，含观测时间、录入时间、来源、操作人/任务编号、字段状态与证据引用（需求 §12.4）。
2. **一律经过校验**：三条路径共用同一个校验器（`validate_import.py` 的规则集），口径违规不得静默通过。
3. **一律标注来源**：`source_type` 必填，便于后续判断证据强度。
4. **一律不得自动改判业务标签**：约数跨阈值时标 `PENDING`（需求 §12.5）。
5. **不覆盖原始证据**：修正走修订记录。

### 4.2 CSV / XLSX 导入流程（第一版主路径，D3）

```text
后台导出 / 手工填表
   ↓
按 templates/metric_import.template.csv 表头整理
   ↓
validate_import.py 校验  →  有字段级错误：修正后重来
   ↓                    →  仅有口径告警：逐条确认或修正
预览差异（新增 / 冲突 / 缺失 / 重复）
   ↓
运营确认 → 写入快照
```

**校验命令**：

```bash
python3 tools/m0/wp03_data/validate_import.py --file <你的文件.csv>
```

### 4.3 截图 OCR 路径的额外要求

- 截图必须**可见观测时间信息**（否则 `observed_at` 只能填 `PENDING`）。
- OCR 候选值必须与截图**逐值对照确认**，禁止批量"全部接受"。
- 截图证据须归档（脱敏后），保留原图引用。
- OCR 识别不确定的数字（如 `0` / `8`、`1.2万` / `12万`）**不得自动入库**。

### 4.4 人工录入路径的额外要求

- 缺失项**必须**显式选择六种状态之一；界面不得提供「留空」这个选项。
- 人工录入的 `note` 建议写明读取位置（如"后台数据页左上角"），便于复核。

## 5. 汇总与展示规则（口径落地）

| 规则 | 说明 | 依据 |
|---|---|---|
| 只对口径一致指标求和 | 不同 `metric_code` 或不同 `metric_scope` 不得相加 | §12.4 |
| 阅读与曝光分别求和 | **禁止**相加成"总触达" | §12.3 |
| 显示覆盖笔记数 | 汇总必须显示覆盖了多少笔记 | §12.4 |
| 显示时间范围 | 汇总必须显示时间范围 | §12.4 |
| 显示时间差 | 每个指标有自己的观测时间，必须显示时间差 | §12.4 |
| 旧快照不覆盖新数据 | 较旧快照不得覆盖较新值 | §12.4 |
| 累计值下降保留 + 提示 | 不强制抹平 | §12.4 |
| 冲突保留提示 | 未经确认保留冲突提示 | §12.4 |
| 不可得不显示 0 | 必须显示"不可自动获取"并引导导入路径 | D3 / §12.3 |
